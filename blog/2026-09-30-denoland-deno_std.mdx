One function in my deno_std scan stands apart: `parseSync` in `xml/_parse_sync.ts`, with cyclomatic complexity 241 against 38 for the fifth-ranked function, `resolve` in `path/windows/resolve.ts`. A 203-point gap makes it a different category of problem from the rest of the list. It is a debt-quadrant function: an activity-weighted risk score of 20.2, zero touches in the last year, and 57 days since last change, so the argument here is blast radius when someone next edits it, not current churn. The scan covers 3,200 functions, 231 of them in the critical band, and all five functions I analyze below sit in the debt quadrant.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `parseSync` — xml/_parse_sync.ts

<FunctionCard fn='parseSync' file='xml/_parse_sync.ts' risk='20.2' band='debt' cc='241' nd='11' fo='78' touches='0' />

<MetricBar label='Fan-out' value='78' threshold='15' max='80' />

`parseSync` ranks first by activity-weighted risk (20.2) and it pairs the second-highest complexity with by far the highest fan-out in the list: 78 distinct functions called. The excerpt shows why it is flagged as a god function. It reads options, normalizes line endings, and then defines a pile of nested closures inside its body: namespace binding management, position computation, illegal-character checks, and more, all sharing mutable parser state (`pos`, `stack`, `root`, `declaration`, `rootClosed`).

That shared closure state is the real coupling problem. Nesting depth 11 and CC 241 would be painful in any function, but when the helpers are closures over local variables, you cannot test or move them without carrying the state along. It was last changed 57 days ago, the most recent of the five, though still with 0 touches in the last year, and the file has 2 commits in its history from 1 distinct author in the last 90 days. That is a single-owner file with no review-comment history, so the knowledge of how these pieces interact may sit with one person.

I would promote the closures into a parser class or a set of functions over an explicit state object. That alone would turn a 241-path function into smaller units that can be tested individually.

### `_globToRegExp` — path/_common/glob_to_reg_exp.ts

<FunctionCard fn='_globToRegExp' file='path/_common/glob_to_reg_exp.ts' risk='18.28' band='debt' cc='77' nd='20' fo='6' touches='0' />

This one is an outlier for a different reason. CC 77 is modest next to the XML functions, but nesting depth 20 is the deepest in the list by a wide margin. Nesting depth 20 is a strong refactoring signal on its own. The function converts a glob string into a regular expression, and the excerpt shows why it nests so deeply: a loop over segments contains an inner character-by-character loop, which contains handling for escapes, bracket ranges, POSIX character classes such as alnum and alpha, extended glob groups, and globstar logic.

The file-level history is thin (1 commit, no bug-linked commits), and the function hasn't been changed in 134 days. Glob semantics are full of edge cases, and deep nesting makes it hard to see which state flags (in a range, in an escape, inside a group) apply at a given line. I would split the work into a tokenizer that classifies glob characters and a builder that emits regex fragments, and lift the POSIX class mapping into a lookup table. The if-else chain on class names in the excerpt is a natural first extraction.

### `process` — xml/_tokenizer.ts

<FunctionCard fn='process' file='xml/_tokenizer.ts' risk='18.15' band='debt' cc='298' nd='17' fo='5' touches='0' />

<MetricBar label='Cyclomatic Complexity' value='298' threshold='30' max='300' />

This has the highest cyclomatic complexity in the scan, and on raw structure alone I would start here. From the excerpt, `process` is the main loop of a streaming XML tokenizer: it takes a chunk, normalizes line endings, then runs a `while` loop over a `switch` on the current parser state, with each state branching on character codes and firing callbacks. Nesting depth 17 means many of those branches sit inside several layers of conditionals. The fan-out is only 5, so the function does not coordinate many helpers; the complexity is inline branching, with each state's logic living directly in the switch.

It hasn't been changed in 134 days and has 0 touches in the last year, so this is debt rather than live churn. The danger is that any future change to tokenizing, such as a new XML construct or a spec edge case, lands in a 298-path function where every path is a required test case. The exit-heavy and long-function patterns reinforce that: many return points make coverage hard to reason about. I would extract each state's handling into its own method and reduce the switch to a dispatch table. The author has already pulled out helpers like the text and name capture methods, so the pattern exists; it just stops short of the states themselves.

### `iterableEquality` — expect/_utils.ts

<FunctionCard fn='iterableEquality' file='expect/_utils.ts' risk='18.03' band='debt' cc='33' nd='8' fo='14' touches='0' />

This is the equality logic behind the `expect` matchers, and a good example of complexity that cyclomatic count alone understates. CC is 33, but the excerpt shows the function recursing into itself with copied stacks for circular-reference detection, rebuilding its own custom-tester list on each call, and then branching by type: sets, maps, and generic iterables, each with its own comparison loop. In TypeScript, the `any` parameters (annotated with lint-ignore comments) mean the compiler does not help narrow types inside those branches, so the type-specific logic rests on runtime checks.

Fan-out of 14 and the god-function label fit that picture. It hasn't been changed in 134 days. Because this sits under the assertion library, a subtle change in equality behavior would show up as test results changing for downstream users, which is what I mean by high blast radius. I would split the Set and Map comparison into separate functions behind the type dispatch, which takes the nesting down and lets each comparison be tested on its own.

### `resolve` — path/windows/resolve.ts

<FunctionCard fn='resolve' file='path/windows/resolve.ts' risk='17.99' band='debt' cc='38' nd='8' fo='10' touches='0' />

The smallest of the five by complexity, and the only one flagged as a hub function in addition to god function. It resolves Windows path segments: walking segments from the end, handling drive letters, UNC roots (the double-separator matching visible in the excerpt), and the current-directory fallback. The code is a long chain of character-code scans over separators, with nested conditionals deciding whether a root was matched.

CC 38 with nesting depth 8 and fan-out 10 makes this the most approachable refactor in the list, which is why I would use it to set a pattern. I would extract the root-detection logic (drive letter, UNC, rooted path) into a function that returns the device and root-end position, and let `resolve` focus on the segment walk. It hasn't been changed in 134 days, and like the others it has just 1 commit in its file history and no bug-linked activity.

**What I would do with this list**

The fire-quadrant functions outside the top five make a useful contrast. Several functions in the `net/`, `http/` and `async/` directories were changed within the last 8 days. They are far less complex than the XML pair, but they are the ones being edited right now. With a limited review budget, I would spend it on those for active regression risk, and schedule the five above as refactors before anyone extends the XML module further.
