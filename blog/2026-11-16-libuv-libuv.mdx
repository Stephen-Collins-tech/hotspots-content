Five functions top libuv's risk ranking, and they all sit in one file. Every one lives in src/unix/linux.c, is classed critical and active, and was last changed 1 day before the analyzed commit. The leader, `uv__io_poll`, has an activity-weighted risk score of 2.59, with cyclomatic complexity 37 and fan-out 23 in code that has been touched 18 times in the last year, which suggests it deserves review soon. libuv is the C event-loop and platform abstraction library, and this analysis covers 3,247 functions, 284 of them critical. I would start with `uv__io_poll`, then read the rest of linux.c as one module, because the same 18 touches and the same 4 distinct authors in the last 90 days show up on every function in the file.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `uv__io_poll` — linux.c

<FunctionCard fn='uv__io_poll' file='src/unix/linux.c' risk='2.59' band='critical' cc='37' nd='4' fo='23' touches='18' />

This is the Linux event-loop poll function, and it is the one I would review first. Cyclomatic complexity is 37, nesting depth is 4, and fan-out is 23, so it combines many execution paths with broad coupling to other functions. It also carries the highest activity-weighted risk score in the repository at 2.59, and it was changed 1 day before the analyzed commit.

<MetricBar label='Cyclomatic Complexity' value='37' threshold='10' max='60' />

From the source excerpt, the function declares large stack arrays of epoll events, builds an optional signal mask, adjusts timeouts when idle-time metrics are enabled, and drains a queue of watchers, choosing between adding and modifying epoll registrations. It also has a branch that diverts those registrations through an io_uring control ring when one is present. That is several concerns interleaved in one function: timeout bookkeeping, watcher registration, and (judging by the local variables for iou events and signals) event dispatch. Each is a separate path a test has to exercise.

My recommendation: extract the watcher-queue drain into its own function, since it is a self-contained loop with a clear input (the loop's watcher queue) and a clear side effect (epoll or ring registrations). That alone should remove a meaningful share of the 37 paths and a chunk of the fan-out, and it isolates the io_uring-versus-epoll decision in one place.

### `uv_cpu_info` — linux.c

<FunctionCard fn='uv_cpu_info' file='src/unix/linux.c' risk='2.54' band='critical' cc='33' nd='3' fo='18' touches='18' />

This public API function reports per-CPU information, and its cyclomatic complexity is 33 with fan-out of 18. Because it is a public entry point, every libuv consumer inherits any behavioral change here. The excerpt shows a large block of preprocessor conditionals selecting model-marker strings per architecture (PPC, ARM, AArch64, MIPS, LoongArch), a static lookup table of ARM part numbers, a very large stack footprint (a bitmap, a model table, and a 1,024-byte buffer), and a heap allocation sized for the kernel's maximum CPU count. It also uses a goto-based cleanup path.

Preprocessor branching is not counted the way runtime branches are, so the real variation surface is wider than the metrics suggest. Each architecture is effectively its own variant of the function.

My recommendation: separate parsing from collection. A helper that parses the /proc/stat lines into the internal CPU struct, and another that resolves model names, would let each be tested with canned text input instead of a live /proc.

### `uv_interface_addresses` — linux.c

<FunctionCard fn='uv_interface_addresses' file='src/unix/linux.c' risk='2.45' band='critical' cc='16' nd='3' fo='8' touches='18' />

Cyclomatic complexity is 16 and fan-out is 8, which on their own would not put this function at the top. The score comes from where it lives: the same actively changing file. The excerpt shows a three-pass structure over the interface list, one pass to count entries and size a name buffer, one to fill address and netmask data, and one to match physical addresses to aliased interface names. It also performs a manual single-allocation layout, placing name strings after the address array in the same block, which is the kind of pointer arithmetic that cyclomatic complexity does not capture.

My recommendation: this is a modest, safe extraction. The physical-address matching pass is self-contained and could become its own static function. I would also add a test for alias interfaces, since the name-matching logic accepts both an exact match and a name followed by a colon.

### `uv__iou_init` — linux.c

<FunctionCard fn='uv__iou_init' file='src/unix/linux.c' risk='2.42' band='critical' cc='17' nd='2' fo='8' touches='18' />

The name and body point to io_uring setup: it checks whether io_uring should be used, derives a kernel-version-dependent flag, calls the ring setup, verifies three feature bits, computes submission and completion queue sizes, and maps two regions of memory. Cyclomatic complexity is 17 and nesting depth is only 2, so the function is flat; most of the paths are early-exit checks that jump to a shared failure label.

That shape is easier to read than deep nesting, but each early exit is a path where mapped memory and the ring descriptor have to be released correctly. The excerpt initializes the mapping pointers to a failure sentinel up front, which is a sensible pattern for that cleanup.

My recommendation: keep the flat structure, but split the feature-probing checks from the memory-mapping work. A function that only answers 'does this kernel support what I need' can be tested against fabricated parameter structs, without touching mmap.

### `uv__get_cgroupv2_constrained_cpu` — linux.c

<FunctionCard fn='uv__get_cgroupv2_constrained_cpu' file='src/unix/linux.c' risk='2.4' band='critical' cc='12' nd='2' fo='8' touches='18' />

This is the smallest of the five by complexity, with cyclomatic complexity 12, nesting depth 2, and fan-out 8. It walks up a cgroup v2 hierarchy from the current cgroup path, reading a cpu.max file at each level and keeping the minimum quota. The excerpt shows repeated path construction with bounded buffers, several skip-and-continue branches that use goto, and a loop terminated by a path comparison against the mount point.

Its risk score is driven mainly by file activity. The structure is already readable, and the comments describe the traversal clearly. The place I would look is the string handling: fixed-size path buffers and prefix comparisons are exactly where edge cases like unusually long cgroup paths matter.

My recommendation: factor out a function that parses a single cpu.max buffer into a quota value, with the zero-period and 'max' cases handled in one place. Then the loop body shrinks and the parsing can be tested with plain strings.

## Where to start

I would start with `uv__io_poll`: it has the highest score, the highest complexity and fan-out of the five, and it is on the path every Linux event loop takes. After that, I would give the other four a single review pass as a group instead of scheduling them separately, because they share the same recent change history and the same set of authors. If extraction work lands in linux.c, I would keep each refactor in its own small change so the file's 4 recent authors are not reviewing overlapping edits to the same regions.
