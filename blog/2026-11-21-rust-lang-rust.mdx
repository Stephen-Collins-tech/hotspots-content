Across the 160,084 functions analyzed, 3,733 land in the critical band, and these five are where complexity and ongoing change overlap most.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `suggest_traits_to_import` — suggest.rs

<FunctionCard fn='suggest_traits_to_import' file='compiler/rustc_hir_typeck/src/method/suggest.rs' risk='3.92' band='active' cc='102' nd='7' fo='60' touches='197' />

I would start here because it has the highest activity-weighted risk score (3.92) and the code was last changed 1 day ago. From the excerpt, it builds a 'you probably forgot a `use`' diagnostic. It takes twelve parameters, probes the receiver type under several alternative self-type forms (plain, mutable reference, shared reference), skips a list of well-known traits, and then does more work inside each successful probe, including checking for multiple crate versions of the same trait. That is a lot of independent decisions in a single function body.

<MetricBar label='Cyclomatic Complexity' value='102' threshold='30' max='170' />

A cyclomatic complexity of 102 means roughly a hundred independent paths, each a candidate test case. A fan-out of 60 means it directly calls 60 distinct functions, so a signature change in any of them can ripple here. File-level history adds a little context: the file's history shows a bug-fix rate of 18.7%, one revert, and 10 distinct authors in the last 90 days. None of those counts proves a defect, but ten recent authors on a function this branchy is the kind of ownership spread that makes accidental interaction between branches more likely.

My recommendation is to extract the arbitrary-self-type probing loop into its own function that returns a small result type. The per-probe diagnostic assembly can then become a second function, and `suggest_traits_to_import` itself would shrink to orchestration. The loop already iterates over a fixed list of (type, prefix, method) tuples, which is a natural seam.

### `report_selection_error` — fulfillment_errors.rs

<FunctionCard fn='report_selection_error' file='compiler/rustc_trait_selection/src/error_reporting/traits/fulfillment_errors.rs' risk='3.87' band='active' cc='167' nd='6' fo='79' touches='258' />

This is the most complex function in the set: a cyclomatic complexity of 167, a fan-out of 79, and 258 touches in the last year, the highest touch count of the five. It was last changed 1 day ago. The excerpt shows a match over the kind of selection error, and inside the 'unimplemented' case there are early returns for several specialized obligation causes (impl-item comparison, const-parameter type errors) before it reaches a second match over the predicate kind. Multiple early exits plus nested matching mean a lot of paths to cover with tests.

<MetricBar label='Fan-out' value='79' threshold='15' max='90' />

The file history shows 177 commits, a bug-fix rate of 26.0%, one revert, and 23 distinct authors in the last 90 days. That is the widest recent ownership spread in this analysis. Combined with 258 touches in a year, it suggests many people are adding cases to one function. That is a normal way for an error reporter to grow, and also the way a function reaches a complexity of 167.

I would split by error variant: one function per top-level selection-error case, with the shared setup (span, long-type-file handling) passed in a small context struct. The early-return branches for impl-item and const-parameter errors are the cheapest first extraction because they already behave as self-contained handlers.

### `suggest_deref_ref_or_into` — suggestions.rs

<FunctionCard fn='suggest_deref_ref_or_into' file='compiler/rustc_hir_typeck/src/fn_ctxt/suggestions.rs' risk='3.86' band='active' cc='54' nd='7' fo='30' touches='177' />

This function tries a sequence of suggestion strategies for a type mismatch (dereference or reference, else-branch closures, calling a function, and others) and returns early with `true` as soon as one applies. A cyclomatic complexity of 54 with a nesting depth of 7 and a fan-out of 30 is moderate by this repository's standards, but the activity numbers keep it high: 177 touches in the last year and a last change 1 day ago.

The excerpt also shows a loop over HIR parent nodes that tracks tuple indexes and walks a local type annotation, nested inside the first suggestion branch. That is where the nesting depth of 7 likely comes from. File history lists 70 commits, a bug-fix rate of 25.7%, no reverts, and 14 distinct authors in the last 90 days.

The recommendation is to lift the tuple-index and annotation walk into a helper that returns an optional annotation span. That should drop the nesting depth meaningfully and leave the main function as a flat chain of 'try this strategy, else the next' calls, which is easier to extend without growing the nesting further.

### `parse_item_kind` — item.rs

<FunctionCard fn='parse_item_kind' file='compiler/rustc_parse/src/parser/item.rs' risk='3.85' band='active' cc='43' nd='22' fo='27' touches='204' />

This is the outlier on nesting. A cyclomatic complexity of 43 is the lowest in the set, but a nesting depth of 22 is far past the point (8+) where I treat nesting as a strong refactoring signal. The excerpt suggests a likely reason: it is a long `if / else if` chain that tests for each kind of top-level item (use, fn, extern crate, extern block, static, trait, impl, const block, const), and the depth may come mostly from the chain's shape rather than deeply layered logic, though the excerpt is truncated so I cannot confirm that.

<MetricBar label='Nesting Depth' value='22' threshold='4' max='25' />

That distinction affects the fix. This function is not hard to follow branch by branch, but every new item kind (the excerpt already includes const-block items and a defaultness-tracking closure) means adding another link in a chain that is already 22 levels deep. It has 204 touches in the last year, was last changed 2 days ago, and its file shows 105 commits, an 18.1% bug-fix rate, no reverts, and 11 distinct authors in the last 90 days.

I would restructure it as a sequence of early-returning checks, one helper per item kind, each returning an optional parsed item. That flattens the nesting to roughly one level without changing the order of the checks, which matters in a parser where earlier checks take priority.

### `run` — test.rs

<FunctionCard fn='run' file='src/bootstrap/src/core/build_steps/test.rs' risk='3.84' band='active' cc='120' nd='4' fo='64' touches='236' />

This one is in the bootstrap build tooling, not the compiler itself, but it is the most recently touched function in the set: 0 days since last change, with 236 touches in the last year. A cyclomatic complexity of 120 with a nesting depth of only 4 describes a long, flat function. From the excerpt it handles the test-suite setup for compiletest: a stage-0 guard, early returns for doc-only and disabled codegen tests, a special case for `ui-fulldeps` at stage 1, and several conditional `ensure` calls that build the compiler, standard library, wasm proc-macro support, or debugger scripts depending on the suite.

The file history shows 137 commits, a bug-fix rate of 10.2% (the lowest of the five), no reverts, 16 distinct authors in the last 90 days, and the highest review-comment density value in the set (5.0). I read that as a function that gets scrutinized in review but keeps absorbing new suite-specific branches. A fan-out of 64 means a lot of build steps are coupled to this single method.

The obvious extraction is per-suite setup: ui-fulldeps handling, debuginfo handling, and the shared prerequisite builds could each be a method on the step, with `run` reduced to sequencing them. Since the nesting depth is only 4, this should be a mechanical refactor.

## Where to start

I would start with `suggest_traits_to_import`. It has the top risk score, a cyclomatic complexity of 102, and a fan-out of 60, and it sits in diagnostics code where 10 authors have been active in the last 90 days. `report_selection_error` is the larger structural problem (cyclomatic complexity 167, fan-out 79, 23 recent authors), but splitting it by error variant is a bigger job, so I would schedule it after the smaller wins. `parse_item_kind` is the cheapest fix with the clearest payoff: flattening a nesting depth of 22 is mostly mechanical. I did not see any lower-ranked functions that change this picture; the context-only functions in the hashbrown module sit in the high band but are quiet (last changed 57 days ago, 22 touches in the last year), so their risk is structural debt and blast radius rather than live regression, and they rank below any of the five above.
