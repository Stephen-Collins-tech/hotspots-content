Change anything about how zustand persists state and you will work inside src/middleware/persist.ts, home to three of the top five hotspots in pmndrs/zustand: `persistImpl`, `createJSONStorage`, and `hydrate`. That concentration matters more than any single score, because 83% of the file's 6 commits are tagged as bug fixes. The analysis covers 89 functions, 2 of them in the critical band. The top-ranked function, `devtoolsImpl` in src/middleware/devtools.ts, is a 'fire' function with an activity-weighted risk score of 11.1 that was changed today, so it deserves review now and not just a place in the backlog.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `devtoolsImpl` — devtools.ts

<FunctionCard fn='devtoolsImpl' file='src/middleware/devtools.ts' risk='11.1' band='fire' cc='24' nd='3' fo='23' touches='2' />

I would start with `devtoolsImpl` because it is the highest-scoring 'fire' function and one of the most actively changing: an activity-weighted risk score of 11.1, 2 touches in the last year, and 0 days since last change. It is the one place where complexity and churn overlap right now.

<MetricBar label='Fan-out' value='23' threshold='15' max='30' />

The numbers point to breadth more than depth. Cyclomatic complexity is 24 and nesting depth is only 3, but fan-out is 23, meaning the function calls 23 distinct functions. From the excerpt, it wraps the store's `setState`, resolves whether the Redux DevTools extension is available, builds action names (falling back to the caller's name from a stack trace), and wires up a cleanup path that touches tracked connections. That is several separate responsibilities inside one closure, which is why the analysis flags it as both a god function and a long function.

The file-level history adds some context. The file has a bug-fix rate of 60% across 10 commits, with 0 commits explicitly linked to bugs and 0 reverts. Pull request review comment density is 25.5, and 2 distinct authors touched it in the last 90 days. I read that as a file that gets scrutiny and iteration, not as evidence of defects.

My recommendation: extract the `setState` wrapper, the action-name resolution, and the `cleanup` logic into separately named helpers that `devtoolsImpl` composes. The file already contains smaller helper functions, so extracting units fits its existing style.

### `shallow` — shallow.ts

<FunctionCard fn='shallow' file='src/vanilla/shallow.ts' risk='10.48' band='debt' cc='11' nd='2' fo='7' touches='0' />

`shallow` is critical band but a 'debt' function, so I would frame it as structural risk and not as live churn. It has not changed in 296 days, has 0 touches in the last year, and its file shows 1 commit total. Nothing suggests it is unstable.

What the metrics reveal is a lot of exit paths: cyclomatic complexity 11 with nesting depth 2, and the analysis tags it as exit heavy. From the excerpt, it short-circuits on identical values, rejects non-objects and null, compares prototypes, then branches between iterable and plain-object comparison. Each early return is a test case, and in TypeScript the narrowing around those guards adds implicit control flow that the complexity number understates.

Anyone using shallow equality for selectors runs through this function, so the blast radius when it next changes is wide even though it is quiet today. I would not refactor it for its own sake. Instead, confirm there is a test for each early-return branch (identical, non-object, prototype mismatch, iterable with entries, iterable without, plain object) before anyone edits it.

**`persistImpl`, `createJSONStorage`, and `hydrate` — persist.ts**

These three share a file and a file-level history, so I will treat them together before giving each its own recommendation.

The persist.ts file has a bug-fix rate of 83% across 6 commits, with 0 commits explicitly linked to bugs, 0 reverts, and pull request review comment density of 36.0, the highest in this analysis. It has 2 distinct authors in the last 90 days. The 83% figure comes from commit tagging and works only as a rough prioritization signal, a reason to review changes here more carefully. It does not tell me the current functions are broken.

<FunctionCard fn='persistImpl' file='src/middleware/persist.ts' risk='9.29' band='fire' cc='4' nd='4' fo='22' touches='1' />

`persistImpl` is the 'fire' function in this file: an activity-weighted risk score of 9.29, 1 touch in the last year, and 0 days since last change. Cyclomatic complexity is only 4, so the branching is modest, but nesting depth is 4 and fan-out is 22. The excerpt shows why: it builds default options, tracks hydration state with two listener sets, wraps both `api.setState` and the config's `set`, and defines `hydrate` inside itself. The analysis marks it as a god function and a long function.

The low cyclomatic complexity is misleading here. Much of the risk lives in shared mutable state (`hasHydrated`, `hydrationVersion`, `stateFromStorage`) captured by closures, which a branch count does not see. My recommendation: pull the storage-unavailable fallback and the `setItem` plumbing into small named helpers so that `persistImpl` reads as configuration followed by wiring.

<FunctionCard fn='hydrate' file='src/middleware/persist.ts' risk='8.47' band='debt' cc='4' nd='4' fo='12' touches='0' />

`hydrate` is nested inside `persistImpl`, has not changed in 220 days, and is structural debt. Nesting depth is 4 with fan-out 12. The excerpt shows a chain of asynchronous steps: it reads from storage, checks the stored version against the configured one, optionally runs a migration (which may or may not return a promise), merges state, and then fires post-rehydration callbacks. It also guards each step against a newer hydration having started, via a version counter that, per the comments, exists to prevent race conditions between concurrent `rehydrate()` calls.

That guard is the part I would handle most carefully. Each `.then` stage repeats the same staleness check, and a future edit that adds a stage without it would reintroduce the race the counter prevents. When someone next changes this function, I would write tests first for the migration branch and the sync-versus-async paths. A concrete refactor: extract the version-mismatch and migration decision into its own function that returns the `[migrated, state]` pair, so the promise chain only handles sequencing.

<FunctionCard fn='createJSONStorage' file='src/middleware/persist.ts' risk='8.55' band='debt' cc='4' nd='1' fo='8' touches='0' />

`createJSONStorage` is the mildest of the three. Cyclomatic complexity is 4, nesting depth is 1, fan-out is 8, and it has not changed in 296 days. The analysis flags it as exit heavy: it returns early when storage can't be obtained (for example during server-side rendering), and `getItem` branches on whether the underlying storage returned a promise. That sync-or-async branch deserves a test, since it is part of the public persistence surface. I would leave the structure alone and make sure both return shapes have coverage.

**What I would do first**

With one review slot, I would spend it on `devtoolsImpl`, because it is the only critical-band function that is also changing today. If persistence work is on the roadmap, I would treat persist.ts as a unit and add tests around `hydrate`'s migration and race-guard paths before touching `persistImpl`. A file with an 83% bug-fix rate and the highest review-comment density in this analysis is where careful review pays off.
