One file holds all five of etcd's top hotspots: `server/etcdserver/server.go`. Anyone changing the server core is working inside a single concentration of structural risk. The top function, `NewServer`, has an activity-weighted risk score of 2.69, a fan-out of 59, and sits in active code with 25 touches in the last year and 3 days since last change, so it is both complex and changing. etcd is a Go distributed key-value store; this snapshot covers 4,636 functions, 579 of them in the critical band. I would start with this file because the five scores sit between 2.62 and 2.69, which tells me the risk is a module-level property, not one outlier.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `NewServer` — server.go

<FunctionCard fn='NewServer' file='server/etcdserver/server.go' risk='2.69' band='critical' cc='23' nd='2' fo='59' touches='25' />

I would start with `NewServer` because its fan-out of 59 is the highest in the set and it is in code changed 3 days before the snapshot. Nesting is shallow at 2 and cyclomatic complexity is a moderate 23, so this is not a tangled-branch problem. It is a wiring problem. The excerpt shows a bootstrap call, construction of a large server struct, and then a long sequence of subsystem setup: the lessor, the token provider, the MVCC store, the corruption checker, and the auth store. One comment in the code states that the lessor must be recovered before the key-value store, so there is an ordering constraint that lives in prose rather than in structure.

<MetricBar label='Fan-out' value='59' threshold='15' max='70' />

There are also deferred cleanup closures keyed on the named return value. Cleanup paths that depend on error state are easy to break when someone inserts a new initialization step. My recommendation is to extract the ordered subsystem setup into named helpers, such as one for the lessor and key-value store and one for auth, so the ordering constraint becomes a function boundary instead of a comment. Each helper can then be tested without standing up the entire server.

### `PromoteMember` — server.go

<FunctionCard fn='PromoteMember' file='server/etcdserver/server.go' risk='2.66' band='critical' cc='19' nd='3' fo='12' touches='25' />

`PromoteMember` is the least coupled of the five, with a fan-out of 12, but it has a cyclomatic complexity of 19 and a nesting depth of 3. The excerpt shows an attempt to promote locally, a metrics branch for success versus failure, a fallback that forwards to the leader over HTTP when the local node is not the leader, and a retry loop over leader peer URLs inside a context-bounded outer loop. Three distinct error types cause an early exit from the retry loop, and everything else keeps retrying until the context ends.

The nested loop with several error-class exits is where complexity concentrates. A loop that retries on unclassified errors until a deadline is also a place where a new error type can silently turn into a long wait. I would move the leader-forwarding loop into its own function with an explicit list of terminal errors, so that adding a new terminal error is a one-line change in one place.

### `parseProposeCtxErr` — server.go

<FunctionCard fn='parseProposeCtxErr' file='server/etcdserver/server.go' risk='2.66' band='critical' cc='18' nd='3' fo='13' touches='25' />

`parseProposeCtxErr` translates a context error into a more specific etcd error. The excerpt shows a switch on cancellation versus deadline exceeded, and inside the deadline case, a time-window comparison against the last leader election, followed by a nested switch on who the current leader is, with connectivity checks against the quorum or the leader. One branch carries a TODO noting that a specific error should be returned when the cluster has no leader.

Cyclomatic complexity of 18 for what is conceptually a classifier is a signal that the decision tree has grown organically. Callers see only the returned error, so each branch is a distinct behavior clients can observe. I would split the deadline case into a helper that returns the most specific timeout error, and add table-driven tests for each branch, including the unresolved no-leader case flagged in the TODO.

### `applySnapshot` — server.go

<FunctionCard fn='applySnapshot' file='server/etcdserver/server.go' risk='2.62' band='critical' cc='19' nd='2' fo='34' touches='25' />

`applySnapshot` combines a cyclomatic complexity of 19 with a fan-out of 34. From the excerpt, it handles an empty-snapshot early return, a panic on an outdated snapshot index, a wait for the raft node to persist the snapshot, then a locked sequence: open the snapshot backend, set the consistent index backend, recover the lessor, and restore the key-value store. Comments in the code call out ordering hazards, including that the consistent index backend must be set before lessor recovery or the old value can overwrite the snapshot's value.

Several failure paths panic instead of returning an error, and there is manual lock handling through a flag that tracks whether the mutex was already released. That pattern is a classic place for a future edit to double-unlock or skip an unlock. Because this function also blocks on a channel waiting for the raft node, it carries goroutine-interaction risk that complexity numbers do not capture. I would extract the backend swap and the store restore into separate steps and replace the unlock flag with a narrower scope for the lock.

### `applyConfChange` — server.go

<FunctionCard fn='applyConfChange' file='server/etcdserver/server.go' risk='2.62' band='critical' cc='31' nd='3' fo='29' touches='25' />

`applyConfChange` has the highest cyclomatic complexity in the top five at 31, which is above the level where I would call a function high-complexity. The excerpt shows a validation step with its own error path, a switch over configuration change types (add node, add learner, remove node, update node), and repeated unmarshal-and-check-member-ID blocks that panic on mismatch. Several of those blocks are near-duplicates across the add and update cases, so part of the complexity is repetition rather than distinct logic.

<MetricBar label='Cyclomatic Complexity' value='31' threshold='15' max='40' />

This function mutates cluster membership and the transport peer set, and it takes a flag controlling whether the v3 store is applied. Each flag combination multiplies the paths a test has to cover. I would pull each switch case into its own method and share the member-ID check, which should take the main function's complexity down by roughly half and give each membership operation a unit-testable seam.

## Where to start

I would sequence the work like this. First, `applyConfChange` and `applySnapshot`, because they carry the highest complexity and coupling respectively and both mutate cluster or storage state. Second, `NewServer`, where extracting ordered setup helpers lowers its fan-out of 59 and documents ordering constraints in structure. Third, `PromoteMember` and `parseProposeCtxErr`, which are smaller and can be tidied with focused extractions.

For framing, there are also quiet-tier functions in `server/storage/backend/backend.go` with high structural complexity. They score lower on activity-weighted risk because they are not changing right now. The `server.go` cluster is the one where complexity and ongoing change overlap.
