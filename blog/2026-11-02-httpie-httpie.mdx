The riskiest function in httpie, `raw_main` in httpie/core.py, hasn't been changed in 808 days, and the other four top hotspots have gone 808 to 956 days untouched, so this is accumulated debt rather than an emergency. All 95 functions in the debt quadrant are structurally complex and dormant, and I counted 17 critical functions out of 507 analyzed at commit 5b604c3. I would start with `raw_main` and `program` in core.py, because they sit on the path every command takes and the next feature that touches them will inherit all of their accumulated branching.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `raw_main` — core.py

<FunctionCard fn='raw_main' file='httpie/core.py' risk='14.71' band='critical' cc='27' nd='4' fo='17' touches='0' />

This is the top-ranked function, with an activity-weighted risk score of 14.71, and it has gone 808 days without a change. From the excerpt, it is the CLI entry wrapper: it decodes raw arguments, switches into daemon mode, loads plugins, merges default options, handles debug and traceback flags, parses arguments, and then runs the main program, with separate exception handlers for nested JSON syntax errors, keyboard interrupts, and system exits on both the parse path and the execution path.

<MetricBar label='Cyclomatic Complexity' value='27' threshold='10' max='60' />

A CC of 27 with a fan-out of 17 means this function coordinates a lot of collaborators, and in Python those calls are resolved at runtime, so the real coupling is probably wider than the number suggests. The exception handling is where the paths multiply: the same interrupt and exit handling appears to be repeated in two places, each with its own traceback check and status assignment. That is also what makes it exit-heavy, since every path needs its own test to confirm the right exit status comes back. The patterns flagged here are complex branching, exit-heavy, god function, long function, and stale complex.

My recommendation: extract the two repeated 'except KeyboardInterrupt / except SystemExit' blocks into one helper that maps an exception to an exit status, and move the nested `handle_generic_error` closure out to module level. That alone should remove several paths and make the function readable in one pass.

### `collect_messages` — client.py

<FunctionCard fn='collect_messages' file='httpie/client.py' risk='13.44' band='critical' cc='23' nd='5' fo='23' touches='0' />

This one has the highest fan-out of the five, 23 distinct calls, and the deepest nesting alongside `program`, at 5 levels. It has gone 956 days without a change. The excerpt shows it building the request: it loads an optional HTTPie session, builds request and send keyword arguments, constructs a requests session, applies session headers, cookies, and auth, dumps debug output, prepares the request, optionally compresses the body, and then enters a generator loop that yields each prepared request and sends it, tracking cookies as it goes.

<MetricBar label='Fan-out' value='23' threshold='15' max='30' />

Because it is a generator, control flow is split across yield points, which makes it harder to reason about than the CC alone suggests: the caller drives execution, and the state held in local variables (response count, expired cookies) lives across yields. This file has 5 total commits, the most of the top five, but none are tagged as bug fixes and there are no reverts.

My recommendation: split the setup half (everything before the loop) into a function that returns a prepared request plus the send settings, leaving the generator loop as a small, separately testable unit. The session-handling block is a natural first extraction.

### `interpret` — nested_json/interpret.py

<FunctionCard fn='interpret' file='httpie/cli/nested_json/interpret.py' risk='13.22' band='critical' cc='14' nd='3' fo='22' touches='0' />

This is the outlier in the group: its CC of 14 and nesting of 3 are modest, but a fan-out of 22 pushes it into the critical band. It has gone 808 days without a change and has only 1 commit in its history. From the excerpt, it walks a parsed key path and builds nested dicts and lists, with branches for key, index, and append actions, plus a type-check helper that constructs detailed error messages and raises a nested JSON syntax error.

The branching is not the problem here; the density is. A type-check closure, an object-factory closure, and a three-way loop body all live in one function, and the error-message construction inside the type check pulls in many collaborators. The index branch also handles negative indexes and list padding inline. I would flag the exit-heavy and god-function patterns as the reason this deserves attention despite the lower CC.

My recommendation: lift `type_check` and `object_for` to module-level functions with explicit arguments, and give each path action its own small handler. That makes the dispatch loop a table lookup and lets each action be tested alone.

### `_compute_new_headers` — sessions.py

<FunctionCard fn='_compute_new_headers' file='httpie/sessions.py' risk='13.04' band='critical' cc='15' nd='4' fo='14' touches='0' />

This method has gone 956 days without a change and has a single commit in the file's history. It filters request headers before they are stored in a session: it skips unset headers, decodes byte values, drops HTTPie's own user-agent, routes cookie headers into the cookie jar and removes them from the request, and skips headers matching a list of ignored prefixes.

It is the smallest of the five, but the pieces are tangled: header filtering and cookie-jar mutation happen in the same loop, and the method mutates its input (removing the cookie header from the request headers) while also building and returning a new set. That side effect is easy to miss and is exactly the kind of thing a future edit could break. The patterns flagged are complex branching and exit-heavy, driven by the repeated 'continue' paths in the loop.

My recommendation: separate the cookie handling into its own method, and write down in a docstring that the input headers are modified. Then add tests for each skip rule individually, since each 'continue' is a distinct path.

### `program` — core.py

<FunctionCard fn='program' file='httpie/core.py' risk='12.88' band='critical' cc='27' nd='5' fo='21' touches='0' />

This function has a CC of 27, nesting of 5, and fan-out of 21, and it has gone 956 days without a change. Its own docstring calls it the main program without error handling, and a TODO in the excerpt says it should be refactored and drastically simplified, especially so that the separator logic lives elsewhere. I do not need to infer the maintainers' view here; the code says it.

<MetricBar label='Nesting Depth' value='5' threshold='4' max='8' />

From the excerpt, it drives the whole request-response cycle: it sets up processing options, handles download mode, iterates over the messages produced by `collect_messages`, decides per message what to write, tracks whether a separator is needed between messages, maps HTTP status to an exit status, and performs cleanup. It also defines two closures, one for writing separators and one for piping request-body chunks to stdout. State variables such as the initial request, final response, previous-body flag, and force-separator flag are carried across loop iterations, so understanding any one branch means tracking several others.

My recommendation: follow the TODO. Pull the separator state (the force-separator and previous-body flags and the `separate` closure) into a small class or helper, and extract the per-message decision into its own function. Together with `raw_main` above, this is the pair I would schedule together, since both live in core.py and both carry a CC of 27.

**Where I would start**

If I had one sprint, I would take `program` first because it carries the deepest nesting and an explicit TODO, then `raw_main` for the repeated exit handling, then `collect_messages` for its fan-out. `interpret` and `_compute_new_headers` are smaller jobs that could be done in parallel. None of this is urgent in the sense of a live regression risk, but the longer these stay untouched, the more of their context is lost.
