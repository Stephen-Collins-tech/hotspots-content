### `assertDocument` — JsonUtf8ReaderTest.java

<FunctionCard fn='assertDocument' file='moshi/src/test/java/com/squareup/moshi/JsonUtf8ReaderTest.java' risk='1.52' band='active' cc='4' nd='3' fo='25' touches='2' />

I would start with `assertDocument` because it is the only function in the file in the high band, with an activity-weighted risk score of 1.52, a fan-out of 25, and a last change 7 days ago. From the excerpt, it is a shared test helper: it builds a lenient reader from a document string and then walks a variable list of expectations, matching each one against a different reader call (begin and end object, begin and end array, name, boolean, string, number, null, or an expected exception class).

<MetricBar label='Fan-out' value='25' threshold='15' max='30' />

Its cyclomatic complexity of 4 is modest and its nesting depth of 3 is only moderate. The standout figure is the fan-out. The function is a long if-else chain that dispatches on sentinel values, and the helper touches most of the reader's API surface in one place. That makes it a single point of coupling for every test that calls it: if the helper's behavior shifts, many test cases change meaning at once, and a failure inside it is harder to attribute to a specific expectation.

My recommendation is to leave the dispatch logic alone for now and tighten what it reports on failure. Replace the bare assertion error in the final else branch with a message that names the unrecognized expectation and its position in the list. Then consider splitting the expectation handling into small named steps so a reviewer can see which reader call each sentinel maps to.

These two share identical numbers: an activity-weighted risk score of 1.38, a cyclomatic complexity of 5, a nesting depth of 1, and a fan-out of 10. Both are in the moderate band. That is not a coincidence. From the excerpts, they are near-duplicates that run the same four malformed array inputs (`[true,,true]`, `[,true]`, `[true,]`, `[,]`) and differ only in which reader method is expected to throw, a null read in one and a skip in the other.

The structure is four repetitions of build a reader, trigger the call, expect an encoding exception. Because the two functions are copies of each other, any new malformed-separator case has to be added in both places, and the two can drift apart without anything flagging it. A parameterized test over the four inputs and the two operations would cut both functions to one table of cases and remove the duplicated try-catch scaffolding.
