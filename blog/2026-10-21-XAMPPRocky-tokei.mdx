The top function in tokei, `print_results` in `src/cli_utils.rs`, hasn't been changed in 747 days, and its nesting reaches 8 levels. That is structural debt with a high blast radius for the next developer who has to touch it, not live churn. Across the 138 functions I analyzed in tokei (a code-counting CLI), 4 are critical, 23 sit in the debt quadrant, and none are in the fire quadrant. I would start with `print_results` because its nesting depth is the highest in the set and it renders the full per-language report.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `print_results` — cli_utils.rs

<FunctionCard fn='print_results' file='src/cli_utils.rs' risk='16.49' band='critical' cc='16' nd='8' fo='7' touches='0' />

This function renders the per-language and per-file report. From the excerpt, it partitions languages into simple and child-bearing groups, loops over both, and then branches again on file listing, compact mode, sort order, and whether a report carries embedded blobs. A nesting depth of 8 is well past what I would call readable, and it is high for a function with only 16 independent paths. The deep nesting is the problem here, more than the raw branch count.

<MetricBar label='Max Nesting Depth' value='8' threshold='4' max='10' />

It also repeats a partition-then-loop shape inside the loop, which suggests the nested block is a second printing routine in disguise. The function has 7 distinct callees, and its file shows a high density of pull-request review comments (5.5), which fits a place where reviewers had things to say. Its last change was 747 days ago, so no recent activity is masking any of this.

My recommendation: extract the file-listing branch (the compact and non-compact report printing) into its own method, and extract the per-report blob rendering below it. That alone should cut the nesting depth roughly in half. It also gives the multiple `?` exit points a smaller surface to test. If tokei has output snapshot tests, run them before and after the extraction, since formatting widths are easy to break by accident.

**`parse_context` and `parse_multi_line_comment` — syntax.rs**

These two functions share a file, and together they decide whether the tool is inside a comment, a string, or an embedded code block. I would review them as a pair.

<FunctionCard fn='parse_context' file='src/language/syntax.rs' risk='15.46' band='critical' cc='28' nd='5' fo='15' touches='0' />

`parse_context` has the highest cyclomatic complexity in my top five at 28, plus a fan-out of 15 and a nesting depth of 5. From the excerpt, it returns early if a quote or comment stack is active, then branches by language family. The Markdown path locates fenced code blocks and recursively parses the embedded language. The Rust path walks doc-comment lines and gathers them as Markdown. Each family looks like its own parser stitched into one match, which explains the god-function and long-function flags. Several early exits also multiply the test cases needed for full path coverage.

<MetricBar label='Cyclomatic Complexity' value='28' threshold='10' max='40' />

The signature takes a mutable reference to parser state plus a regex cache, so the function mixes state mutation with recursive parsing of child languages. Rust ownership hides some of this coupling from CC alone, so I would not read 28 as the whole story. I saw no `unsafe` blocks in the excerpt, so my concern is logic density, not memory safety. The file has 2 total commits on record and no reverts.

My recommendation: split the match arms into one function per language family (`parse_markdown_context`, `parse_rust_doc_context`, and so on), leaving `parse_context` as a thin dispatcher. That takes the CC from 28 to somewhere in the low single digits for the dispatcher and keeps each arm testable on its own.

<FunctionCard fn='parse_multi_line_comment' file='src/language/syntax.rs' risk='10.09' band='critical' cc='11' nd='4' fo='8' touches='0' />

`parse_multi_line_comment` is smaller and less alarming, with a CC of 11, nesting depth of 4, and fan-out of 8. It scans the configured multi-line and nested comment delimiters, pushes the closing delimiter onto a stack when it finds an opening one, and decides whether nesting is allowed. The push decision is a three-way condition inside a loop inside a branch, which is where the nesting comes from. It last changed 810 days ago.

My recommendation is modest: pull the 'should this start push onto the stack' condition into a small named predicate. That flattens one level of nesting and gives the nested-comment rules a name a reader can search for.

### `main` — main.rs

<FunctionCard fn='main' file='src/main.rs' risk='12.87' band='critical' cc='22' nd='2' fo='18' touches='0' />

`main` has the highest fan-out in the set at 18, with a CC of 22 and a shallow nesting depth of 2. That profile reads as a long, flat orchestration function, not a tangled one. From the excerpt, it parses arguments, validates input paths, computes column width, optionally prints a streaming header, gathers statistics, and then branches into output formatting, sorting, and printing. Several of those branches call `process::exit` directly, which gives the function many exit paths and makes it awkward to test without spawning a process.

<MetricBar label='Fan-Out' value='18' threshold='10' max='25' />

The CLI's whole control flow lives here, so any change to a flag or output mode touches this function. It hasn't been changed in 810 days, and the file has 1 commit on record, so I have no history to show how it behaves under change. My recommendation: move the argument validation and early-exit checks into a function that returns a result, and have `main` perform the single exit at the end. The column-width calculation is another self-contained chunk that can come out as a helper. That makes the orchestration testable without process-level exits.

### `parse_lines` — language_type.rs

<FunctionCard fn='parse_lines' file='src/language/language_type.rs' risk='8.37' band='high' cc='17' nd='3' fo='7' touches='0' />

`parse_lines` is the core loop of the counter. It steps through the input line by line, classifies each as code or comment, and delegates embedded languages (Markdown fences, Rust doc comments, Lingua Franca, HTML) to child parsers. It is the only high-band function in my top five, and its CC of 17 comes mostly from a nested match on child language context. Its nesting depth of 3 is modest.

This file has the strongest review-attention signal of the five. Its pull-request review comment density is 13.0, more than double the next file, and its bug-fix rate is 67% across 3 total commits. That is thin evidence, but it fits a function that reviewers found worth discussing. I would not say anything about defects from it. What I would say is that the child-language handling inside the loop is the part to extract: each branch of the context match adds stats and blobs in a slightly different way, and moving that into one function that takes the context and returns the updated stats would shrink the loop body and let you compare the four cases side by side.

**What I would do first**

I would order the work by how much risk each change removes per hour spent. The `parse_context` split is the largest structural win, since it has the highest CC and clean seams between language families. The `print_results` extraction is the best fit for a first refactor because the nesting problem has an obvious fix. `main` and `parse_lines` can wait until one of them needs a feature change, at which point the refactor should come first. None of this is urgent, because none of these functions is changing, but the longer they sit, the less anyone remembers how they behave.
