### `createIonRouter` — router.ts

<FunctionCard fn='createIonRouter' file='packages/vue-router/src/router.ts' risk='19.66' band='fire' cc='58' nd='7' fo='45' touches='2' />

I would start with `createIonRouter`: it has the highest activity-weighted risk score in the repository (19.66) and it changed 14 days ago. Two touches in the last year is not high churn in absolute terms, but the function is large enough that two touches means two chances to alter navigation behavior in a function with a cyclomatic complexity of 58.

The excerpt shows why the numbers are what they are. The function holds several pieces of mutable closure state for navigation information (a current-navigation record, an owner reference, and an 'unclaimed' flag), then registers an `afterEach` hook and an error-handler wrapper that have to coordinate with that state. The comments in the excerpt describe matching staged deltas against a navigation by identity, because two history navigations can move to the same path. That is a subtle invariant to preserve across edits, and it lives inside a function with a nesting depth of 7 and 45 distinct callees. The function is flagged as a god function, long, deeply nested, exit-heavy, and branch-heavy.

The file-level history adds context without proving anything. Of 4 total commits on the file, a bug-fix rate of 75% appears in the data, with no bug-linked commits and no reverts, 3 distinct authors in the last 90 days, and a pull-request review comment density of 11.0, the highest of the five. I read that as a file that gets scrutinized in review and has needed corrective changes, which is a reason to prioritize it, not a finding that the current code is defective.

My concrete recommendation: extract the navigation-info staging state and its three variables into a small dedicated object with explicit claim and discard methods, and move the `afterEach` and error-handler registration into separate named functions. That puts the identity-matching invariant in one place where it can be tested directly.

### `IonRouter` — IonRouter.tsx

I am not calling this actively changing code. I am calling it structural debt with a high blast radius when it is next touched, and since it is the React router component, everyone using the React bindings inherits that change.

The excerpt shows a component that holds a location history, a view stack, a forward-navigation stack keyed on React Router's unique location keys, a current-tab reference, and route info state, with effects that seed the history on mount and sync matched params back into route info. The comments explain a StrictMode double-render concern and a tab-ordering concern with `IonTabBar`. Those are real ordering dependencies buried inside a single component with a cyclomatic complexity of 49, nesting depth of 7, and fan-out of 34.

Nothing there suggests urgency, so I would treat this as overdue for refactoring rather than urgent. The cheapest first step is extracting the forward-stack and location-history bookkeeping into custom hooks, which would lift a block of refs and effects out of the component body.

### `setup` — IonRouterOutlet.ts

<FunctionCard fn='setup' file='packages/vue/src/components/IonRouterOutlet.ts' risk='17.41' band='fire' cc='30' nd='5' fo='51' touches='2' />

`setup` in the Vue router outlet has an activity-weighted risk score of 17.41, a cyclomatic complexity of 30, a nesting depth of 5, and a fan-out of 51. It was last changed 8 days ago, with 2 touches in the last year. The fan-out is the standout: 51 distinct callees makes this function a coupling point for the outlet's whole lifecycle.

The excerpt shows a watcher on the route and matched-route reference, with a long comment listing the cases it must handle: an outlet that should ignore a route that does not apply to it, a different matched route, and a parameterized route where the matched record is the same but the parameters differ (the `/page/1` to `/page/2` case). That comment is doing the job a set of named predicates would do better. There is also a flag for a view that was given leave hooks when its hosting page left, to avoid firing them twice. Each of those cases is a branch someone needs a test for.

The file history shows a bug-fix rate of 66.67% across 3 commits, no reverts, and 3 distinct authors in the last 90 days. Again, supporting context, not a verdict. I would extract the route-change decision into a pure function that takes the current route, matched record, and previous values and returns whether and how to transition. That function can be tested without mounting an outlet, and it would cut the branch count inside `setup` substantially.

### `computeParentPath` — computeParentPath.ts

<FunctionCard fn='computeParentPath' file='packages/react-router/src/ReactRouter/utils/computeParentPath.ts' risk='17.14' band='debt' cc='31' nd='7' fo='14' touches='0' />

`computeParentPath` is the other 'debt' function in my top five, with an activity-weighted risk score of 17.14, a cyclomatic complexity of 31, a nesting depth of 7, a fan-out of 14, 0 touches in the last year, and 57 days since last change. The file has a single commit with a bug-fix rate of 0%, so there is no historical defect signal here at all. This is maintainability debt, plainly.

The excerpt shows an early scope check, a fast path when the mount path is known from React Router's route context, and then a fallback that walks URL segments and tracks three candidate matches (specific, wildcard, and index), with a final selection step. The code comments say the fallback only runs on first render of outlets without a parent match. A nesting depth of 7 in a loop that tracks three competing candidates, with special cases for empty-path routes, is where I would expect a future edit to go wrong.

I suggest extracting the segment walk into its own function that returns the three candidates, and I would keep the scope check and fast path in the caller. That separates 'do we already know the answer' from 'discover the answer', which is the real structure in the code, and it makes each half testable with plain path strings.

**Context from outside the top five**

Routing and transition code is the dominant cluster in this repository, and the 'watch' functions are active but structurally modest, so I would not prioritize them.

**What I would do this week**

If I owned this repository I would put the three 'fire' functions first, in this order: `createIonRouter`, `setup` in the Vue outlet, and `createSheetGesture`. Add characterization tests around the branch cases before the next change lands, then extract along the seams I described. The two React debt functions can wait for a planned refactoring window, but I would schedule that window before the next feature push into the React router.

### `createSheetGesture` — sheet.ts

<FunctionCard fn='createSheetGesture' file='core/src/components/modal/gestures/sheet.ts' risk='16.51' band='fire' cc='47' nd='3' fo='54' touches='1' />

`createSheetGesture` is the outlier in my top five because its nesting depth is only 3. Its risk comes from breadth: a cyclomatic complexity of 47 and a fan-out of 54, the highest fan-out among my top five. It was last changed 6 days ago with 1 touch in the last year, and its activity-weighted risk score is 16.51.

The signature alone is a signal. It takes 14 parameters, including several callbacks (dismiss, breakpoint change, drag start, drag move, drag end) and the animation and element references. Inside, the excerpt shows many pieces of mutable closure state (cached scroll element, cached footer elements, footer position and state, the current breakpoint, an offset, and a flag for whether the dismiss-blocking logic is gating the gesture) plus nested helpers such as `enableBackdrop`, which checks focus-trap and backdrop opt-outs before touching pointer events and a focus-trap class. This is a gesture state machine written as one closure, which is why the branch count is high even though nesting stays shallow.

The file has 2 total commits with a bug-fix rate of 50%, no reverts, 2 distinct authors in the last 90 days, and a review comment density of 2.33. I would introduce a parameter object for the 14 arguments and split the footer caching, backdrop toggling, and breakpoint-snapping logic into separate units that share an explicit state object. Gesture code is hard to test through the DOM, so pulling the breakpoint math into pure functions would buy the most coverage for the least effort.
