The riskiest function in alembic, `_compare_indexes_and_uniques` in `alembic/autogenerate/compare/constraints.py`, hasn't been changed in 42 days, and it carries a cyclomatic complexity of 81 and a fan-out of 40. That makes the top of this list a maintenance concern, not an emergency: structural debt with a large blast radius for whoever touches it next, not a function under active churn. Alembic is the SQLAlchemy migration tool, and I analyzed 1,031 functions at commit b42ebe1, of which 99 landed in the critical band; all five of the highest-scoring ones are in the debt quadrant, and I would start with the autogenerate comparison code and the revision-parsing methods in `alembic/script/revision.py`.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `_compare_indexes_and_uniques` — constraints.py

<FunctionCard fn='_compare_indexes_and_uniques' file='alembic/autogenerate/compare/constraints.py' risk='16.61' band='debt' cc='81' nd='4' fo='40' touches='0' />

I would start with `_compare_indexes_and_uniques` because it has the highest activity-weighted risk score in the repository (16.61) and a cyclomatic complexity of 81, well into the extreme range. Its fan-out of 40 is the other number that stands out. In Python, where call targets resolve at runtime, forty distinct callees probably means more coupling than the number suggests.

<MetricBar label='Cyclomatic Complexity' value='81' threshold='30' max='90' />

From the source excerpt, the function takes the autogenerate context, a set of table-modification operations, a schema, a table name, and a pair of connection and metadata table objects. It builds sets of unique constraints and indexes from the metadata side, then reflects the same from the live database through the inspector. The reflection code is wrapped in separate handlers for `NotImplementedError` and `TypeError`, and each branch applies name filters before moving on. That is a lot of backend-capability handling in one body: the function appears to cover both metadata-side collection and database-side reflection before it reaches the actual comparison.

The file has five commits in its history, two of them linked to bug fixes (a bug-fix rate of 20%), no reverts, and two distinct authors in the last 90 days. That is a modest signal. It doesn't say this function is defective, but it does mean the file has needed corrective changes before. Given that, I recommend extract-method along the seams the comments already mark: pull the metadata collection, the connection reflection (with its capability fallbacks), and the comparison into separate functions. The reflection step in particular could return a small result object carrying the reflected constraints and the two capability flags, so each stage can be tested without a database inspector.

### `generate_revision` — script/base.py

<FunctionCard fn='generate_revision' file='alembic/script/base.py' risk='15.89' band='debt' cc='50' nd='4' fo='25' touches='0' />

`generate_revision` writes a new migration file, and its metrics are CC 50, ND 4, and FO 25. It hasn't been changed in 45 days. The source excerpt shows why the branch count is high: it validates the revision ID, collects the head revisions under an error-translation context, rejects duplicate heads, and then resolves the version path through a chain of conditions that depend on how many version locations are configured. Several of those branches end in a `CommandError`, which is where the exit-heavy flag comes from.

The file-level history is the interesting part. Ten bug-linked commits sit against only four total commits, which suggests the counts overlap or are attributed in a way I can't resolve from this data alone, so I would not read much into the ratio. The bug-fix rate is 0%, there are no reverts, and the file shows a review-comment density of 9.0. I'd treat that as mixed context, not a clear defect signal.

My recommendation is to extract the version-path resolution into its own function. It is a self-contained decision (single location, multiple locations with a head to infer from, or an explicit path), and right now it is interleaved with head validation and file creation. Splitting it out lets each error message be tested directly.

**`_parse_downgrade_target` and `_parse_upgrade_target` — script/revision.py**

I am grouping these two because they share a file, a last-change date of 45 days ago, an identical file-level history, and the same shape of problem.

<FunctionCard fn='_parse_downgrade_target' file='alembic/script/revision.py' risk='15.56' band='debt' cc='29' nd='5' fo='16' touches='0' />

<FunctionCard fn='_parse_upgrade_target' file='alembic/script/revision.py' risk='15.24' band='debt' cc='25' nd='5' fo='14' touches='0' />

Both methods translate a command-line target string, which may be absolute or relative, into revision objects, using the database's current revisions as a starting point. Both reach a nesting depth of 5, which is past the point where I can hold the branching in my head. The excerpts show why: relative-versus-absolute handling, optional branch labels, a symbol that may or may not be present, and a nested fallback for when a branch label is given but isn't a current head. Both also carry type-ignore comments on calls into the lineage filter, which tells me the typing around these revision tuples is already strained.

This file is the most heavily reviewed in the set, with a review-comment density of 22.0, and it shows four bug-linked commits out of four total, a bug-fix rate of 0%, and no reverts. I would not call the functions buggy on that basis. What I would say is that the file has drawn more reviewer attention than the others, and because the two functions mirror each other, any change to relative-target semantics likely needs to be made twice.

The concrete step is to pull the shared relative-destination match and the branch-label lineage logic into common helpers, and to flatten the nesting with early returns for the cases that raise errors. Getting the nesting depth from 5 to 3 in each would do more for readability than any other single change here.

### `tox_parameters` — tools/toxnox.py

<FunctionCard fn='tox_parameters' file='tools/toxnox.py' risk='15.54' band='debt' cc='14' nd='6' fo='20' touches='0' />

`tox_parameters` is the odd one out. It sits in `tools/toxnox.py`, a build-tooling file rather than library code, so this is a maintainability issue for the project's test matrix, not a runtime risk to users. Its cyclomatic complexity is a modest 14, but its nesting depth of 6 and fan-out of 20 are what push it into the critical band.

From the excerpt, it is a decorator factory that builds nox parametrization from the product of token lists, with nested helper functions and a recursive generator inside it. The closures nested inside a decorator are probably where the depth comes from, since Python counts the helpers' bodies in the enclosing function's structure. The history is light: six commits, a bug-fix rate of 16.67%, and no bug-linked commits or reverts.

I would rate this lowest of the five for urgency. If it gets touched, lift the helper functions to module level so the decorator body is only the assembly step. That removes most of the nesting without changing behavior.

**What I would do with this list**

I would schedule the two `revision.py` functions and `_compare_indexes_and_uniques` first, because they carry the highest risk scores and the deepest structural debt in the list. For context, the fire quadrant, with 17 functions, shows where the active work is right now, and I would watch those functions as well.
