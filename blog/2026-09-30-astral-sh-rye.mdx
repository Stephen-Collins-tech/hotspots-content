The top function, `sync` in rye/src/sync.rs, hasn't been changed in 362 days, and it carries CC 29, nesting depth 5 and fan-out 11. That is latent debt rather than an emergency: the next developer to touch it will be working in code that branches heavily and has been dormant for a year. Rye's repository analysis covers 449 functions, 54 of them critical, and every function in the top five sits in the debt quadrant, so I would argue for refactoring before the next feature push rather than as a reaction to live regressions.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `sync` — sync.rs

<FunctionCard fn='sync' file='rye/src/sync.rs' risk='15.32' band='critical' cc='29' nd='5' fo='11' touches='0' />

I would start with `sync` because it has an activity-weighted risk score of 15.32, hasn't been changed in 362 days, and combines CC 29 with nesting depth 5. It is also the entry point for synchronizing a project's virtualenv, so a mistake here affects a very common user operation.

<MetricBar label='Cyclomatic Complexity' value='29' threshold='10' max='60' />

From the source excerpt, the function does several unrelated jobs in sequence. It loads the project file and resolves lockfile and virtualenv paths. It applies three project-level settings (hash generation, universal locking, locking with sources) onto the lock options. It ensures the bootstrap environment exists, decides whether the virtualenv must be recreated by comparing a marker's Python version and recorded path, fetches a toolchain, and deletes the old environment. That is the shape of a god function: environment validation, option resolution, recreation policy and cleanup all share one body, and the analysis flags it as long, deeply nested and exit-heavy as well.

The external signals are light. The file has 1 bug-linked commit out of 5 total commits and no reverts, though the recorded bug-fix rate is 0%, which does not line up with that one bug-linked commit, so I would not lean on either number. I read that as maintainability debt rather than a defect history. My recommendation is concrete: extract the recreation decision (the block that checks the marker, compares Python versions, detects a relocated virtualenv and handles the forced and python-only cases) into its own function that returns a simple decision. It is the most nested part of the body, and isolating it lets you test each branch without standing up a real virtualenv.

### `finalize_lockfile` — lock.rs

<FunctionCard fn='finalize_lockfile' file='rye/src/lock.rs' risk='15.22' band='critical' cc='19' nd='6' fo='8' touches='0' />

`finalize_lockfile` has CC 19 but nesting depth 6, and the nesting is what worries me. It hasn't been changed in 322 days. From the excerpt, it walks the resolver's output line by line and decides what to do with each one: skip blank lines and index options, strip trailing backslashes, rewrite editable file URLs as relative paths, comment out excluded requirements along with their hash continuation lines, and annotate dependency comments. A stateful loop with an exclusion flag carried across iterations is easy to get subtly wrong, and the code itself carries a TODO noting that it does not evaluate markers.

The file's history gives this one more weight than `sync`. It has 3 bug-linked commits out of 7 total, a bug-fix rate of about 14%, no reverts, and a pull-request review comment density of 6.0. None of that proves the function is defective, but a complex, deeply nested parser with a documented limitation and some review discussion behind it deserves higher review priority. I would split the per-line classification from the output writing, so each line type becomes a small function with its own tests, especially for the exclusion-with-hashes continuation case.

### `unpack_archive` — mod.rs

<FunctionCard fn='unpack_archive' file='rye/src/utils/mod.rs' risk='15.07' band='critical' cc='17' nd='6' fo='8' touches='0' />

`unpack_archive` is the longest-dormant function in the top five at 453 days since last change. It unpacks zip and tar archives, strips leading path components, and writes entries under a destination directory. The excerpt shows it guards against unsafe paths by checking that each computed path stays inside the destination, and it duplicates the strip-components and containment logic across the zip and tar branches.

I would prioritize this one on security grounds rather than complexity alone. Archive extraction is a classic place for path traversal mistakes, and here the safety check exists twice, once per format. If someone adds a third format or changes one branch, the two can drift apart. The file has 4 total commits, with a bug-fix rate of 50% and no bug-linked commits or reverts; with so few commits, I would not over-read that percentage. I would extract one shared helper that computes the destination path and performs the containment check, then call it from both branches. That removes the duplication and shrinks the nesting without changing behavior.

### `execute` — init.rs

<FunctionCard fn='execute' file='rye/src/cli/init.rs' risk='15.01' band='critical' cc='45' nd='3' fo='27' touches='0' />

This is the highest-CC function in the list at 45, and its nesting depth is only 3. That combination tells a different story from `sync`: it is not deeply nested, it is wide. Fan-out of 27 means it reaches 27 distinct callees, and the excerpt shows why. It handles project initialization end to end: resolving the directory, choosing the Python version from several sources, reconciling the minimum version with the pin, slugifying a project name, picking a license and rendering a template, and importing metadata from other tools. It hasn't been changed in 178 days, the most recent of the five.

The file history shows 2 total commits, a bug-fix rate of 50%, no bug-linked commits, and a pull-request review comment density of 21.0, the highest in this set. With only two commits, the percentage means little, but heavy review discussion on a small history suggests this code drew attention. Because the nesting is shallow, extract-method is straightforward here: pull out version resolution, license file creation and metadata import as separate functions, each taking the parsed arguments it needs. I would start with version resolution, since it branches across several sources and carries the most decision logic.

### `perform_install` — rye.rs

<FunctionCard fn='perform_install' file='rye/src/cli/rye.rs' risk='14.17' band='critical' cc='30' nd='3' fo='18' touches='0' />

`perform_install` has CC 30, nesting depth 3 and fan-out 18, and hasn't been changed in 362 days. It is the installer for rye itself. The excerpt shows a long run of console output interleaved with environment variable fallbacks for the toolchain path and version, Windows symlink checks, and mode-dependent messaging. Much of that is presentation mixed into decision logic.

The file has 1 bug-linked commit out of 5 total and a bug-fix rate of 20%, with no reverts. That is thin evidence, so I would frame this as debt. An installer also runs rarely and is hard to test end to end, which is exactly why a year of silence is worth noticing. I would separate gathering inputs (arguments plus environment fallbacks) from printing the welcome and details text, and from the actual installation steps. The first part becomes a pure function that returns a configuration value and is easy to unit test.

**What I would do with this list**

The two structural shapes here call for different fixes. `sync`, `finalize_lockfile` and `unpack_archive` are deeply nested (depth 5 to 6), so flattening with early returns and extracted decision functions pays off most. `execute` and `perform_install` are wide rather than deep, with fan-out of 27 and 18, so extract-method along responsibility lines is the better tool. Since none of these are changing right now, there is a cheap window to add characterization tests and refactor before the next development push lands on top of them.
