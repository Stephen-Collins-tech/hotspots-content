`Run` in pkg/action/uninstall.go has not been changed in 94 days, yet it carries a cyclomatic complexity of 95, a fan-out of 36, and an activity-weighted risk score of 18.4. Nothing is churning today, but the next developer who has to touch uninstall behavior inherits a single function with 95 independent paths. Helm's snapshot at commit e74a4c6 covers 1,614 functions, 341 of them in the critical band, and 688 sit in the debt quadrant against only 9 in fire. I would start with the debt, then watch the one fire-quadrant function in the top five, `RunWithContext`, which is the live regression risk.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

The pattern counts tell the same story from another angle. Exit-heavy and god-function patterns lead, which fits an action layer where each CLI verb (install, uninstall, render) funnels through one large orchestrating function with many early returns. Go's explicit error handling inflates both numbers: every `if err != nil { return ... }` is a branch and an exit path, so some of this complexity is the language's idiom rather than tangled logic. It still has to be tested, one path at a time.

### `Run` — uninstall.go

<FunctionCard fn='Run' file='pkg/action/uninstall.go' risk='18.4' band='debt' cc='95' nd='6' fo='36' touches='0' />

This is the top-ranked function and a debt-quadrant one: zero touches in the last year and 94 days since last change. The risk here is blast radius, not churn. From the source excerpt I can see it checks cluster reachability, builds a waiter (with a type assertion for an options-capable client), then branches into a dry-run path that reads release content, splits and sorts manifests, builds resources, verifies ownership before delete, and logs warnings for unowned and unverifiable resources. That dry-run block alone is nested several levels deep before the real uninstall logic begins.

<MetricBar label='Cyclomatic Complexity' value='95' threshold='10' max='110' />

A cyclomatic complexity of 95 means 95 independent paths and, in principle, 95 test cases. A nesting depth of 6 and a fan-out of 36 compound that: the function is coupled to many collaborators, so a change in any of them can alter its behavior. The file's history adds mild context: 1 bug-linked commit out of 14 total, a bug-fix rate of about 29%, no reverts. That is not alarming, and it does not prove this function is defective. It does mean the file has had fixes before, and this function holds most of the file's logic.

My recommendation: extract the dry-run ownership reporting into its own function. It is a self-contained block (verify ownership, then log three categories of resource), and removing it would cut both nesting depth and path count substantially without touching the real delete path. Do it before the next feature lands in uninstall, not during.

### `renderResources` — action.go

<FunctionCard fn='renderResources' file='pkg/action/action.go' risk='18.05' band='debt' cc='104' nd='6' fo='29' touches='0' />

This has the highest cyclomatic complexity in the top five at 104, 0 touches in the last year, and 59 days since its last change. It checks chart and cluster Kubernetes version compatibility, chooses between a remote-connected template engine and a local one, extracts NOTES.txt from the rendered files, and then handles post-rendering with several strategies, including separating hooks from manifests. Its signature takes 13 parameters, four of them booleans, which is a signal in itself: callers have to get a long positional list right, and each flag likely multiplies the paths inside.

The historical signals are sharper here than for `Run`. The file's bug-fix rate is about 58% across 12 commits, with a pull-request review comment density of 7 and 1 distinct author in the last 90 days. A high bug-fix share on a complex file is a reason to rank it higher for review, though it describes the file, not this function specifically.

My recommendation: split along the seams the code already has. Version checking, engine selection and rendering, notes extraction, and post-render handling are four separable stages. Replace the boolean parameters with an options struct so the stages can be tested without a 13-argument call.

### `RunWithContext` — install.go

<FunctionCard fn='RunWithContext' file='pkg/action/install.go' risk='17.1' band='fire' cc='78' nd='3' fo='45' touches='1' />

This is the one fire-quadrant function in the top five, and it is why I would not file all of this under backlog. It was last changed 3 days ago, it has 1 touch in the last year, and 3 distinct authors have been in the file in the last 90 days. A complex function that several people are modifying at once is where regressions come from.

Nesting depth is only 3, so the difficulty is breadth, not depth: a cyclomatic complexity of 78 and a fan-out of 45, the highest in the top five. From the excerpt, it type-switches on the chart value, checks cluster reachability, validates dry-run and secret-hiding combinations, resolves the release name, processes dependencies, installs CRDs, swaps in mock capabilities for client-only mode, and continues into rendering and release creation. Each of those stages has its own error return, wrapped and logged.

The file history leans toward review priority: 2 bug-linked commits out of 9 total, a bug-fix rate of about 78%, and no reverts. Again, this is file-level context, not proof of a current defect, but a file where most recent commits are fixes and several authors are active is where I would put extra review attention.

My recommendation: extract the client-only setup (mock capabilities, fake kube client, in-memory release storage) into a named function. It is a cohesive block that is easy to isolate and easy to test, and it removes one fork from the main flow.

**`Create` and `Query` — sql.go**

<FunctionCard fn='Create' file='internal/storage/driver/sql.go' risk='17.07' band='debt' cc='23' nd='2' fo='30' touches='0' />

<FunctionCard fn='Query' file='internal/storage/driver/sql.go' risk='16.55' band='debt' cc='23' nd='2' fo='16' touches='0' />

I am grouping these because they share a file, a quadrant, and a profile: both have a cyclomatic complexity of 23, a nesting depth of 2, no touches in the last year, and 38 days since last change. They are much smaller than the action-package functions, and the file has only 1 commit in its history with a bug-fix rate of 0%, so there is no historical defect signal at all. I would frame these as maintainability debt, not risk.

`Create` encodes a release, opens a transaction, builds an insert with nine columns, and on failure runs a follow-up select to distinguish a duplicate key from another error, then inserts filtered system labels. Its fan-out of 30 is the larger concern: it mixes query building, transaction handling, logging, and label storage in one body. One detail worth a test is the failure path, where a build error on the follow-up select returns the original error rather than the build error. That looks deliberate, but with branches this dense it deserves an explicit test.

`Query` validates label names against a known set, sorts keys, builds a filtered select, decodes each record, and fetches custom labels per record. A cyclomatic complexity of 23 with a fan-out of 16 is moderate by this repository's standards. I would extract the per-record decode-and-label step; it also hides a subtle behavior (a failed decode skips the record, but a failed label fetch aborts the whole query) that is easy to lose in a long function.

For both, the cheap win is separating query construction from execution so the SQL building can be tested without a database connection.

**What I would do first**

The fire-quadrant function, `RunWithContext`, is the only one in the top five where complexity and current activity overlap, so it gets review attention now. The two largest debt functions, `Run` and `renderResources`, get refactored before the next feature work touches them. The SQL driver functions can wait, but they are cheap to improve while someone is already in that file.
