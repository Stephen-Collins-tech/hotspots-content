## Large Repo Analysis

wezterm is a large repository. To stay within memory constraints, this analysis used **hybrid touch mode**: structural complexity — CC, ND, FO — is measured precisely for every function. Git activity is tracked at the function level (via `git log -L`) only for files with 5 or more commits in the touch window (365 days by default); other files use a file-level approximation. Rankings therefore surface functions that are both structurally complex and in the most actively-changing parts of the codebase. Dormant code with high structural complexity will rank lower than it would under a full per-function analysis — to surface it, run `hotspots analyze . --per-function-touches` on a machine with sufficient memory.

### `render_to` — terminfo.rs

<FunctionCard fn='render_to' file='termwiz/src/render/terminfo.rs' risk='19.38' band='fire' cc='121' nd='8' fo='14' touches='2' />

<MetricBar label='Cyclomatic Complexity' value='121' threshold='10' max='130' />

This is the top-ranked function, and I would put it first. From the excerpt, it takes a slice of `Change` values and writes terminal output, with a large match over variants such as `ClearScreen`, `ClearLine`, and `ClearToEndOfLine`. An `#[allow(clippy::cyclomatic_complexity, clippy::cognitive_complexity)]` attribute sits on the function, so the source already acknowledges the complexity. A cyclomatic complexity of 121 means 121 independent paths, each a potential test case, and a nesting depth of 8 is a strong refactoring signal on its own.

Several arms repeat the same preamble: build default attributes with a background color, compare against the current attributes, flush pending attributes, then clear the pending state. That repetition suggests an extractable helper. The file has two commits in total, no bug-linked commits, no reverts, a bug-fix rate of 0%, and one distinct author in the last 90 days, so the history gives me no reason to read this as a defect cluster. I would extract the per-variant arms into methods, starting with the repeated attribute-reset sequence, and keep the outer match as a thin dispatcher. It was touched twice in the last year and last changed 22 days ago, so the context is fresh and now is a reasonable time to do it.

### `run_ls_fonts` — main.rs

<FunctionCard fn='run_ls_fonts' file='wezterm-gui/src/main.rs' risk='19.12' band='fire' cc='39' nd='8' fo='34' touches='3' />

This function implements a font-listing subcommand and lives in the GUI crate's `main.rs`. The excerpt shows a long sequence of jobs: checking configuration errors, building a font configuration and render metrics, resolving text from either a text argument or a comma-separated list of hex codepoints, then shaping clusters and resolving fallback fonts. A fan-out of 34 means it directly calls 34 distinct functions, so a change to any of those collaborators can surface here. Cyclomatic complexity is 39, but the nesting depth of 8 is the more striking number.

It was touched three times in the last year and last changed 37 days ago. The file has three commits in total, a bug-fix rate of 0%, and no reverts, so I read this as a maintainability concern rather than a stability one. Input parsing (text versus codepoints) and the shaping-and-reporting loop are natural seams. I would move the codepoint parsing into a function that returns the text, and give the per-cluster shaping and output their own function, which should cut the nesting depth substantially.

### `do_shape` — harfbuzz.rs

<FunctionCard fn='do_shape' file='wezterm-font/src/shaper/harfbuzz.rs' risk='18.14' band='debt' cc='36' nd='7' fo='35' touches='1' />

Unlike the two above, this one is in the 'debt' quadrant, not 'fire': it was touched once in the last year and hasn't changed in 91 days. I would frame it as structural debt with a high blast radius when it is next touched, not as live churn. From the name and the excerpt, it runs text through HarfBuzz shaping with a fallback-font loop, skipping fonts whose presentation doesn't match the wanted one and recomputing font metrics when size or DPI changes. A fan-out of 35 and a nesting depth of 7 give it broad coupling.

Comments in the excerpt reference two GitHub issues about script inference for Hangul, which tells me some of the branching exists for specific shaping edge cases. I would pin those cases with tests before any refactor. The file has one commit in total and no distinct authors in the last 90 days. I would separate the metrics-recompute block (guarded by the size-and-DPI comparison) from the fallback-iteration loop so each can be tested in isolation. Because the function is quiet right now, this refactor is cheapest before the next feature push.

### `render_screen_line` — screen_line.rs

<FunctionCard fn='render_screen_line' file='wezterm-gui/src/termwindow/render/screen_line.rs' risk='17.82' band='fire' cc='58' nd='5' fo='39' touches='3' />

According to its own doc comment, this function renders one line of the terminal screen into a vertex buffer, and its fan-out of 39 is the highest in my top five. The excerpt shows an early return for double-height bottom lines, scale calculations for double-width and double-height lines, cursor-position logic, and handling for text being composed through dead keys. Cyclomatic complexity is 58 with a nesting depth of 5, so the branching is wide rather than deep.

It is the only one of the five with a non-zero bug-fix rate: 67% across its three commits in the file, with two distinct authors in the last 90 days. The sample is small and none of the commits are tagged as bug-linked or reverted, so I would not read it as proof of a defect. Still, it is the strongest historical signal in my top five, and it comes with three touches in the last year and a last change 19 days ago. That combination gives it the strongest review priority after `render_to`. I would extract the cursor and composition calculations into a helper that returns a small struct, which removes a chunk of the early-function branching without touching the rendering loop.

### `key` — window.rs

<FunctionCard fn='key' file='window/src/os/windows/window.rs' risk='17.57' band='fire' cc='52' nd='6' fo='24' touches='2' />

This `unsafe fn` in the Windows backend handles keyboard messages: the excerpt matches on messages such as `WM_KEYDOWN`, `WM_CHAR`, and `WM_DEADCHAR`, handles IME activity, reads the keyboard state, and builds up a modifiers value. Because it is unsafe and calls into the Win32 API, the complexity numbers likely understate the risk: a cyclomatic complexity of 52 tells me about branching, not about whether every raw call is sound. A comment in the excerpt explains that a `RefCell` borrow is deliberately dropped before calling `translate_message` to avoid a borrow conflict, exactly the sort of subtle ordering constraint that makes a function like this fragile to edit.

Pull-request review comment density on the file is 6.5, the highest of my five, so reviewers have clearly spent attention here. The file has two commits, a bug-fix rate of 0%, and one distinct author in the last 90 days. It was touched twice in the last year and last changed 38 days ago. I would split out the modifier-gathering block (the long run of key-state checks that set modifier flags), since it is pure with respect to the message handling, and document the borrow-release ordering with a test or an explicit comment at the call site.

**What I would do with this list**

The input path keeps surfacing beyond the top five, in keyboard handling across platforms and layers. If I were planning refactoring time, I would treat input handling as one theme and rendering as another, rather than fixing five functions in isolation.
