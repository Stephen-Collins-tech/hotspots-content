### `ATRewriteTable` — tablecmds.c

<FunctionCard fn='ATRewriteTable' file='src/backend/commands/tablecmds.c' risk='131.27' band='fire' cc='41' nd='4' fo='60' touches='1' />

From the name and the excerpt, this is the routine that rewrites a table's contents, opening the old relation and optionally a new heap, and preparing bulk-insert state and executor state along the way. The excerpt also shows it building expression states for constraints and partition-check quals. A cyclomatic complexity of 41 is high, but the number that stands out is fan-out: 60 distinct callees is the highest of the five, so the function touches a very wide slice of the backend. That is the main blast-radius concern for any change here.

The visible structure suggests several distinct phases in one body: relation setup, insert-state setup, executor and constraint preparation, and presumably the row-processing loop. I would start here and extract the setup phases into named helpers so the core rewrite loop can be reviewed on its own. With a nesting depth of only 4, extraction should be mechanical rather than a restructuring exercise.

### `ATExecChangeOwner` — tablecmds.c

<FunctionCard fn='ATExecChangeOwner' file='src/backend/commands/tablecmds.c' risk='130.99' band='fire' cc='38' nd='4' fo='49' touches='1' />

This handles ALTER ... OWNER. The excerpt shows a switch over relation kinds that decides whether ownership can change: tables, views, materialized views and foreign tables are allowed, indexes are handled with a warning, partitioned indexes error out unless the call is recursive, and sequences have their own checks. Much of the complexity of 38 appears to come from that per-kind policy, with a fan-out of 49 on top.

The relkind policy is the natural seam. A small function that answers 'can this relation kind change owner, and how' would pull the switch and its messages out of the main flow and leave the ownership update easier to follow. Because the function is exit-heavy, each early-out path is a distinct test case, so I would write one test per relkind branch before moving anything.

### `MergeConstraintsIntoExisting` — tablecmds.c

<FunctionCard fn='MergeConstraintsIntoExisting' file='src/backend/commands/tablecmds.c' risk='130.79' band='fire' cc='26' nd='5' fo='28' touches='1' />

This is the only function in the set flagged as deeply nested, with a nesting depth of 5, the deepest of the five. The excerpt shows an outer scan over the parent's constraints with an inner scan over the child's, matching CHECK constraints by name and NOT NULL constraints by attribute number. A nested catalog-scan loop with different matching rules per constraint type is where depth and branching pile up.

I would extract the inner child-matching logic into a function that returns the matching child constraint, if any. That should reduce the nesting and lets the CHECK and NOT NULL matching rules be tested separately. The complexity of 26 is the second-lowest of the five, behind `RemoveInheritance` at 23, and the fan-out of 28 is the lowest, so this is probably among the cheaper ones to improve.

### `ATExecCmd` — tablecmds.c

<FunctionCard fn='ATExecCmd' file='src/backend/commands/tablecmds.c' risk='130.19' band='fire' cc='76' nd='2' fo='54' touches='1' />

Here the cyclomatic complexity is the highest in the set at 76, yet the nesting depth is only 2. The excerpt explains why: it is a large switch over ALTER TABLE subcommand types, with most cases dispatching to a dedicated routine such as the add-column, drop-column, set-statistics and add-index handlers, then breaking. That is a dispatch table written as a switch, which is easier to reason about than the same complexity expressed through nested conditionals.

Still, 76 paths with a fan-out of 54 means every new ALTER TABLE subcommand adds another case here, and every subcommand passes through this one function. I would not rush to split it. A first step would be to confirm that each case stays a thin call, and to move the cases that do more than dispatch, such as those that transform the command first, into their own handlers so the switch stays uniform.

### `RemoveInheritance` — tablecmds.c

<FunctionCard fn='RemoveInheritance' file='src/backend/commands/tablecmds.c' risk='130.0' band='fire' cc='23' nd='4' fo='35' touches='1' />

This detaches a child relation from a parent. The excerpt shows it deleting the inheritance record, erroring differently for partitions and for ordinary inheritance when the link is missing, then scanning the child's attributes to decrement inheritance counts, with further handling for check and not-null constraints afterwards. Its complexity of 23 is the lowest of the five, but it carries a fan-out of 35 and a nesting depth of 4.

It appears to handle three separate catalog concerns in sequence: the inheritance row, the attributes and the constraints. Each is a candidate for its own helper, which would leave the top-level function reading as three named steps. The partition-versus-inheritance error handling is a small decomposition on its own.

## What the neighbors tell me

The other functions in the same file that the analysis surfaces as context are low in structural complexity, with complexity values between 3 and 6. Their scores are likely elevated by the same recent activity (1 touch, 12 days since last change) seen across the file. They are in the watch quadrant, not refactoring priorities. The neighbor-risk flag on the top five is the more useful signal: changes in these functions may need coordinated edits elsewhere, and every function listed shows the same 12 days since last change.

## Where I would put effort

1. Start with `ATRewriteTable`: highest fan-out (60) and highest score.
2. Add per-branch tests to `ATExecChangeOwner` before touching its relkind switch.
3. Flatten the nested scans in `MergeConstraintsIntoExisting`.
4. Leave `ATExecCmd` as a switch, but keep each case a thin call.
5. Split `RemoveInheritance` into its three catalog steps.
