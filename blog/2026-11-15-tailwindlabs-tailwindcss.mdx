### `collapseGroup` — canonicalize-candidates.ts

<FunctionCard fn='collapseGroup' file='packages/tailwindcss/src/canonicalize-candidates.ts' risk='3.33' band='active' cc='49' nd='7' fo='76' touches='33' />

I would start with `collapseGroup` because it has the highest activity-weighted risk score in the repository at 3.33, and it combines a cyclomatic complexity of 49 with a nesting depth of 7 and a fan-out of 76. It is a nested function inside `collapseCandidates`, and from the source excerpt it takes a list of candidate class names, looks up their CSS properties through several design-system storage lookups, and tries to collapse them into shorter equivalent utilities.

The excerpt shows a hard-coded special case for line-height and font-size combinations, with several levels of loops over seen values and conditional branches on whether a value is a valid spacing multiplier. That is where much of the nesting depth comes from. A fan-out of 76 means this one function directly calls 76 distinct functions, so a change to any of them can alter its behavior.

<MetricBar label='Fan-out' value='76' threshold='15' max='90' />

The file's history is worth noting: 33 touches in the last year, 0 days since last change, and a bug-fix rate of 27% across 33 commits. There are no commits explicitly linked to bugs and no reverts, so I read this as a file under steady iteration, not one with a defect record. The review comment density of 3.6 suggests changes here get scrutiny.

My recommendation: extract the line-height/font-size pre-computation block into its own named function. It is self-contained in the excerpt, it is explicitly labelled as an optimization, and pulling it out would remove a large share of both the nesting and the branch count without touching the main collapsing logic.

### `modernizeArbitraryValuesVariant` — canonicalize-candidates.ts

<FunctionCard fn='modernizeArbitraryValuesVariant' file='packages/tailwindcss/src/canonicalize-candidates.ts' risk='3.26' band='active' cc='123' nd='6' fo='22' touches='33' />

This function has the highest cyclomatic complexity in the top five by a wide margin: 123, against a rule of thumb where 30 is already high and 100 is extreme.

<MetricBar label='Cyclomatic Complexity' value='123' threshold='30' max='130' />

From the excerpt, it walks a variant tree and rewrites arbitrary variants into their modern equivalents. The visible pattern is a long sequence of independent `if` blocks, each matching a specific selector shape and replacing it. Examples in the excerpt include rewriting `[&>*]` to `*`, `[&_*]` to `**`, and `[&:has(…)]` to `has-[…]`. Each rule is guarded by conditions on the parent being null and on the exact node kinds and values at specific positions in the parsed selector.

That shape matters. A cyclomatic complexity of 123 here is mostly breadth, not depth: many sibling rules, with a nesting depth of 6 and a modest fan-out of 22. Breadth is the easier problem to fix. Each rewrite rule is independent, so each one is a candidate for its own small function or an entry in a table of rules, and each needs its own test case regardless of how the code is organized.

My recommendation: split the rewrites into a list of named rule functions, each taking a variant and returning a replacement or nothing. The main loop then iterates the list. That would bring the complexity of the walker itself down dramatically and make it possible to test each rewrite in isolation.

### `collapseCandidates` — canonicalize-candidates.ts

<FunctionCard fn='collapseCandidates' file='packages/tailwindcss/src/canonicalize-candidates.ts' risk='3.25' band='active' cc='15' nd='7' fo='89' touches='33' />

`collapseCandidates` is the outer function that contains `collapseGroup`, and its own numbers are different in character: cyclomatic complexity of only 15, but a nesting depth of 7 and a fan-out of 89, the highest in the top five. The outer logic, per the excerpt, groups candidates by their variants and important flag, then calls `collapseGroup` on each group and reassembles the results.

Because `collapseGroup` is defined inside this function, its nesting and fan-out are plausibly counted toward the outer function as well. I cannot confirm that from the data alone, but the near-identical nesting depth and the very high fan-out suggest it. The practical consequence is that the two entries are partly the same risk: refactoring `collapseGroup` out into a module-level function should reduce the numbers on both.

My recommendation: move `collapseGroup` to the module level, passing the design system and signature options explicitly. That is a mechanical change, and it makes the dependencies of the inner function visible instead of implicit through closure.

### `arbitraryUtilities` — canonicalize-candidates.ts

<FunctionCard fn='arbitraryUtilities' file='packages/tailwindcss/src/canonicalize-candidates.ts' risk='3.16' band='active' cc='16' nd='6' fo='17' touches='33' />

`arbitraryUtilities` is the smallest of the four by complexity, with cyclomatic complexity 16, nesting depth 6, and fan-out 17. From the excerpt, it takes an arbitrary property or arbitrary value candidate, computes its signature, and tries to find an existing utility with the same signature to replace it. It contains an inner generator, `tryReplacements`, that yields candidate replacements, including handling for multiple matches, a preference for positive over negative values, and a retry with the modifier stripped.

It is the one in this file I would worry least about structurally, but it is still in the critical band because it is changing along with the rest of the file. The generator is a sensible seam: it already separates finding replacements from validating them. In TypeScript, generator control flow and the type narrowing on candidate kinds add paths that cyclomatic complexity understates.

My recommendation: lift `tryReplacements` out to module level, as with `collapseGroup`, and add tests that cover the branch where several non-negative replacements exist and the function bails.

### `resolveValueFunction` — utilities.ts

<FunctionCard fn='resolveValueFunction' file='packages/tailwindcss/src/utilities.ts' risk='3.15' band='active' cc='47' nd='7' fo='18' touches='34' />

The fifth hotspot is in a different file, `packages/tailwindcss/src/utilities.ts`, and it has a different history. Cyclomatic complexity is 47, nesting depth 7, fan-out 18, with 34 touches in the last year and 0 days since last change. Unlike the file above, this one has 3 bug-linked commits and a bug-fix rate of 9% across 34 commits, with 2 distinct authors in the last 90 days and a review comment density of 4.0. That is a modest historical signal, and it does not prove this function is defective, but together with the complexity it makes this a stronger review candidate than its raw score suggests.

From the excerpt, the function resolves the `--value(…)`, `--modifier(…)`, and `--default(…)` forms used in custom utilities. It loops over the function's arguments and branches on whether the value is a literal in quotes, a theme key (with and without a wildcard suffix, and with nested keys), or a bare value of an allowed data type. That is a chain of mutually exclusive cases, each with its own nested resolution logic.

<MetricBar label='Cyclomatic Complexity' value='47' threshold='30' max='60' />

My recommendation: split each resolution kind (literal, theme key, nested theme key, bare value) into its own helper that returns a result or nothing, and keep the loop as a dispatcher. Each case then gets a focused test, which matters most for the theme-key branches where the excerpt shows several levels of nesting.

## Where to start

I would start with `canonicalize-candidates.ts` as a whole. Moving `collapseGroup` and `tryReplacements` to module level, extracting the line-height/font-size block, and turning the rewrite rules in `modernizeArbitraryValuesVariant` into a list of small named functions would address four of the five hotspots in one coordinated pass. Because all four functions share the same 33 touches and the same 4 recent authors, that pass is easier to coordinate than five separate efforts. Then I would turn to `resolveValueFunction`, where the added history of bug-linked commits supports reviewing it soon.
