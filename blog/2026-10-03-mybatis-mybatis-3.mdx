### `equals` — ArrayUtil.java

<FunctionCard fn='equals' file='src/main/java/org/apache/ibatis/reflection/ArrayUtil.java' risk='15.87' band='critical' cc='9' nd='7' fo='23' touches='0' />

I would start with `equals`, which has the highest activity-weighted risk score in the repository at 15.87, with a nesting depth of 7 and a fan-out of 23. From the excerpt, it compares two objects, handling nulls, class mismatches, and non-array objects first, then branches on the array's component type: one path for long, int, short, char, byte, boolean, float and double, and a fallback for object arrays. Each branch is a one-line call into the matching Arrays comparison, so no single branch is hard to read. The risk lives in the ladder as a whole. A cyclomatic complexity of 9, 7 levels of nesting and 23 distinct calls force a reader to hold a long chain of mutually exclusive checks in mind, and the exit-heavy shape (many early returns) means each path needs its own test case.

The function has not been touched in 434 days, so I frame this as maintainability debt, not an active regression risk. My recommendation is a data-driven dispatch: map each primitive component type to a small comparison strategy, so the ladder collapses to a lookup plus one fallback. That would cut both the nesting and the number of branches a reviewer has to verify.

**`hashCode` and `toString` — ArrayUtil.java**

These two share an identical profile: an activity-weighted risk score of 15.48, a cyclomatic complexity of 7, a nesting depth of 7, and a fan-out of 21. The excerpts show the same structure as `equals`: a null check, a non-array shortcut, then the same component-type ladder calling the matching Arrays method. I treat the three as one finding, because the duplication is the real issue. The same eight-way type dispatch is written out three times in one 100-line class, so any fix, such as adding a new array type or changing how arrays are handled, has to be applied consistently across all three, and nothing in the structure enforces that.

This is a good refactoring candidate precisely because it is small and stable. Neither function has been changed in 434 days, so there is no in-flight work to collide with. I would extract a single component-type resolver, have all three methods share it, then confirm behavior with a parameterized test over each primitive type plus null and mismatched-class cases. The file would end up with one place where the dispatch lives.

### `execute` — MapperMethod.java

<FunctionCard fn='execute' file='src/main/java/org/apache/ibatis/binding/MapperMethod.java' risk='15.31' band='critical' cc='10' nd='6' fo='26' touches='0' />

`execute` in MapperMethod.java has an activity-weighted risk score of 15.31, a cyclomatic complexity of 10, a nesting depth of 6, and a fan-out of 26. Based on the excerpt, it switches on the command type (insert, update, delete, select, flush) and delegates. The select case carries its own chain of checks on the method's return shape: void with a result handler, many results, a map, a cursor, or a single result with optional wrapping. A final guard rejects a null result for a primitive return type.

The fan-out of 26 is the number I would focus on. In a Java framework like this, the effective coupling is wider than static analysis shows, since this method sits between mapper interfaces and the SqlSession and is reached through dynamic proxies. Anything that changes the contract of a mapper method lands here. The select branch is the natural extraction point: pulling it into its own method would reduce the switch to a flat dispatch and give the return-shape logic its own focused tests. The function is unchanged for 434 days, so I would do this before the next feature that touches mapper return types, not after.

### `popConnection` — PooledDataSource.java

<FunctionCard fn='popConnection' file='src/main/java/org/apache/ibatis/datasource/pooled/PooledDataSource.java' risk='15.24' band='critical' cc='11' nd='7' fo='42' touches='0' />

<MetricBar label='Fan-out' value='42' threshold='15' max='45' />

`popConnection` has the highest fan-out in my top five at 42, alongside a cyclomatic complexity of 11 and a nesting depth of 7. It is the only function here flagged as a god function, a long function, and stale complex, and the excerpt shows why. Inside a retry loop under a lock, it takes an idle connection, creates a new one, claims an overdue connection (with a rollback attempt and statistics updates), waits on a condition, and finally validates the connection it ended up with. That is several distinct responsibilities in one method, with pool statistics bookkeeping and debug logging threaded through each branch.

This is the function where I would be most cautious about blast radius, because connection pooling is concurrency-sensitive and the method holds a lock while it runs. I would extract methods along the existing comments: one per acquisition strategy (idle, create, claim overdue, wait), with the statistics updates grouped behind a small helper. I would do that only after writing strong tests around the overdue-claim and interrupted-wait paths, since those are the least obvious to verify. With 434 days since last change, there is room to do it deliberately.

**What I would do in order**

Given one afternoon, I would do the ArrayUtil consolidation: it is low-risk, self-contained, and removes three of the five hotspots in one change. `popConnection` and `execute` are higher-value but need more care, so I would schedule them after the test coverage work.
