qaSection:
  - question: "What is a god function and why does it matter in gorm?"
    answer: "A god function is one that calls into an unusually large number of distinct functions, accumulates many execution paths, and effectively owns too much behaviour to be reasoned about or tested in isolation. Fan-out — the count of distinct functions directly called — is the clearest structural signal: a fan-out of 15 or more means a change to the function can ripple into a wide range of downstream behaviours simultaneously. In gorm, `setupValuerAndSetter` calls into 84 distinct functions and has a cyclomatic complexity of 126, making it the most extreme example; `CreateInBatches` calls 24 distinct functions while actively receiving commits. God functions are hard to unit-test because exercising one path may silently trigger side effects in many callees, and they concentrate regression risk — a subtle mistake in one branch can break unrelated features that happen to share the same function."
  - question: "How do I reduce cyclomatic complexity in Go?"
    answer: "The most effective technique is extract-method refactoring: identify cohesive groups of branches that handle a single sub-concern, give them a descriptive name, and move them into their own functions. A cyclomatic complexity above 15 warrants splitting; above 30 it warrants immediate attention because each independent path is both a potential bug surface and a required test case. A concrete first step for `setupValuerAndSetter` — which has a cyclomatic complexity of 126 — would be to identify the top-level type-dispatch switch or if-else chain and extract each case arm into a named helper; that single change could reduce the measured complexity by a third or more and make the remaining function shallow enough to reason about. In Go specifically, table-driven dispatch maps can replace long chains of type assertions, further flattening the control structure."

### `CreateInBatches` — finisher_api.go

This is gorm's live regression risk. `CreateInBatches` sits in the **fire** quadrant — it was touched 1 time in the last 30 days and carries an activity-weighted risk score of 11.12. That combination means structural complexity and active change are happening simultaneously. With a fan-out of 24 distinct called functions, this is the structural centre of gravity for batch insert operations: a single misplaced change here can silently break interactions with hooks, callbacks, association handlers, and transaction wrappers all at once. The file-level signals add important context — `finisher_api.go` shows a `bug_fix_commit_ratio` of 0.50 across 6 total commits and a `pr_review_comment_density` of 9.0, meaning past changes here have drawn significant review scrutiny and roughly half the file's commits have been fixes. None of that proves the current function is defective, but it does reinforce that this file has historically required careful attention.

The concrete recommendation: before the next change lands, ensure integration tests exercise each of the 24 call targets that `CreateInBatches` depends on. Given the fan-out breadth, consider extracting the batch-boundary logic and the hook-dispatch logic into separately testable helpers — this would reduce the blast radius of any single future edit and make the remaining core easier to reason about under code review.

### `AlterColumn` — migrator/migrator.go

Also in the **fire** quadrant, `AlterColumn` in `migrator/migrator.go` scores an activity-weighted risk of 8.44 and was touched 1 time in the last 30 days. Its structural metrics are modest by themselves — cyclomatic complexity of 3, nesting depth of 2, fan-out of 6 — but the file-level historical signals elevate concern significantly. `migrator/migrator.go` has a `bug_fix_commit_ratio` of 0.857 across 7 commits, the highest ratio in this dataset, and a `pr_review_comment_density` of 13.25. That ratio means the overwhelming majority of this file's commit history has been corrective in nature, and reviews have consistently generated discussion. Three distinct authors have touched the file in the last 90 days, which increases the coordination surface. Schema migration is an inherently high-stakes operation — a defect here can corrupt table structure in production — so the combination of active change, broad ownership, and a historically correction-heavy commit record warrants explicit review gates. Add a migration-specific test fixture that exercises `AlterColumn` against a representative schema before any further changes are merged.

### `setupValuerAndSetter` — schema/field.go

`setupValuerAndSetter` is the most structurally complex function in this analysis and the clearest example of accumulated debt. It hasn't been touched in **170 days** — zero commits in the last 30 days, zero authors active in the last 90 days — but when the next development push arrives, it will be carrying a cyclomatic complexity of 126, a max nesting depth of 9, and a fan-out of 84. Those numbers place it firmly in god-function territory: 84 distinct callees means that reasoning about a change here requires simultaneously tracking dependencies across a substantial fraction of the schema subsystem. The deeply nested control flow (ND 9) and complex branching patterns mean that even a small modification requires tracing paths through many conditional layers, and the exit-heavy structure multiplies the number of paths that need test coverage. The `pr_review_comment_density` of 17.0 — the highest in this dataset — suggests that historically, reviewers have found this function difficult to evaluate quickly.

This function is overdue for a decompose-and-extract refactoring. A practical first step: identify the top-level type-dispatch branches (likely handling different field kinds) and extract each into a named helper. Getting the cyclomatic complexity below 30 would meaningfully reduce the blast radius before this function is touched again.

### `BuildCondition` — statement.go

`BuildCondition` in `statement.go` shares the debt quadrant with `setupValuerAndSetter` and has been dormant for **241 days** — the longest gap in this dataset. With a cyclomatic complexity of 27, a nesting depth of 10, and a fan-out of 22, it exhibits both deeply nested control structures and broad coupling. The `stale_complex` pattern flag is particularly relevant here: this is a function that has grown complex over time and then gone quiet, meaning the team that last understood it may no longer be active on it. The `author_count_90d` of 0 confirms no one has been in this code recently. When query-building behaviour eventually needs to change — new clause types, dialect handling, edge-case fixes — whoever opens this file will be navigating 10 levels of nesting with no recent context.

Prioritize adding characterization tests before any modification. Because `BuildCondition` is a query-construction entry point, its output can be diffed against known-good SQL strings — this gives future contributors a safety net before they refactor the deeply nested branching.
