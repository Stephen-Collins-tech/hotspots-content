### `send` — response.js

<FunctionCard fn='send' file='lib/response.js' risk='1.49' band='active' cc='26' nd='4' fo='7' touches='10' />

<MetricBar label='Cyclomatic Complexity' value='26' threshold='10' max='30' />

`send` is the method behind `res.send(body)`. Reading the excerpt, it does several jobs in one body. It branches on the type of the payload (string, boolean, number, object, buffer view) and sets a content type to match. It decides whether to generate an ETag, works out a content length, checks request freshness to return a 304, and strips headers for 204 and 304 responses. A CC of 26 is consistent with that: each of those decisions adds paths, and each path is a test case.

The nesting depth of 4 and fan-out of 7 are moderate on their own. The CC is the outlier, and the combination matters here. The same function handles several header decisions that interact. For example, the Content-Length logic checks for a Transfer-Encoding header, and the 204/304 branch later removes both headers. I would want a test that pins each interaction rather than relying on the happy path.

The file-level history gives context without suggesting a defect. There are 10 commits in the file, 4 distinct authors in the last 90 days, a bug-fix rate of 40%, and zero bug-linked commits, reverts, or review comments. A 40% bug-fix rate across 10 commits is a reason to look closely, but those numbers describe the file, not this function specifically, and I would not read them as proof of a problem in `send`.

My recommendation is extract-method along the seams the excerpt already shows: one helper that normalizes the body and content type, one that computes length and ETag, and one that applies the 304/204 header stripping. Keeping `send` as a short orchestrator would drop its CC well below 15 and give each concern its own tests. Do this before the next feature lands in this file, since 4 authors are working in it.

### `sendfile` — response.js

<FunctionCard fn='sendfile' file='lib/response.js' risk='1.4' band='active' cc='4' nd='2' fo='9' touches='10' />

`sendfile` is a different kind of risk. Its CC is only 4 and its nesting depth is 2, so the branching is simple. What lifts it into the critical band is fan-out of 9 combined with the same activity as `send`: 10 touches in the last year and 24 days since last change.

The excerpt explains the shape. It defines a set of small inner handlers (aborted, directory, error, end, file, finish, stream), wires them to events on the file object, and uses a shared 'done' flag so the callback fires once. That is event-driven control flow, and the static complexity numbers undercount it. The real behavior depends on the order in which events arrive, and a cyclomatic count does not capture that. The finish handler defers part of its logic through `setImmediate` and checks a streaming flag, which means the correctness of the callback-once guarantee depends on timing.

The file-level signals are the same as for `send`, since both functions live in `lib/response.js`: a 40% bug-fix rate, no reverts, no bug-linked commits, 4 distinct authors in the last 90 days. I would treat that as supporting context only.

My recommendation is to leave the structure alone and invest in tests for the event ordering: abort before end, directory error, connection reset during finish, and double-fire protection. Those are the cases where the shared 'done' flag matters, and they are hard to cover by reading the code. If the handlers are ever extracted into a small state object, the 'done' and 'streaming' flags would become explicit and easier to reason about.

### `View` — view.js

<FunctionCard fn='View' file='lib/view.js' risk='0.38' band='quiet' cc='8' nd='2' fo='3' touches='1' />

`View` is the constructor for Express view objects. From the excerpt, it works out the file extension, falls back to a default engine, loads the engine module if it is not already registered, and then looks up the file path. It has two explicit error throws, one for a missing engine and one for a module that does not provide a view engine.

CC 8 with fan-out of 3 is on the modest end for the high band. It is quiet, with 1 touch in the last year and 343 days since last change, so the blast radius when it is next changed matters more than current churn. The constructor does I/O-adjacent work (a `require` of the engine and a filesystem lookup) at construction time, which makes it harder to unit test than a pure function. The natural improvement is to separate extension resolution from engine loading so each can be tested alone.

### `resolve` — view.js

<FunctionCard fn='resolve' file='lib/view.js' risk='0.33' band='quiet' cc='5' nd='1' fo='4' touches='1' />

`resolve` on the view prototype tries two candidate paths: the file itself and an index file inside a directory of the same name. It uses a stat helper to check each. With CC 5, nesting depth 1, and fan-out of 4, this is the smallest function in the list and the easiest to understand. It is in the high band with a risk score of 0.33, and it is quiet with 343 days since last change.

I would not refactor it. If anything, I would make sure both lookup branches have direct tests, since both return paths depend on the stat helper behaving as expected. It relies on a small stat helper in the same file.

## Where to start

I would start with `send`, and I would do it before any other change lands in `lib/response.js`. It has the largest complexity gap in the list, it is in an active file with 4 recent authors, and a split into three helpers is a bounded piece of work. Then add event-ordering tests around `sendfile` without restructuring it. The three quiet entries are not urgent: I would leave `View` and `resolve` until the next time `lib/view.js` needs a change, and decide separately whether the MVC example belongs in the analysis at all.
