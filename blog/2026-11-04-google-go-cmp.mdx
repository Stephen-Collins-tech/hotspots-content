Five functions in go-cmp are both structurally complex and in code that is changing now, and every one of them shows zero days since last change. The top-ranked one, `compareAny` in cmp/compare.go, has an activity-weighted risk score of 1.98, a cyclomatic complexity of 42 and a fan-out of 40, so it is where I would start reading. go-cmp is a Go library for comparing values with reflection, and in the commit I analyzed (5deca1c) 27 of its 258 functions land in the critical band and 112 sit in active code. If I were shipping a change to this repo this week, I would read these five functions before touching anything else.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `compareAny` — compare.go

<FunctionCard fn='compareAny' file='cmp/compare.go' risk='1.98' band='critical' cc='42' nd='2' fo='40' touches='2' />

`compareAny` is the recursive core of the library. From the source excerpt, it pushes a step onto the current path, notifies reporters, checks for slice cycles, tries user options, tries an Equal method, and then falls through to a large switch over reflect kinds that dispatches to `compareStruct`, `compareSlice`, `compareMap`, `comparePtr` and `compareInterface`. The cyclomatic complexity of 42 comes mostly from that kind switch, so the nesting depth of 2 is a fair reflection of its shape: wide and flat, not deep.

<MetricBar label='Fan-out' value='40' threshold='15' max='60' />

The fan-out of 40 is the number I would worry about most. Every kind-specific comparison, every reporter call and every path-stack operation is a direct dependency, so a change to any of them is a change that this function has to absorb. The function was touched twice in the last year and changed today. The file it lives in shows a bug-fix rate of 35% across 17 commits, no reverts, and one distinct author in the last 90 days. Those historical signals are not evidence that this function is defective, but a single-author file with this much coupling and a PR review comment density of 3.5 is one where reviewer attention is already being spent.

My recommendation: keep the three-rule ordering (options, then Equal method, then kind) as the visible spine of `compareAny`, and move the primitive-kind cases (bool, ints, uints, floats, complex, string, chan, func) into a small `compareScalar` helper. That cuts a large block of cases out of the switch without touching the recursion, and it makes the panic on an unhandled kind a single, testable default.

### `appendTypeName` — cmp/internal/value/name.go

<FunctionCard fn='appendTypeName' file='cmp/internal/value/name.go' risk='1.94' band='critical' cc='75' nd='4' fo='27' touches='2' />

This has the highest cyclomatic complexity of my top five, at 75, with a nesting depth of 4 and fan-out of 27. From the name and the excerpt, it renders a reflect type as a string: named types, then a switch over unnamed kinds for channels, funcs, structs and presumably maps, slices and pointers. It recurses into itself for element types, parameters and results, and it carries a source comment that flags a known limitation in how Go reflection handles same-named types declared inside different functions.

<MetricBar label='Cyclomatic Complexity' value='75' threshold='30' max='100' />

The file has one bug-linked commit out of 5 total, a bug-fix rate of 40%, no reverts, and one distinct author in the last 90 days. With only five commits, that rate is a small sample, so I would treat it as context and not as a trend. What the metrics do say clearly is that a cyclomatic complexity of 75 means roughly 75 independent paths, and each one is a case a test should cover. Channel direction, variadic parameters, zero, one or many return values, and anonymous struct fields all multiply the combinations.

My recommendation: split by kind. An `appendFuncTypeName`, `appendStructTypeName` and `appendChanTypeName` would each be small enough to test with a table, and the dispatcher left behind would be a short switch. The existing recursion stays intact because each helper still calls back into `appendTypeName`.

### `IsType` — cmp/internal/function/func.go

<FunctionCard fn='IsType' file='cmp/internal/function/func.go' risk='1.89' band='critical' cc='43' nd='2' fo='7' touches='1' />

`IsType` validates that a reflected function matches one of a handful of signatures: predicate, equality, ordering, transformer and similar shapes. It does so with a switch on a function-type enum, each case checking input and output counts and a few type equalities. The cyclomatic complexity of 43 with a fan-out of only 7 tells me this is a different problem from `compareAny`: it is not tightly coupled, it is just a lot of conditions.

It was touched once in the last year and changed today. The file shows a bug-fix rate of 25% over four commits, no reverts and no review comment activity. This one reads to me as maintainability debt more than live danger. The structure is regular, which makes it a good candidate for a table-driven rewrite: describe each signature as data (expected input count, output count, and a type predicate) and loop. That would replace most of the branches with one loop and make adding a new signature a one-line change.

### `EquateComparable` — cmp/cmpopts/equate.go

<FunctionCard fn='EquateComparable' file='cmp/cmpopts/equate.go' risk='1.87' band='high' cc='8' nd='2' fo='7' touches='3' />

This is the outlier in the group. Its cyclomatic complexity is only 8, nesting 2 and fan-out 7, and it is in the high band, not critical. It ranks fourth by activity risk, but it has the highest touch count of the five: three times in the last year, changed today, in a file with 15 total commits and two distinct authors in the last 90 days, a bug-fix rate of 33% and no reverts. The function validates its arguments (non-comparable types and duplicates both panic) and builds a filtered comparer.

I would not refactor this one. The activity is the signal, and the structure is small enough to read in one sitting. What I would do is make sure the two panic paths each have a test, because those are the branches a future edit is most likely to disturb.

### `Transformer` — cmp/options.go

<FunctionCard fn='Transformer' file='cmp/options.go' risk='1.82' band='critical' cc='13' nd='2' fo='12' touches='2' />

`Transformer` validates the supplied function, derives or validates a name, and builds the option. From the excerpt, it has several panic paths (invalid function, nil function, invalid name) and a name-derivation branch that falls back to a lambda placeholder. Cyclomatic complexity is 13 with fan-out 12, in the critical band.

This is the only file in my top five with a recorded revert: one across 16 commits, alongside a bug-fix rate of about 19% and a review comment density of 2.56. A revert in the file history is a reason to look closer at how changes here are verified, though it does not point at this specific function. The same file also contains `Comparer`, which repeats the same validate-then-build shape, so I would extract the shared validation into one helper before the two drift apart.

**The quiet debt behind the live list**

The most structurally extreme functions in go-cmp are not in my top five because they are quiet. `formatDiffList` in cmp/report_compare.go has a cyclomatic complexity of 13 and nesting of 5, and it has not changed in 1,520 days. `FormatDiffSlice` in cmp/report_slices.go has a fan-out of 12 and a cyclomatic complexity of 13, unchanged for 1,517 days. `isLess` and `resolveReferences` have gone 2,227 days without a change.

I would describe these as structural debt with a high blast radius whenever someone next touches the diff-reporting code. They are not a this-week concern, but whoever opens the report formatting files next should budget for refactoring first.
