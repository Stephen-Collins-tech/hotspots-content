Ask a senior engineer which files on the team scare them, and they'll usually name the same two or three without hesitating. Ask them how they know, and the answer is almost always some version of "I've seen it break before." That's not intuition — it's pattern recognition over a specific kind of history, and it's sitting in your git log whether or not anyone's looked at it directly.

The pattern is simple and a little uncomfortable: the files that had bug fixes last year are, on average, more likely to have bug fixes next year. Not because a bug fix jinxes a file. Because the underlying conditions that produced last year's bugs — the tangled logic, the unclear ownership, the accumulated shortcuts — are usually still there. Fixing a bug removes the bug. It doesn't remove whatever made that file bug-prone in the first place.

This is a different claim than "complex code is risky," which is true but hard to act on because complexity is expensive to measure and easy to argue about. History is neither. It's already recorded, and it doesn't require reading the code at all — just asking git what's happened.

## What "attracts complexity" actually looks like

It's rarely one root cause. A file becomes the kind of place that keeps generating bug fixes for a mix of reasons that reinforce each other:

- **It's a natural collision point.** Multiple features route through it, so multiple teams touch it, and nobody has full context on all the ways it's used.
- **It grew organically instead of by design.** Each fix was locally reasonable and globally added one more edge case to a function that already had a dozen.
- **The people who understood it best have moved on.** The tribal knowledge that made changes safe left with them, and every change since has been a little more of a guess.

None of that shows up in a complexity score. All of it shows up in the shape of the commit history — specifically, in the *rate* and *recurrence* of fixes, not their existence. One bug fix is normal. A file that keeps needing them, commit after commit, quarter after quarter, is a different situation.

## Three commands, five minutes

Before opening a codebase you've inherited — or before your next sprint planning session — these three commands tell you where the attention should already be going:

```bash
# Which files have the most fix-flagged commits in the last year
git log --since="1 year ago" --name-only --format="" --grep="fix\|bug" -i | sort | uniq -c | sort -rn | head -20

# Of those, which ones keep coming back — fixed more than once
git log --since="1 year ago" --format="%H" --grep="fix\|bug" -i -- path/to/suspect.ts | wc -l

# Who's been doing the fixing, and is it spread out or concentrated
git log --since="1 year ago" --format="%an" --grep="fix\|bug" -i -- path/to/suspect.ts | sort | uniq -c
```

The list this produces almost always matches what the senior engineers already tell you informally — which is itself worth noting. It's not a surprising signal. It's an *unused* one, because most teams' review and refactoring effort is driven by what's currently visible — a recent PR, a big diff, whoever's loudest in standup — not by which files have quietly kept generating fixes for a year.

## The actual takeaway

You don't need a model, a dashboard, or a new tool to start using this. You need to run the query. The files with the longest tail of recurring fixes are your highest-value refactoring targets, not because they're the most complex by some abstract measure, but because they have the most concrete evidence that whatever's making them hard hasn't been addressed yet. Past bugs aren't a life sentence for a file — but they're the closest thing to a confirmed diagnosis you're going to get without opening the code at all.
