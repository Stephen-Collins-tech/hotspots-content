Across lazygit's 4,368 analyzed functions, 419 land in the critical band, and the single riskiest one — `onKey` in `pkg/gocui/gui.go` — carries an activity-weighted risk score of 17.94 despite zero touches in the last 30 days and 42 days since its last change. That's the archaeology story here: the top of the list isn't a live regression risk, it's structural debt with a long fuse. Two of the five hotspots I'd flag first sit in the 'fire' quadrant instead — `execKeybindings` and `performRefresh` — both touched within the last 30 days, and a third, `GetWorktrees`, was changed the same day as this analysis, which means the input-handling and refresh subsystems are both complex and under active edit right now.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `onKey` — pkg/gocui/gui.go

<FunctionCard fn='onKey' file='pkg/gocui/gui.go' risk='17.94' band='critical' cc='82' nd='6' fo='29' touches='0' />

This is the top-ranked function in the whole scan, and it sits in the debt quadrant — 82 independent paths, six levels of nesting, and a fan-out of 29 distinct calls, but zero touches in the last year and 42 days since anyone last modified it. From the source, it's a single `switch` over event types (key events, mouse events) with a long cascade of nested conditionals handling mouse capture, drag gestures, hyperlink clicks, and paste-mode key remapping — all in one function body. The file's history shows a bug-fix rate of about 10.5% across 19 total commits and a single author active in the last 90 days, so this isn't a function with a documented defect trail, but it is one almost nobody currently holds context on. My recommendation: before the next person has to touch this for a new terminal-compatibility fix (the Ghostty paste-handling comment suggests this happens periodically), split the key-event and mouse-event branches into two functions. That alone would cut the paths any single function has to reason about roughly in half.

### `getBoxDrawingChars` — pkg/gui/presentation/graph/cell.go

<FunctionCard fn='getBoxDrawingChars' file='pkg/gui/presentation/graph/cell.go' risk='17.2' band='critical' cc='83' nd='16' fo='1' touches='0' />

This one is a curiosity worth calling out directly: cyclomatic complexity of 83 and a nesting depth of 16, yet a fan-out of just 1. Looking at the source, it's a flat `if/else if` chain checking four booleans (up, down, left, right) to pick box-drawing characters — sixteen branches, one per combination, each returning a literal string pair. The high complexity and nesting numbers here are an artifact of an exhaustive boolean truth table, not tangled logic — there's no hidden coupling since it calls out to nothing else. It's in the debt quadrant: 78 days since its last change, and its one historical commit was itself tagged as a bug fix (a bug-fix rate of 100% on a single-commit history, so treat that as a small-sample signal, not a trend). The fix is mechanical: replace the sixteen-way `if/else if` chain with a lookup table keyed by the four-bit combination of directions. That would drop the complexity to near 1 without changing behavior.

### `execKeybindings` — pkg/gocui/gui.go

<FunctionCard fn='execKeybindings' file='pkg/gocui/gui.go' risk='17.15' band='critical' cc='49' nd='6' fo='12' touches='1' />

This sits in the same file as `onKey`, but in the fire quadrant — one touch in the last year, 26 days since last change, an activity-weighted risk score of 17.15. The source shows it resolving which keybinding handler fires for a given key event, with early-return branches for search-mode keys, parent-view keybinding fallback, and global keybinding fallback layered on top of a loop over all registered keybindings. Forty-nine paths through that resolution logic is a lot of surface for a function that runs on every keypress. The file overall carries the same bug-fix rate as `onKey` (about 10.5% across 19 commits) and a review-comment density of 1.0, meaning reviewers have historically left about as many comments as there are commits on this file — worth reading as a signal that this logic invites scrutiny. Given it's actively being modified, I'd extract the search-mode-key handling into its own helper before the next change lands here, since that block is logically separable from the general keybinding-matching loop.

### `performRefresh` — pkg/gui/controllers/helpers/refresh_helper.go

<FunctionCard fn='performRefresh' file='pkg/gui/controllers/helpers/refresh_helper.go' risk='17.15' band='critical' cc='90' nd='3' fo='79' touches='3' />

The standout number here is fan-out: 79 distinct calls out of one function, the highest of anything in this list, paired with 90 cyclomatic paths. That's a genuine hub function — coordinating scope-based refresh logic, worker-thread versus UI-thread dispatch, generation-guarded state capture, and input-blocking behavior, all visible in the comments as deliberate concurrency safeguards around goroutine and repo-switch races. Three touches in the last year and only 5 days since the last change put this firmly in the fire quadrant. The file has three commits linked to bug fixes out of 33 total (a bug-fix rate of about 15%) and a review-comment density of 3.0 — three comments per commit on average — both consistent with a function that reviewers already treat carefully. Given the low nesting (3) but extreme fan-out, this reads less like tangled conditionals and more like a coordination point with too many responsibilities glued together. I'd look for the natural seams — UI-thread capture, scope-set resolution, and batch-update dispatch look like three separable units from the excerpt — and extract at least one before the next refresh-related feature touches it.

### `GetWorktrees` — pkg/commands/git_commands/worktree_loader.go

<FunctionCard fn='GetWorktrees' file='pkg/commands/git_commands/worktree_loader.go' risk='16.77' band='critical' cc='41' nd='4' fo='29' touches='1' />

Changed the same day as this analysis was run, with a fan-out of 29 and 41 execution paths, this function sits in the fire quadrant and parses `git worktree list --porcelain` output line by line before spinning up a goroutine per worktree to resolve its git directory in parallel via a `sync.WaitGroup`. That parallel-resolution step is worth flagging specifically: structural metrics like cyclomatic complexity don't capture goroutine coordination risk, and a bug here (a race on `current` during line parsing, or a wait-group mismatch) wouldn't necessarily show up as a branching problem. The file shows one bug-linked commit out of four total (a bug-fix rate of 25%), which is a small-sample signal but worth noting given the function was just modified. My recommendation: given it's actively changing and touches concurrent code, add a focused test for the goroutine fan-out path (missing directories, malformed porcelain output) rather than relying on the sequential-parsing tests alone.
