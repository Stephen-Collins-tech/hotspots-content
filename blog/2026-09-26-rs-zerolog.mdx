### `appendFieldList` — fields.go

<FunctionCard fn='appendFieldList' file='fields.go' risk='14.88' band='critical' cc='218' nd='5' fo='50' touches='0' />

This is the single highest-risk function in the repository, and the numbers explain why. A cyclomatic complexity of 218 is extreme by any standard — the source excerpt shows a large outer loop over key-value pairs wrapped around nested type switches: one switch on the value type (string, bytes, error, slice of errors, slice of marshalers, bool, and more), and inside the error case a second nested switch on the result of `ErrorMarshalFunc`, and inside that a third switch when stack traces are involved. A max nesting depth of 5 combined with a fan-out of 50 distinct calls means this function is both deeply layered and extremely widely coupled — it is effectively the central dispatch point for how every field type gets serialized. The file's commit history shows a bug-fix rate of about 33% across 9 total commits, with an average of roughly 2.3 review comments per commit, suggesting past changes here have not been trivial to review. It hasn't been changed in 238 days, so nobody is actively fighting fires here today, but the combination of a god-function shape and this fan-out means any future change to how field values are appended has a wide blast radius. My recommendation: split the value-type switch into per-type helper functions (`appendErrorField`, `appendErrorStackField`, `appendSliceField`) before the next feature touches this — trying to extend 218 branches in place is where regressions get introduced.

### `decodeTagData` — internal/cbor/decode_stream.go

<FunctionCard fn='decodeTagData' file='internal/cbor/decode_stream.go' risk='14.71' band='critical' cc='41' nd='3' fo='20' touches='0' />

This is the file I'd flag first for anyone planning to touch CBOR decoding in zerolog. Three separate functions from the same file all land in my top five, and all three have gone untouched for exactly 1,136 days — over three years. That points to a single decode path that hasn't been revisited in a long time.

`decodeTagData` is the most complex of the three, with a cyclomatic complexity of 41 spread across nested switches on CBOR tag types — timestamps, embedded CBOR, embedded JSON, network addresses, network prefixes, and hex strings each get their own branch, several with their own inner switch on byte length or sub-type. The 'exit_heavy' and 'god_function' patterns both apply here: I count panic calls scattered through nearly every branch as the error-handling mechanism, and a fan-out of 20 means it's calling into a wide set of helper decoders (`decodeTimeStamp`, `decodeIntAdditionalType`, `decodeString`, `decodeInteger`, and more). In Go, that many explicit panic-based exit points is worth flagging on its own — each one is an implicit error path that a table-driven test suite needs to cover, and panics deep in a decoder mean malformed input can crash the calling goroutine if it isn't recovered upstream.

`decodeSimpleFloat` (complexity 29) follows the same shape at smaller scale — a major-type switch, then a minor-type switch, with a NaN/Inf special case nested inside the float-decoding branch, and multiple panic exits for unrecognized types.

`map2Json` (complexity 28, nesting depth 4, the deepest of the three) implements the key-value alternation logic for CBOR maps — tracking even/odd position to know whether it's writing a key or a value, with a separate branch for indefinite-length maps that requires peeking ahead for a break marker. The nesting here is the specific risk: four levels deep, the logic for 'is this an indefinite-length map, and if so, have I hit the break byte' is duplicated between the key path and the value path in the excerpt.

All three functions share the same file-level history: 3 total commits, a bug-fix rate of about 67%, and zero authors active in the last 90 days. A two-out-of-three bug-fix rate on a low commit count doesn't prove the current code is defective, but it does tell me this decoder had a bumpy history when it was being written, and nobody has gone back to harden it since. Given the panic-heavy error handling and the shared duplication pattern across all three functions, I'd treat this file as a single refactoring unit rather than three separate tickets — extract the peek-and-check-break logic into one shared helper, and replace the panic calls with returned errors so malformed CBOR input doesn't propagate a crash up the call stack.

### `appendSlogAttr` — slog.go

<FunctionCard fn='appendSlogAttr' file='slog.go' risk='13.36' band='critical' cc='39' nd='2' fo='25' touches='0' />

This one stands apart from the others in shape: complexity of 39 but a nesting depth of only 2, meaning the branching is wide rather than deep — mostly a flat switch over `slog.Kind` values (string, int64, uint64, float64, bool, duration, time, and an 'any' case that itself contains a nested type switch for errors, durations, times, and byte slices). A fan-out of 25 confirms this is a dispatch function bridging Go's standard-library `slog.Attr` type to zerolog's own `Event` builder methods — every attribute kind maps to a specific `Event` method call. The file shows only 1 total commit and a review comment density of 19 on that commit, which is unusually high and suggests this bridging code got heavy scrutiny when it was introduced, likely because it's the seam between two logging APIs. It hasn't changed in 175 days, and sits in the debt quadrant rather than under active development. Given the recursive call for `slog.KindGroup` (the function calls itself to flatten nested attribute groups), I'd want explicit test coverage for deeply nested groups before this code sees its next change — the recursion combined with 39 branches means a regression here could show up only under specific group-nesting shapes that are easy to miss in a quick review.
