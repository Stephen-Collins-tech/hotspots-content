*Risk score = structural complexity (cyclomatic complexity × nesting depth × fan-out) × recent commit frequency — a function that is both complex and actively changing scores highest.*

**Highest-risk repositories:**

- [postgres/postgres](/blog/2026-10-28-postgres-postgres/) — risk 131.3

- [openssh/openssh-portable](/blog/2026-10-16-openssh-openssh-portable/) — risk 20.9

The gap between average and median risk scores tells the real story here. Across 11 C repositories, the median top risk score sits at 15.1 while the average lands at 22.3—a spread that suggests most C codebases stay reasonably disciplined until one project blows the curve. That outlier is PostgreSQL, with a risk score of 131.3, nearly six times higher than the next-highest repository. What makes a 40-year-old database engine accumulate that much structural debt while curl and OpenSSH hover around 20?

## Methodology

We calculated activity risk by combining structural complexity (cyclomatic complexity × nesting depth × fan-out) with recent commit frequency. Functions that are both complex and actively changing score highest because they represent immediate maintenance burden. The analysis window covered recent git history across 11 established C repositories, ranging from system utilities to major infrastructure projects.

## The Most Common Antipatterns

Three patterns tie for most prevalent: complex branching, exit-heavy functions, and god functions each appear in 6 of 11 repositories analyzed. Long functions match that count as well. Deeply nested control structures follow at 5 of 11.

The prevalence of complex branching and exit-heavy functions reflects C's low-level nature. Without exceptions or early-return idioms common in higher-level languages, C functions accumulate multiple return paths to handle error conditions, resource cleanup, and edge cases. Each `if (err) { cleanup(); return NULL; }` block adds another exit point and another branch to track.

God functions—those combining high complexity, high fan-out, and excessive length—appear frequently because C lacks the encapsulation mechanisms that force decomposition in other languages. A function in C can grow indefinitely without syntax pressure to split it, and the manual memory management often discourages extraction since local cleanup logic becomes harder to share.

The 5-of-11 prevalence of deep nesting connects directly to the error-handling patterns. Each nested condition adds another level, and without try-catch blocks, error checks stack up inside success paths.

## The Highest-Risk Repositories

[postgres/postgres](/blog/2026-10-28-postgres-postgres/) leads with a risk score of 131.3, driven by neighbor risk, exit-heavy patterns, and god functions. The neighbor risk pattern indicates that high-complexity functions cluster together—when one risky function calls another, both scores compound. For a codebase managing query planning, execution, and storage, this clustering makes sense but creates concentrated maintenance burden.

[FFmpeg/FFmpeg](/blog/2026-10-26-FFmpeg-FFmpeg/) scores 21.2, with god functions, long functions, and complex branching as primary patterns. Video codec implementation inherently involves state machines and format-specific branching, but the god function prevalence suggests consolidation opportunities exist.

[openssh/openssh-portable](/blog/2026-10-16-openssh-openssh-portable/) at 20.9 shows complex branching, deep nesting, and exit-heavy functions. Security-critical code often exhibits these patterns due to extensive input validation and error path handling.

[curl/curl](/blog/2026-09-28-curl-curl/) scores 20.3 with the same pattern combination as OpenSSH—complex branching, deep nesting, and exit-heavy functions. Protocol handling code shares similar structural pressures.

[jqlang/jq](/blog/2026-10-06-jqlang-jq/) rounds out the top five at 20.2, with god functions, complex branching, and deep nesting. Parser and interpreter code tends toward these patterns as language semantics get encoded in control flow.

## What This Means for C Developers

The data suggests that C's most common structural problems stem from its error-handling idioms rather than carelessness. When every function must explicitly check and propagate errors, complexity accumulates in predictable ways. The repositories with highest risk aren't poorly maintained—they're handling genuinely complex domains without language features that would distribute that complexity differently.

The practical response isn't to avoid these patterns entirely but to recognize where they concentrate risk. A function with complex branching that rarely changes poses less immediate concern than one with the same complexity that sees weekly commits. PostgreSQL's outlier score reflects both its domain complexity and its active development, making those high-scoring functions genuine priorities for refactoring attention.

## Analyze Your Own Repository

To identify structural hotspots in your own C codebase, install the CLI:

```bash
brew install Stephen-Collins-tech/tap/hotspots
```

Or on any platform with Rust:

```bash
cargo install hotspots-cli
```

Then run analysis against your local repository:

```bash
hotspots analyze .
```

The output will surface functions where complexity and change frequency intersect—the same risk calculation applied to the repositories above.
