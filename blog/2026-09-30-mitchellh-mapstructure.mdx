One file, mapstructure.go, holds all five of the top hotspots in mitchellh/mapstructure, and that concentration matters: the decode entry point and the per-kind decoders hanging off it form a single interlocking unit, so a change to one tends to be read against the others. The analysis at commit 8508981 covers 41 functions, 18 of them in the critical band, and all 35 non-ok functions fall in the debt quadrant, with none in fire. The top function, decodeArray, has an activity-weighted risk score of 15.7 and hasn't been changed in 1,118 days, so I am framing this as structural debt with a high blast radius when next touched, not as live regression risk.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `decodeArray` — mapstructure.go

<FunctionCard fn='decodeArray' file='mapstructure.go' risk='15.7' band='critical' cc='24' nd='5' fo='26' touches='0' />

`decodeArray` has the top activity-weighted risk score at 15.7 despite the lowest cyclomatic complexity of the five. Its nesting depth of 5 is the deepest in the set, and it hasn't been changed in 1,118 days, the longest dormancy of any of them. The excerpt shows why depth is the problem: the main branch sits inside a check on whether the target array is still zero or zero-fields is set, then inside a check on the input kind, then inside a weakly-typed-input check, then inside a switch. The function also retries itself by wrapping the input in a single-element slice, so recursion is part of its control flow, and the two error returns for wrong-kind and too-long input add to the exit count.

Guard clauses are the lowest-effort fix: invert the outermost conditions so the wrong-kind and too-long errors return early and the main loop is no longer buried three levels down. That should bring nesting back to 3 or below without changing behaviour. A test covering the weak-typing lift, the empty-map case, and the oversize-input error would pin current behaviour before any restructuring.

### `decodeSlice` — mapstructure.go

<FunctionCard fn='decodeSlice' file='mapstructure.go' risk='15.41' band='critical' cc='34' nd='4' fo='27' touches='0' />

`decodeSlice` is `decodeArray`'s sibling, with a higher CC of 34, nesting of 4, fan-out of 27, and 602 days since last change. The excerpt shows the same weak-typing conversion logic, with extra cases for empty maps and for strings converted to byte slices, followed by the allocation logic and the per-element decode loop. The exit-heavy and god-function patterns both apply.

The two functions duplicate much of their shape: the wrong-kind check, the weak-typing lift, the element loop with error accumulation, and the final set-and-return-errors tail. I would look at extracting the shared element loop and error-wrapping tail so array and slice decoding differ only in how the destination is allocated. Whether the duplication is intentional, given that arrays and slices have different allocation rules, is something only the maintainers can judge, but the shared tail is visible in both excerpts.

**What I would do with this list**

The five functions share a file, a coding style, and two recurring shapes: input normalization at the top and error accumulation at the bottom. With no function currently changing, this is a good moment for the work, since refactoring dormant code is cheaper than refactoring under active feature pressure. I would sequence it as tests first around `decode`, then the two collection decoders, then the two struct/map functions, which carry the highest CC and fan-out.

Most of these functions return errors explicitly rather than through panics, which is idiomatic Go and keeps the error paths visible. It is also why the exit counts are high: every one of those returns is a path a test has to reach.

### `decodeStructFromMap` — mapstructure.go

<FunctionCard fn='decodeStructFromMap' file='mapstructure.go' risk='15.13' band='critical' cc='82' nd='4' fo='36' touches='0' />

<MetricBar label='Cyclomatic Complexity' value='82' threshold='10' max='90' />

I would start with `decodeStructFromMap`: it has the highest cyclomatic complexity in the set at 82 and the highest fan-out at 36, and it hasn't been changed in 604 days. A CC of 82 means 82 independent paths, each a potential test case. From the excerpt, the function validates map key types, builds several bookkeeping maps for used and unused keys, walks a work queue of structs to flatten embedded and squashed fields, and parses struct tags for options like squash and remain. That is several distinct jobs in one body, and both the long-function and god-function patterns fire.

The nesting depth of 4 is modest, so the difficulty is breadth, not depth: a long function with a great many branches, with error accumulation running through the whole thing. I would extract method along the natural seams visible in the excerpt. A field-collection step (walking structs, handling squash and remain tags) can become its own function that returns the list of fields, and the per-field decode loop can follow as a second step. My first move would be a characterization test suite around the current behaviour of squash and remain handling, before any splitting.

### `decodeMapFromStruct` — mapstructure.go

<FunctionCard fn='decodeMapFromStruct' file='mapstructure.go' risk='14.69' band='critical' cc='47' nd='4' fo='35' touches='0' />

`decodeMapFromStruct` mirrors the previous function: where that one fills a struct from a map, this one fills a map from a struct. Its CC is 47, its fan-out is 35, and it hasn't been changed in 604 days. The excerpt shows a loop over struct fields that skips unexported ones, checks assignability to the map's element type, resolves the key name from the tag, and then handles squash, the omit marker, and omitempty inside a nest of conditionals before a switch on the field kind.

The tag-parsing logic (find the comma, check for the skip marker, check for omitempty, check for squash) is the obvious extraction. I would pull key-name and options resolution into a small helper that returns the key, whether to skip, and whether to squash. That alone would flatten the nested conditionals and leave the loop body reading as resolve, skip or continue, then dispatch on kind. Since squash handling exists in both this function and `decodeStructFromMap`, I would also check whether the two tag-interpretation paths can share one implementation; divergent readings of the same tag are the kind of thing that breaks quietly.

### `decode` — mapstructure.go

<FunctionCard fn='decode' file='mapstructure.go' risk='14.41' band='critical' cc='53' nd='3' fo='23' touches='0' />

`decode` is the central dispatcher, which is why its numbers matter more than the raw score suggests. Its CC is 53 with nesting of only 3, which fits the shape in the excerpt: early exits for nil and invalid input, a decode-hook step, then a large switch on the output kind that calls decodeBool, decodeString, decodeStruct, decodeMap, decodeSlice, decodeArray and others. The exit-heavy pattern flags the many return paths, and each is a separate test-coverage obligation. It hasn't been changed in 604 days.

The switch is reasonable structure for a dispatcher, so I would leave it alone. What I would extract is the preamble: the typed-nil check, the zero-fields handling, and the metadata key bookkeeping repeat in several branches and push the path count up. A small function that normalizes the input and reports whether to stop early would let `decode` read as normalize, run hook, dispatch, record metadata. Most of the other functions in this list are reached through `decode`, so it is also where a test suite pays back the most.
