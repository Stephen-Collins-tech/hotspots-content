### `visit_insert` — compiler.py

I would start with `visit_insert` because it has the highest activity-weighted risk score in the repository, 59.93, and the largest cyclomatic complexity in this list at 64. It has 0 touches in the last year and has gone 88 days without a change, so this is structural debt rather than live churn. That is exactly why I would schedule it: the next person to edit it inherits 64 independent paths and a fan-out of 22.

The excerpt shows why the number is so high. The function handles top-level versus CTE-nested compilation, positional versus named bind parameters, a numeric-bind special case, an empty-insert check that depends on three separate dialect capability flags, and a multi-parameter branch that again depends on dialect support. Each of those is a decision that stacks onto the others. It is also flagged exit-heavy, so the number of return and raise paths adds to the test burden on top of the branching.

My recommendation is extract-method along the seams the code already shows. The positional bind-parameter counting block (the part commented as needed for insertmanyvalues) can become its own helper with a clear return value. The dialect capability validation for empty inserts can move into a small guard method. Neither change alters behavior, and each one removes branches from the main body. Because the function is dormant right now, this is a good window to do it with no merge conflicts against in-flight work.

### `visit_cte` — compiler.py

<FunctionCard fn='visit_cte' file='lib/sqlalchemy/sql/compiler.py' risk='58.42' band='debt' cc='39' nd='3' fo='21' touches='0' />

`visit_cte` is the second 'debt' function, with an activity-weighted risk score of 58.42, cyclomatic complexity of 39, nesting depth of 3 and a fan-out of 21. It has also gone 88 days without a change and has 0 touches in the last year. Nesting depth 3 is modest, so the difficulty here is breadth of branching rather than depth.

From the excerpt, the function tracks CTEs by level and name, decides whether an incoming CTE is new, a repeat, a restatement, or enclosed by another same-named CTE, and handles a 'nest_here' relocation case that raises a compile error if stated in two places. That is a lot of identity and ordering logic in one method, and it reads and mutates several pieces of compiler state (the stack, the by-level-name tables, the CTE collection). Mutating shared state is what makes high complexity here expensive to test: a case has to set up the right prior state before it can exercise a branch.

I would separate the lookup of an existing CTE from the decision about what to do with it. A function that answers 'what is the existing CTE at this level and name, and has it been relocated' could return a small result, and the remaining body would branch on that result. That also gives a natural place to write focused tests for the relocation and restatement cases.

### `_process_parameters_for_postcompile` — compiler.py

<FunctionCard fn='_process_parameters_for_postcompile' file='lib/sqlalchemy/sql/compiler.py' risk='58.14' band='fire' cc='27' nd='5' fo='23' touches='1' />

This is the first 'fire' function in the list, and the one I would put at the top of the live-risk queue. It has an activity-weighted risk score of 58.14, cyclomatic complexity of 27, a nesting depth of 5, and a fan-out of 23, with 1 touch in the last year and 13 days since last change. Nesting depth 5 is the deepest in the top five and is the only function here flagged as deeply nested.

The docstring says it handles 'expanding' parameters (typically IN tuples rendered per element for an otherwise fixed SQL string) and literal-bind parameters marked for literal execution. The excerpt shows it maintaining a large amount of local state before the main loop even starts: new processors, replacement expressions, sets to update, a set of names the expanded elements are not allowed to take, and separate positional and non-positional position lists. The comments in the excerpt also distinguish escaped from unescaped parameter names across different structures, which is the kind of invariant a reader has to hold in their head while editing.

Because it was changed 13 days ago and sits at nesting depth 5, I would prioritize review of recent changes to it and add test cases that combine features (positional plus numeric binds, expanding plus literal-execute) rather than testing each in isolation. For refactoring, the pre-loop setup could be extracted into a small state-holder object, and the per-parameter body could be split into one helper for literal-execute parameters and one for expanding parameters. Flattening that nesting is the most direct way to bring the nesting depth down.

### `_deliver_insertmanyvalues_batches` — compiler.py

<FunctionCard fn='_deliver_insertmanyvalues_batches' file='lib/sqlalchemy/sql/compiler.py' risk='56.88' band='debt' cc='40' nd='4' fo='35' touches='0' />

<MetricBar label='Fan-out' value='35' threshold='15' max='40' />

This function has the highest fan-out of the five at 35 distinct functions called, with cyclomatic complexity of 40 and nesting depth 4. It is a 'debt' function: 0 touches in the last year and 88 days since last change. In Python, where calls resolve at runtime, a fan-out of 35 probably understates the real coupling, since the dialect and the insertmanyvalues object it reads from can change what actually runs.

The excerpt shows an opening decision chain that picks between row-at-a-time and batched delivery, with comments explaining several distinct reasons for downgrading to row-at-a-time: a backend that cannot use DEFAULT for repeated rows, a request for deterministic parameter order without sentinel columns, and upsert behavior with bound parameters in the SET clause (the code references issue #13130). After that decision, there is the delivery logic itself. A generator that returns an iterator of batches also carries invisible control flow, because the body does not run until it is consumed.

The cleanest first move is to extract the opening decision chain into a method that returns the two booleans it already computes (row-at-a-time and downgraded). That chain is pure decision logic with documented rationale, so it is straightforward to unit test by dialect capability. It would take a sizable share of the branches out of a function that is otherwise about producing batches. Anyone adding a new reason to downgrade, as the upsert case appears to have been, would then touch a small, well-named method instead of the generator body.

### `_literal_execute_expanding_parameter` — compiler.py

<FunctionCard fn='_literal_execute_expanding_parameter' file='lib/sqlalchemy/sql/compiler.py' risk='55.43' band='fire' cc='12' nd='2' fo='11' touches='1' />

The last 'fire' function in the list is also the least complex of the five: cyclomatic complexity of 12, nesting depth of 2, and fan-out of 11, with an activity-weighted risk score of 55.43. It was last changed 13 days ago, the same day as `_process_parameters_for_postcompile`. Its position in the top five comes mostly from activity plus the file-level context, not from raw branching.

The docstring references ticket 13695 and explains the recent change: element names generated for an expanding parameter can collide with other parameter names, so a counter-based uniquifier is applied. The excerpt also shows local render helpers that differ depending on whether bind casts are rendered.

I would treat this as a review-and-test item rather than a refactor. Recently changed code in a function with a mutable shared set of taken names deserves tests that cover collisions across multiple expanding parameters and across tuple elements, since those are the cases the docstring says motivated the change. If the function grows further, the empty-values, tuple, and scalar branches are natural candidates for separate helpers.

**What the file-level picture suggests**

Three of the five are 'debt' functions that have been quiet for 88 days, and two are 'fire' functions changed 13 days ago. My practical ordering would be: review recent changes to `_process_parameters_for_postcompile` first, because it combines nesting depth 5 with recent activity; schedule extract-method work on `visit_insert` and `_deliver_insertmanyvalues_batches` while they are dormant; and add collision-focused tests around `_literal_execute_expanding_parameter`.
