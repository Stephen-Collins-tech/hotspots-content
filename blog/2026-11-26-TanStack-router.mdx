### `build` — router.ts

<FunctionCard fn='build' file='packages/router-core/src/router.ts' risk='2.56' band='critical' cc='53' nd='3' fo='34' touches='106' />

<MetricBar label='Cyclomatic Complexity' value='53' threshold='10' max='60' />

This is the function I would look at first. From the excerpt, it takes a destination object and produces a parsed location. It handles an optional href that gets parsed and rewritten, resolves a current location from several fallbacks, runs a development-only check that the `from` path exists in the route tree, resolves the target path, and then looks up a destination route and builds its branch. That is several distinct responsibilities in one closure.

A cyclomatic complexity of 53 is well past the 30 mark I treat as high, and a fan-out of 34 means it calls 34 distinct functions directly. Nesting depth is only 3, so this is a wide function rather than a deep one. The excerpt shows a lazily computed lightweight match, a usage flag set when the current location is read, and a nullish-assignment cache on the destination route's branch. Those are the kinds of implicit state that complexity counts understate, and they make the order of reads matter.

My recommendation: extract the href-rewrite step and the development-only `from` validation into their own functions first. Both appear self-contained in the excerpt, and the validation is already gated behind a non-production check. That would remove several branches and a visible chunk of fan-out without touching the core path-resolution logic. Because the file's history includes 3 reverts, I would land those extractions as separate, small changes.

### `BaseTanStackRouterDevtoolsPanel` — BaseTanStackRouterDevtoolsPanel.tsx

<FunctionCard fn='BaseTanStackRouterDevtoolsPanel' file='packages/router-devtools-core/src/BaseTanStackRouterDevtoolsPanel.tsx' risk='2.56' band='critical' cc='37' nd='3' fo='49' touches='15' />

<MetricBar label='Fan-out' value='49' threshold='15' max='60' />

The highest fan-out in this analysis belongs to the devtools panel component: 49 distinct functions called. From the excerpt, it owns local-storage-backed tab and route selection state, a history signal with an overflow flag, a pending-matches derivation, and effects that poll the router cache every 500 milliseconds and track the current match into history. It also attaches styles when a mount element is provided.

That is a component acting as a state container, a polling loop, and a view at once. The cache-refresh effect compares sizes and then walks values by index to detect change, which is hand-rolled change detection living inside the component body. With a cyclomatic complexity of 37, this is a lot to hold in your head, and a fan-out of 49 means a change to almost any signal or helper API can touch it.

The file has been touched 15 times in the last year, with a bug-fix rate of 40%, 1 revert, and only 1 distinct author in the last 90 days. It was last changed 4 days ago. The single-author pattern matters for review: pull request comment density is 2.5, so there is less independent scrutiny on this file than on router.ts. I would not call that a problem on its own, but it raises the value of splitting the component.

My recommendation: move the cache-polling effect and the history-tracking effect into custom hooks, and keep the component to composition. Both are self-contained enough in the excerpt to extract without changing the rendered output.

### `matchRoutesInternal` — router.ts

<FunctionCard fn='matchRoutesInternal' file='packages/router-core/src/router.ts' risk='2.53' band='critical' cc='47' nd='4' fo='16' touches='106' />

This private method matches a parsed location against the route tree and returns an array of route matches. The excerpt shows it deciding whether a not-found entry is needed, choosing between a legacy not-found route and a global not-found mode, and then looping serially over matched routes to validate search parameters. A comment in the code explains why the loop must be serial: each route's search can depend on its parent's, and the result feeds the match key.

A cyclomatic complexity of 47 with nesting depth 4 and fan-out 16 is a narrower profile than `build`. The risk here is the number of execution paths inside one loop body: search validation with error wrapping, strict versus merged search tracking, and previous-match lookup with a special case for the not-found route. In TypeScript, the try/catch around validation that rewraps unknown errors is another place where type narrowing matters and where complexity counts understate the real branching.

My recommendation: pull the per-route search resolution, the part that computes the merged search, the strict search, and any error, into a function that returns a small result object. The loop body then shrinks to orchestration. That is a mechanical extract-method change, and it makes the serial-dependency rule testable on its own.

### `RouteComp` — BaseTanStackRouterDevtoolsPanel.tsx

<FunctionCard fn='RouteComp' file='packages/router-devtools-core/src/BaseTanStackRouterDevtoolsPanel.tsx' risk='2.5' band='critical' cc='15' nd='4' fo='20' touches='15' />

This component renders a single route entry in the devtools route tree. The excerpt shows memoized derivations for the active matches, the match for this route, a display parameter built by stripping a leading dollar sign from the path and looking it up in the match params, and a navigation target that flattens all params and interpolates the full path. Both the param memo and the navigation memo return empty or undefined on several early exits.

A cyclomatic complexity of 15 is moderate, but nesting depth of 4 and fan-out of 20 push it into the critical band. Much of its weight is the very long inline prop type, a deeply parameterized route type that would be better as a named alias, plus the derivation logic stacked inside memos. The param memo wraps everything in a try/catch that returns an empty string, which hides failures in the lookup.

My recommendation: name the props type, and extract the param-display and navigation-target derivations as plain functions that take a route, matches, and params. They become testable without rendering a component, and the component shrinks to its markup.

### `getSearchMiddlewares` — router.ts

<FunctionCard fn='getSearchMiddlewares' file='packages/router-core/src/router.ts' risk='2.43' band='critical' cc='12' nd='6' fo='4' touches='106' />

<MetricBar label='Nesting Depth' value='6' threshold='4' max='8' />

This one is a different shape. Its cyclomatic complexity of 12 and fan-out of 4 are modest, but nesting depth is 6, which is where I start to read code more slowly. The excerpt shows it collecting middlewares from each destination route, with a legacy branch that wraps old pre-search and post-search filters into a middleware, marked with a TODO to remove them in v2, and a validation middleware that catches and ignores errors because they are handled elsewhere in route matching.

The legacy branch is the interesting part. Code carrying a removal TODO alongside the current path is a sign of an API surface that has not fully settled, and it sits in a file that changed 106 times in the last year. Nested closures defined inside a loop inside a conditional are what push depth to 6.

My recommendation: lift the legacy-filter wrapper and the validation middleware into named factory functions outside the loop. That should bring nesting depth down to about 3 without changing behavior, and it gives the v2 removal a single obvious deletion target.

## Where to start

I would start with `build` in router.ts: it has the highest activity-weighted risk score at 2.56, the largest cyclomatic complexity of the five at 53, and sits in a file with 106 touches in the last year and 3 reverts. Extract the href-rewrite and the development-only validation first, then move to `matchRoutesInternal` and its per-route search resolution. `getSearchMiddlewares` is a cheap win because its problem is nesting depth, not complexity.

For the devtools file, `BaseTanStackRouterDevtoolsPanel` is the priority, with a fan-out of 49. Moving the two effects into hooks is the smallest change that makes a visible difference. Neither file's history proves a defect, but both are complex and both are changing, which is the combination worth reviewing before the next development push.
