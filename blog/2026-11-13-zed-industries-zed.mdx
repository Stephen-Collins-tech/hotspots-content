Four of the five highest-ranked functions in zed-industries/zed are both structurally complex and in code that is changing right now, which makes them worth reviewing first. The top function, `handle_thread_event` in `crates/agent_ui/src/conversation_view.rs`, has an activity-weighted risk score of 3.75, a cyclomatic complexity of 106, a fan-out of 32, 214 touches in the last year, and was last changed 1 day ago. Zed has 44,993 analyzed functions, 1,359 of them in the critical band, and I would start with the agent and markdown paths because their risk comes from complexity combined with daily change, not from age.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `handle_thread_event` — conversation_view.rs

<FunctionCard fn='handle_thread_event' file='crates/agent_ui/src/conversation_view.rs' risk='3.75' band='active' cc='106' nd='3' fo='32' touches='214' />

I would start with `handle_thread_event` because it combines a cyclomatic complexity of 106 with 214 touches in the last year and a last change 1 day ago. From the source excerpt, this is a single large dispatch over thread event variants (status changes, submission updates, new entries, entry updates, and more). It begins with an ownership check that returns early if the thread is not the current owner, then branches by event type, and many arms reach into the active thread view to update state and sync UI pieces like the generating indicator and list state.

<MetricBar label='Cyclomatic Complexity' value='106' threshold='10' max='150' />

Nesting depth is only 3, so this is wide rather than deep: the cost is the number of independent paths, each of which is a test case, and a fan-out of 32 means a change to any arm can ripple into view-state, list-state, and editor-mode code. The file's bug-fix rate is 16.4%, with no bug-linked commits and no reverts recorded, and 14 distinct authors in the last 90 days. That is a lot of hands on one dispatcher. My concrete recommendation is to turn each match arm into its own handler method (for example, one for new entries and one for entry updates), leaving the top-level function as ownership check plus dispatch. That would cut its complexity by most of its current value and let each handler be tested alone.

### `request_layout` — markdown.rs

<FunctionCard fn='request_layout' file='crates/markdown/src/markdown.rs' risk='3.68' band='active' cc='150' nd='5' fo='79' touches='122' />

`request_layout` has the highest cyclomatic complexity in the set at 150 and a fan-out of 79, and it was last changed 0 days ago, with 122 touches in the last year. The excerpt shows it building highlights from search and selection state, then looping over every parsed markdown event while tracking a pile of mutable flags: whether it is inside an image block, an HTML block, a Mermaid block, or a metadata block. That flag-driven loop is a classic place for complexity to accumulate, since each new markdown feature adds another flag and another skip condition.

<MetricBar label='Fan-out' value='79' threshold='15' max='90' />

The file has a bug-fix rate of 27.9%, 2 reverts, and 23 distinct authors in the last 90 days, the widest ownership spread in this set. Those are context for review priority, not proof that this function is defective. I would extract the per-event handling into separate functions per block kind (code, image, HTML, Mermaid, metadata) and replace the cluster of booleans with an explicit state enum, so that the combinations that cannot occur become unrepresentable.

### `run_turn_internal` — thread.rs

<FunctionCard fn='run_turn_internal' file='crates/agent/src/thread.rs' risk='3.67' band='active' cc='53' nd='4' fo='17' touches='236' />

`run_turn_internal` has the most touches of the five at 236 in the last year, with a last change 2 days ago, a cyclomatic complexity of 53, and a nesting depth of 4. It is an async function running a loop that checks for cancellation, performs compaction when needed, and handles errors by downcasting to a completion error type and retrying with an attempt counter. The excerpt shows telemetry updates repeated inside several nested match arms, and it tracks a refusal-fallback model across loop iterations.

I read this as retry, cancellation, compaction, and telemetry concerns braided into one loop. The file has 2 reverts, a bug-fix rate of 16.1%, 15 distinct authors in the last 90 days, and a review-comment density of 4, the highest in the set. Because the loop carries state across iterations in an async context, a cancellation or error path that is slightly off is easy to introduce and hard to spot in review. My recommendation is to pull the compaction-error handling into its own async helper that returns a single outcome enum, and to centralize the repeated telemetry-outcome emission so each exit path calls one function.

### `from_chunks` — element.rs

<FunctionCard fn='from_chunks' file='crates/editor/src/element.rs' risk='3.66' band='active' cc='31' nd='7' fo='24' touches='212' />

`from_chunks` has the lowest cyclomatic complexity of the active four at 31, but its nesting depth of 7 is the deepest in the set, and it has the strongest historical signals: 3 bug-linked commits, a bug-fix rate of 25%, and 9 reverts across 212 commits, with the last change 0 days ago. For an editor line layout builder, that is the combination I would weight most heavily. Deep nesting makes it hard to hold the state in your head, and the excerpt shows why: it manages a growing set of mutable accumulators (line text, byte offsets, styles, fragments, width, row) while looping over highlighted chunks and branching on replacements, inlays, and length limits.

The revert count of 9 is the highest in the data, and I would not read it as a defect claim, but it does mean changes here have been undone before. I would flatten the nesting by extracting the replacement-chunk path (flush the pending text line, then handle the renderer case) into a helper, using early continues in the main loop. Getting the depth from 7 to 4 would be a meaningful readability win before the next feature lands.

### `imitate_human_edits` — split_commit.rs

<FunctionCard fn='imitate_human_edits' file='crates/edit_prediction_cli/src/split_commit.rs' risk='1.99' band='quiet' cc='64' nd='6' fo='28' touches='19' />

This one is a different kind of finding. `imitate_human_edits` has a cyclomatic complexity of 64, a nesting depth of 6, and a fan-out of 28, but it has 19 touches in the last year, hasn't been changed in 156 days, and has 0 distinct authors in the last 90 days. That makes it quiet, structural debt with a high blast radius when someone next opens it, not a live regression risk. It sits in the edit prediction CLI and, per the excerpt, parses two unified diffs, locates the first edit, and then walks through a long series of guard checks that each return the unchanged inputs before tokenizing and diffing the lines.

The repeated early-return pattern accounts for much of the complexity. The file shows no bug-linked commits, no reverts, and a bug-fix rate of 15.8%. I would not prioritize it ahead of the four active functions, but I would split the guard-clause section into a separate function that returns the validated source and target lines, so the next person to touch the splitting logic starts from a smaller function.

## Where to start

If I had one week, I would split `handle_thread_event` first, because it has the highest activity-weighted risk score at 3.75 and the arms are already naturally separable. Next I would flatten `from_chunks`, since its 9 reverts and nesting depth of 7 make it the most fragile-looking of the four active functions. Then I would take `request_layout` and `run_turn_internal`, where state flags and mixed concerns are the main problem. `imitate_human_edits` can wait for the next time someone works on edit prediction tooling.
