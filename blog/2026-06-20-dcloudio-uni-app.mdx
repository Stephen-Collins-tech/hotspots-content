## Large Repo Analysis

uni-app is a large repository. To stay within memory constraints, this analysis used **hybrid touch mode**: structural complexity — CC, ND, FO — is measured precisely for every function. Git activity is tracked at the function level (via `git log -L`) only for files with 5 or more commits in the last 30 days; other files use a file-level approximation. Rankings therefore surface functions that are both structurally complex and in the most actively-changing parts of the codebase. Dormant code with high structural complexity will rank lower than it would under a full per-function analysis — to surface it, run `hotspots analyze . --per-function-touches` on a machine with sufficient memory.

## Codemod / Tooling Files in Results

Two of the five top hotspots — `verify$1` and `parse` in `src/uni_modules/uni-pay-x/uniCloud/cloudfunctions/uni-pay-co/libs/jsonwebtoken.js` — are functions inside a fully inlined, minified bundle that concatenates `jsonwebtoken`, `jws`, `jwa`, `semver`, and several lodash utilities into a single file. The third hotspot `lt` in `uni-config-center/index.js` is similarly a compiled artifact embedding lodash merge and semver. Their high complexity scores reflect the inherent branching in those upstream libraries, not authored application logic. To remove them from future analyses, add the following to `.hotspotsrc.json`: `{ "exclude": ["**/libs/jsonwebtoken.js", "**/uni-config-center/index.js"] }`. ## Top 5 Hotspots

### `createOrder` — pay.js

<FunctionCard fn='createOrder' file='src/uni_modules/uni-pay-x/uniCloud/cloudfunctions/uni-pay-co/service/pay.js' risk='16.82' band='debt' cc='59' nd='5' fo='22' touches='0' />

`createOrder` is the entry point for initiating a payment order in uni-pay-x's cloud function layer. Based on the source excerpt, it accepts a large destructured parameter object covering provider type, payment amounts, order identifiers, client context, cloud context, and provider-specific virtual payment fields for both WeChat Pay and Apple IAP. The function is flagged as both a `god_function` and a `long_function`, and the structural numbers bear that out: a cyclomatic complexity of 59 means there are at least 59 independent execution paths through the function, every one of which is a required test case.

The nesting depth of 5 is visible in the excerpt: provider-type guards (`wxpay-virtual`, `appleiap`, and a catch-all else) each contain their own nested field validations, and those sit inside a larger validation preamble before the actual order creation logic begins. The fan-out of 22 means the function reaches out to 22 distinct callees — config accessors, DAO methods, library utilities, and error constant lookups — so any refactoring of those dependencies has a direct path to this function.

<MetricBar label='Cyclomatic Complexity' value='59' threshold='10' max='70' />

The external signals show only a single commit touching this file and zero bug-linked commits or reverts — there is no historical defect signal here. But the `complex_branching` and `deeply_nested` patterns, combined with the `exit_heavy` classification (the function throws structured error objects at eight or more guard points before reaching business logic), mean that any future contributor extending payment provider support will be working inside one of the hardest functions in the entire repo.

My recommendation: extract the per-provider validation blocks into standalone validator functions — one for `wxpay-virtual`, one for `appleiap`, and one for standard fee-based providers. That alone would reduce the cyclomatic complexity by roughly 15–20 paths and collapse the nesting depth from 5 to 3. The remaining order-creation logic can then be read without first parsing the full provider dispatch tree.

### `verifyReceiptFromAppleiap` — pay.js

<FunctionCard fn='verifyReceiptFromAppleiap' file='src/uni_modules/uni-pay-x/uniCloud/cloudfunctions/uni-pay-co/service/pay.js' risk='14.19' band='debt' cc='27' nd='3' fo='24' touches='0' />

`verifyReceiptFromAppleiap` handles Apple In-App Purchase receipt verification against Apple's StoreKit v1 API. The source excerpt shows the function: resolves an order record by either `out_trade_no` or `appleiap_account_token` (with a token case-normalization step and a DAO lookup), then builds and signs a JWT using an ES256 private key read from disk, constructs the App Store Connect API URL, and makes an HTTP request with a retry loop of up to 5 attempts on failure.

That retry loop is itself a complexity contributor — it adds a try/catch inside a `for` loop, contributing to the cyclomatic complexity of 27. The fan-out of 24 covers DAO access, the `jsonwebtoken` library, Node's `fs` module, `uniCloud.request`, config accessors, and multiple error-constant lookups. The `god_function` and `long_function` flags are accurate: this function owns the full lifecycle from order lookup through JWT issuance through HTTP request through response parsing.

<MetricBar label='Cyclomatic Complexity' value='27' threshold='10' max='35' />

The `exit_heavy` pattern is visible in the multiple early-return paths: silent returns with `errCode: 0` when `out_trade_no` cannot be resolved, throws when `payOrderInfo` is missing, and a series of status-code checks on the Apple response. Each of these is a distinct test scenario that requires a separate mock setup.

I would split this function at the JWT-generation boundary: extract a `buildAppleJWT(config)` function and a `requestAppleTransaction(url, token)` function with the retry logic. The order-lookup preamble could become a shared `resolveAppleOrder(data)` helper also used by any future re-verification flow. That decomposition would bring the remaining orchestrator function below CC 10.

`verify$1` is the JWT verification function from a bundled copy of the `jsonwebtoken` npm package, inlined into `libs/jsonwebtoken.js`. The source excerpt confirms this: it contains the full `verify` implementation including `JsonWebTokenError`, `NotBeforeError`, `TokenExpiredError` class definitions, HMAC and RSA signer/verifier factories, ECDSA signature formatting, and the complete semver library — all concatenated into one file.

A cyclomatic complexity of 41 on `verify$1` specifically reflects the JWT spec's own branching requirements: algorithm whitelist checks, signature presence checks, `nbf` / `exp` / `aud` / `iss` / `sub` / `jwtid` / `nonce` / `maxAge` claim validations, and both synchronous and callback-based execution paths. The fan-out of 19 covers the JWS decode/verify pipeline, error constructors, timespan utilities, and lodash type-check helpers.

This is a vendored file. The analysis correctly identifies high structural complexity, but the right response is exclusion rather than refactoring — see the vendor note.

### `parse` — jsonwebtoken.js

<FunctionCard fn='parse' file='src/uni_modules/uni-pay-x/uniCloud/cloudfunctions/uni-pay-co/libs/jsonwebtoken.js' risk='13.73' band='debt' cc='69' nd='3' fo='2' touches='0' />

`parse` is the semver version-string parser bundled inside the same `libs/jsonwebtoken.js` artifact. With a cyclomatic complexity of 69 it is the most structurally complex individual function in the top five — the semver `parse` function contains a large regex match followed by a switch-case over every recognized time unit string (`years`, `yrs`, `yr`, `y`, `weeks`, `week`, `w`, `days`, …, `milliseconds`, `msecs`, `msec`, `ms`), each branch returning a scaled numeric value. That switch statement alone accounts for most of the 69 paths.

<MetricBar label='Cyclomatic Complexity' value='69' threshold='10' max='75' />

The fan-out of only 2 distinguishes this from the other top functions — `parse` is relatively self-contained, calling only `String()` and `parseFloat()`. The `exit_heavy` pattern comes from the early-return on strings longer than 100 characters and the default case returning `undefined`. At CC 69 this would normally be an immediate refactoring target, but again this is bundled third-party code. Excluding `libs/jsonwebtoken.js` from analysis is the correct first step.
