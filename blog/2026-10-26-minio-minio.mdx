### `combineCrossVer` — docs/debugging/xl-meta/main.go

The activity-weighted risk score is 19.65, with a cyclomatic complexity of 224 and a nesting depth of 10. The function hasn't been changed in 167 days and has zero touches in the last year. Anything above 100 is already extreme on the usual scale; 224 means a huge number of independent paths, each one a potential bug surface and a path that needs a test.

From the excerpt, the function takes a map of file names grouped by version, indexes them by part number, then loops through parts, versions, and blocks, reading and mapping data, comparing against other versions, and merging previously gathered 'global' block data. The visible nesting includes labeled loops (`nextFile`, `nextAttempt`, `compareFile`) with `continue` and `break` jumping between levels. Labeled control flow at that depth is hard to reason about, because a single `continue nextFile` can skip a lot of surrounding logic.

The file path matters for framing: this lives under docs/debugging, so it looks like a diagnostic utility for inspecting xl.meta data, not part of the server request path. File-level history is thin, with 3 total commits, no bug-linked commits, no reverts, and a bug-fix rate of 0%. I would treat this as maintainability debt rather than a quality concern. My recommendation is concrete: split the function along the loop boundaries visible in the excerpt. One extractor builds the part index, one reads and maps a block, and one merges shared data into the filled-block state. That alone would bring the nesting depth of 10 down to something a reviewer can hold in their head.

### `SiteReplicationMetaInfo` — cmd/site-replication.go

<FunctionCard fn='SiteReplicationMetaInfo' file='cmd/site-replication.go' risk='18.59' band='debt' cc='163' nd='6' fo='48' touches='0' />

This one scores 18.59, with cyclomatic complexity of 163, nesting depth of 6, and fan-out of 48. It hasn't been changed in 167 days. Unlike `combineCrossVer`, it sits in the server's `cmd/` package and belongs to the site replication subsystem, which synchronizes configuration between deployments.

The excerpt shows a long run of near-identical blocks. For each bucket, the code checks whether a configuration blob (tagging, versioning, object lock, quota, encryption, and more) is non-empty, base64-encodes it, assigns it to a field on a bucket-info struct, and copies over an updated-at timestamp. That is repetition more than genuine branching, and I suspect much of the 163 comes from this pattern repeated across bucket, policy, IAM, and other entity types. A fan-out of 48 means a change here touches a wide surface of collaborators.

File-level history shows 5 total commits, a bug-fix rate of 20%, no reverts, and a review-comment density of 1.0. One in five commits being a bug fix is modest, but it is a nonzero historical signal, and it puts this function slightly ahead of `combineCrossVer` in review priority despite the nearly identical score. I would replace the repeated 'if non-empty, encode, assign, copy timestamp' blocks with a small table-driven helper, then split the per-entity sections (buckets, policies, users, groups) into separate functions. Because there is an early error path and multiple return branches, each extracted piece needs its own error-path tests.

### `StartFromSource` — cmd/batch-handlers.go

The number that stands out is the fan-out of 66, the highest in this set, next to a cyclomatic complexity of 58 and a nesting depth of 6. The function hasn't been changed in 295 days, and it carries the stale-complex flag. It is a method on a batch replication job, and it starts a job that replicates from a source.

The excerpt shows job initialization, retry and delay defaults, a seeded random source, and a large inline `skip` closure that evaluates age, creation-time, tag, and metadata filters against each object. That closure is essentially a filter engine embedded inside a job runner. With 66 distinct callees, the function is coupled to the object layer, metrics, tagging, header helpers, and more, so a change to any of them can ripple into it.

History is light: 4 total commits and a bug-fix rate of 25%, with no reverts. I would lift the `skip` closure into a named filter type with its own unit tests, since it is the most self-contained piece and the part most likely to change when filter options are added. After that, the retry-and-delay handling can become a small helper, leaving the job loop itself readable.

### `CreatePoolEndpoints` — cmd/endpoint.go

<FunctionCard fn='CreatePoolEndpoints' file='cmd/endpoint.go' risk='18.33' band='debt' cc='94' nd='6' fo='44' touches='0' />

Cyclomatic complexity 94, nesting depth 6, fan-out 44, and 295 days since the last change. The name and excerpt indicate this builds the endpoint list for each server pool at startup. It validates the layout, checks that the listen address is valid for the host, handles a single-drive setup as a special case, then converts layout arguments into endpoints, assigning pool, set, and disk indexes and checking for cross-device mounts.

The excerpt shows a sequence of guard clauses returning errors, followed by nested loops over pools, sets, and disks. That explains why exit-heavy appears in the pattern list: nearly every step has its own error return, and each one needs a test. Startup code like this has its own risk profile. A mistake here could affect whether a node comes up or how drives are assigned.

File-level history is the quietest in the set: 2 total commits, a bug-fix rate of 0%, no reverts. I would call this pure maintainability debt. A sensible first split pulls the single-drive branch into its own function and the per-pool endpoint construction into another, leaving `CreatePoolEndpoints` as an orchestrator that runs the validation steps in sequence.

### `streamMetadataParts` — cmd/metacache-set.go

<FunctionCard fn='streamMetadataParts' file='cmd/metacache-set.go' risk='18.06' band='debt' cc='77' nd='6' fo='31' touches='0' />

Cyclomatic complexity 77, nesting depth 6, fan-out 31, and 295 days since the last change, with the stale-complex flag. It is a method on the erasure-coded object layer in the metadata cache listing code, and the excerpt shows an unbounded retry loop around reading metadata parts from disks.

This is the function where I would be most careful, and the metrics alone understate why. The excerpt shows a retry counter incremented in several places, reset to 1 in one branch and set to -1 in another, plus sleeps of different lengths, a local `retryWait` closure, context-cancellation checks, a periodic cache-state check after many failures, and a type switch on error kinds. State mutated from that many places is hard to verify by reading. Go adds a concurrency dimension that structural metrics do not capture: the code comments note that operations run without locks and must tolerate failures, so correctness depends on timing and disk state as well as branching.

File-level history shows 5 total commits and a bug-fix rate of 40%, the highest in this set, with no reverts. Two of five commits being fixes is not proof of a defect in this function, since the signal is file-level, but combined with the retry-counter manipulation it earns the strongest review priority of the five from me. I would pull the retry policy (counter, delays, reset rules) into a small type with explicit methods, so the loop body stops mutating a bare integer in several branches, and then test the retry transitions directly.

**What the five have in common**

None of these functions has been touched in the last year, and they share a shape: long top-to-bottom orchestration with many early returns. Functions like this gather branches whenever a new option or edge case appears. The risk is not that the maintainers wrote them badly. It is that the next edit lands on a large, dormant function, and any one of them will be edited the day a new replication option, filter, or disk-layout rule arrives. I would schedule the refactoring before that day, not during it.
