Four of the top five hotspots in rancher/rancher sit in a single file, pkg/settings/setting.go, which was touched 80 times in the last year, most recently 7 days ago, by 14 distinct authors in the last 90 days. That is a whole module under constant change, not one function to fix, and anyone editing it is working in a file under constant change. The repository has 6,290 functions, 1,703 of them in the critical band, and the fifth hotspot, `Create` in pkg/ext/stores/kubeconfig/store.go, is where the structural risk actually concentrates: a cyclomatic complexity of 128 and fan-out of 62 in code touched 22 times in the last year.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `GetMachineProvisionImagePullPolicy` — setting.go

<FunctionCard fn='GetMachineProvisionImagePullPolicy' file='pkg/settings/setting.go' risk='2.75' band='high' cc='8' nd='1' fo='3' touches='80' />

This is the top-ranked function in the list, with an activity-weighted risk score of 2.75, and its structure is modest: cyclomatic complexity of 8, nesting depth of 1, fan-out of 3. From the source excerpt, it reads a setting, switches over the Kubernetes pull policy values, and falls back to Always with a logged warning when the value does not parse. That is a flat switch with a default branch, which is about as readable as branching gets. The risk here comes from the file's activity, not from the function's shape: 80 touches in the last year, last changed 7 days ago, and a bug-fix rate of 8.75% across the file's 80 commits, with no bug-linked commits and no reverts recorded. It is an active function in the high band, so it bears watching rather than refactoring. I would not refactor it. I would put a table-driven test around the three valid values and the fallback so that the next edit to the file cannot silently change the default.

**`GetQuantityAsInt64` and `GetDuration` — setting.go**

<FunctionCard fn='GetDuration' file='pkg/settings/setting.go' risk='2.69' band='high' cc='5' nd='1' fo='3' touches='80' />

I am grouping these because they share a pattern: each reads a setting's string value, parses it into a typed result, and handles the parse failure. `GetDuration` logs the error, then retries with the setting's default, and returns zero if the default also fails. `GetQuantityAsInt64` wraps a Kubernetes quantity parse error and returns the caller-supplied fallback if the quantity does not fit in an int64. Both have a cyclomatic complexity of 5 and nesting depth of 1, so they are easy to read. The two functions handle failure differently, though: one swallows it into a log line and a zero value, the other returns an error to the caller. In a file where 14 distinct authors have committed in the last 90 days, that inconsistency is the kind of thing that drifts. My recommendation is to settle on one convention for typed getters, document it at the top of the file, and cover each getter with a malformed-value test.

### `Create` — kubeconfig/store.go

This is the function I would start with. Its cyclomatic complexity of 128 is far past the 100 mark I treat as extreme, its fan-out of 62 means it calls 62 distinct functions, and the file was touched 22 times in the last year, most recently 11 days ago. It is an active, critical-band function. The source excerpt shows why the path count is so high: the function resolves the calling user, rejects non-Rancher users, requires a request token ID and fetches the token, type-asserts the object to a kubeconfig, runs create validation, checks cluster uniqueness, and then works through default and maximum token TTL handling in a switch before moving on to server URL parsing. Each of those steps has its own error return, so the Go convention of explicit error branching multiplies the path count. The file's history gives this some weight: a bug-fix rate of 31.82% across 22 commits and one recorded revert. Those are file-level signals and do not prove a defect in `Create`, but combined with the complexity they move it to the front of the review queue. My concrete recommendation is extract-method along the seams already visible in the code: pull authentication and token resolution into one helper, TTL computation and validation into another, and the remaining kubeconfig assembly into a third. The TTL switch is the cleanest first cut because it takes plain values and returns a value or a bad-request error, so it can be unit-tested without any Kubernetes plumbing. That single extraction would remove a visible chunk of the branching.

## Where to start

I would start with `Create` in pkg/ext/stores/kubeconfig/store.go: split out the TTL logic first, then the authentication steps. For setting.go, I would not refactor anything. Instead I would add malformed-input tests for the typed getters, log the silent failure path in `init`, and agree on one error-handling convention across the getters, because the risk there comes from how many people are editing the file, not from how hard any single function is to read.
