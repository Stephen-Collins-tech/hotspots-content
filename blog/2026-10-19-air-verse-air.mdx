### `proxyHandler` — proxy.go

<FunctionCard fn='proxyHandler' file='runner/proxy.go' risk='15.58' band='fire' cc='47' nd='3' fo='34' touches='1' />

<MetricBar label='Cyclomatic Complexity' value='47' threshold='10' max='60' />

This is the function I would look at first. Its activity-weighted risk score is 15.58, it was touched once in the last year, and that change was 25 days ago. That makes it a live regression risk rather than a backlog item. The excerpt shows why the numbers are what they are: one handler builds the upstream URL, parses the form, constructs the outgoing request, copies and filters headers, sets forwarding and Via headers, runs a retry loop until the app comes back up after a restart, copies response headers, and then branches on whether the response is streaming or non-HTML. Request preparation, retry policy, and response rewriting all live in a single function.

The nesting depth of 3 is not the problem. Breadth is: 47 independent paths and 34 distinct callees, with several early exits via `http.Error`. Each of those exits is a test case, and a fan-out of 34 means a change to any of the calls it makes can affect behaviour here.

The file-level history adds context. The file has 7 commits in total, 71% of them tagged as bug fixes, with no reverts, no commits linked to bugs, and a single author in the last 90 days. A bug-fix rate that high on a small commit history is a reason to give this file stronger review priority, though it is not evidence that this specific function is broken.

I would split along the seams the code already shows: one function to build the outbound request, one to wait for the app with the timeout and retry logic, and one to copy and filter response headers. The retry loop is the easiest piece to extract first and test in isolation, because it has a clear input (a request and a timeout) and a clear failure mode (context expiry).

### `preprocess` — config.go

<FunctionCard fn='preprocess' file='runner/config.go' risk='14.95' band='debt' cc='45' nd='3' fo='22' touches='0' />

`preprocess` scores 14.95, nearly the same as `proxyHandler`, but the risk is a different kind. It has 0 touches in the last year, so this is structural debt with a high blast radius when it is next modified, not a function under live churn. With a cyclomatic complexity of 45 and a fan-out of 22, it sits in the startup path. The excerpt shows it applying command-line overrides, changing directory from an environment variable, expanding the root path, refusing dangerous root directories, defaulting temp and test-data directories, resolving the entrypoint binary, normalizing include directories and rules, appending runtime arguments, and compiling exclude regexes.

The file-level history here is the busiest of the five: 30 commits in total, a bug-fix rate of 43%, one commit linked to a bug, and 2 reverts. Two reverts on a file this central is a signal I would weigh when planning review effort. Config loading runs for every user on every start, so a mistake here has wide reach.

The function is a sequence of independent normalization steps, which makes it a good candidate for extract-method. I would group the steps into path resolution, defaults, rule normalization, and regex compilation, each returning an error to a short orchestrating function. Pin current behaviour with tests first, especially the dangerous-root check and its override flag, since those branches change what the tool refuses to do.

**`buildRun` and `runBin` — engine.go**

These two share a file, a history, and a dormancy profile, so I am treating them together. Both have 0 touches in the last year and were last changed 97 days ago, which puts them firmly in the 'debt' quadrant. The file has 17 commits in total with a bug-fix rate of 65%, no reverts, no commits linked to bugs, and no distinct authors in the last 90 days.

<FunctionCard fn='buildRun' file='runner/engine.go' risk='13.47' band='debt' cc='23' nd='3' fo='13' touches='0' />

`buildRun` has an activity-weighted risk score of 13.47. Its excerpt shows a per-build stop channel used as a token through a semaphore-style channel, two select checks against the stop and exit channels (one before the pre-command, one after the build), and error branches for the pre-command and the build that behave differently depending on whether the config says to stop on error. A cyclomatic complexity of 23 is manageable on its own. The risk is the combination of channel synchronization and several early returns. Structural metrics cannot see ordering problems between goroutines, so I would want race-detector tests around the stop-token handling before anyone edits it.

A concrete first step is to pull the repeated 'did someone ask me to stop' select into a small helper. That removes duplicated control flow and leaves the build sequence readable as a list of steps.

<FunctionCard fn='runBin' file='runner/engine.go' risk='13.35' band='debt' cc='13' nd='3' fo='29' touches='0' />

`runBin` scores 13.35 with a fan-out of 29 against a cyclomatic complexity of only 13. The excerpt explains the gap: it defines a kill closure that returns a shutdown channel, spawns a goroutine that selects between a shutdown request and process exit, takes a lock to clear the stop channel, and attempts to kill the command, then launches a second goroutine that loops starting the process. Two nested goroutines, closures, and several channels in one function mean the complexity lives in the interactions, not in the branch count. That is where I would be most careful, because a cyclomatic complexity of 13 understates how hard this is to reason about.

I would promote the kill closure to a named method that takes its dependencies explicitly. That makes the shutdown protocol testable on its own, and it shrinks the outer function enough that the start loop can be read without the shutdown logic in the way.

Because both functions live in the same untouched file, I would plan the work as one change: tests around stop and exit behaviour first, then the extractions.

### `ruleMatches` — rule.go

<FunctionCard fn='ruleMatches' file='runner/rule.go' risk='13.29' band='debt' cc='25' nd='3' fo='9' touches='0' />

`ruleMatches` scores 13.29 with a cyclomatic complexity of 25 and a fan-out of 9, has 0 touches in the last year, and was last changed 39 days ago. It is the cleanest case of the five: the file has 1 commit in total, no bug-fix history, and no reverts. With nothing in the history suggesting trouble, I would frame this as maintainability debt, not a defect risk.

The excerpt shows a sequence of filters: an include-directory check, exclusion by compiled regex, a shortcut when no extensions or files are configured, extension matching with a wildcard, and finally an exact relative-file match. Each filter has its own early return, which is the exit-heavy pattern in practice, and each return is a case a test must cover: directory miss, regex exclusion, empty include lists, extension hit, wildcard, file hit, and no match at all.

The low-effort improvement is a table-driven test with one row per exit, and a split of the function into a directory predicate and an extension-or-file predicate. That brings the complexity of each piece well below the point where I would worry about it.
