My last post was about auditing hotspots' own scoring formula against a year of confirmed research and getting three things wrong along the way before getting them right. I said then that writing down what you actually checked — including the parts you got wrong — is the standard this project holds itself to. This post is the next installment of that same ledger: three weeks of CLI releases, and a research thread that spent its time trying to break its own test harness before trusting its own results.

## The CLI side: 2.0, then 2.1, then 2.2

v2.0.0 is the big one. The short version: hotspots' JSON output — snapshot, diff, coordinate, the `--axes` flag — used to be several independently-shaped payloads that had each grown their own quirks over time. 2.0 folds all of them into one versioned envelope. That's a breaking change by definition, which is why it's a major version and not a quiet patch.

The more interesting part is *why* it was breaking. The scoring-formula audit from my last post wasn't the only drift that turned up that round. A second audit — this time of the schema documentation itself, not the scoring math — found that `shared/snapshot-schema.json` in this very repo described fields the CLI's `build_summary()` function didn't actually emit (`lrs`, a `quadrant` enum, `touches_30d`), and left out one it did emit (`risk_tier`). hotspots-cloud had its own version of the same problem: a `file_churn` field that no longer existed, and a code comment describing gating behavior that had already changed underneath it. Neither was a correctness bug in the CLI — the CLI was fine. The documentation describing it to downstream consumers wasn't.

So 2.0 did two things at once: it removed genuinely dead or unvalidated fields from the live output (`depth_score`, the neighbor-churn score, the never-validated Centrality axis — the same kind of unweighted, non-contributing term the scoring audit flagged last time, just in the output shape rather than the ranking formula), and it closed the loop on documentation drift by adding a golden schema-shape test that fails CI the moment a field quietly disappears, instead of waiting for the next person who happens to notice. There's also a new rule in `CONTRIBUTING.md`: a JSON-output change now has to update this repo, hotspots-cloud, and hotspots-research's consumers in the same release window. The audit found the drift once. The policy is there so I don't have to find it again by accident in another year.

2.1.0 and 2.2.0 are smaller and more ordinary — the kind of releases that don't need a confirmed-research citation to justify. 2.1 adds a `missing_docstring` detection signal and fixes a real crash: C++ content showing up inside a `.h` file (a legitimate, common pattern) was tripping the language detector instead of being skipped cleanly. 2.2, shipped yesterday, adds Astro (`.astro`) language support and drops the stale Centrality reference from the schema docs that 2.0's removal had left behind. None of this touches the scoring formula itself — fan-in and cyclic-dependency are still out, the touch window is still 365 days by default. This round was entirely about making the output honest again, not about changing what the output means.

## The research side: can an LLM safely de-duplicate code across files

While the CLI was catching up on its own documentation debt, hotspots-research was running a much narrower experiment than "can AI refactor code" — because that question is too broad to actually falsify. The question it asked instead: given two files with a genuine, well-scoped chunk of duplicated logic, can an LLM consolidate them into one without changing behavior, verified against the project's real test suite, not a diff that merely looks plausible?

It took six rounds (internally labeled F173 through F178) to get an answer worth trusting, and the most useful parts of the process were the two places it caught itself being wrong.

The first catch was about measurement, not the LLM. An earlier round had logged what looked like two duplication-reduction wins. Adding response-truncation logging — prompted, honestly, by someone just asking a token-usage question — revealed that one of those "wins" had silently truncated mid-response, and the real, untruncated comparison showed the unguided baseline finding the identical fix on its own. No guidance needed, no effect to report. One win became a null result the moment the harness was instrumented to tell the truth about what actually happened.

The second catch was more interesting, because the bug wasn't in the LLM's output at all — it was in the test harness built to grade it. The sharpest version of this test (round six, F178) ran three deliberately narrow cross-file cases against Django: each one scoped specifically to forbid the LLM from creating any new file, so the only way to pass was genuine in-place consolidation. Two of three passed clean, verified against Django's actual test suite (598 and 742 real tests respectively, not a synthetic check). The third failed — and when the failure got traced, it turned out the harness's own file-generation step had silently overwritten an existing Django module and broken two unrelated call sites. Structurally, the LLM's fix looked fine. Correctness-wise, it wasn't, because the tool checking correctness had a collision bug nobody had needed to hit before. That got fixed with an explicit collision check, and the next three cross-file candidates, run through the corrected harness, came back clean — including one case designed specifically to re-create the same failure mode and confirm it was actually gone, not just avoided.

Net result so far: on cleanly-scoped cases — a genuine shared chunk of logic, not two files that merely share a build tag or a sprawling, loosely-related function family — an LLM can reduce duplication across files without regressing behavior, checked against real tests rather than eyeballing a diff. The sample is still small by the research's own standard (single digits of verified non-additive passes), and every well-scoped candidate that didn't meet the bar — a Go build-tag pair, a scattered scikit-learn function family — got rejected before anything was run on it, specifically so the result wouldn't be flattered by only testing the easy cases.

## What this isn't

This isn't an announcement that hotspots is about to auto-fix duplicated code. hotspots-research exists precisely to keep "is this true" and "should we ship this" as two separate questions — the same discipline that, in my last post, caught a research-backed security-mode proposal as a product-fit mistake even though the underlying finding was accurate. A verified capability on a deliberately small, hand-picked set of open-source repos is evidence toward a feature, not a feature. If cross-file duplication-aware suggestions ever land in the CLI, they'll go through the same confirmed-and-promoted path the touch-window change and the fan-in removal went through before they touched the live score.

What I do think is worth saying plainly: the most useful finding from six rounds of this experiment wasn't about whether LLMs can de-duplicate code. It was that the test harness checking the LLM's work had its own uncaught bug, and the only reason that surfaced is that the test was run against a real, 742-test codebase instead of a toy fixture. The caution that applies to AI-written code applies just as directly to AI-adjacent tooling built to grade it.

hotspots v2.2.0 is on npm, PyPI, crates.io, and Homebrew now. The duplication-reduction findings referenced above (F173–F178) are logged in full in `hotspots-research`'s own findings record, including the rejected candidates and the harness bug, for anyone who wants more than fits in a blog post.
