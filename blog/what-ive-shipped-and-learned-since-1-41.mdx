My last post was about auditing hotspots' own scoring formula against a year of confirmed research and getting three things wrong along the way before getting them right. I said then that writing down what you actually checked — including the parts you got wrong — is the standard this project holds itself to. This post is the next installment of that same ledger: three weeks of CLI releases, and what they taught me about a quieter kind of drift.

## 2.0, then 2.1, then 2.2

v2.0.0 is the big one. The short version: hotspots' JSON output — snapshot, diff, coordinate, the `--axes` flag — used to be several independently-shaped payloads that had each grown their own quirks over time. 2.0 folds all of them into one versioned envelope. That's a breaking change by definition, which is why it's a major version and not a quiet patch.

The more interesting part is *why* it was breaking. The scoring-formula audit from my last post wasn't the only drift that turned up that round. A second audit — this time of the schema documentation itself, not the scoring math — found that `shared/snapshot-schema.json` in this very repo described fields the summary output didn't actually emit (`lrs`, a `quadrant` enum, `touches_30d`), and left out one it did emit (`risk_tier`). Downstream consumers had their own version of the same problem: a field that no longer existed, and a code comment describing behavior that had already changed underneath it. Neither was a correctness bug in the CLI — the CLI was fine. The documentation describing it to downstream consumers wasn't.

So 2.0 did two things at once: it removed genuinely dead or unvalidated fields from the live output (`depth_score`, the neighbor-churn score, the never-validated Centrality axis — the same kind of unweighted, non-contributing term the scoring audit flagged last time, just in the output shape rather than the ranking formula), and it closed the loop on documentation drift by adding a golden schema-shape test that fails CI the moment a field quietly disappears, instead of waiting for the next person who happens to notice. There's also a new contributing rule: a JSON-output change now has to update every consumer in the same release window. The audit found the drift once. The policy is there so I don't have to find it again by accident in another year.

2.1.0 and 2.2.0 are smaller and more ordinary. 2.1 adds a `missing_docstring` detection signal and fixes a real crash: C++ content showing up inside a `.h` file (a legitimate, common pattern) was tripping the language detector instead of being skipped cleanly. 2.2 adds Astro (`.astro`) language support and drops the stale Centrality reference from the schema docs that 2.0's removal had left behind. None of this touches the scoring formula itself — fan-in and cyclic-dependency are still out, the touch window is still 365 days by default. This round was entirely about making the output honest again, not about changing what the output means.

## What I'd take from it

Documentation drifts exactly like code does, and nothing fails when it does. A schema doc that lists fields nobody emits is wrong in the same way a scoring term that contributes nothing is wrong: both look fine until someone depends on them. The fix in both cases is the same — pin the shape with a test, and make updating every consumer part of the change rather than a follow-up.

hotspots v2.2.0 is on npm, PyPI, crates.io, and Homebrew now.
