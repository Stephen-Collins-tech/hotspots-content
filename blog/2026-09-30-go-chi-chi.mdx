Three of the top five hotspots in go-chi/chi live in one file: tree.go. That's not a coincidence — it means the routing engine's core matching logic is concentrated risk, not scattered risk. The top function, `findRoute`, carries an activity-weighted risk score of 17.18 and sits in the 'debt' quadrant: 74 branches deep with 7 levels of nesting, but zero touches in the last year and 40 days since its last change. Across 245 analyzed functions, 20 sit in the critical band, and this analysis covers the five that matter most right now. I'd frame the priority here as blast radius, not urgency — this is code that will be expensive to change safely whenever someone next has to touch it.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `findRoute` — tree.go

<FunctionCard fn='findRoute' file='tree.go' risk='17.18' band='critical' cc='74' nd='7' fo='10' touches='0' />

This is the trie-walking route matcher at the center of chi's request dispatch — the function that decides which handler answers an incoming request. A cyclomatic complexity of 74 with nesting 7 levels deep is the highest combination in the dataset, and the source confirms why: a `switch` over node types (static, param, regexp, catch-all) with a nested loop-and-continue pattern searching sibling nodes, multiple early returns once a matching endpoint is found, and inline handling of the 'method not allowed' case. The 'exit_heavy' and 'god_function' tags are earned here — I count returns embedded at three different nesting levels in the excerpt alone, each one a distinct test case a reviewer has to reason through.

It hasn't been touched in 40 days and shows zero commits in the last year, so this isn't a live regression risk today — it's the highest blast-radius function in the repo for whenever the next routing change lands. The file's history shows a bug-fix rate of 8.33% across 12 total commits and 3 distinct authors in the last 90 days, and a fairly high review-comment density (1.67), which tells me past changes here have drawn real scrutiny, not been rubber-stamped. My recommendation: before the next routing feature touches this function, extract the per-node-type matching logic (static / param-regexp / catch-all) into three separate helper functions. That alone would cut the branching a reviewer has to hold in their head at once without changing behavior.

### `patNextSegment` — tree.go

<FunctionCard fn='patNextSegment' file='tree.go' risk='14.72' band='critical' cc='34' nd='5' fo='4' touches='0' />

This one parses a route pattern segment — splitting out `{param}`, `{param:regexp}`, and `*` wildcard syntax — and it's the most dormant complex function in the set: 602 days since its last change. The complexity comes from manually walking brace characters to find a matching `}` (tracking an open/close counter), then branching on regexp-vs-param, then validating wildcard placement with two separate `panic` calls for malformed patterns. That's a hand-rolled mini-parser with cyclomatic complexity 34 and nesting depth 5, sitting in the same 'debt' quadrant as `findRoute` — same file, same low bug-fix history (8.33% across the shared 12-commit, 3-author history), same zero-touches-but-high-consequence profile.

The practical risk here is that a parsing bug in route-pattern syntax would stay silent until someone registers an unusual route. My recommendation: this is a strong candidate for table-driven unit tests covering every branch — regexp param, plain param, tail delimiter variations, and both panic conditions — before anyone refactors it, since the current test coverage isn't visible in this data and the panic-based validation makes untested edge cases genuinely risky.

### `ThrottleWithOpts` — middleware/throttle.go

<FunctionCard fn='ThrottleWithOpts' file='middleware/throttle.go' risk='12.34' band='critical' cc='21' nd='2' fo='10' touches='0' />

This is the constructor for chi's throttling middleware, and it's a genuinely different risk shape than the tree.go trio — it's Go concurrency code, not tree traversal. The excerpt shows a nested `select` over four channel cases (context cancellation, backlog token, immediate token, timeout) with a deferred token-return in three separate branches. Cyclomatic complexity of 21 is moderate on paper, but for concurrent code that number understates the real risk: reasoning about channel interleaving and goroutine scheduling isn't captured by branch counts alone, and a subtle change to one `select` arm can shift ordering guarantees that structural metrics can't see.

It's 'debt' quadrant with zero touches in the last year and 399 days since last change, and the file's bug-fix rate of 25% (from only 4 total commits) is the highest bug-fix ratio in this top five, though on a small commit sample. Fan-out of 10 — matching `findRoute`'s — means this function coordinates a lot of moving pieces: token channels, timers, and the wrapped handler. My recommendation: if this needs a change, pair it with a concurrency-focused test (race detector on, deliberately delayed contexts) rather than relying on the existing test suite's shape, since channel-based logic like this is exactly where unit tests can pass while race conditions slip through.

### `NewCompressor` — middleware/compress.go

<FunctionCard fn='NewCompressor' file='middleware/compress.go' risk='11.37' band='critical' cc='17' nd='4' fo='8' touches='0' />

This is the constructor for chi's response-compression middleware, building the allowed content-type set and registering default encoders (deflate, gzip). The complexity here is mostly straightforward branching — wildcard content-type validation with two `panic` guards, a fallback to a default type list, then sequential encoder registration — giving cyclomatic complexity 17 and nesting 4, tagged simply as 'complex_branching' without the exit-heavy or god-function markers seen elsewhere in this list.

What stands out is the file-level history: a bug-fix rate of 54.55% across 11 commits, plus one recorded revert, the highest of any function in this top five. That's a meaningful signal — not proof this specific function is defective, but strong evidence that middleware/compress.go as a file has had a rockier maintenance history than tree.go or throttle.go. Combined with 3 distinct authors in the last 90 days and a review-comment density of 2.25 (also the highest here), this reads as an area that's drawn disagreement or correction before. This function itself sits at 40 days since its last change, so it's dormant like the rest of the list, but the file around it has been busier than tree.go or throttle.go historically. My recommendation: if you're touching this function, check recent closed issues and PRs against this file specifically before assuming the wildcard-matching logic is settled.

### `findPattern` — tree.go

<FunctionCard fn='findPattern' file='tree.go' risk='11.21' band='critical' cc='19' nd='3' fo='6' touches='0' />

The third tree.go entry, and the most dormant function in the entire top five: 1,073 days since it last changed. It's a recursive pattern-matching walk — the function calls itself (`n.findPattern(xpattern)`) after slicing off a matched segment, with a `switch` over node type and a `panic` on an unrecognized type. Recursion plus a four-way switch is why cyclomatic complexity lands at 19 with fan-out of 6, even though nesting is comparatively shallow at 3.

Three years without a change, on code this central to routing, tells me this logic has proven stable — but it also means nobody currently holds the full mental model of its edge cases fresh in mind. If a change to `findRoute` or `patNextSegment` ever needs a matching update here, budget real review time, not a quick pass.

Taken together, these three functions make tree.go the file I'd flag first for anyone planning routing changes in chi — not because any one function is broken, but because 60% of the current critical-risk list sits behind the same set of imports and shared node types. A change to the trie structure has to be checked against all three.
