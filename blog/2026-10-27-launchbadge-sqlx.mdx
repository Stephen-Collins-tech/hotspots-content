### `explain` — explain.rs

<FunctionCard fn='explain' file='sqlx-sqlite/src/connection/explain.rs' risk='18.75' band='critical' quadrant='debt' cc='231' nd='8' fo='26' touches='0' />

<MetricBar label='Cyclomatic Complexity' value='231' threshold='10' max='240' />

I would start with `explain`. A cyclomatic complexity of 231 is extreme by any reasonable reading, and its nesting depth of 8 and fan-out of 26 mean the paths are both numerous and deep. From the source excerpt, this function runs SQLite's `EXPLAIN` on a query, collects the resulting bytecode program, and walks it with a branch-aware interpreter: a loop over pending branch states, an inner loop over instructions, and a very large `match` over opcode names (`OP_INIT`, `OP_GOTO`, `OP_GO_SUB`, `OP_FK_IF_ZERO` and so on). It also tracks an instruction budget and a per-instruction visit limit to stop runaway loops. That is a mini virtual machine living inside one function.

The pattern flags agree: god function, long function, complex branching, deeply nested, exit-heavy, and stale complex. The stale-complex flag fits the numbers, with 0 touches in the last year and no change in 203 days. Its file-level history is thin, with 2 total commits, a bug-fix rate of 50%, no bug-linked commits, and no reverts. I would not read that as a defect signal; two commits is too small a sample. To me it looks like a function that was written once, largely left alone, and is now hard to extend.

I would split along the structure the excerpt already shows. Move the opcode `match` arms into small handler functions grouped by opcode family, each taking the mutable branch state, and leave `explain` as the driver that sets up the program, loops over states, and dispatches. Most arms appear to mutate registers and the program counter, so a handler signature like `fn(&mut QueryState, &Instruction)` would let each be unit-tested with a hand-built state. That cuts the driver's CC by an order of magnitude and makes per-opcode behavior testable without a live SQLite connection.

### `fmt` — logger.rs

<FunctionCard fn='fmt' file='sqlx-sqlite/src/logger.rs' risk='18.52' band='critical' quadrant='debt' cc='40' nd='8' fo='18' touches='0' />

Second is `fmt` in `sqlx-sqlite/src/logger.rs`, the other half of the same subsystem. From the excerpt, it renders the recorded query-plan history as a Graphviz dot graph: it builds lookup maps from branch operations, iterates over program instructions, emits a cluster per instruction, and diffs states between consecutive steps. Its cyclomatic complexity is 40, nesting depth 8, and fan-out 18, with 0 touches in the last year and 68 days since last change.

The file has 2 total commits, a bug-fix rate of 50%, no reverts, and 1 distinct author in the last 90 days. As with `explain`, I would treat that as thin history rather than evidence of trouble. What stands out is that `fmt` is a `Display` implementation doing a graph-building job, with maps and sets constructed inline before any output is written. I would separate the data preparation (building the state and children maps) from the writing, so the graph model can be tested without string output and the writer becomes a flat loop over a prepared structure. A diagnostic logger is unlikely to sit on a hot path, so the risk is less about runtime than about whether anyone can safely adjust the output format.

### `decode` — array.rs

<FunctionCard fn='decode' file='sqlx-postgres/src/types/array.rs' risk='15.28' band='critical' quadrant='debt' cc='28' nd='5' fo='12' touches='0' />

I am covering the two Postgres `decode` functions together because they share a shape and a status. Both are debt-quadrant, both have 0 touches in the last year, and neither has changed in 409 days. Each has exactly one file-level commit on record, with no bug-linked commits, no reverts, a bug-fix rate of 0%, and no distinct authors in the last 90 days. The history says these files were written and left alone.

In `sqlx-postgres/src/types/range.rs`, `decode` has a cyclomatic complexity of 32 and nesting depth of 6. The excerpt shows it handling two wire formats in one body: a binary branch that reads a flags byte and decodes lower and upper bounds conditionally, and a text branch that walks characters with state variables for quoting, escaping, and element counting. That text branch is a hand-written character state machine, which is where nesting and branch counts pile up. In `sqlx-postgres/src/types/array.rs`, `decode` has a cyclomatic complexity of 28 and nesting depth of 5, and follows the same binary-versus-text split, with binary validation of dimension count, element type, length, and lower bound.

These are Rust trait implementations sitting on the boundary between database bytes and typed values, and the excerpts show buffer reads such as `get_u8` and `get_i32` on slices, plus slicing of strings by index. I cannot tell from the data whether those are guarded elsewhere, but code at an untrusted-input boundary with this many paths is where I would want property-based or fuzz-style tests. My recommendation for both is the same: make the binary and text formats separate private functions, so `decode` becomes a two-arm dispatcher. That halves the path count per function immediately, and in `range.rs` it isolates the character state machine so it can be tested directly against quoted and escaped inputs.

### `parse` — input.rs

<FunctionCard fn='parse' file='sqlx-macros-core/src/query/input.rs' risk='15.26' band='critical' quadrant='debt' cc='14' nd='7' fo='5' touches='0' />

Fifth is `parse` in `sqlx-macros-core/src/query/input.rs`, the outlier in the other direction: a cyclomatic complexity of only 14, but nesting depth of 7 and fan-out of 5. It has 0 touches in the last year and 409 days since last change, with 2 file-level commits, a bug-fix rate of 0%, and no reverts. The excerpt shows a `syn` parser that loops over `key = value` pairs and dispatches on the key through an `if`/`else if` chain: `source`, `source_file`, `args`, `record`, `scalar`, `checked`, with an error for anything else.

This is the function that anchors the CC comparison in my intro. Nesting rather than path count drives its score, so it is a different problem from `explain`. The `record` and `scalar` arms both check for a collision with a prior record type, which is duplicated logic. I would turn the key chain into a `match` on the key string, pull the collision check into a small helper, and consider a builder struct that accumulates the parsed fields. It is a small, low-risk change and a good first refactor on this list, because a procedural macro's input grammar is easy to cover with compile-pass and compile-fail tests.

**What the list tells me**

Exit-heavy is the most common pattern across the repository's flagged functions, at 11, followed by long function at 10 and god function at 6. Multiple return paths burden test coverage: each early return, and each `?` on a fallible call, is a path that needs a case. All five of my hotspots lean on `?`-style early exits, and `explain` pairs that with a very large opcode match.

The fire-quadrant functions outside this top five are a different kind of concern: several MySQL protocol and handshake functions are being edited now, so a bad change there lands immediately. If I were allocating review time this month, I would split it: planned refactoring on `explain` and the two Postgres decoders, and ordinary careful review on the MySQL protocol and handshake changes.
