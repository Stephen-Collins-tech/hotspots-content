### `pkey_private_bytes` — src/rust/src/backend/utils.rs

&lt;FunctionCard fn='pkey_private_bytes' file='src/rust/src/backend/utils.rs' risk='18.11' band='critical' cc='47' nd='7' fo='3' touches='1' /&gt;

This is the top-ranked hotspot in the repository, and the source confirms why. It's a private-key serialization function branching across encoding types (Raw, PKCS8, TraditionalOpenSSL), format checks, password validation, and encryption-algorithm instance checks — a cyclomatic complexity of 47 with nesting reaching 7 levels deep and a fan-out of 3. The `#[allow(clippy::too_many_arguments)]` annotation on the signature itself is a tell: eight parameters feeding a single function that has to validate combinations of encoding, format, and encryption together. It carries one touch in the last 30 days and last changed 19 days ago, and with one author in that period and zero bug-linked commits on the file, this reads as fresh, deliberate work rather than a function accumulating fixes over time. My recommendation: split the Raw-key path, the PKCS8 path, and the TraditionalOpenSSL path into separate helper functions — each currently nested inside one long if-chain, and each independently testable once extracted.

### `write` — src/rust/src/declarative_asn1/encode.rs

&lt;FunctionCard fn='write' file='src/rust/src/declarative_asn1/encode.rs' risk='16.97' band='critical' cc='76' nd='5' fo='13' touches='1' /&gt;

This is the highest cyclomatic complexity in my top five at 76, and the source shows why: it's a match statement over ASN.1 type variants — Sequence, SequenceOf, Set, SetOf, and more — each branch building its own writer closure and iterating over fields. A fan-out of 13 means this one function directly calls into thirteen distinct functions, and the 'god_function' and 'long_function' patterns both flag it. That combination of high fan-out and a large match block means a bug in one ASN.1 type's encoding path is unlikely to be isolated — the function's size makes it hard to verify each branch gets equivalent test coverage. It last changed 19 days ago with one touch in that window and one author, so this reads as active feature work on the declarative ASN.1 encoder, not decay. I'd extract each match arm (`Type::Sequence`, `Type::SequenceOf`, `Type::Set`, `Type::SetOf`, and whatever remains below the excerpt) into named helper functions — that alone would cut the top-level complexity by more than half.

### `_normalize_field_type` — src/cryptography/hazmat/asn1/asn1.py

&lt;FunctionCard fn='_normalize_field_type' file='src/cryptography/hazmat/asn1/asn1.py' risk='16.84' band='critical' cc='40' nd='4' fo='23' touches='1' /&gt;

This is the fan-out outlier of the group: 23 distinct function calls from a single function, the highest of any in my top five. In a duck-typed language, that number understates the real coupling — the function is resolving Python type-hint machinery (`typing.get_origin`, `typing.Annotated`, `typing.get_args`) at runtime against a growing set of ASN.1 field types (TLV, unions, SIZE-constrained types), and each new supported type shape adds another branch here. Cyclomatic complexity of 40 with nesting depth 4 reflects that this function is the central point where every declarative ASN.1 field definition gets validated and normalized before use — which makes it the natural hub for the whole declarative ASN.1 layer's correctness. One touch in the last 30 days and one author in that period puts this squarely in the same recent development wave as `write` above; it also last changed 19 days ago, the same as the others. Given the fan-out, I'd introduce a small dispatch table keyed on field-type category (Annotated, Union/Optional, TLV, root-type) instead of the current sequential if/elif chain — it turns 40 branches into N smaller, independently testable functions.

### `load_pkcs1_vectors` — tests/utils.py

&lt;FunctionCard fn='load_pkcs1_vectors' file='tests/utils.py' risk='16.23' band='critical' cc='73' nd='4' fo='14' touches='1' /&gt;

This is a test-fixture parser, not production crypto code, but its complexity is nearly as high as the production ASN.1 encoder above — cyclomatic complexity 73 driven by a long chain of `line.startswith(...)` checks for PKCS#1 vector-file markers (`# Message`, `# Salt`, `# Seed`, `# Signature`, `# Encryption`, `# Example`), each toggling parser state. The 'exit_heavy' and 'god_function' patterns both apply: it accumulates state across many elif branches and continues/returns scattered through the loop, which makes it hard to know all the ways a malformed vector file could be silently mis-parsed. Because this feeds cryptographic test vectors into the RSA test suite, a subtle parsing bug here could mask a real regression in the RSA implementation rather than catch one. It shares the same one-touch-in-30-days, 19-day-old change pattern as the others, suggesting it was touched in the same recent wave of edits. I'd break the state-machine parsing into a small explicit parser class with named states, replacing the `attr` string-flag pattern with an enum — that removes most of the branching without changing behavior.

### `identify_key_type` — src/rust/src/x509/sign.rs

&lt;FunctionCard fn='identify_key_type' file='src/rust/src/x509/sign.rs' risk='15.62' band='critical' cc='11' nd='8' fo='2' touches='1' /&gt;

This one is the odd shape in the group: cyclomatic complexity is only 11 — moderate by itself — but nesting depth hits 8, the deepest of any function in my top five, despite a fan-out of just 2. The source shows why: it's a straight `if/else if` chain checking `private_key.is_instance(...)` against seven key types (RSA, DSA, EC, Ed25519, Ed448, ML-DSA-44/65/87), and the nesting comes from that structural mismatch between low branching and how the checks are laid out. This function decides which key type a signing operation is dealing with, so it sits upstream of every certificate-signing code path in the file — low fan-out means it isn't calling much, but its result gates behavior elsewhere. One touch in the last 30 days, 19 days since last change, one author in that period — consistent with the ML-DSA post-quantum key types being recently added to this dispatch chain. I'd flatten this into a match on a type-check helper or a lookup table over `(PyType, KeyType)` pairs, since `if/else if` chains that only ever return a variant are a textbook match-statement candidate in Rust.
