### `DialContext` — client.go

I would start with `DialContext` because it combines a cyclomatic complexity of 101 with an activity-weighted risk score of 17.67 and 0 days since last change. It was touched once in the last year, and that touch is recent, so this is actively changing code rather than a backlog item. Fan-out of 41 means it calls 41 distinct functions, and nesting depth of 4 is modest. The complexity here comes from breadth, not depth.

From the source excerpt, the function does a lot of sequential setup: it generates a challenge key, parses the URL, maps the ws and wss schemes to http and https, rejects URLs with user info, builds the HTTP request, copies cookies from the jar, assembles the handshake headers by hand, and rejects duplicate or reserved header names from the caller. The excerpt ends in compression negotiation, and the metrics indicate much more follows. Nearly every step has its own error return, which fits the exit-heavy pattern. The long-function and god-function patterns both fire, and I read that as one function owning URL validation, request construction, header policy, and connection setup.

The file-level history adds some context without proving anything about this function. The file has 22 commits in total, a bug-fix rate of 22.7%, 2 reverts, and no commits directly linked to bugs. Review comment density is 3.25.

My recommendation is extract-method along the seams already visible in the excerpt: one function for URL and scheme normalisation, one for building the handshake request headers, and one for the connection and response handling that follows. Each extraction can be pinned with the existing behaviour first, since the header-rejection rules are exactly the kind of logic that breaks quietly. Because this function is changing now, I would do this before the next feature lands in it, not after.

### `advanceFrame` — conn.go

<FunctionCard fn='advanceFrame' file='conn.go' risk='15.39' band='debt' cc='84' nd='3' fo='24' touches='0' />

`advanceFrame` has a cyclomatic complexity of 84, nesting depth of 3, and fan-out of 24, and it hasn't been changed in 256 days. It is structural debt with a high blast radius when next touched, not something under active churn. Its activity-weighted risk score of 15.39 comes with 0 touches in the last year, so the number reflects how hard the function is to change safely, not how often it is changing.

The excerpt shows a read-side frame parser. It skips the remainder of the previous frame, reads and decodes the first two header bytes, checks the reserved bits against whether compression is enabled, validates opcode rules separately for control, data, and continuation frames, checks the mask bit against whether the connection is a server, and then moves on to the payload length encoding. It accumulates protocol errors in a list and reports them together, which is a deliberate debugging choice, but it also means many conditions feed one exit. The stale-complex, exit-heavy, god-function, and long-function patterns all apply.

The file-level signals for conn.go are the same as for `WriteControl`: 31 total commits, a bug-fix rate of 32.3%, 3 reverts, and review comment density of 3.08, with no commits directly linked to bugs. That is a higher bug-fix rate than the dial path, and I would treat it as a reason to prioritise review, not as evidence of a defect in this function.

The excerpt is already organised into numbered steps in its comments, which makes the extraction plan straightforward: a header-flag decoder, a frame-type validator that returns the collected errors, and a length decoder. Because this function is not changing, I can do that refactor deliberately and with a thorough test set, rather than under time pressure.

### `echoReadAll` — examples/autobahn/server.go

<FunctionCard fn='echoReadAll' file='examples/autobahn/server.go' risk='14.68' band='debt' cc='31' nd='4' fo='13' touches='0' />

`echoReadAll` has a cyclomatic complexity of 31, nesting depth of 4, fan-out of 13, and 2350 days since last change. This is the most dormant function in my top five, and it lives in an example server for the Autobahn test suite, not in the library itself.

The excerpt shows an echo loop that reads a message, checks text payloads for valid UTF-8, then branches on two boolean parameters into three write strategies: a plain message write, a prepared-message write, or a streaming writer. Almost every branch logs and returns on error. The complex-branching and exit-heavy patterns match what I see: the two flags multiply the paths. Three thin wrappers (`echoReadAllWriter`, `echoReadAllWriteMessage`, `echoReadAllWritePreparedMessage`) call it with different flag combinations.

Because it is example code with no changes in over six years, this is a low-urgency cleanup. If anyone does touch it, splitting the three write strategies into separate functions would make the flags unnecessary and cut the branching substantially. The file-level history is small, with 7 commits, a bug-fix rate of 28.6%, and 2 reverts, so I would not read much into it.

### `WriteControl` — conn.go

<FunctionCard fn='WriteControl' file='conn.go' risk='13.96' band='debt' cc='29' nd='3' fo='16' touches='0' />

`WriteControl` has a cyclomatic complexity of 29, nesting depth of 3, fan-out of 16, and hasn't been changed in 226 days. It sits at the edge of what I would call high complexity, and the interesting part is the concurrency, which the metrics cannot capture.

The excerpt shows it validating the message type and payload size, building the frame bytes (with a masking branch for the client side), and then acquiring a write lock through a channel. The lock acquisition has three variants: block with no deadline, fail fast if the deadline has passed, or try the lock and fall back to a timer. After that it checks a shared write error under a mutex, sets the write deadline, writes the frame, and records a close-sent state for close messages. In Go, that channel-and-timer interplay is where subtle bugs tend to live, and a cyclomatic count of 29 understates it. The god-function, exit-heavy, and stale-complex patterns apply.

The file history matches `advanceFrame`: 31 commits, a bug-fix rate of 32.3%, and 3 reverts. My recommendation is to extract the lock-acquisition-with-deadline logic into its own function, which isolates the most concurrency-sensitive part and can be tested with deadline and contention cases directly.

### `main` — examples/echo/client.go

<FunctionCard fn='main' file='examples/echo/client.go' risk='13.36' band='debt' cc='17' nd='3' fo='19' touches='0' />

The echo client's `main` has a cyclomatic complexity of 17, nesting depth of 3, fan-out of 19, and 278 days since last change. It is the fifth-ranked function, and the contrast with `DialContext` is the point of this list: a CC of 17 is moderate, while 101 is extreme.

The excerpt shows an example program with a reader goroutine, a ticker-driven write loop, and a select that handles done, tick, and interrupt cases, including a clean close handshake with a timeout. The complexity comes from the select-based structure and the error handling in each case. The god-function, exit-heavy, and stale-complex patterns are flagged, but this is demonstration code and the structure mirrors what it is demonstrating. I would leave it alone unless it needs to grow, and if it does, extracting the shutdown sequence into a helper is the first move. The file has only 4 commits, with 1 revert and a bug-fix rate of 25%, which is too little history to draw conclusions from.

**What I would do first**

Two things stand out when I read the list as a whole. First, the library code that matters (`DialContext`, `advanceFrame`, `WriteControl`) falls into two different situations: one is changing now, and the other two are dormant. I would split `DialContext` first because it is the only one where complexity and activity coincide. Second, two of the five are example programs, which suggests that excluding or deprioritising `examples/` would make the top of the list more representative of the library itself.
