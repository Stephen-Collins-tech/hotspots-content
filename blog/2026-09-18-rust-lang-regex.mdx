Across 3,575 functions and 216 flagged critical, the sharpest concentration of risk in rust-lang/regex sits in the search implementations under `regex-automata/src/hybrid/search.rs` and its DFA sibling — three of my top five hotspots come from this pair of files, two of them from the hybrid version alone. The top-ranked function, `find_fwd_imp` in the hybrid search path, carries an activity-weighted risk score of 18.76 and sits in the 'fire' quadrant: it had 1 touch in the last 30 days despite a cyclomatic complexity of 35 and a nesting depth of 8, making it a live regression risk rather than a backlog cleanup item. The rest of the top five split between that same live-risk profile and a set of overlapping-search and reverse-search variants that haven't changed in 350 days but still carry blast-radius complexity that will hit hard whenever someone finally touches them.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `find_fwd_imp` — regex-automata/src/hybrid/search.rs

&lt;FunctionCard fn='find_fwd_imp' file='regex-automata/src/hybrid/search.rs' risk='18.76' band='critical' cc='35' nd='8' fo='19' touches='1' /&gt;

This is the top-ranked hotspot in the whole repository, and the source excerpt shows exactly why. It's the forward-search driver for the hybrid (lazy) DFA — it handles prefilter dispatch, a tagged-vs-untagged state fast path, and a hand-unrolled inner loop with four `unsafe` blocks doing raw byte indexing via `get_unchecked`. A cyclomatic complexity of 35 combined with a nesting depth of 8 means a reviewer has to hold eight levels of control flow in their head simultaneously just to verify one branch is correct, and a fan-out of 19 distinct calls means this function is deeply wired into the cache, DFA, and prefilter machinery around it. It had 1 touch in the last 30 days and last changed 25 days ago — recent enough that whatever edit landed there is still fresh, and any regression from it would surface in exactly this kind of high-throughput hot path. The `unsafe` macro `next_unchecked!` sits right in the middle of the highest-complexity branch, which in Rust means ownership and bounds-safety reasoning is layered on top of the branching complexity, not separate from it. My recommendation: extract the unrolled unsafe loop into its own clearly-bounded helper with its own safety-invariant documentation block, separate from the prefilter-dispatch logic above it — that alone would cut the effective nesting a reviewer has to track in the main function.

### `find_fwd_imp` — regex-automata/src/dfa/search.rs

&lt;FunctionCard fn='find_fwd_imp' file='regex-automata/src/dfa/search.rs' risk='18.51' band='critical' cc='35' nd='8' fo='14' touches='1' /&gt;

This is the non-lazy DFA counterpart to the function above, and the metrics are almost a mirror: same complexity of 35, same nesting depth of 8, one fewer point of fan-out coupling at 14. Reading the excerpt, the unrolling here is even more explicit — four consecutive unsafe `next_unchecked!` calls chained with early breaks on special-state checks, each one advancing the cursor by one byte. That's a textbook exit-heavy pattern: multiple early-return and break paths inside a hot loop, each one a distinct execution path that needs its own test case to be confident in. Like its hybrid sibling, it had 1 touch in the last 30 days and last changed 25 days ago, keeping it in the fire quadrant. Because these two functions are near-duplicates of the same algorithm across two DFA implementations, I'd treat them as a pair for any refactor — extracting the shared unrolling pattern into a common macro or generic helper would cut duplicated review effort roughly in half rather than fixing one and leaving its twin untouched.

### `find_overlapping_fwd_imp` — regex-automata/src/hybrid/search.rs

&lt;FunctionCard fn='find_overlapping_fwd_imp' file='regex-automata/src/hybrid/search.rs' risk='16.91' band='critical' cc='22' nd='7' fo='17' touches='0' /&gt;

Here the picture changes. This function had zero touches in the last 30 days and hasn't changed in 350 days, which puts it squarely in structural debt rather than live risk. But the complexity hasn't gone anywhere: cyclomatic complexity of 22, nesting depth of 7, and a fan-out of 17 distinct calls into the cache and DFA state machine. The excerpt shows a state machine inside a state machine — an outer match on `state.id` to decide whether this is a fresh search or a resumed one, then an inner loop checking tagged states, start states, match states, dead states, and quit states each with their own branch. That's a lot of exit conditions for a function that also has to coordinate mutable state across calls (`OverlappingState`). Because it's dormant, the near-term regression risk is low, but the next person who needs to add a new state-handling case here inherits all 22 paths at once with no recent history to lean on for context. I'd flag this as a candidate for decompose-conditional before it's touched again — splitting the resume-state handling from the main search loop would make the next change safer and faster to review.

### `find_overlapping_fwd_imp` — regex-automata/src/dfa/search.rs

&lt;FunctionCard fn='find_overlapping_fwd_imp' file='regex-automata/src/dfa/search.rs' risk='16.69' band='critical' cc='23' nd='7' fo='12' touches='0' /&gt;

The non-lazy-DFA twin of the function above tells the same story: zero touches in the last 30 days, 350 days since it last changed, cyclomatic complexity of 23 and nesting depth of 7. The excerpt shows the same overlapping-match resume logic, but with an added acceleration path — a branch that calls `accel::find_fwd` to skip ahead using a needle-based accelerator when the state supports it. That's an extra execution path layered on top of an already branch-heavy function, and it's why the pattern detector flags this as both a god function and stale-complex: complexity has accumulated but hasn't been revisited in nearly a year. Given that this and the hybrid version above share the same overlapping-match algorithm shape, I'd treat any refactor of one as an opportunity to reconcile both — right now a bug found in one implementation's state-handling has no guarantee of being checked against its counterpart.

### `find_rev_imp` — regex-automata/src/hybrid/search.rs

&lt;FunctionCard fn='find_rev_imp' file='regex-automata/src/hybrid/search.rs' risk='16.07' band='critical' cc='24' nd='6' fo='14' touches='0' /&gt;

The reverse-search counterpart to the forward-search functions above rounds out the picture of this file: three of my five hotspots now come from `hybrid/search.rs` alone. Cyclomatic complexity of 24 and a fan-out of 14, with zero touches in the last 30 days and 350 days since last change — another debt-quadrant function. The excerpt shows the same unrolled-unsafe-loop pattern as the forward version, adapted for backward iteration with its own empty-input special case handled via a separate `eoi_rev` call before the main loop even starts. That special-casing at the top is itself a signal: reverse search needs different edge-case handling than forward search, and that logic currently lives inline rather than being isolated. Given that this file now accounts for three of the five riskiest functions in the repository — two live, one dormant — I'd treat `hybrid/search.rs` as a unit for review rather than picking off individual functions. Anyone assigned to touch overlapping or reverse search in this file should budget time to read all three functions together, since the unrolling pattern and state-machine shape repeat across them.
