The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

First, what this ranking means. High activity-weighted risk says a function is structurally complex and recently changed. It does not say the code is buggy, and I am not judging the maintainers. Still, the file-level history is worth reading alongside the structure. lib/adapters/http.js has 6 commits in its history, and 83% of them are tagged as bug fixes. It has no reverts, no commits explicitly linked to bugs, and no pull-request review comments recorded, and 4 distinct authors touched it in the last 90 days. A high bug-fix rate on a small commit count is a weak signal, but combined with the complexity below it raises my review priority for this file. It does not prove any particular function is defective.

The pattern counts point the same direction. Neighbor risk shows up 7 times across the top hotspots, which suggests changes in these functions may require coordinated edits elsewhere. That fits an adapter whose job is to translate a config object into Node's transport layer.

### `dispatchHttpRequest` — http.js

<FunctionCard fn='dispatchHttpRequest' file='lib/adapters/http.js' risk='28.44' band='fire' cc='142' nd='7' fo='117' touches='1' />

This is the inner async function that `httpAdapter` wraps, and from the source excerpt it does a great deal in one place. It reads a long list of config values through a pollution-safe accessor (own properties only, ignoring values injected onto Object.prototype). It then validates the HTTP version, normalizes the DNS lookup option, and sets up an abort emitter and a connect-phase timer, with more below what I could see. Validation, setup, and nested helpers all share one function body.

<MetricBar label='Cyclomatic Complexity' value='142' threshold='30' max='150' />

CC 142 is far into the extreme range. Each independent path is a potential bug surface and a test case you would have to write. Fan-out of 117 means the function reaches into more than a hundred distinct callees, so a change to any of them can surface here. At nesting depth 7, I stop trusting my own reading of the control flow. The function was touched once in the last year, 29 days ago, so it is not churning, but it is recent enough that the risk is live. It also carries the exit-heavy pattern: many return and throw paths, each needing coverage.

My recommendation is extract-method along the phases visible in the excerpt. Config reading and the version validation (the three separate AxiosError throws for non-numeric, NaN, and unsupported protocol versions) can become a single `resolveHttpVersion` helper that is trivially unit-testable. That one move removes a visible block of branches without touching the request lifecycle. The abort and timer handling is the next candidate.

### `httpAdapter` — http.js

<FunctionCard fn='httpAdapter' file='lib/adapters/http.js' risk='24.24' band='fire' cc='79' nd='7' fo='118' touches='1' />

`httpAdapter` is the outer function. The excerpt shows it returning the result of wrapping `dispatchHttpRequest`, so the two entries overlap heavily: the inner function is defined inside the outer one, and the outer one's metrics include the inner body. I would not read these as two independent problems. The numbers to watch are its cyclomatic complexity of 79 and fan-out of 118, and fixing `dispatchHttpRequest` will pull both down.

In practice, any refactor of one is a refactor of the other, so I would plan them as a single change. Hoisting the inner function out to module scope, with the config and callbacks passed in explicitly, would make its dependencies visible and testable instead of captured from the enclosing closure.

### `handleResponse` — http.js

<FunctionCard fn='handleResponse' file='lib/adapters/http.js' risk='24.18' band='debt' cc='33' nd='4' fo='26' touches='0' />

This one is debt, not fire. `handleResponse` has not been changed in 74 days and was touched zero times in the last year, so it is structural debt with a high blast radius when next changed rather than something actively moving. It is the callback passed to the transport's request call, and the excerpt shows it handling response streams: download progress and rate limiting, then content-encoding handling that switches across gzip, deflate, brotli, and zstd cases, deleting the encoding header in several branches.

CC 33 with 26 distinct callees is a lot for a callback. The switch over content encodings is a natural seam: each case does a small, similar thing (push a decompression stream, remove a header), so a lookup from encoding to stream factory would collapse several branches. Because the function is dormant, now is a cheap time to do that, before the next feature (another encoding, say) forces a change under deadline.

### `factory` — fetch.js

<FunctionCard fn='factory' file='lib/adapters/fetch.js' risk='22.86' band='fire' cc='118' nd='6' fo='66' touches='1' />

This is the only top-five entry outside http.js, and it is the fetch adapter's setup. From the excerpt, it merges environment overrides, detects whether fetch, Request, Response, and ReadableStream are available, and probes runtime capabilities (request streaming, response streaming, and cache-mode support) before returning the adapter. It is in the fire quadrant, changed 29 days ago.

CC 118 and nesting depth 6 are high for what reads like feature detection plus the adapter body. The file-level history shows 5 commits with an 80% bug-fix rate, 3 distinct authors in the last 90 days, and a review-comment density of 10.0, the only top-five file with recorded review discussion. That is supporting context for a closer look, not evidence of a defect.

I would split the capability probes into small named functions, one per runtime feature. They are already shaped that way (each is a `test(...)` call), so the extraction is mostly mechanical. What remains in `factory` would be the request-sending logic, which is where the remaining complexity probably lives.

### `setProxy` — http.js

<FunctionCard fn='setProxy' file='lib/adapters/http.js' risk='22.14' band='fire' cc='59' nd='4' fo='19' touches='1' />

`setProxy` resolves a proxy from config or environment, strips stale proxy credentials and tunneling agents on redirects, and builds proxy authorization. The comments in the excerpt show that much of the branching is deliberate defensive handling: own-property reads so a polluted Object.prototype cannot inject credentials or redirect traffic to an attacker-controlled host, and case-insensitive removal of the Proxy-Authorization header on redirects.

That context shapes how I would refactor it. CC 59 is still high, though nesting depth 4 and fan-out of 19 make it narrower than the adapter functions above, and the branches encode security behavior, so each one needs a test before anything moves. My first step would be characterization tests for the redirect cases and the polluted-prototype cases, then extraction of the redirect cleanup into one function and the proxy-auth construction into another. The seven-parameter signature is also a signal: an options object would make call sites clearer.

**How these fit together**

The order I would work in: characterization tests around `setProxy` and `handleResponse` first, then the extract-method passes on `dispatchHttpRequest`, then the capability probes in `factory`.
