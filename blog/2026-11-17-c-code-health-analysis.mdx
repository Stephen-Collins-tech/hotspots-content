The most striking pattern in C codebases isn't that they contain complex code—that's expected in systems programming. It's the variance. The maximum risk score of 131.3 is nearly 8x the median of 17.7. When C code goes wrong, it goes dramatically wrong.

## Methodology

We analyzed 10 open-source C repositories using static analysis combined with git history from the past 90 days. The activity risk metric multiplies structural complexity (cyclomatic complexity × nesting depth × fan-out) by recent commit frequency. Functions that are both complex and actively changing score highest, since they represent the most immediate maintenance burden.

## The Most Common Antipatterns

Three antipatterns tied for first place, each appearing in 6 of the 10 repositories analyzed: complex branching, exit-heavy functions, and god functions. Long functions matched this count as well, with deeply nested code close behind at 5 occurrences.

Complex branching dominates C codebases because the language lacks the abstraction mechanisms that higher-level languages use to reduce cyclomatic complexity. Without pattern matching, sum types, or exception handling that centralizes error paths, C developers write explicit conditionals for every edge case. This isn't necessarily bad design—it's the language working as intended—but it does mean individual functions accumulate decision points quickly.

Exit-heavy functions follow the same logic. C's error handling convention of checking return values after each call leads to multiple early returns. A function that makes five system calls and checks each result will have at least six exit points before it does anything else.

God functions in C often emerge from performance optimization. Inlining logic to avoid function call overhead, or keeping related operations together to improve cache locality, produces functions that handle too many responsibilities. The tradeoff between runtime performance and code maintainability is real, but the debt accumulates.

## The Highest-Risk Repositories

[postgres/postgres](/blog/2026-10-28-postgres-postgres/) leads with a risk score of 131.3—more than 6x the next highest. The patterns driving this score are neighbor risk, exit-heavy code, and god functions. PostgreSQL's query executor and planner contain functions that both call and are called by other high-complexity code, creating clusters of risk that compound each other.

[FFmpeg/FFmpeg](/blog/2026-10-26-FFmpeg-FFmpeg/) scores 21.2, with god functions, long functions, and complex branching as primary patterns. Video codec implementations require handling dozens of formats and edge cases within single decode paths, making this somewhat inevitable for the domain.

[openssh/openssh-portable](/blog/2026-10-16-openssh-openssh-portable/) at 20.9 shows complex branching, deep nesting, and exit-heavy patterns. Security-critical code that must handle every possible failure mode explicitly tends toward these characteristics.

[curl/curl](/blog/2026-09-28-curl-curl/) scores 20.3 with the same pattern combination as OpenSSH. Protocol handling code shares similar constraints—many states, many error conditions, many explicit checks.

[jqlang/jq](/blog/2026-10-06-jqlang-jq/) rounds out the top five at 20.2, driven by god functions, complex branching, and deep nesting. Parser and interpreter code typically exhibits these patterns as recursive descent and tree-walking algorithms naturally accumulate complexity.

## What This Means for C Developers

The data suggests that C's antipatterns are often language-inherent rather than developer-caused. You can't add exceptions to C, so you write exit-heavy functions. You can't add generics, so you write god functions that handle multiple types inline. This doesn't mean the patterns aren't worth addressing, but it does mean the solutions look different than they would in other languages.

For teams maintaining C codebases, the variance in risk scores matters more than the patterns themselves. A repository with a 131.3 risk score has fundamentally different maintenance characteristics than one at 17.7. Prioritize refactoring efforts on the outlier functions—the ones where structural complexity meets high change frequency. Breaking up a stable god function that hasn't changed in two years is lower priority than simplifying a 15-branch function that gets modified weekly.

## Analyze Your Own Repository

To identify the highest-risk functions in your own C codebase, install the CLI:

```bash
brew install Stephen-Collins-tech/tap/hotspots
```

Or on any platform:

```bash
cargo install hotspots-cli
```

Then run:

```bash
hotspots analyze .
```

The output ranks functions by activity risk, showing exactly where structural complexity intersects with recent churn. Start with the top five results and work down.
