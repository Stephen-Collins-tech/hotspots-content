### `Process` — inbound.go

<FunctionCard fn='Process' file='proxy/vless/inbound/inbound.go' risk='18.61' band='critical' cc='18' nd='9' fo='109' touches='0' />

This is the inbound connection handler for the VLESS proxy protocol. From the source excerpt I can see it does a lot in one place: it reads the first bytes of an incoming connection, attempts to decode a VLESS request header, and — if that fails — pivots into a multi-stage fallback path that negotiates ALPN, inspects HTTP path bytes in raw buffer data, and eventually dials an upstream fallback destination. The entire fallback branch lives inside the same function as the primary request path.

The numbers tell the story clearly. A cyclomatic complexity of 18 means 18 independent execution paths, each of which is a required test case and a potential bug surface in Go's explicit error-return style. The max nesting depth of 9 is a strong refactoring signal on its own — ND 4 is where reasoning becomes hard, and this function nearly doubles that. But the figure that concerns me most is the fan-out of 109: this function directly calls 109 distinct other functions. In a library context, that means a change to `Process` can produce unexpected ripple effects across more than a hundred call sites. The function has not been touched in 870 days and has zero recent authors (`author_count_90d: 0`), so institutional knowledge of its full behavior is likely diffuse.

The source excerpt also shows a large commented-out block inside the fallback path — dead code that was never removed. That's a maintenance signal independent of the metrics.

**Recommendation:** Extract the fallback routing logic — ALPN negotiation, path parsing, and upstream dialing — into a dedicated `routeFallback` function. That alone would collapse the nesting depth significantly and give the fallback path its own test surface. The primary `Process` function should then be readable as: decode header → if error, delegate to `routeFallback` → otherwise handle authenticated request.

### `fallback` — server.go

<FunctionCard fn='fallback' file='proxy/trojan/server.go' risk='16.96' band='critical' cc='10' nd='7' fo='64' touches='0' />

The Trojan server's `fallback` function is structurally similar to the VLESS inbound fallback path — and the source excerpts confirm they share recognizable logic: ALPN detection via type assertions against `*tls.Conn` and `*xtls.Conn`, HTTP path byte-scanning in a raw buffer, and exponential-backoff dialing to an upstream destination. It has an explicit `// nolint: lll` comment on its signature, which tells me the parameter list was already long enough to trigger a linter warning.

<MetricBar label='Max Nesting Depth' value='7' threshold='4' max='10' />

At CC 10, the branching complexity is moderate — not extreme on its own. But combined with ND 7 and a fan-out of 64, this function is harder to reason about than the raw CC suggests. Seven levels of nesting means there are code paths where you are tracking seven simultaneous preconditions to understand what a line does. The function last changed 870 days ago and has had zero authors in the last 90 days — it sits squarely in the debt quadrant, carrying high structural complexity with no recent activity.

The structural overlap between this function and the VLESS inbound fallback is itself a risk signal: if a bug or behavioral change is required in the fallback protocol (say, a new ALPN value or a different path-detection heuristic), there are at least two places to update, and they are in different proxy implementations with no shared abstraction.

**Recommendation:** Before refactoring either fallback function in isolation, I would first extract the shared ALPN-detection and HTTP-path-scanning logic into a common package-level utility. That removes the duplication, reduces fan-out in both callers, and makes the behavioral contract testable in one place. The `fallback` function in `server.go` is overdue for this kind of decomposition.

### `Process` — outbound.go

<FunctionCard fn='Process' file='proxy/vless/outbound/outbound.go' risk='14.98' band='critical' cc='15' nd='4' fo='52' touches='0' />

This is the outbound counterpart to the inbound `Process` above — it picks a server, dials a connection, builds a VLESS request header, and negotiates XTLS flow modes before handing off to the transport layer. The source excerpt shows a `switch` on `requestAddons.Flow` that branches on several VLESS flow variants (`XRO`, `XRD`, their `-udp443` suffixes), with nested `switch` statements on the request command type inside each case. In Go, each arm of that structure is an explicit error-return branch, so the CC of 15 directly corresponds to test cases that currently need to exist to cover the function.

The nesting depth of 4 is more manageable here than in the inbound function, but the fan-out of 52 is still broad. This function sits at a public API boundary for the VLESS outbound handler — every caller that dials a VLESS connection goes through it, so a change here propagates to all of them. Like the other four functions in this list, it has not been touched in 870 days and sits in the debt quadrant: high structural complexity, no recent activity.

The flow-mode logic (`vless.XRO`, `vless.XRD`, XTLS direct mode) is where I would focus first. These mode distinctions each carry their own preconditions and error cases; grouping them inside a single `Process` function makes the function's contract harder to document and harder to test in isolation.

**Recommendation:** Extract the flow-mode negotiation — the `switch requestAddons.Flow` block and the XTLS connection setup — into a `configureXTLSFlow(conn, request, addons)` helper. This reduces the CC of `Process` toward a more manageable level and makes the XTLS-specific logic independently reviewable, which matters especially if XTLS support is ever modified or deprecated.

### `New` — server.go

<FunctionCard fn='New' file='app/dns/server.go' risk='14.83' band='critical' cc='7' nd='5' fo='38' touches='0' />

This is the DNS server constructor — a `New(ctx, config)` function that wires up the full DNS client roster based on configuration. From the source excerpt, it branches on address family and URI scheme to decide which DNS client type to instantiate: a local resolver for `localhost`, a DoH-local client for `https+local://` URIs, a remote DoH client for `https://` URIs, and a classic UDP client otherwise. The DoH remote branch uses a deferred feature-registration callback (`core.RequireFeatures`) to inject the routing dispatcher after construction, which adds an asynchronous initialization path to what looks like a synchronous constructor.

<MetricBar label='Fan-out' value='38' threshold='15' max='60' />

The cyclomatic complexity of 7 is the lowest of the five hotspots, but the god-function and long-function patterns reflect that this constructor is doing far more than allocation and field assignment. The nesting depth of 5 comes from the multi-level address-family branching inside an inner closure (`addNameServer`), which itself is defined inside `New`. The `bug_fix_fraction` for this file is 0.5 — half of its two historical commits were tagged as bug fixes — which is worth noting as supporting context when prioritizing review, though it doesn't prove the current code is defective. This function last changed 869 days ago and has had no authors in the last 90 days.

The function also calls `log.Fatalln` on DNS config errors in several branches, which is an aggressive failure mode for a constructor in a library.

**Recommendation:** Replace the inline type-dispatch logic with a `buildNameServerClient(ns *NameServer, ctx context.Context, clientIP net.IP) Client` factory function. Each address-family branch becomes a named case inside that factory, the nesting depth drops, and `New` returns to doing what constructors should do: allocate, validate, and delegate.

### `DecodeRequestHeader` — server.go

<FunctionCard fn='DecodeRequestHeader' file='proxy/vmess/encoding/server.go' risk='14.29' band='critical' cc='8' nd='4' fo='60' touches='0' />

This function decodes an incoming VMess request header from a raw reader, handling both the modern AEAD authentication path and the legacy MD5-based path. The source excerpt reveals security-sensitive implementation details: it computes a deterministic drain size using a seeded dice roll, defines a `drainConnection` closure that reads a calculated number of bytes before returning an error (an anti-probing measure to prevent traffic analysis from distinguishing valid from invalid auth IDs), and then branches on whether AEAD succeeds, whether legacy auth succeeds, or whether both fail.

<MetricBar label='Fan-out' value='60' threshold='15' max='80' />

The fan-out of 60 is notable for a parsing function. Header decoding at this level touches cryptographic primitives, buffer management, user validation, and connection draining — each of which is a distinct concern. The `bug_fix_fraction` for this file is also 0.5 across two historical commits, consistent with the DNS server file. Neither alone is alarming, but both files have a history where a meaningful share of changes were corrective. This function has not been touched in 870 days and carries no recent authors — structural debt with a meaningful blast radius if the VMess protocol or its authentication scheme ever requires a change.

From a security standpoint, the draining logic is intentional and well-motivated, but embedding it as a closure inside the decode function means it cannot be unit-tested independently, and the drain parameters (visible in the log output as `BaseDrainSize`, `RandDrainMax`, `RandDrainRolled`) are coupled to the same function scope that does the cryptographic validation. If the AEAD or legacy validation logic ever needs updating — for a protocol change or a security advisory — the developer will be working inside a function with 60 dependencies and no separation between the drain logic and the auth logic.

**Recommendation:** Extract `drainConnection` into a named, package-level function with an explicit signature. This makes the drain behavior independently testable and removes one layer of closure nesting. As a second step, consider separating the AEAD and legacy decode paths into distinct functions called from a thin dispatcher inside `DecodeRequestHeader`, which would also make it easier to eventually remove the legacy path when it is fully deprecated.
