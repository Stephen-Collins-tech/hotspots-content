The top function, `ProcessConfigOverrides`, has an activity-weighted risk score of 59.1 and sits in the 'fire' quadrant, meaning it is both structurally complex (CC 24, ND 8, FO 22) and was changed 6 days ago. Across the repo's 27,467 functions, 1,109 are critical, and this one file accounts for the whole top five.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `ProcessConfigOverrides` — cpplint.py

<FunctionCard fn='ProcessConfigOverrides' file='tools/cpplint.py' risk='59.1' band='fire' cc='24' nd='8' fo='22' touches='1' />

I would start with `ProcessConfigOverrides` because it combines the deepest nesting in the set (ND 8, the threshold I treat as a strong refactoring signal) with a fan-out of 22 and an activity-weighted risk score of 59.1. From the source excerpt, it walks up the directory tree looking for a configuration file, reads it line by line, and then dispatches on option names in a long if/elif chain: filters, excluded files, line length, extensions, root, headers, third-party headers, and include order, with an error branch for anything unrecognized. It also assigns module-level globals for the line length and root directory from inside that loop, so its behavior depends on state that other functions in the file can read.

The nesting comes from stacking a directory-walk loop, a file-open try block, a per-line loop, and the option dispatch, with further conditions inside the exclusion branch. Several exits, including early returns of false when a file is excluded, add to the test burden. The pattern tags (god function, long function, deeply nested, exit heavy, neighbor risk) match what I see in the excerpt.

My recommendation: split it into three pieces. One function finds the applicable config files by walking up the directory tree. A second parses a single config file into a plain options structure without mutating globals. A third applies that structure. Once parsing is separate from applying, each option handler can be tested with a one-line input instead of a temp directory tree. The 'neighbor risk' tag also suggests changes here may need coordinated edits elsewhere, so I would check the option-handling helpers it calls (`ProcessExtensionsOption`, `ProcessHppHeadersOption`, `ProcessThirdPartyHeadersOption`, `ProcessIncludeOrderOption`) as part of the same change.

### `CheckForNonConstReference` — cpplint.py

<FunctionCard fn='CheckForNonConstReference' file='tools/cpplint.py' risk='56.7' band='fire' cc='29' nd='5' fo='16' touches='1' />

`CheckForNonConstReference` has an activity-weighted risk score of 56.7, with CC 29, ND 5, and FO 16. From its docstring and excerpt, it scans backward from the current line to detect non-const reference parameters, and it spends much of its length on a special case: types split across two lines. The excerpt shows early exits for lines without an ampersand, for derived functions, and for out-of-line method definitions, followed by regex-based joining of the previous line, plus a separate path for template arguments split across lines that calls `ReverseCloseExpression`.

The complexity here comes from formatting variations, a different problem from a wide rule list. Each continuation form is a distinct branch, and the nesting reaches 5 inside the multi-line handling. The exit-heavy pattern shows in the three early returns at the top.

My recommendation: extract the line-joining logic into a function that takes the current line and returns the logical line to check. That isolates the part with the most branching and the most regular expressions, and it can be tested with plain strings. The early-exit guards can stay in the main function because they are cheap to read and clearly ordered.

### `CheckLanguage` — cpplint.py

<FunctionCard fn='CheckLanguage' file='tools/cpplint.py' risk='56.09' band='fire' cc='50' nd='3' fo='21' touches='1' />

`CheckLanguage` has the highest cyclomatic complexity in the group at 50, well past my threshold of 30 for high complexity, though its nesting depth of 3 is modest. That shape matters: this is not a tangle of nested conditions but a very wide function. The excerpt shows it applying a sequence of independent rules to a single source line: return early on empty lines, hand off include lines, reset include state on preprocessor directives, call several other check functions (casts, global statics, printf), then run inline pattern checks for C integer types and operator overloading. Its fan-out of 21 reflects that dispatcher role.

Each inline rule is a separate path with its own regular expression, so 50 paths means 50 potential test cases, and the god-function and long-function tags are consistent with that. The multiple exits (the exit-heavy tag) add to the count.

My recommendation is the most mechanical in this post: extract each inline rule into its own small check function with the same signature as the existing delegated checks (`CheckCasts`, `CheckGlobalStatic`, `CheckPrintf`), then let `CheckLanguage` become a short list of calls. The file already follows that convention for some rules, so finishing the job fits its own style. Because the rules appear independent, this should cut the function's complexity by well over half without changing behavior.

**`FindEndOfExpressionInLine` and `FindStartOfExpressionInLine` — cpplint.py**

<FunctionCard fn='FindEndOfExpressionInLine' file='tools/cpplint.py' risk='56.06' band='fire' cc='35' nd='5' fo='5' touches='1' />

<FunctionCard fn='FindStartOfExpressionInLine' file='tools/cpplint.py' risk='55.64' band='fire' cc='29' nd='5' fo='4' touches='1' />

I group these two because they are near mirror images with the same profile: complex branching, deep nesting, and many exits, but a low fan-out (5 and 4). That sets them apart from the other three. They are not coordinators; they are self-contained character scanners. The excerpts show each walking a line one character at a time while maintaining a stack of open brackets and angle brackets, with special handling for the ambiguity between template angle brackets and comparison, shift, and arrow operators. `FindEndOfExpressionInLine` scores CC 35 and `FindStartOfExpressionInLine` CC 29, both at ND 5.

The low fan-out is good news for blast radius: changes inside them are unlikely to ripple through many callees. The risk is in the logic itself. The angle-bracket handling is the hard part, because a single character can mean different things depending on the previous character and on whether the text before it ends in an operator keyword. Every one of those combinations is a path that needs a test.

The source describes the two functions as near-reverses of each other, so they have to stay consistent. A fix to how one treats an operator case would need a matching check in the other. My recommendation is a shared table-driven test that feeds both functions the same set of tricky inputs (shift operators, arrows, operator overloads, mismatched brackets, a semicolon inside a pending template list) and asserts the expected position or leftover stack for each. That test gives the next person to touch either function a safety net, and it is cheaper than restructuring the scanners. After that, extracting the angle-bracket decision into a small helper in each would reduce nesting.

**What the context-only functions add**

The five context-only functions are all in the 'watch' quadrant, with CC between 3 and 5 and an activity-weighted risk score between 46.65 and 47.13. They are low-complexity functions that scored high only because they were touched recently, and I would not prioritize them for refactoring.

**Where I would spend review time**

Given one afternoon, I would first write the shared tests for the two expression-scanning functions, since that locks down behavior at the lowest cost. Second, I would decompose `CheckLanguage` by extracting its inline rules, the safest large reduction in complexity. Third, I would split `ProcessConfigOverrides` into discovery, parsing, and application. The 'fire' label on all five reflects a recent change rather than a long record of trouble, and the file-level history I have shows no bug-linked commits and no reverts, so I would frame this as maintainability work to do while the file is recently open, not as an incident follow-up.
