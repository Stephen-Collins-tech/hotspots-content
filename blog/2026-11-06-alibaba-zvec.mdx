Five hotspots, one file. Every top-ranked function in alibaba/zvec sits in src/db/index/segment/segment.cc, so anyone touching the segment layer is working inside a single dense module. The file is in the active tier, with 45 touches in the last year and 1 day since last change, and the top function carries an activity-weighted risk score of 3.55, so this is live regression risk rather than a backlog item. I analyzed zvec at commit b1670ff, which has 13,380 functions in total and 1,253 in the critical band. I would start with the fetch method on the segment implementation: its cyclomatic complexity of 56 and fan-out of 106 sit in code that eight distinct authors touched in the last 90 days. Because this is C++, with templates and macros that static analysis cannot fully see, I read the ranking as a reading order rather than a measurement.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

The tier split above puts the file in context. Roughly 54% of zvec's functions are in active files, so activity alone does not single out segment.cc. What does is that all five of its top functions pair critical-band complexity with the same file-level activity: 45 touches in the last year, 1 day since last change, and 8 distinct authors in the last 90 days.

The file-level history is worth stating carefully. About 53% of the file's 45 commits are bug-fix commits (a bug-fix rate of 53.33%). The data shows no commits explicitly linked to bugs and no reverts. Pull-request review comment density is 3.75. I read that as a file that gets a lot of corrective attention and review discussion, not as proof that any one function below is defective. Since the signals are file-level, they apply equally to all five functions, so I use them to raise the review priority of the whole module rather than to rank within it.

There is also a contrast in the rest of the ranking. The highest-scoring functions outside segment.cc that I looked at are quiet-tier, with 2 to 3 touches in the last year and 48 to 56 days since last change. They are structural debt that is overdue for refactoring, but their activity-weighted risk scores of 1.56 to 1.70 are less than half of segment.cc's scores of 3.46 to 3.55. The gap between those scores is the case for starting with segment.cc.

**`fetch` (the long-signature overload) — segment.cc**

<FunctionCard fn='SegmentImpl::fetch' file='src/db/index/segment/segment.cc' risk='3.55' band='critical' cc='56' nd='5' fo='106' touches='45' />

This is the top-ranked function, with an activity-weighted risk score of 3.55. The parsed name in the data is truncated (it appears as the tail of the signature, `string>>&,bool)`), and the source excerpt shows it is `SegmentImpl::fetch(g_doc_id, output_fields, include_vector)`, which retrieves a single document by global ID.

<MetricBar label='Fan-out' value='106' threshold='15' max='110' />

The excerpt shows several distinct jobs sharing one body: taking a shared lock, validating the ID against the segment's maximum, binary-searching the document ID list, choosing which forward columns to return based on whether output fields were requested, building an Arrow result schema column by column, and then running the actual fetch and checking the row count. Each of those has its own error path with a log-and-return-null exit, which is part of why cyclomatic complexity reaches 56 (a count of independent paths, and each path is a test case). Fan-out of 106 distinct callees is the highest of the five.

My recommendation is to extract the column-selection logic and the Arrow schema construction into separate helpers. Both are visible in the excerpt as self-contained loops that depend only on the schema and the requested field list, so they can be tested without a segment, a lock, or a store.

### `alter_column` — segment.cc

<FunctionCard fn='SegmentImpl::alter_column' file='src/db/index/segment/segment.cc' risk='3.51' band='critical' cc='34' nd='5' fo='99' touches='45' />

With cyclomatic complexity 34, nesting depth 5, and fan-out 99, this is a schema-mutation routine, and the excerpt shows why it is wide. It validates preconditions (memory-store segments are rejected, the column must exist, scalar blocks must be non-empty), converts the new schema to an Arrow field, reads the affected blocks into a table, evaluates an expression over it, writes the new column back in blocks, and then, if the new schema has an inverted index, reopens, removes, and recreates the column indexer.

That is a multi-stage pipeline in one function. The index-rebuild branch at the end is the one I would extract first, since it is a distinct phase with its own sequence of status checks. A function that rewrites on-disk blocks and then swaps indexers benefits from phase boundaries that can be tested separately and reasoned about when something fails halfway.

### `fetch_normal` — segment.cc

<FunctionCard fn='SegmentImpl::fetch_normal' file='src/db/index/segment/segment.cc' risk='3.47' band='critical' cc='36' nd='4' fo='79' touches='45' />

This function batches fetches across blocks. The excerpt shows two explicit phases, a first loop mapping each (document, column) pair to its block and block-local row, and a second executing a batched fetch per block. It also special-cases a local row ID column and falls back to the in-memory store when a document is not in any persisted block, using an index of -1 as a sentinel.

The sentinel convention is the part I would look at in review. Any code that groups requests by block index has to remember that -1 means memory store, and that knowledge is spread across the function. Pulling the phase 1 mapping into its own function would let it be tested against persisted-only, memory-only, and mixed layouts without running the fetch itself. Cyclomatic complexity 36 with nesting depth 4 is a bit shallower than its neighbors, so this is probably the most tractable of the five to split.

### `create_fts_index` — segment.cc

<FunctionCard fn='SegmentImpl::create_fts_index' file='src/db/index/segment/segment.cc' risk='3.47' band='critical' cc='21' nd='5' fo='50' touches='45' />

This is the smallest of the group by complexity (cyclomatic complexity 21, fan-out 50) but it reaches nesting depth 5. From the excerpt, it validates parameters, short-circuits if the field is already indexed with identical parameters, rejects a type mismatch, then snapshots or freshly creates a full-text index directory, removes any existing field indexer, creates the new one, and scans the forward store to replay existing documents.

Note how many exit paths there are: several of them call a directory-removal helper before returning an error, so cleanup is repeated by hand at each failure point. That pattern is easy to get wrong when another early return is added. I would wrap the new index directory in a small scope guard or cleanup object so that every early return is covered by one mechanism. That change reduces the number of places a future edit can forget cleanup, without altering the function's behavior.

### `scan` — segment.cc

<FunctionCard fn='SegmentImpl::scan' file='src/db/index/segment/segment.cc' risk='3.46' band='critical' cc='23' nd='5' fo='38' touches='45' />

The lowest-ranked of the five, with fan-out of 38 and cyclomatic complexity of 23. The excerpt shows it validating columns, taking a shared lock, gathering readers from each persisted scalar block (grouped by document ID range), adding a reader for the in-memory store when it has rows, and then assembling an Arrow field list with special handling for the global document ID, user ID, and local row ID columns.

It shares a pattern with `fetch`: both build an Arrow schema by walking the requested columns and special-casing the same reserved names. I would extract that schema construction into one shared helper. That removes a duplicated branch ladder and means a new reserved column only needs to be handled once.

## Where to start

I would begin with the shared pieces rather than any single function. The Arrow schema construction appears in both `fetch` and `scan`, and block-to-row mapping logic sits in `fetch_normal` and `fetch`. Extracting those first reduces complexity in two top-five functions at once. After that, I would split the index-rebuild phase out of `alter_column` and add scope-based cleanup to `create_fts_index`. Because the file changed 1 day before this analysis and had 8 distinct authors in the last 90 days, I would do this in small, separately reviewable changes rather than one large refactor. The quiet-tier benchmark functions in tools/db/fts_bench_main.cc can wait: they are overdue for refactoring, but they carry structural debt rather than live regression risk, with 3 touches in the last year and 48 days since last change.
