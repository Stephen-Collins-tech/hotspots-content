I found 34 'fire' quadrant functions in hyperfine (out of 320 analyzed at commit c516152), and the top five are all critical-band functions that were last changed 4 days before the analysis. The headline is `run` in `src/benchmark/mod.rs`: an activity-weighted risk score of 16.33, 41 touches in the last year, a cyclomatic complexity of 25 and a fan-out of 28. I would start with `run`, then `print` in `src/output/report.rs`, and treat the rest as follow-ups.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `run` — src/benchmark/mod.rs

<FunctionCard fn='run' file='src/benchmark/mod.rs' risk='16.33' band='fire' cc='25' nd='3' fo='28' touches='41' />

I would start with `run` because it pairs the highest activity-weighted risk score (16.33) with the heaviest churn in the top five: 41 touches in the last year and 4 days since last change. The file has 51 total commits, and 41 of them touched this function in the last year. The file has 5 distinct authors in the last 90 days, which may raise the odds of overlapping assumptions.

The source excerpt shows why the numbers are high. In one body, `run` resolves the preparation and conclusion commands (each with the same pattern of 'one value shared, or one per benchmark'), builds closures to invoke them, runs the setup command, builds a progress header, and then enters a warmup phase with its own progress bar handling. The excerpt cuts off there, but the metrics imply more phases follow. A fan-out of 28 means the function directly depends on 28 other functions. The god-function, long-function and exit-heavy patterns all fit: many responsibilities, a lot of lines, and many early exits through `?`, each of which is a path a test needs to cover.

The file-level bug-fix rate is low (about 4%, with 0 bug-linked commits and 0 reverts), so this is not a bug magnet. It is a function that every benchmarking feature has to touch. My recommendation is extract-method along the phases the code already labels: one function to resolve the preparation and conclusion commands (the duplicated resolution logic is the obvious first extraction), one for the warmup phase, one for the timed runs. Nesting is only 3, so the problem is breadth, not depth, and extraction should be mechanical.

### `print` — src/output/report.rs

<FunctionCard fn='print' file='src/output/report.rs' risk='15.74' band='fire' cc='30' nd='6' fo='29' touches='2' />

`print` has the highest cyclomatic complexity in the group (30) and the deepest nesting (6), with a fan-out of 29. It has only 2 touches in the last year and 2 total commits on the file, yet it was changed 4 days before the analysis, so the score reflects that recent change. Two commits leave almost no history to judge stability from, and I would not call it settled.

From the excerpt, it builds a table: it picks a compact layout based on terminal width, assembles a header that varies with whether there are multiple runs and whether there is a reference benchmark, loops over selected metrics, chooses display units, and formats change and factor columns against a baseline. Rendering decisions, unit selection and comparison formatting all live in one function. That is where a nesting depth of 6 and 30 independent paths come from, and each combination of compact/not compact, single/multiple runs and comparison/no comparison is a distinct path a test would need to hit.

I would split it in two: one function that turns a metric and its summary into a row of strings (the loop body), and another that handles column alignment and output. The loop body is the natural seam because it already has a clear input (a metric selection, a summary, an optional baseline) and a clear output (a row plus a unit suffix). Do this before more metrics or layout modes arrive; a file with 2 commits is cheap to restructure now.

### `build_from_cli_arguments` — src/command.rs

<FunctionCard fn='build_from_cli_arguments' file='src/command.rs' risk='14.2' band='fire' cc='15' nd='5' fo='16' touches='2' />

This function turns parsed arguments into the list of commands to benchmark, branching on the parameter mode: a parameter scan, a parameter list, or the plain case. In the list branch, the excerpt shows it tokenizing values, checking for duplicate parameter names, computing the size of the parameter space, validating the number of command names against it, and then iterating through that space with a labeled loop and a manually managed index vector. A cyclomatic complexity of 15 with nesting of 5 and a fan-out of 16 is moderate by CC alone, but the nesting is what I find most relevant: a multi-dimensional index walk inside a branch inside a match is hard to reason about.

This file also has the highest historical bug-fix rate among the five at about 22% (2 of 9 commits), with no reverts and no bug-linked commits. The sample is small, so I would not over-read it, but it is the one place in the top five where the history gives a mild reason to prioritize. Parameter lists crossing multiple commands are exactly the kind of logic where off-by-one errors in indexing hide.

I would extract the 'parameter list' branch into its own function that returns the commands, mirroring how the scan case already delegates to a helper. Then pull the index-vector iteration into a small helper (or an iterator) so the cartesian-product logic can be tested without going through argument parsing.

### `run` — src/main.rs

<FunctionCard fn='run' file='src/main.rs' risk='12.74' band='fire' cc='7' nd='3' fo='10' touches='6' />

This is the other `run`, and it is a different kind of hotspot. Its cyclomatic complexity is only 7 and nesting 3, so structurally it is modest. It ranks in the critical band because it was changed 4 days ago, was touched 6 times in the last year, and has 4 distinct authors in the last 90 days across 12 total commits on the file. It is the entry point that wires everything together: parse arguments, build options and commands, validate, check for shell-syntax problems when running without a shell, create the export manager, run the scheduler, do the final export.

I would not refactor this one for complexity. I would watch it, because every new CLI feature has to be wired through here, and the shell-syntax validation loop (which rejects commands starting with a variable assignment or containing unquoted operators) is user-facing policy embedded in the startup path. If that validation grows, I would move it into its own function so the entry point stays a short sequence of steps. The Windows terminal setup behind a conditional-compilation attribute is also worth keeping isolated.

### `run_command_and_measure_common` — src/benchmark/executor.rs

<FunctionCard fn='run_command_and_measure_common' file='src/benchmark/executor.rs' risk='12.68' band='fire' cc='20' nd='3' fo='9' touches='7' />

This function prepares and executes a single command, sets environment variables for the iteration, and then decides what to do with a non-zero exit status. A cyclomatic complexity of 20 with shallow nesting (3) and modest fan-out (9) tells me the branching is wide rather than deep. The excerpt confirms it: a match on the failure action (raise, ignore all, ignore specific codes), a lookup of the exit code, and a match on the iteration kind to build the error message, followed by a hint that depends on whether the failure action was set per command.

It was touched 7 times in the last year and changed 4 days ago, with 3 distinct authors in the last 90 days and a bug-fix rate of about 6% across 31 commits. No reverts. This is where hyperfine decides whether a failed benchmark run aborts the whole benchmark, so a mistake in the exit-code logic changes user-visible behavior directly.

I would split the failure-policy decision (should this exit status be treated as a failure?) from the message construction. The decision is a pure function of the failure action and the exit status, which makes it easy to unit test across all three policies and the no-exit-code case. The message builder is another pure function of the iteration, exit status and hint flag. That would take the remaining function down to the setup-execute-check shape its name implies.

**What I would do first**

If I only had time for two changes, I would extract the phases of `run` in `src/benchmark/mod.rs` and split the row-building out of `print` in `src/output/report.rs`. The first has the most churn and the most authors; the second has the highest complexity and nesting and is cheapest to fix while the file's history is only 2 commits. The 'debt' functions outside the top five have not been changed in a long time, so they are not where I would spend effort this week.
