Three of the top five hotspots in vis-network live in one file, lib/network/dotparser.js, so I would treat that module as the unit of work rather than any single function. The top-ranked function, `parseAttributeList`, has an activity-weighted risk score of 25.67, but it sits in the debt quadrant with 0 touches in the last year and 101 days since last change. That makes this a structural-debt argument with high blast radius when next touched, not a live-churn argument. Across 797 functions in the repository, 40 are critical and 145 are debt, and the fire quadrant is empty.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `parseAttributeList` — dotparser.js

<FunctionCard fn='parseAttributeList' file='lib/network/dotparser.js' risk='25.67' band='critical' cc='45' nd='8' fo='8' touches='0' />

<MetricBar label='Cyclomatic Complexity' value='45' threshold='10' max='60' />

I would start here, because the function combines CC 45 with a nesting depth of 8 and hasn't been changed in 101 days. From the excerpt, it parses bracketed DOT attribute lists in a loop and, inside that loop, converts DOT concepts into vis-network options: edge styles, arrowhead and arrowtail shapes mapped through lookup tables. It also builds up a list of attributes and a list of attribute names that later steps reconcile. So one body handles token checks, error reporting (several syntax-error throws for a missing name, equal sign or value), and DOT-to-vis translation.

The nesting depth of 8 is the stronger refactoring signal. At ND 8 and beyond, following the control flow means holding too many conditions in your head at once. The exit-heavy pattern, with multiple throw paths, also means each failure mode needs its own test case. The inline style and arrow conversions share a loop with the token handling, and that is where I would cut first.

My recommendation: extract the name/value translation (style, arrowhead, arrowtail) into a separate function that takes a name and value and returns the translated pair. Then extract the single-attribute read (name, equals sign, value, with their three syntax checks) as its own step. That should pull the nesting depth down and let you test the translation table without constructing a token stream. The neighbor-risk pattern also suggests that edits here may need coordinated changes in nearby functions in the same file.

### `clusterByEdgeCount` — Clustering.js

<FunctionCard fn='clusterByEdgeCount' file='lib/network/modules/Clustering.js' risk='23.02' band='critical' cc='20' nd='7' fo='7' touches='0' />

This is the only top-five function outside the DOT parser, and the only one in a file that is part of the runtime network behavior rather than an import format. CC is 20, ND is 7, and FO is 7, with 107 days since last change. From the excerpt, it iterates every node, counts qualifying edges, and when a node matches the requested edge count it gathers neighbors under an optional join condition. It then looks for existing cluster data containing any gathered node id. The excerpt shows nested loops, closures defined inside loops (the join-condition check and the cluster-data search), and a manual early-break flag (the gathering-success boolean).

I would look at the closures inside nested loops first. They hide the real inputs of each step, because they capture loop variables, and that makes the function hard to test without building a whole body of nodes and edges. With ND 7, it is also easy to lose track of which loop an index belongs to.

My recommendation: lift the join-condition check and the cluster-data search out as methods that take their inputs explicitly. Then separate the collection pass (find qualifying nodes and their edges) from the cluster-forming pass. That would flatten the nesting and make the two phases testable independently. Since it has sat untouched for 107 days, I would do this before the next clustering feature, not during it.

### `getToken` — dotparser.js

<FunctionCard fn='getToken' file='lib/network/dotparser.js' risk='22.47' band='critical' cc='45' nd='4' fo='8' touches='0' />

`getToken` matches `parseAttributeList` on CC (45) but nests only 4 deep, so its problem is breadth rather than depth. The excerpt shows a lexer: it skips whitespace, handles three kinds of comments (hash line comments, double-slash line comments, and block comments), checks for end of input, and then tries two-character and one-character delimiters before moving on to other token types. Most of those branches are sequential character checks, which is why CC is high while nesting stays modest.

Handwritten lexers tend to look like this, and I would not call it wrong. The cost is that CC 45 means 45 independent paths, and the exit-heavy pattern means many early returns that each need a test. It has gone 107 days without a change, so the blast radius falls on whoever next has to add a token type or change comment handling.

My recommendation: split the comment-skipping loop into its own function (for example, a `skipWhitespaceAndComments` helper). The excerpt shows that block already has a clean boundary, a do-while loop that ends when no comment was found. Pulling it out would likely cut CC substantially and give you a unit-testable piece for the three comment styles.

### `parseDirAttribute` — dotparser.js

<FunctionCard fn='parseDirAttribute' file='lib/network/dotparser.js' risk='22.44' band='critical' cc='29' nd='8' fo='4' touches='0' />

The third dotparser.js function in the top five has CC 29, ND 8, and FO 4, and has sat untouched for 107 days. Based on the excerpt, it reconciles the DOT `dir` attribute (both, forward, back, none) with the vis `arrows` attribute produced earlier by `parseAttributeList`. It finds indexes of the arrows and dir entries, adds default arrow entries if none were assigned, and then rewrites or merges entries depending on which combination of `to` and `from` shapes is present.

The low fan-out of 4 tells me this function is mostly self-contained branching over a small set of cases. The depth of 8 comes from nesting by direction type, then by which arrow shapes exist. In effect it is a decision table written as nested conditionals. I would also flag the coupling to `parseAttributeList`: the two functions share an attribute list structure, so a change to the shape of entries in one can silently break the other. That is the kind of coordinated-edit risk the neighbor-risk label points at, though `parseDirAttribute` itself doesn't carry that tag.

My recommendation: separate the 'add default arrows' step from the 'merge arrows by direction' step, then handle each of the four direction values in its own small function. The repeated pattern of pushing an arrows entry that copies the dir attribute's owner is a candidate for a small helper.

### `_condenseHierarchy` — LayoutEngine.js

<FunctionCard fn='_condenseHierarchy' file='lib/network/modules/LayoutEngine.js' risk='22.04' band='critical' cc='6' nd='4' fo='30' touches='0' />

<MetricBar label='Fan-out' value='30' threshold='15' max='35' />

This one ranks fifth on coupling, not branching. CC is only 6 and ND is only 4, but FO is 30, and the god-function pattern is attached to it. It has gone 101 days without a change. From the excerpt, it defines a long list of nested helper closures (shifting trees, getting tree sizes, collecting branch nodes, computing branch boundaries) inside one method of the layout engine for hierarchical layouts. Those helpers reach into the hierarchical structure, the direction handler, and the node map.

With a fan-out of 30, a change to any of the objects it talks to can ripple into this function, and a change here can affect all of them. The low CC misleads on its own: you can follow the function line by line, but reasoning about it as a unit is hard, because so much of its behavior lives in closures that share state such as the still-shifting flag and the branches map. The neighbor-risk pattern adds that edits here may require coordinated changes elsewhere.

My recommendation: promote the helper closures to private methods or to a small collaborator object that owns the tree-shifting logic. That makes each helper individually testable and shows the real dependencies explicitly. Since hierarchical layout is a self-contained feature, I would start by extracting the tree-size and tree-shift helpers, because the excerpt shows they have the clearest boundaries.

**What I would do with this**

The concentration in dotparser.js is the practical takeaway. `parseAttributeList`, `getToken`, and `parseDirAttribute` have CC of 45, 45, and 29, and two of them have a nesting depth of 8. They share parser state and attribute-list structures, so refactoring them one at a time without tests around the whole DOT import path risks breaking the pieces you did not touch. I would write characterization tests that feed representative DOT inputs through the parser first, and only then split the functions. None of this is urgent in the live-regression sense, since nothing in the top five has been touched in the last year. The value is in finishing the work before the next change to DOT import, clustering, or hierarchical layout forces someone into these functions under deadline.
