### `run_app` — main.rs

<FunctionCard fn='run_app' file='src/main.rs' risk='19.27' band='fire' cc='46' nd='7' fo='27' touches='1' />

<MetricBar label='Cyclomatic Complexity' value='46' threshold='10' max='60' />

This is the top-level orchestrator, and the excerpt shows what that costs. Its cyclomatic complexity is 46, nesting depth reaches 7, and it calls 27 distinct functions. The excerpt shows it handling version and help output, setting the calling process for subcommands, dispatching through a long else-if chain of subcommand flags (completion generation, language listing, theme listing and showing, colors, ANSI parsing), then handling the show-config case, building the configuration, and starting pager setup. Argument interpretation, subcommand dispatch and output wiring all live in one body. The function is flagged as complex branching, deeply nested, exit-heavy, a god function and long.

The activity signal makes it urgent. It has 1 touch in the last year and was changed today, so any work in progress lands in a function where every one of those 46 paths is a candidate test case and the many early returns each need their own coverage. The file-level history is quiet: 6 total commits, no bug-linked commits, no reverts, one distinct author in the last 90 days. That reads as a file that is rarely edited but being edited now, in its most complex function.

I recommend extracting the subcommand dispatch chain into its own function that returns an optional result, and pulling the pager and output setup into a second helper. The dispatch chain in the excerpt is a flat run of mutually exclusive flags, so it should lift out without touching the lifetime-sensitive writer block the source comments warn about. Even that one extraction would remove a large share of the branching.

### `calling_process_cmdline` — process.rs

<FunctionCard fn='calling_process_cmdline' file='src/utils/process.rs' risk='13.73' band='debt' cc='30' nd='4' fo='10' touches='0' />

To work out which command invoked delta, this function inspects the process tree: the parent first, then parent-of-parent, then a naive sibling pid, and finally a pid-range search. It has cyclomatic complexity 30, nesting depth 4 and fan-out of 10, and it hasn't been changed in 633 days. It is generic over a process-interface trait and a closure, with a test-only branch compiled in under the test configuration, so some of its paths exist only for tests.

I would treat this as structural debt with a high blast radius when next touched. The behaviour depends on pid adjacency and process-tree shape across operating systems, which is hard to reproduce in tests, and the multiple return paths mean each strategy needs its own fake. The file has a bug-fix rate of 20% across 5 commits, with no bug-linked commits and no reverts, so I would call that a mild flag, not a defect signal. My first step would be splitting the three lookup strategies (parents, sibling, closest match in the process tree) into separate functions, so the orchestration reads as a short fallback chain.

### `truncate_str_impl` — mod.rs

<FunctionCard fn='truncate_str_impl' file='src/ansi/mod.rs' risk='13.08' band='debt' cc='14' nd='8' fo='10' touches='0' />

Here the problem is depth, not breadth. Cyclomatic complexity is a moderate 14, but nesting reaches 8, which is the level I treat as a strong refactoring signal. The excerpt shows a loop over ANSI-aware segments, an inner loop over graphemes, and inside that the double-width handling with optional fill characters and a fallback branch for unexpectedly wide graphemes. The function also calls itself to measure the tail, so the recursion adds a second thing to reason about.

It hasn't been changed in 756 days. The file-level numbers are the most notable on my list: a bug-fix rate of 66.67% across 3 commits, and a pull-request review comment density of 1.0, the only nonzero value among my five. There are no bug-linked commits and no reverts, and three commits is a small sample, so I would not read this as proof of defects. Still, a deeply nested text-width function with a history skewed toward fixes is where I would want tests around double-width and combining characters before anyone edits it. Extracting the per-grapheme step into a helper that returns whether to continue would flatten the nesting by several levels.

### `show_themes` — show_themes.rs

<FunctionCard fn='show_themes' file='src/subcommands/show_themes.rs' risk='13.04' band='debt' cc='15' nd='4' fo='14' touches='0' />

This subcommand renders a sample diff for each available theme. Cyclomatic complexity is 15 and fan-out is 14, with nesting at 4. The excerpt shows it reading either a built-in sample diff or piped stdin, constructing options and configuration repeatedly from git config, setting up a pager, and then looping over themes with a compound dark/light/color-mode filter and error handling that exits the process on a broken pipe. It is flagged as a god function and exit-heavy, and it hasn't been changed in 756 days.

The history is thin: 2 commits, no bug-linked commits, no reverts. I would frame this as maintainability debt with limited urgency. The cheap win is lifting the dark/light/color-mode condition into a small named predicate, then pulling the per-theme rendering into its own function. That makes the filter testable without a terminal or pager.

### `list_languages` — assets.rs

<FunctionCard fn='list_languages' file='src/utils/bat/assets.rs' risk='12.87' band='debt' cc='9' nd='4' fo='11' touches='0' />

The lowest-complexity function on the list, `list_languages` has cyclomatic complexity 9, nesting depth 4 and fan-out of 11. It collects and sorts syntaxes, then prints them either as a plain list or as aligned columns with line wrapping for long extension lists. The excerpt shows two local constants (`loop_through` and `colored_output`) fixed in the function body, which may leave one of the two output modes unused as written, the kind of thing a refactor would surface. It hasn't been changed in 756 days and the file has a single commit in its history.

Its risk score is high on the strength of fan-out and the god-function pattern, not on branching, which is why it earns a place here at all. It is the entry I would leave for last. If someone is in the file anyway, separating the data gathering from the formatting would make the wrapping logic testable on its own.

**What I would do in order**

My order of attack: break up `run_app` first because it is complex and moving, add tests around `truncate_str_impl` and `calling_process_cmdline` before anyone next edits them, and treat `show_themes` and `list_languages` as opportunistic cleanups.
