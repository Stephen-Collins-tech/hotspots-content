You were asked to fix one thing. Three files touch it. Which one is the landmine?

I used to open unfamiliar code the same way everyone does: read the file, understand the function, make the change. That works fine right up until the change breaks something two files away, in a module nobody mentioned in the ticket. The fix isn't to read more code before touching it — it's to spend five minutes asking the repository's history a few pointed questions first.

## The checklist

**1. Who actually owns this file, recently — not ever.**

```bash
git log --since="6 months ago" --format="%an" -- path/to/file.ts | sort | uniq -c | sort -rn
```

This tells you who to ask, and it's not always the person in the `CODEOWNERS` file. A file can list one owner and be maintained, in practice, by whoever's been closest to the bugs lately.

**2. How often has this actually changed.**

```bash
git log --oneline -- path/to/file.ts | wc -l
```

A file with three commits in five years and a file with three commits last week are both "low activity" by some metrics, but they carry completely different risk. The first is settled. The second is in the middle of something.

**3. How many of those changes were fixes, not features.**

```bash
git log --oneline --grep="fix\|bug\|patch" -i -- path/to/file.ts | wc -l
```

This is a blunt instrument — commit message quality varies wildly — but a file where a third of the history is fixes is telling you something a feature-shipping file isn't.

**4. What else changes when this file changes.**

```bash
git log --format="%H" -- path/to/file.ts | xargs -I{} git show --name-only --format="" {} | sort | uniq -c | sort -rn | head -20
```

This is the one people skip, and it's the one that catches the landmine. If your target file almost always changes alongside a file nobody mentioned in the ticket, that's a coupling the ticket didn't know about. Touch one without the other and you've shipped half a change.

**5. When was the last time, and was it calm or urgent.**

```bash
git log -3 --format="%ad %s" --date=relative -- path/to/file.ts
```

A file last touched two years ago in a routine refactor is a different animal from one touched last Tuesday with a commit message that says "urgent hotfix." Recency plus tone tells you whether you're stepping into calm water or a still-warm incident.

## What this doesn't tell you

None of this is a substitute for reading the code, and none of it tells you *why* a file changed the way it did — commit messages lie, get abbreviated, or just say "wip." It also can't see intent that never made it into a commit: a deliberate decision to leave something alone, a known workaround nobody documented. Treat the output as a set of questions to ask a human, not a verdict.

What it does give you, in five minutes, before you write a line of code: who to loop in, whether you're in stable or volatile territory, and what else might break. That's usually enough to change how carefully you make the first commit.
