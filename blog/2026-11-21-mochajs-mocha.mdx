Of the 909 functions I analyzed in mochajs/mocha at commit 5b5afa7, 29 are critical, and all five of my top hotspots sit in 'active' tier code, meaning they are being changed now and the complexity is live regression risk rather than a backlog item. The top-ranked function, `parseReport` in `scripts/merge-coverage.js`, has an activity-weighted risk score of 2.06, a nesting depth of 10 and was last changed 9 days ago. If you are shipping changes to Mocha's parallel mode, CLI option validation, or coverage tooling this week, these are the functions I would read first.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `parseReport` — merge-coverage.js

<FunctionCard fn='parseReport' file='scripts/merge-coverage.js' risk='2.06' band='critical' cc='13' nd='10' fo='20' touches='1' />

I would start with `parseReport` because it combines a nesting depth of 10, a fan-out of 20 and a last change only 9 days ago. It has the highest activity-weighted risk score in the repository at 2.06. From the source excerpt, it reads an LCOV-style coverage file line by line and dispatches on record prefixes (source file, function, function hit, line hit, branch hit, end of record) inside a single loop. That is an if/else-if chain living inside a for loop, with state (the current source entry, a function list, a hit counter, a per-line seen map) carried across iterations.

<MetricBar label='Max Nesting Depth' value='10' threshold='4' max='12' />

A nesting depth of 10 is well past the point where I would call code hard to reason about; the usual signal to refactor starts around 8. The cyclomatic complexity of 13 is only moderate, so the difficulty here comes from the shape of the code more than from the number of paths. The pairing of function records with hit records depends on ordering and a running counter, and the excerpt shows an explicit error when there are more hit records than function records. That is the kind of implicit contract that is easy to break when someone changes one branch without reading the others.

The file has one commit in the last year, one author in the last 90 days, no bug-linked commits, no reverts and no review comments. So this is not a history of trouble; it is a recently written script that has not yet been reviewed over time. My recommendation: split the loop body into one small handler per record type (for example a function for function records, one for line records, one for branch records) and have the loop only select the handler. That would cut the nesting depth to a handful and make each record type testable with a three-line fixture.

### `run` — worker-core.js

<FunctionCard fn='run' file='lib/nodejs/worker-core.js' risk='1.78' band='critical' cc='11' nd='1' fo='15' touches='1' />

`run` has an activity-weighted risk score of 1.78, a cyclomatic complexity of 11 and a fan-out of 15, with a last change 9 days ago. By name and path, and confirmed by the excerpt, this is the entry point a worker process uses to execute a single test file in parallel mode. It validates its arguments, deserializes options from a string, merges in worker-specific overrides, runs the one-time bootstrap, loads the file, and then wraps the actual Mocha run in a promise with cleanup in a finally block.

The nesting is flat (depth 1), so this is not hard to follow line by line. The risk is breadth: argument validation, option deserialization, bootstrap, file loading, process listener cleanup and result serialization all live in one function, and fan-out of 15 means a change to any of those collaborators can surface here. The excerpt also shows deserialization done by evaluating a string, and a TODO comment noting that the failure path of serialization is not fully worked out. I flag the TODO only because it marks a place the authors already consider unsettled, and this function is being edited now.

My recommendation is to extract the argument validation and option deserialization into a separate function that returns the final options object. That is the part with the most early-return branches, and moving it out would take a large share of the cyclomatic complexity with it and give you a unit-testable seam that does not need a real Mocha instance.

### `createWorker` — worker-core.js

<FunctionCard fn='createWorker' file='lib/nodejs/worker-core.js' risk='1.77' band='critical' cc='5' nd='1' fo='17' touches='1' />

`createWorker` is the factory that contains `run`, and the two share a file, a last-change date of 9 days ago and nearly identical scores (1.77 versus 1.78). Its cyclomatic complexity is only 5, but its fan-out is 17, the second highest among my top five. From the excerpt, it takes injectable implementations of Mocha, the requires handler, the serializer and the plugin validator, and defines the bootstrap and run closures inside.

I read the fan-out here as a design choice: the injection parameters make the worker testable, and they also inflate the count of distinct functions referenced. In JavaScript, closures like these also create hidden coupling that a static fan-out count tends to undercount, because the inner functions share mutable state (the root hooks value and a bootstrap function that overwrites itself with a no-op after the first call). That self-replacing pattern is clever, and it is also exactly the sort of thing that surprises the next person who reads it.

Because `run` and `createWorker` sit in the same file and share a last-change date, I would review them as one unit. My recommendation for this one is documentation and tests rather than restructuring: add a test that pins the 'bootstrap runs once per worker' behavior, so a future edit to the closure cannot silently change it.

### `validateRunOptions` — run.cjs

<FunctionCard fn='validateRunOptions' file='lib/cli/run.cjs' risk='1.75' band='critical' cc='11' nd='2' fo='9' touches='5' />

`validateRunOptions` is the one function in my top five with real recent history: 5 touches in the last year, a last change 19 days ago, 2 distinct authors in the last 90 days, a bug-fix rate of 20% (1 of 5 commits) and a review-comment density of 16. Its activity-weighted risk score is 1.75, with a cyclomatic complexity of 11, nesting depth of 2 and fan-out of 9.

The excerpt shows a sequence of guard clauses that reject incompatible command-line flag combinations: one-and-done options that are mutually exclusive, an invert flag that needs a pattern flag, two pattern flags that cannot be combined, and a set of restrictions that apply when parallel mode is on (no file option, no sort option, and certain reporters are rejected). Each rule is simple, but every new option in the CLI is a candidate for another rule here, and the cyclomatic complexity grows with it.

The review-comment density of 16 is the highest of the five, which fits a function where reviewers have opinions about each rule. One bug-fix commit in five is a modest signal and does not tell me the current code is wrong, but combined with 5 touches it is the clearest case in this list of a function that keeps being edited. I would convert the parallel-mode rules into a small table of conflicting option pairs and loop over it, so adding a new incompatibility is a data change instead of a new branch. That would cut the branch count roughly in half and make the rules readable at a glance.

### `mergeInto` — merge-coverage.js

<FunctionCard fn='mergeInto' file='scripts/merge-coverage.js' risk='1.69' band='high' cc='7' nd='3' fo='4' touches='1' />

`mergeInto` is the smallest of the five and the only one in the high band rather than critical, with an activity-weighted risk score of 1.69, a cyclomatic complexity of 7, nesting depth of 3 and fan-out of 4. It was last changed 9 days ago, in the same change window as `parseReport`. From the excerpt, it folds one coverage map into another by summing hit counts for lines, branches and functions, with a special case for sources that do not yet exist in the target.

I include it because it is the second half of the same script and shares the same recent change. Its structure is three near-identical loops, each doing a get-or-default-then-add. That repetition is a small refactoring opportunity: a single helper that merges two count maps would remove two of the three loops and shrink the cyclomatic complexity. Since the file has one commit and one author in the last 90 days, I would treat this as low-effort cleanup to do alongside the `parseReport` split, not as a separate project.

## Where to start

I would start with `parseReport`, because a nesting depth of 10 in a function changed 9 days ago is the clearest case of complexity and activity overlapping. Do `mergeInto` in the same pass, since both live in `scripts/merge-coverage.js` and a single reviewer can hold the whole file in their head. Next, review `run` and `createWorker` together in `lib/nodejs/worker-core.js`, focusing on a test that pins the once-per-worker bootstrap behavior. Last, take `validateRunOptions` because it has the most real change history of the five; turning its flag-conflict rules into a table is the cheapest way to stop its complexity growing with every new CLI option.

One caveat on scope: I treated only the five functions above as priorities; other code I looked at for context is in quiet tier and I would not prioritize it.
