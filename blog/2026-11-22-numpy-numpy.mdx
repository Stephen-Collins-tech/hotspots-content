### `PyUFunc_GeneralizedFunctionInternal` — ufunc_object.c

<FunctionCard fn='PyUFunc_GeneralizedFunctionInternal' file='numpy/_core/src/umath/ufunc_object.c' risk='3.55' band='critical' cc='62' nd='5' fo='49' touches='45' />

This is the execution path for generalized ufuncs, the ones with core dimensions such as matrix-style operations. From the source excerpt I can see a long declaration block of fixed-size arrays sized by the maximum argument and dimension counts, followed by a sequence of validation steps (casting validation, initialization of variable parts, keepdims and axis support checks) that jump to a shared `fail` label on error. That goto-cleanup shape is idiomatic C, but it means every new resource acquired mid-function has to be reflected in the failure path.

Cyclomatic complexity of 62 means 62 independent paths, each a candidate test case. Fan-out of 49 is tied for the broadest coupling in the group, and nesting of 5 is the deepest. The activity-weighted risk score of 3.55 is the highest in the repo, and with 45 touches in the last year and a change 1 day ago, this is where I would start.

<MetricBar label='Cyclomatic Complexity' value='62' threshold='10' max='70' />

My recommendation: the argument-validation preamble (casting, keepdims, axis) is a natural extract-method candidate. Pulling it into a single prepare-and-validate helper would shrink the function without touching the iteration logic.

### `ufunc_generic_fastcall` — ufunc_object.c

<FunctionCard fn='ufunc_generic_fastcall' file='numpy/_core/src/umath/ufunc_object.c' risk='3.48' band='critical' cc='55' nd='4' fo='28' touches='45' />

This looks like the main call entry point for ufuncs: the excerpt shows a vectorcall-style signature taking positional arguments and keyword names. It begins with a fast path for single scalar input, then checks the positional argument count, allocates a scratch workspace, and carves it into pointer regions for signatures, operands, dtypes, and descriptors. It then separates positional `out` arguments from keyword ones.

Cyclomatic complexity of 55 with nesting of 4 and fan-out of 28 tells me this one function is parsing arguments, handling several calling conventions, and managing memory layout all at once. Because this sits on the path of every ufunc call, a change here has wide reach even though its fan-out is lower than its siblings'.

My recommendation: separate the argument-parsing phase from the dispatch phase. The scalar fast path and the scratch-space layout are each self-contained enough to move into their own functions.

**`PyUFunc_Accumulate` and `PyUFunc_Reduceat` — ufunc_object.c**

<FunctionCard fn='PyUFunc_Accumulate' file='numpy/_core/src/umath/ufunc_object.c' risk='3.47' band='critical' cc='66' nd='3' fo='49' touches='45' />

<FunctionCard fn='PyUFunc_Reduceat' file='numpy/_core/src/umath/ufunc_object.c' risk='3.47' band='critical' cc='61' nd='3' fo='49' touches='45' />

I am grouping these because their excerpts share a structure. Both open with the same per-output setup: a local owned copy of the output array pointers, an operand-axes table, and an initialized array of first-element copy descriptors. Both then fetch the buffer size and error mask, and `PyUFunc_Accumulate` goes on to promote and resolve the implementation through `reducelike_promote_and_resolve`. The comments in both mention multi-output support, which suggests this machinery was recently generalized from a single output to several. That fits the recent-change numbers.

`PyUFunc_Accumulate` has the highest cyclomatic complexity in the whole top five at 66, and `PyUFunc_Reduceat` follows at 61. Both have fan-out of 49 and nesting of only 3, so the risk here is breadth of paths and coupling rather than deep nesting. Duplicated setup across two functions of this size is a classic way for a fix to land in one and miss the other.

<MetricBar label='Cyclomatic Complexity' value='66' threshold='10' max='70' />

My recommendation: extract the shared per-output setup and teardown into one helper used by both. That removes a duplication hazard and gives the multi-output logic a single place to be tested.

### `try_reduce_contiguous` — ufunc_object.c

<FunctionCard fn='try_reduce_contiguous' file='numpy/_core/src/umath/ufunc_object.c' risk='3.46' band='critical' cc='43' nd='4' fo='25' touches='45' />

The name and excerpt point to a fast path for reductions over contiguous data. It starts with a long compound condition that decides whether the fast path applies (no output provided, no where-mask, no initial value, all axes reduced, trivially iterable and aligned input, matching descriptors) and returns 0 to fall through to the general path otherwise. After that it chooses between stack storage for scalar returns and allocating 0-d result arrays, then queries for an initial value.

This is the smallest of the five at cyclomatic complexity 43, but it is the least forgiving to change because a fast path must agree exactly with the slow path it shortcuts. The eligibility condition is a single dense boolean expression, which is hard to review and easy to get subtly wrong when a new case is added.

My recommendation: pull the eligibility test into a named predicate such as a can-use-contiguous-fast-path helper, so each clause can be read, commented, and tested separately.

## Where to start

I would start with `PyUFunc_GeneralizedFunctionInternal`, because it has the highest activity-weighted risk score at 3.55, the deepest nesting at 5, and fan-out of 49. The scores are tightly clustered (3.46 to 3.55), so the ranking among the five matters less than the fact that the whole file is one risk surface.
