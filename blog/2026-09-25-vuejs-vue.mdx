### `genElement` — src/compiler/codegen/index.ts

<FunctionCard fn='genElement' file='src/compiler/codegen/index.ts' risk='21.72' band='critical' cc='27' nd='8' fo='10' touches='0' />

This is the top-ranked hotspot in the repo, and it's a debt-quadrant function, not a fire one — zero touches in the last 30 days, and 784 days since its last change. The source shows why the complexity number is earned: a long if/else-if chain ('el.staticRoot', 'el.once', 'el.for', 'el.if', template/slot special cases) that ultimately falls through to a nested component-vs-element branch with its own inner conditionals for data generation, script-setup binding checks, and a final loop over module transforms. A nesting depth of 8 lines up with that fallthrough branch nesting three or four levels of decision-making before it ever calls '_c(...)'. The fan-out of 10 means this function is a routing hub for the rest of codegen — 'genStatic', 'genOnce', 'genFor', 'genIf', 'genSlot', 'genComponent', 'genData', 'genChildren' are all one call away. Two total commits on record, at least one of them a bug fix, which raises the stakes for whoever edits this next without a full mental model of the branch order. My recommendation: before the next feature touches this, extract the component/element branch (the 'else' block with 'code = genComponent(...)' vs the data/tag/children logic) into its own named function. That alone would cut nesting by a level and isolate the highest-churn-risk logic from the routing chain above it.

### `createPatchFunction` — src/core/vdom/patch.ts

<FunctionCard fn='createPatchFunction' file='src/core/vdom/patch.ts' risk='20.15' band='critical' cc='61' nd='9' fo='70' touches='0' />

This is the classic god-function pattern, and the numbers back it up: cyclomatic complexity of 61, nesting depth of 9, and a fan-out of 70 — the highest coupling number in this whole set. It's also flagged as a long function and stale-complex. The excerpt shows why: it's a factory that builds a closure over 'cbs', 'emptyNodeAt', 'createRmCb', 'removeNode', 'isUnknownElement', 'creatingElmInVPre', and 'createElm', wiring up module hooks in a nested double loop before defining a cluster of inner functions that all share that closure scope. A fan-out of 70 means changes to this function's internals can ripple into DOM creation, component creation, node removal, and hook dispatch simultaneously — that's a wide blast radius for a single edit. This is a debt-quadrant function: it hasn't been changed in 353 days, and half of its two recorded commits were bug fixes. Given the sheer surface area, I wouldn't attempt a single refactor pass here — I'd start by pulling the standalone helper functions ('emptyNodeAt', 'createRmCb', 'removeNode', 'isUnknownElement') out of the closure and testing them independently, since they don't obviously need to share scope with 'createElm'. That's a low-risk first cut that reduces the god-function's line count without touching the patch algorithm itself.

### `compileScript` — packages/compiler-sfc/src/compileScript.ts

<FunctionCard fn='compileScript' file='packages/compiler-sfc/src/compileScript.ts' risk='19.48' band='critical' cc='185' nd='7' fo='81' touches='0' />

This one deserves its own paragraph because a cyclomatic complexity of 185 is in a different category from everything else on this list.

<MetricBar label='Cyclomatic Complexity' value='185' threshold='30' max='190' />

A fan-out of 81 compounds it — this function is coordinating parser plugin selection, TypeScript detection, script-vs-script-setup merging, binding analysis, and CSS variable rewriting, all inside one body. The excerpt shows early branching just to assemble the Babel parser plugin list (checking 'scriptLang', 'scriptSetupLang', decorator support) before it even gets to the actual compile logic, and a try/catch around the no-script-setup path that silently falls back to the raw script on parse failure. That silent fallback is worth flagging on its own: it's a legitimate design choice for tolerating custom Babel syntax, but it's also an easy-to-miss exit path buried inside an already dense function. Eight of ten recorded commits being bug fixes is the strongest historical signal on this list — which doesn't prove this specific function is buggy, but it does tell me this area of the compiler has needed correction before. This function sits in the debt quadrant too: it's been 353 days since anyone touched it, with zero touches in the last 30 days. Given the conditional-type-heavy nature of TypeScript compiler code, I'd treat 185 as a hard trigger for decompose-conditional refactoring — start by extracting the plugin-list assembly (the 'jsx'/'typescript'/'decorators-legacy' block) into its own function, since it's self-contained and easy to unit test in isolation.

### `parseFilters` — src/compiler/parser/filter-parser.ts

<FunctionCard fn='parseFilters' file='src/compiler/parser/filter-parser.ts' risk='18.45' band='critical' cc='50' nd='9' fo='7' touches='0' />

This is a hand-written character-by-character parser — the excerpt shows a 'charCodeAt' scan tracking quote state ('inSingle', 'inDouble', 'inTemplateString', 'inRegex') alongside bracket-depth counters ('curly', 'square', 'paren'), with a switch statement handling each punctuation character and a nested loop to detect regex-vs-division ambiguity. A nesting depth of 9 is the deepest in this entire set, and it's earned honestly: the regex-detection logic alone nests a backward character scan inside the main forward scan. Low fan-out (7) means this function isn't broadly coupled to the rest of the codebase — it's self-contained, which is good news for isolated testing but doesn't reduce how hard it is to reason about on its own terms. Only one commit on record, and this is another debt-quadrant function: it's gone 784 days without a change, with zero touches in the last 30 days. Because this is fundamentally a state machine, the clearest refactoring path is to make the states explicit — replace the boolean flag cluster ('inSingle'/'inDouble'/'inTemplateString'/'inRegex') with a single enum-like state variable and a lookup table of transitions. That collapses several of the 'else if' branches into one dispatch and would meaningfully cut both the complexity and nesting numbers.

### `parseHTML` — src/compiler/parser/html-parser.ts

<FunctionCard fn='parseHTML' file='src/compiler/parser/html-parser.ts' risk='17.96' band='critical' cc='50' nd='6' fo='33' touches='0' />

The excerpt confirms this is the main HTML tokenizer loop — a 'while (html)' scan that branches through comment detection, conditional-comment handling, doctype matching, end-tag matching, and start-tag matching, each with its own early-continue exit. That's the exit-heavy pattern in practice: I count at least five distinct 'continue' points in the visible excerpt alone, each representing a separate path a test suite needs to cover. A fan-out of 33 and god-function/long-function flags both point to a tokenizer that's grown to own too much — comment parsing, tag parsing, and text-boundary detection are all interleaved in the same loop body rather than being separated into smaller matchers. This function rounds out the debt quadrant: it's gone 652 days without a change, on two recorded commits, with zero touches in the last 30 days. Given the exit-heavy shape, I'd prioritize extracting each branch (comment, conditional-comment, doctype, end-tag, start-tag) into its own named matcher function that returns a consumed-length or null — that turns five inline exit points into five testable units and shrinks the main loop back down to a dispatch table.
