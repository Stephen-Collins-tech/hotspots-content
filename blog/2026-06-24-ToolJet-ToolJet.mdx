  - question: "What is a god function and why does it matter in ToolJet?"
    answer: "A god function is a single function that has accumulated so many responsibilities that it knows about and directly controls a disproportionate share of the system's behaviour. In structural terms, it shows up as a combination of high cyclomatic complexity, high nesting depth, and high fan-out — the function branches extensively, nests those branches deeply, and calls a large number of other functions directly. In ToolJet, `Table` in the database UI calls 170 distinct functions from inside a single component body, while `EditRowForm` and `RowForm` each combine CC above 70 with fan-out above 58. The concrete problem this creates is that any change to a god function — or to any of its many dependencies — requires the author to hold an unusually large mental model, which increases the probability of introducing a regression. It also makes the function nearly impossible to test in isolation without mocking most of the application."

### `resolveReferences` — utils.js

<FunctionCard fn='resolveReferences' file='frontend/src/_helpers/utils.js' risk='21.36' band='critical' cc='37' nd='6' fo='19' touches='1' />

`resolveReferences` is the expression-evaluation heart of ToolJet's dynamic binding system. Looking at the source excerpt, it dispatches on the runtime type of an `object` argument and then handles at least three distinct interpolation syntaxes: `{{ }}` double-curly for JavaScript expressions, `%% %%` percent-delimited for server variables, and mixed dynamic-variable strings. The large `switch` on `objectType` immediately fans into deeply nested conditionals — the excerpt shows at least four levels of nesting within the `'string'` case alone, and the function recurses into itself for nested dynamic variables.

A cyclomatic complexity of 37 means there are 37 independent execution paths through this function — each one a required test case and a potential defect surface. The nesting depth of 6 makes it genuinely hard to trace a single value from input to output without losing context. The fan-out of 19 tells me the function directly calls `resolveString`, `resolveCode`, `getDynamicVariables`, `validateMultilineCode`, `removeNestedDoubleCurlyBraces`, and at least 14 other functions — changes to any of those callees can alter behaviour here in ways that are not immediately obvious, especially given JavaScript's dynamic property access patterns.

The file-level external signals show that exactly half of all commits to `utils.js` have been tagged as bug fixes (`bug_fix_fraction: 0.5`). That is historical context, not proof that this function is broken, but it does suggest the file has required correctness corrections before. Two authors have touched the file in the last 90 days.

The function was last modified 19 days ago and has been touched once in the last 30 days — active, but not frantic. The risk here is that the next change to the expression-evaluation logic — adding a new interpolation syntax, adjusting server-variable validation — has 37 paths it could break.

**Recommendation:** The three interpolation branches (`{{ }}` single-expression, `{{ }}` multi-expression, and `%% %%`) are distinct enough to extract into three named functions: `resolveSingleCurlyExpression`, `resolveMultiCurlyExpression`, and `resolvePercentExpression`. That decomposition alone would bring each extracted function's CC well below 15 and make the top-level dispatcher trivially testable.

### `SwitchBranchModal` — SwitchBranchModal.jsx

<FunctionCard fn='SwitchBranchModal' file='frontend/src/AppBuilder/Header/SwitchBranchModal.jsx' risk='20.78' band='critical' cc='54' nd='8' fo='58' touches='2' />

`SwitchBranchModal` is the React component responsible for the branch-switching dialog in the AppBuilder. The source excerpt shows it pulling state from two separate stores — `useStore` (the app-level store) and `useWorkspaceBranchesStore` — destructuring roughly 15 state values from each. It then computes `currentBranchName` through a multi-arm ternary that handles workspace git sync, per-app branching with version-type checks, and a fallback to a default branch derived from either HTTPS or SSH remote configs.

A CC of 54 and a nesting depth of 8 in a single React component function is a significant structural burden. The fan-out of 58 is the second-highest in the top five; that breadth of direct calls makes it a hub through which a large portion of the branch-management interaction flows. The `useEffect` in the excerpt alone branches on `branchingEnabled` to dispatch either workspace-level or per-app fetch sequences using `Promise.all`, which means async error paths multiply the effective execution complexity further — JavaScript's async callback chains can obscure coupling that fan-out metrics may undercount.

This function has been touched twice in the last 30 days and was last modified just 7 days ago — it is the most recently changed entry in the top five. With CC 54 and two authors active on the file in the last 90 days, concurrent edits to this component carry meaningful merge-conflict and regression risk.

**Recommendation:** The two fetch strategies (`branchingEnabled` vs. per-app branching) are sufficiently independent to split into a custom hook — something like `useBranchLoader(appId, organizationId, branchingEnabled)` — leaving the component to handle only rendering. The `currentBranchName` derivation chain is a second extraction candidate: isolating that logic into a pure function makes it directly unit-testable without mounting the component.

### `EditRowForm` — EditRowForm.jsx

<FunctionCard fn='EditRowForm' file='frontend/src/TooljetDatabase/Forms/EditRowForm.jsx' risk='20.69' band='critical' cc='84' nd='8' fo='67' touches='1' />

`EditRowForm` renders the form for editing an existing row in ToolJet's built-in database UI. The source excerpt reveals why the CC reaches 84: the component must reason about every column's data type, null status, default value, and primary-key constraint simultaneously, and it does so through parallel `useEffect` hooks that each iterate over `columns` and `currentValue` in nested conditional chains. The nesting depth of 8 is visible in the excerpt — a `useEffect` body that iterates over keys, filters by null, then filters again by default-value comparison, with separate handling for `jsonb` types inside each loop.

<MetricBar label='Cyclomatic Complexity' value='84' threshold='10' max='100' />

A CC of 84 means this single component function contains 84 independent execution paths. The fan-out of 67 means it directly invokes 67 distinct functions — form state setters, context accessors, comparison utilities like `compareValueInObject`, and toast utilities — making it a god function in the truest sense: it knows about and depends on a large fraction of the database UI's surface area.

The file-level `bug_fix_fraction` is 1.0 — every recorded commit to `EditRowForm.jsx` has been tagged as a bug fix. As a file-level signal this does not tell me which function caused those fixes, but it is worth noting: a function of this structural complexity, in a file with that commit history, warrants careful test coverage before any further modification. One author has been active on this file in the last 90 days.

**Recommendation:** The per-column tab-state initialisation logic (deciding whether a column shows 'Custom', 'Null', or 'Default') is a clear extraction target — it appears in both the `useEffect` and the initial state setup, suggesting it is already partially duplicated. A `getInitialTabState(columns, currentValue)` pure function would eliminate that duplication, reduce CC substantially, and be testable without a React render.

### `Table` — TooljetDatabase/Table/index.jsx

<FunctionCard fn='Table' file='frontend/src/TooljetDatabase/Table/index.jsx' risk='20.69' band='critical' cc='94' nd='8' fo='170' touches='1' />

`Table` is the primary data-table component for ToolJet's internal database explorer. The source excerpt shows it managing an extraordinary amount of local state directly: column editing, row creation, bulk upload, filter visibility, cell-level click and edit state, foreign-key cache, referenced column details, and progress tracking for uploads — all declared as `useState` calls in a single function body, alongside context consumption from `TooljetDatabaseContext`.

<MetricBar label='Fan-out (distinct callees)' value='170' threshold='15' max='200' />

The fan-out of 170 is the outlier in this entire analysis. It is not just high — it means `Table` directly calls 170 distinct functions, making it the most broadly coupled function I found in the repository. In a JavaScript React context, that coupling is likely a mix of context method calls, service calls like `tooljetDatabaseService.findOne`, query-builder method chains (`PostgrestQueryBuilder`), and child component callbacks. Any change to any of those 170 dependencies has a potential interaction with this component. Combined with a CC of 94 and a nesting depth of 8, this is the highest blast-radius function in the codebase.

The `bug_fix_fraction` at the file level is 1.0, consistent with `EditRowForm.jsx`. One author has been active in the last 90 days.

**Recommendation:** The foreign-key data fetching logic — `fetchFkDataForColumn` — is already defined as an inner function in the excerpt. Promoting it and similar inner functions to module-level or custom-hook scope is the highest-leverage first step: it would reduce the component's fan-out meaningfully and make the async data-fetch logic independently testable. The cell-edit state cluster (`cellClick`, `cellVal`, `editPopover`, `defaultValue`, `nullValue`) is a second cohesive group that warrants extraction into a `useCellEditState` hook.

### `RowForm` — RowForm.jsx

<FunctionCard fn='RowForm' file='frontend/src/TooljetDatabase/Forms/RowForm.jsx' risk='20.62' band='critical' cc='72' nd='8' fo='58' touches='1' />

`RowForm` handles new-row creation in the TooljetDatabase UI and shares much of its structural DNA with `EditRowForm`. The source excerpt shows the same pattern: parallel arrays for primary-key and non-primary-key columns built by iterating `columns` in the function body, followed by `defaultActiveTab` and `inputValuesDefaultValues` helper functions defined inline — each containing their own branching logic over column types, constraints, and null/default combinations.

The inline `inputValuesDefaultValues` function in the excerpt alone has at least five `if`/`else` branches handling `timestamp with time zone`, auto-increment primary keys, non-null defaults, primary-key defaults, and the fallback case. That nesting is inside a `.map()` callback inside the outer component function, contributing directly to the nesting depth of 8. With CC 72 and fan-out 58, the structural profile is nearly identical to `EditRowForm`, which makes sense — both forms operate on the same column-schema model and appear to have evolved in parallel rather than being abstracted into a shared base.

The `bug_fix_fraction` for this file is also 1.0, with one commit and one active author in the last 90 days. That single-author ownership on a CC-72 function is a knowledge-concentration risk: the context required to reason about all 72 paths lives with one engineer.

**Recommendation:** `RowForm` and `EditRowForm` share enough of the same column-resolution logic that a shared `useColumnFormState(columns, initialRowValues)` hook would serve both. Extracting it would reduce duplication, bring both components' CC below 40 with moderate effort, and distribute the cognitive load currently concentrated in one author's mental model. The `defaultActiveTab` and `inputValuesDefaultValues` inner functions are the natural first extraction points — they are already named and scoped, making the refactor mechanical rather than architectural.

## What the pattern distribution tells me

All five top hotspots carry the god-function, long-function, complex-branching, deeply-nested, and exit-heavy patterns simultaneously. That is not a coincidence — it reflects a consistent approach to building complex UI forms and components by accumulating logic inside the component function itself rather than extracting it into hooks, services, or pure utility functions. The TooljetDatabase forms (`RowForm`, `EditRowForm`, `Table`) are the most concentrated example: three functions in the same subdirectory, all with CC above 70, nesting depth of 8, and file-level bug-fix fractions of 1.0.

The `resolveReferences` and `SwitchBranchModal` functions are structurally different problems — a utility dispatcher and a feature-modal respectively — but they share the same root cause: responsibilities that should be separated have been allowed to accumulate in single function bodies.

For context: `resolve` in the same `utils.js` file sits in the 'watch' quadrant with CC 6 — proof that the helpers file is capable of housing simple, focused functions. The complexity in `resolveReferences` is not an inherent property of what the function does; it is a property of how much it does at once.
