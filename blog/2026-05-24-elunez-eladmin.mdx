### `getPredicate` — `eladmin-common/src/main/java/me/zhengjie/utils/QueryHelp.java`

`getPredicate` is the structural centre of gravity for eladmin's dynamic query construction. It calls into 103 distinct functions — a fan-out that makes it the broadest coupling point in the entire analyzed codebase — while simultaneously carrying a cyclomatic complexity of 25 and a max nesting depth of 8. Those three numbers together explain why it has accumulated every major structural anti-pattern in this dataset: god function, long function, complex branching, deeply nested, exit-heavy, and stale-complex. The exit-heavy designation is particularly significant here: multiple return paths scattered across 8 levels of nesting mean that achieving meaningful test coverage requires enumerating a large number of distinct execution paths, each of which represents a potential bug surface.

The function has not been touched in 1,039 days, and no authors have committed to its file in the last 90 days. This is not a sign that the code is safe — it is a sign that the debt has been deferred. The file's historical commit data shows a bug-fix commit ratio of 0.25 across 4 total commits, which is worth noting as context: roughly one in four historical commits to this file has been a bug fix, though this does not prove the current function is defective. When this function is next modified — whether to add a new query operator, fix a filter edge case, or extend a data type — the engineer doing it will be navigating 8 levels of nesting and 103 dependencies with no recent institutional memory (0 authors in 90 days). The recommendation is to decompose `getPredicate` using extract-method refactoring before the next feature touches it: identify the top-level dispatch logic and pull each query-type handler into a dedicated private method or strategy class. That alone would cut nesting depth and reduce the per-path cognitive load substantially.
