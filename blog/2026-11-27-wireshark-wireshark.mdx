### `dissect_oran_c_section` — packet-oran.c

<FunctionCard fn='dissect_oran_c_section' file='epan/dissectors/packet-oran.c' risk='3.74' band='critical' cc='399' nd='7' fo='62' touches='100' />

This is the top-ranked function with an activity-weighted risk score of 3.74. It has 100 touches in the last year, was last changed 3 days before the analysis, and had 6 distinct authors in the last 90 days.

<MetricBar label='Cyclomatic Complexity' value='399' threshold='30' max='460' />

From the excerpt, the function parses the C-Plane section of the O-RAN fronthaul protocol. It takes 14 parameters, declares a long list of local state variables up front (fixed-size arrays for PRB flags and UE IDs, bitmask and subtree handles), and then branches on section type. One condition groups section types 0, 1, 2, 3, 5, 9, 10 and 11 as 'similar, so handle as common with per-type differences', with further type checks nested inside it. Several comments in that excerpt flag things I'd read as unfinished work, such as 'TODO: mark as ignored if SE6, SE12 or SE19 present'.

That structure is a branch-per-section-type pattern, and the domain explains much of it: the protocol defines many section types and extensions. The cost still falls on whoever touches it. With 399 paths, a complete test suite would need hundreds of cases, and a nesting depth of 7 plus fan-out of 62 mean a change in one section-type branch is hard to reason about in isolation. A 100-touch history on a function this size is also where merge conflicts and accidental cross-branch edits are most likely.

My recommendation is to split along the section-type boundary that the code already draws: pull the common ST0/1/2/3/5/9/10/11 handling into one helper and give the other section types their own functions, with the shared local state passed as a small struct instead of 14 parameters. The extensions are a second natural seam, since they are separate protocol concepts.

### `dissect_oran_c` — packet-oran.c

<FunctionCard fn='dissect_oran_c' file='epan/dissectors/packet-oran.c' risk='3.7' band='critical' cc='152' nd='6' fo='61' touches='100' />

This is the caller of the function above, in the same file, with an activity-weighted risk score of 3.7 and an identical change history: 100 touches in the last year, 3 days since last change, 6 distinct authors in the last 90 days. Its cyclomatic complexity is 152, nesting depth 6, fan-out 61.

The excerpt shows an entry-point dissector doing several jobs at once: setting protocol and info columns, building the subtree, reading the eAxC ID, looking up per-conversation flow state, allocating that state on first visit, and doing sequence-number checks that record unexpected sequence numbers in a results table. That combination of presentation, state management and protocol validation in one function is what drives the 61 distinct callees.

The fact that both O-RAN functions share the same touch count and last-change date suggests they usually change together, which is what I'd expect from a caller and callee pair. My recommendation is to extract the conversation-state and sequence-analysis block into its own function first. The excerpt shows it runs only on the first visit of a frame, which makes it a plausible candidate for testing apart from the tree-building code.

### `dissect_tns_message` — packet-tns.c

<FunctionCard fn='dissect_tns_message' file='epan/dissectors/packet-tns.c' risk='3.67' band='critical' cc='458' nd='6' fo='92' touches='145' />

This function has the highest cyclomatic complexity in the data, 458, and the highest fan-out, 92, with an activity-weighted risk score of 3.67. It was touched 145 times in the last year, most recently 7 days before the analysis, by 4 distinct authors in the last 90 days. Its bug-fix rate is about 7.6%, the lowest of the five.

<MetricBar label='Fan-out' value='92' threshold='15' max='100' />

The excerpt shows a switch over a data function ID, with each case parsing a different Oracle TNS message type. The SET_PROTOCOL case alone has two near-identical loops, one for the request side and one for the response side, each reading version bytes until a zero terminator and appending them to a subtree. The only differences are the field identifiers and a few surrounding items. There is also an early return to a separate OCI-specific dissector, `dissect_tns_oci_message`, for server responses to OCI clients, which shows the authors have already been peeling pieces off this function.

That is the direction I'd continue. Make each case of the switch a function of its own, starting with the cases that duplicate request and response logic, and keep `dissect_tns_message` as a dispatcher. With 145 touches in a year, this is the most frequently changed function of the five, so every case extracted removes lines from the place that is edited most.

### `proto_custom_set` — proto.c

<FunctionCard fn='proto_custom_set' file='epan/proto.c' risk='3.62' band='critical' cc='60' nd='6' fo='34' touches='53' />

This is a different kind of hotspot. At cyclomatic complexity 60 it is much smaller than the dissectors, but it lives in `epan/proto.c`, which the dissectors all depend on. It had 53 touches in the last year, was changed 0 days before the analysis, and has a bug-fix rate of about 24.5% with 2 distinct authors in the last 90 days.

From the excerpt, it evaluates a list of custom column fields and writes comma-separated results into two caller-supplied character buffers, tracking two offsets and checking against a size limit before each separator. That is manual buffer management in C, where the offset arithmetic is part of the complexity beyond what the cyclomatic count captures. The loop handles several cases: a display filter that returns values, one that only passes or fails, and plain field lookups, with an occurrence index adjusting which value is picked. The comments contain several 'XXX' notes about unresolved design questions, such as how occurrence should apply when multiple fields are involved.

The bug-fix rate is the highest in this list, but there are still no bug-linked commits or reverts recorded for the file, so I'd treat it as a prompt for careful review, not evidence of defects. My recommendation is to separate the 'filter returned values' branch from the 'filter passed or failed' branch and the plain-field branch, and to put the append-with-separator logic in one helper so the bounds check exists in one place instead of being repeated.

### `proto_registrar_dump_values` — proto.c

<FunctionCard fn='proto_registrar_dump_values' file='epan/proto.c' risk='3.58' band='critical' cc='50' nd='6' fo='18' touches='53' />

This is the fifth function and the smallest by every structural measure, with cyclomatic complexity 50, nesting depth 6 and fan-out 18. It shares `proto.c`'s history: 53 touches in the last year, changed 0 days before the analysis, 2 distinct authors in the last 90 days, and a bug-fix rate of about 24.5%.

Based on its name and the excerpt, it walks the registered header-field table, skips deregistered entries, protocols and text-only fields, and then selects a value-string, range-string, 64-bit value-string, true/false or unit-name table depending on the field's type and display flags. The condition that checks whether the type is one of roughly twenty numeric types is a long chain of equality comparisons, which contributes much of the complexity count without adding any real decision logic.

This is the easiest fix on the list. Move the numeric-type check into a small predicate function and the table-selection logic into its own function, and the cyclomatic complexity should drop well below its current 50. It is a good first change for anyone wanting to build confidence in refactoring this file before touching `proto_custom_set`.

## Where to start

I would start with `dissect_tns_message`. It has the highest cyclomatic complexity and fan-out, and with 145 touches in the last year it is the most frequently changed function here, so every extracted case pays off quickly. Next I would take the section-type split in `dissect_oran_c_section` and the state-and-sequence extraction in `dissect_oran_c`, since they share a file, a change history and 6 recent authors, and are likely edited together. The two `proto.c` functions are cheap, low-risk practice for the same techniques, but because that file underpins every dissector, I would make sure any refactoring there has a test in place first.

Other critical-band functions outside the top five are quiet-tier: structural debt, not live churn.
