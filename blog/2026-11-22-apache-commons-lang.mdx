### `replaceEachOnce` — StringUtils.java

<FunctionCard fn='replaceEachOnce' file='src/main/java/org/apache/commons/lang3/StringUtils.java' risk='3.35' band='critical' cc='25' nd='3' fo='16' touches='70' />

I would start with `replaceEachOnce` because it has the highest activity-weighted risk score in the repository scan (3.35), a cyclomatic complexity of 25, and a fan-out of 16, in a file last changed 4 days ago.

From the excerpt, this is a private helper that replaces each of several search strings at most once. It validates its inputs and throws on mismatched array lengths. It then runs a search loop over the search list, estimates a buffer size, and runs a second replacement loop. A cyclomatic complexity of 25 means 25 independent paths, each one a test case you need. The nesting depth of 3 is modest, so the complexity comes from many sequential branches and compound conditions rather than deep nesting. A comment in the source flags that the search logic is duplicated, with markers noting where the duplicated block starts and ends. Duplicated logic inside one function is a specific change hazard: a fix applied to one copy and not the other is the usual failure mode.

<MetricBar label='Cyclomatic Complexity' value='25' threshold='10' max='30' />

My recommendation: extract the 'find the earliest matching search string' loop into a named helper and call it from both places where the logic currently repeats. That removes the duplicated block, lets you unit test the search step on its own, and should cut the main function's path count substantially. Do the same for the buffer-size estimation loop.

### `splitByWholeSeparatorWorker` — StringUtils.java

<FunctionCard fn='splitByWholeSeparatorWorker' file='src/main/java/org/apache/commons/lang3/StringUtils.java' risk='3.29' band='critical' cc='10' nd='5' fo='11' touches='70' />

`splitByWholeSeparatorWorker` has a modest cyclomatic complexity of 10 but a nesting depth of 5, the deepest of the five, and a fan-out of 11. Its risk comes from how the branches are arranged, not from how many there are.

The excerpt shows a while loop containing an if on whether the separator was found, which contains an if on whether the match is non-empty, which contains an if on whether the token limit has been reached, with a parallel nesting for the preserve-all-tokens case. The code itself carries comments explaining the index arithmetic, including one that restates the calculation as an equivalent expression to justify it. When a function needs that much commentary to convince the reader that the arithmetic is right, the structure is doing too much work. Another comment spells out the trailing-token case, which tells me this boundary behaviour is something people have had to reason about carefully.

My recommendation: flatten the nesting with early continues or by extracting the 'add token or stop at max' step into a small helper. The max-token check appears in two branches, and a shared helper would put that decision in one place. A target of nesting depth 3 or less is realistic without changing behaviour, provided the existing tests around empty tokens and the max parameter are kept green.

### `substringsBetween` — StringUtils.java

<FunctionCard fn='substringsBetween' file='src/main/java/org/apache/commons/lang3/StringUtils.java' risk='3.23' band='critical' cc='9' nd='2' fo='11' touches='70' />

`substringsBetween` is the least alarming function here on its own terms: a cyclomatic complexity of 9 and a nesting depth of 2, both comfortably under the thresholds I worry about. It ranks in the critical band because it sits in a file that changes constantly, and its fan-out of 11 is higher than its size suggests.

The excerpt shows a single while loop that finds an opening delimiter, then a closing one, collects the text between them, and advances. It has several early exits: null or empty arguments return null, an empty input returns an empty array, and an empty result list also returns null. Multiple exit paths are a test burden, since each one needs its own case. I would not refactor this one for its structure. I would make sure those return-null versus return-empty distinctions are pinned by tests, because that is the kind of detail a change in the surrounding file can disturb.

My recommendation: leave the logic alone and treat it as a candidate for characterization tests rather than extraction. The refactoring effort is better spent on the functions above and below.

### `indexOfDifference` — StringUtils.java

<FunctionCard fn='indexOfDifference' file='src/main/java/org/apache/commons/lang3/StringUtils.java' risk='3.22' band='critical' cc='15' nd='2' fo='8' touches='70' />

`indexOfDifference` has a cyclomatic complexity of 15 with only a nesting depth of 2 and a fan-out of 8. That profile points to a flat function with many branches, mostly in conditions rather than in nested blocks.

The excerpt shows an identity check, a null check, a character-by-character comparison loop, and then a compound condition that adjusts the result when the difference falls in the middle of a surrogate pair. That last condition combines five checks in one expression, which is where most of the complexity is hiding. A comment explains why it is there, so someone has already hit this edge case. Compound boolean conditions are easy to get subtly wrong when edited, and each operand is a path to cover.

My recommendation: move the surrogate-pair adjustment into a small private method with a descriptive name, such as one that decides whether the difference splits a pair. That drops the main function's path count noticeably and gives the surrogate logic a place for focused tests with supplementary characters.

### `matches` — StringUtils.java

<FunctionCard fn='matches' file='src/main/java/org/apache/commons/lang3/StringUtils.java' risk='3.2' band='critical' cc='14' nd='3' fo='14' touches='70' />

`matches` is a private helper, and from the excerpt its content looks like the matching phase of a string-similarity calculation: it finds characters within a sliding window, collects the matched characters from each string, counts transpositions, and measures a common prefix. It returns four numbers in an array. A cyclomatic complexity of 14, a nesting depth of 3, and a fan-out of 14 put it in the same neighbourhood as `replaceEachOnce` for coupling.

This function does five jobs in sequence: window matching, building two matched-character arrays, counting transpositions, measuring the prefix, and packaging the result. They are separated by blank lines and share local state. The positional return array (matches, transpositions, prefix, length) is also an implicit contract that every caller has to remember.

My recommendation: split the sequential stages into named helpers and return a small result object instead of a four-element int array. The positional array is the part most likely to cause a quiet bug when someone edits a caller, and the stages are already naturally separate.

## Where to start

I would take the functions in this order. First `replaceEachOnce`, because it has the highest score, the highest complexity, and an explicit duplicated block. Then `splitByWholeSeparatorWorker` for its nesting depth of 5. Then `matches` and `indexOfDifference`, where one extract-method pass each gets most of the benefit. I would leave `substringsBetween` for tests rather than refactoring.

The bigger point is the file. With 70 touches in the last year and 6 distinct authors in the last 90 days, StringUtils.java is edited often by several people, and these five functions are the places where an edit is hardest to reason about. Any one refactor will touch the same file other contributors are changing, so I would land them as small, separate commits.
