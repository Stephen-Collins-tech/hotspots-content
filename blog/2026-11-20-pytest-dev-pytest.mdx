### `reorder_items_atscope` — fixtures.py

<FunctionCard fn='reorder_items_atscope' file='src/_pytest/fixtures.py' risk='3.38' band='critical' cc='18' nd='7' fo='19' touches='51' />

I would start with `reorder_items_atscope` because it combines the deepest nesting in the top five with the widest fan-out, and it lives in code that changed 2 days ago. Its activity-weighted risk score is 3.38, the highest in this top five. Cyclomatic complexity is 18, nesting depth is 7, and it calls 19 distinct functions.

<MetricBar label='Nesting Depth' value='7' threshold='4' max='10' />

From the source, this function reorders test items so that those sharing parametrized fixture arguments at a given scope run together. The structure is a nested loop pair driving a double-ended queue, with an inner loop that walks matching items, then iterates over higher scopes, then over argument keys, and finally branches on whether the interpreter is PyPy. That PyPy branch is a workaround for an interpreter-specific bug, referenced by issue links in a comment. It also calls itself recursively with the next lower scope. Recursion plus a queue that is mutated while being consumed means you have to track loop state, queue contents, and an ignore set at once to know what a change will do.

Nesting depth 7 is past the point where I would call the control flow reasonable to hold in your head. The recommendation: extract the innermost block, the one that rewrites the per-argument-key ordering with the PyPy special case, into a named helper. That alone removes several levels of nesting and isolates the interpreter workaround so it can be tested and deleted independently when the upstream bug is no longer a concern.

### `_get_active_fixturedef` — fixtures.py

<FunctionCard fn='_get_active_fixturedef' file='src/_pytest/fixtures.py' risk='3.22' band='critical' cc='14' nd='2' fo='15' touches='51' />

This one is a different kind of complexity. Nesting depth is only 2, but cyclomatic complexity is 14 and fan-out is 15, with an activity-weighted risk score of 3.22. The shape is a long, mostly flat sequence of guard clauses and lookups: a special case for the request fixture, a cache check, a lookup of fixture definitions with a dynamic fallback, two separate error raises for missing definitions, override-chain index arithmetic, parametrization handling, a scope check, a deprecation warning path for lookups during teardown, and finally execution.

Flat does not mean simple. Each of those steps is a decision point that needs its own test, and the override-chain logic depends on walking the request chain, which is easy to get subtly wrong. I would split the function along its own comments: one helper to resolve which fixture definition applies given overrides, one to build the sub-request with its parameter and scope, and leave the original as a short coordinator. Because `execute` in the same file calls it, any change to its behavior propagates to every fixture setup.

### `formatrepr` — fixtures.py

<FunctionCard fn='formatrepr' file='src/_pytest/fixtures.py' risk='3.16' band='critical' cc='12' nd='4' fo='17' touches='51' />

`formatrepr` builds the error report shown when a fixture lookup fails. Cyclomatic complexity is 12, nesting depth is 4, and fan-out is 17, giving an activity-weighted risk score of 3.16. It does two jobs in one body: it walks the fixture stack collecting source lines for each function (with a fallback when source is unavailable), and it composes a diagnostic message that distinguishes a recursive dependency from a plainly missing fixture, appending a sorted list of available fixtures.

This is a good extract-method candidate because the two jobs are independent. Moving the source-gathering loop into one function and the message composition into another would let each be tested with plain inputs. Error-message code is also where regressions are least likely to be noticed, since formatting changes rarely break functional tests, which is one more reason to give it direct test coverage.

### `pytest_generate_tests` — fixtures.py

<FunctionCard fn='pytest_generate_tests' file='src/_pytest/fixtures.py' risk='3.13' band='critical' cc='9' nd='3' fo='7' touches='51' />

`pytest_generate_tests` is the smallest of the group by complexity: cyclomatic complexity 9, nesting depth 3, fan-out 7, activity-weighted risk 3.13. It ranks in the top five largely because of where it lives. It is a hook that applies parametrized fixtures to a test's metadata, skipping arguments the test itself parametrizes, and walking overriding fixtures in reverse order. The comments reference two issue numbers and an xfail'd test describing a known unhandled case, which tells me the override handling has edge cases the maintainers are already aware of.

I would not refactor this one first. I would leave it alone structurally and make sure the known gap, the transitively requested super-fixture case, stays covered by its expected-failure test so it is visible when someone changes the surrounding logic.

### `execute` — fixtures.py

<FunctionCard fn='execute' file='src/_pytest/fixtures.py' risk='3.11' band='critical' cc='8' nd='3' fo='12' touches='51' />

`execute` has cyclomatic complexity 8, nesting depth 3, fan-out 12, and an activity-weighted risk score of 3.11. By the numbers it is the mildest function here, but the source shows why it deserves care: it resolves dependent fixtures, checks a cache with a fallback comparison for objects whose equality raises, tears down stale parametrized instances, registers finalizers conditionally by scope, and dispatches to hooks. Ordering is the hazard. The comments reference issue numbers for finalizer registration order and for a cache invalidation case, which suggests earlier bugs here came from the sequence of steps rather than from any single branch.

The practical recommendation is to pin that ordering down with tests that assert finalizer order explicitly, so a refactor of the neighbors cannot silently reorder teardown.

## Where to start

The order I would work in: `reorder_items_atscope` first, because it has the deepest nesting and widest fan-out and is the highest-scoring function; then `_get_active_fixturedef`, which gates every fixture lookup; then `formatrepr`, which has the cleanest split available. The last two, `pytest_generate_tests` and `execute`, are better served by tests than by restructuring.

For contrast, other functions in the repo are structurally comparable but quiet, with no change in 73 days or more. I would schedule those for refactoring before the next development push in those areas, and keep the fixtures work as the immediate priority.
