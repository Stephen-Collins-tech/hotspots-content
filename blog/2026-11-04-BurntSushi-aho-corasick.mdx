### `try_find_fwd_imp` — automaton.rs

<FunctionCard fn='try_find_fwd_imp' file='src/automaton.rs' risk='1.76' band='critical' cc='26' nd='7' fo='11' touches='1' />

I would start here because it has the highest activity-weighted risk score in the repo, 1.76, and it was last changed 7 days ago. From the name and the source excerpt, this is the forward search routine for ordinary (non-overlapping) matching. It is an inline-always generic function over the automaton trait. It sets up a start state, handles a match at the start position, consults an optional prefilter, and then runs a byte-at-a-time loop that checks for dead and match states.

The metrics say a lot about why this is hard to review. A cyclomatic complexity of 26 means 26 independent paths, each a test case. A nesting depth of 7 is well past the point where I would call the control flow easy to hold in my head, and the loop body nests a state-classification check, a dead/match branch, and an anchored-search filter inside it. Fan-out of 11 means a change here touches the automaton trait's surface in many places at once.

The source comments are unusually candid about the design. They explain that anchored and unanchored searches share one automaton, and that anchored searches ignore matches that don't begin at the search start. That is a subtle invariant living inside a single function. There is also a comment recording that loop unrolling and bounds-check elision were tried without a consistent benchmark win. I read that as a sign the function is deliberately shaped for performance, so my recommendation is conservative: extract the match-handling branch (the anchored-start filtering and match construction) into a small helper, and verify with benchmarks that the inlining behavior is unchanged before merging anything.

Historical context is mild. The file has a bug-fix rate of 23% across 13 commits, with no bug-linked commits and no reverts recorded. That is context for review priority, not evidence of a defect in this function.

### `try_find_overlapping_fwd_imp` — automaton.rs

<FunctionCard fn='try_find_overlapping_fwd_imp' file='src/automaton.rs' risk='1.75' band='critical' cc='22' nd='7' fo='10' touches='1' />

This is the overlapping-match counterpart, with an activity-weighted risk score of 1.75, also last changed 7 days ago, and the same file-level history as the function above. Its cyclomatic complexity is 22, nesting depth 7, fan-out 10.

The structural difference matters. Where the non-overlapping version returns a match, this one takes a mutable overlapping-state object and threads resumption logic through it: the code has to distinguish a first call from a continuation, track how many matches in the current state have been reported, and re-enter the scan loop at the right offset. That resumable-state design explains a good share of the complexity. The loop then handles dead states, match states, and a start-state prefilter case, with an assertion guarding the assumption that a special non-dead, non-match state with an active prefilter is a start state.

The two functions share most of their skeleton, which means a fix to one often needs a mirrored fix in the other. My recommendation is to pull the shared state-classification step into one helper that both call, and to split the state-initialization prefix of this function (the `None` versus `Some` handling at the top) into its own function so the loop is readable on its own. I would also add a test that exercises resumption after each kind of early return, since each early return is a distinct path out.

### `build` — util/prefilter.rs

<FunctionCard fn='build' file='src/util/prefilter.rs' risk='1.63' band='critical' cc='32' nd='3' fo='4' touches='1' />

This function has the highest cyclomatic complexity of the five, 32, but with shallow nesting (3) and low fan-out (4). It was changed today, and the file has one author in the last 90 days. The pattern is different from the search loops: this is wide rather than deep.

From the excerpt, it decides which prefilter to construct. It returns early when prefilters are disabled, prefers a memmem-based prefilter when there is a single pattern, considers a packed prefilter, and then compares start-byte and rare-byte prefilters using pattern length, minimum length, byte counts, and rank sums. The comments describe these as heuristics for picking the cheaper option. That is a decision table written as nested conditionals and early returns.

The file has a bug-fix rate of 20% over 5 commits, no bug-linked commits, no reverts, and a review-comment density of 1.33 per pull request, the highest of the top five. That suggests reviewers are engaging with this file. Because the logic is a heuristic selection, each branch is a behavior choice rather than a correctness requirement, and those are the changes that are easiest to get subtly wrong and hardest to notice, since results stay correct while performance shifts. My recommendation is to extract the start-versus-rare byte comparison into a named function that returns an enum of which prefilter to prefer, then test that function directly with table-driven cases. That would take the main function well below the point where I would flag it.

**`build` and `add` — packed/api.rs**

I group these two because they share a file, a history, and a story. Both are in the high band rather than critical, both were changed today, and both have been touched twice in the last year. The file has 7 commits, a bug-fix rate of 0%, no reverts, and one distinct author in the last 90 days.

The `build` function (cyclomatic complexity 11, fan-out 8) constructs the packed searcher from accumulated patterns. From the excerpt, it returns nothing when the builder is inert or empty, clones and configures the patterns, constructs a Rabin-Karp helper, and then selects Teddy or Rabin-Karp depending on a forced-algorithm setting. The `add` function (cyclomatic complexity 7, fan-out 6) accumulates patterns and silently makes the builder inert when it exceeds a pattern limit or receives an empty pattern.

Neither is structurally alarming. Their score comes mostly from sitting in a file that is changing. What I would watch is the silent-inert behavior in `add`: a builder that quietly stops accepting patterns and later returns nothing from `build` is a design where a caller can lose patterns without a signal. I would not refactor either function now. I would add tests pinning down the inert transitions (limit exceeded, empty pattern) so that the ongoing changes to this file cannot alter that behavior unnoticed.
