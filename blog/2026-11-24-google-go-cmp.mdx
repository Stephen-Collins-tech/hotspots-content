All five of my top go-cmp hotspots were last changed within the last 15 days, so I would treat them as a near-term review priority rather than a backlog item. The top function, `compareAny` in cmp/compare.go, has an activity-weighted risk score of 1.57, a cyclomatic complexity of 42 and a fan-out of 40, and it is in the active tier. The repository has 258 functions in total, 27 of them in the critical band, and 112 are in active code, which means the top five are the sharpest end of a broader pattern rather than outliers.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `compareAny` — cmp/compare.go

<FunctionCard fn='compareAny' file='cmp/compare.go' risk='1.57' band='critical' cc='42' nd='2' fo='40' touches='3' />

This is the recursive entry point of the comparison. From the excerpt, it pushes the current step onto a path stack and notifies reporters, checks for cycles on slice elements, tries options, then tries an Equal method, and finally dispatches on the underlying reflect kind with a large switch. That switch is why the cyclomatic complexity is 42 while nesting stays at only 2: the function is wide rather than deep.

<MetricBar label='Fan-out' value='40' threshold='15' max='60' />

A fan-out of 40 is the number I would focus on. This function directly calls into reporters, the recursion checker, the cycle detector, option handling, method handling, and every per-kind comparison helper. A change to any of those collaborators can surface here, and every new reflect.Kind branch increases the testing burden. The function has had 3 touches in the last year, the latest 15 days ago, with a bug-fix rate of 33% across 3 commits. There are no bug-linked commits, reverts, or review comments recorded, so I read this as a maintainability concern rather than evidence of defects. It has one author in the last 90 days.

My recommendation: the simple scalar cases (bool, ints, uints, floats, complex, string, chan, func) are one-line reports. I would group them into a single helper that returns the equality result, leaving the switch to route only the composite kinds. That shrinks the branch count without changing the rule ordering, which is the part of this function I would not touch.

### `appendTypeName` — cmp/internal/value/name.go

<FunctionCard fn='appendTypeName' file='cmp/internal/value/name.go' risk='1.53' band='critical' cc='75' nd='4' fo='27' touches='3' />

This function has the highest cyclomatic complexity of the five at 75, with nesting depth 4 and fan-out 27. From the excerpt, it renders a reflect.Type as text, handling named types, then each unnamed kind (channels with direction, functions with variadic and multiple returns, structs and so on) by recursing into itself for element types. The excerpt also contains a comment marking a known limitation: reflection cannot distinguish two same-named types declared in different function scopes.

<MetricBar label='Cyclomatic Complexity' value='75' threshold='30' max='120' />

It has 3 touches in the last year, the most recent 15 days ago, with a bug-fix rate of 33% over 3 commits. Again there are no bug-linked commits or reverts, so the history does not point to a defect. The risk here is that every new type kind or formatting rule lands in one 75-path function.

My recommendation: split by kind. Chan, Func, Struct and the remaining composite kinds each have enough internal branching (direction handling, variadic handling, multi-value returns) to justify their own append helper. The function-signature branch in particular nests loops and a nested switch and is the best first extraction.

### `EquateComparable` — cmp/cmpopts/equate.go

<FunctionCard fn='EquateComparable' file='cmp/cmpopts/equate.go' risk='1.49' band='high' cc='8' nd='2' fo='7' touches='4' />

This is the outlier in the list, and it is in the high band rather than critical. Its complexity is modest (cyclomatic complexity 8, fan-out 7), so it is here because of activity: 4 touches in the last year, the most recent 14 days ago, with 2 distinct authors in the last 90 days, the only function in my top five with more than one. Its bug-fix rate is 25% over 4 commits, with no bug-linked commits or reverts.

From the excerpt, it validates each supplied type, panicking on non-comparable or duplicate types, and builds a filter. I would not refactor it; in a high band, an active function like this bears watching rather than a rewrite. I would instead make sure the two panic paths are covered by tests, since this is the function in the group most likely to be edited by more than one person.

### `IsType` — cmp/internal/function/func.go

<FunctionCard fn='IsType' file='cmp/internal/function/func.go' risk='1.48' band='critical' cc='43' nd='2' fo='7' touches='2' />

A cyclomatic complexity of 43 with nesting of only 2 and fan-out of 7 describes a flat validator. The excerpt shows an early-return guard followed by a switch over function shapes (predicate, comparer, less, transformer-style signatures), with a compound condition per case. The path count comes from those conditions, not from deep structure, so this is one of the more readable 43s I have seen in an analysis.

It has 2 touches in the last year, 15 days since the last change, a bug-fix rate of 0% and 1 author in the last 90 days. My recommendation is a table-driven test that covers each function shape with one accepting and one rejecting signature. That is cheaper than restructuring and protects the next person who adds a shape.

### `Transformer` — cmp/options.go

<FunctionCard fn='Transformer' file='cmp/options.go' risk='1.42' band='critical' cc='13' nd='2' fo='12' touches='3' />

This is the public constructor for transformer options, with cyclomatic complexity 13 and fan-out 12. From the excerpt, it validates the supplied function and name (panicking on invalid input), derives a default name when none is given, falls back to a placeholder name if the derived one is not a valid identifier, and records a filter type unless the input is an empty interface.

It has 3 touches in the last year and 15 days since the last change, with a bug-fix rate of 0% and no reverts. I would pull the name-resolution branch (explicit name versus derived name versus placeholder) into a small helper, which would take roughly half the branches out of the constructor and make the naming rules testable on their own.

## Where to start

I would start with `compareAny` and `appendTypeName`, in that order. They have the highest activity-weighted risk scores (1.57 and 1.53) and the highest combination of complexity and recency, and both can be split along seams that already exist in the code: reflect kinds in each case. `IsType` and `Transformer` come next, with tests first for `IsType` and a small extraction for `Transformer`. `EquateComparable` needs coverage rather than refactoring.

The quiet tier tells a different story. Several critical functions in the diff-reporting code have had 1 touch in the last year and have not changed in 300 days. That is structural debt with a high blast radius when someone next touches the diff-reporting code, and I would schedule that refactoring before the next feature that needs to change report output, not now.

One caveat on Go specifically: these metrics say nothing about goroutine or channel interactions, and the error handling in this code is mostly panics rather than returned errors, so the path counts above reflect branching in the comparison logic itself.
