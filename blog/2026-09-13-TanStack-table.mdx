Across 7,520 functions in TanStack/table, 142 land in the critical band, but the single riskiest one — `cellKeyboardShortcuts` in the material-react-table example — hasn't been changed in 45 days despite carrying a cyclomatic complexity of 46 and a nesting depth of 9. That's the defining pattern in this repo's top five: every one of them sits in the 'debt' quadrant, meaning the risk isn't from live churn but from complexity that's been quietly accumulating with nobody currently looking at it. I'd treat all five as pre-emptive refactoring targets — the danger isn't that they're breaking today, it's that whoever touches them next inherits a function with 27 to 71 fan-out and little recent context to work from.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `cellKeyboardShortcuts` — cell.utils.ts

&lt;FunctionCard fn='cellKeyboardShortcuts' file='examples/react/material-react-table/src/material-react-table/utils/cell.utils.ts' risk='19.55' band='critical' cc='46' nd='9' fo='27' touches='0' /&gt;

This is the top-ranked function in the whole analysis, and it hasn't been touched in 45 days. Looking at the source, it's a single keyboard-event handler branching on which cell or header was focused — row selection, select-all, row expansion, expand-all, row pinning, column actions menu, sort toggling, and arrow-key navigation are all handled inside one function body via a long `if / else if` chain. A nesting depth of 9 is genuinely deep for TypeScript, and combined with cyclomatic complexity of 46, that's 46 independent paths a test suite would need to cover to claim real coverage. The historical signal here is thin — one total commit, one author in the last 90 days, zero bug-linked commits — so this isn't a function with a documented defect history. It's untested structural debt: a single author wrote a wide keyboard-shortcut dispatcher and nobody has had reason to revisit it since. I'd split it into one handler per interaction type (selection, expansion, pinning, sorting, clipboard) before the next person needs to add a new shortcut and has to trace all 9 nesting levels to find where it belongs.

### `DataTableFilterList` — kitchen-sink-shadcn-base and kitchen-sink-shadcn-radix

&lt;FunctionCard fn='DataTableFilterList' file='examples/react/kitchen-sink-shadcn-base/src/components/data-table/data-table-filter-list.tsx' risk='16.37' band='critical' cc='31' nd='5' fo='38' touches='0' /&gt;

This function appears twice in the top five, once in the shadcn-base example and once in shadcn-radix, with identical metrics: cyclomatic complexity of 31, fan-out of 38, and 45 days since either copy was last changed. The source shows a component managing column-filter state — building filter definitions per column type (multi-select, number, date, select, text), handling add/update/remove operations against a controlled filter array, and coordinating a handful of generated IDs for accessibility. A fan-out of 38 is the standout number here: this function reaches into nearly 40 other functions or hooks, so any change to filter-variant logic or the underlying column-filter shape has a wide blast radius across both copies. Because it's duplicated verbatim across two example apps, a fix in one won't propagate to the other — that duplication is itself worth flagging. I'd extract the filter-variant resolution and the add/update/remove handlers into a shared hook that both examples import, cutting fan-out at each call site and eliminating the need to fix the same bug twice.

### `useGridInteractions` and `createGridInteractions` — the spreadsheet examples

&lt;FunctionCard fn='useGridInteractions' file='examples/react/spreadsheet/src/useGridInteractions.ts' risk='15.47' band='critical' cc='20' nd='4' fo='68' touches='0' /&gt;

&lt;FunctionCard fn='createGridInteractions' file='examples/solid/spreadsheet/src/createGridInteractions.ts' risk='15.47' band='critical' cc='20' nd='4' fo='71' touches='0' /&gt;

These two are the React and Solid ports of the same spreadsheet-interaction logic, and they track each other almost exactly: cyclomatic complexity of 20, nesting depth of 4, and 39 days since either was last changed. What jumps out is fan-out — 68 for the React version, 71 for the Solid version, the highest of any function in this top five. Looking at the source, each one wires together cell lookup by row and column id, active-range tracking, scroll-to-cell behavior, selection movement, edit-session start, and value commit, all as interdependent callbacks sharing closures over the same maps. That's a textbook god-function shape: one function orchestrating six or seven distinct concerns, each calling out to a wide set of table APIs (`getRowsInDisplayOrder`, `getStartVisibleLeafColumns`, `extendCellSelection`, and more). With zero touches in the last 30 days for both, this isn't breaking right now, but it's the kind of function where a single change to selection behavior forces a developer to reason about scrolling, editing, and undo/redo simultaneously. I'd start by extracting the selection-and-scroll logic (`getActiveRange`, `scrollToActiveCorner`, `moveSelection`) into its own hook shared by both ports, since it appears to be nearly identical cross-framework logic duplicated rather than shared.

### What this means next to the fire-quadrant functions

None of the top five are in the fire quadrant, but it's worth contrasting them with what is. `rebuildRowModel` and `rebuildRows` in `packages/table-core/src/worker/rebuildRowModel.ts` sit at an activity-weighted risk score of 14.43 and 13.19 with 3 and 2 touches in the last 30 days respectively — that's core row-model code being actively worked on right now, with cyclomatic complexity of 12 and 17. Those are lower-complexity than anything in the top five, but they're live: someone is actively iterating on row-model rebuilding logic in the actual table-core package. That's a healthier risk profile than the top five — active work on moderate complexity beats dormant work on severe complexity. It also means core engine code isn't where this repo's structural debt concentrates; it's concentrated in the example applications, which apparently get written once by a single author (every top-five function shows exactly one author in the last 90 days) and then left alone.
