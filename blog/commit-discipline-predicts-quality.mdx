Look at the commit messages on your last ten bug fixes. Do they say "fix"? "Fix #1234: description"? "fixed the thing (finally)"? Something else entirely? The answer isn't just a style preference — it determines how much information your team's own history can give back to you later, and most teams never notice they're leaving that information on the table.

## History is only as queryable as it is consistent

A git log is, among other things, a dataset. Every "which files keep breaking," "who actually owns this," or "how often does this module get touched defensively instead of proactively" question is answerable directly from the log — but only if the commits themselves carry enough structure to be filtered on. A commit message that says "fix" tells a future reader nothing about what was fixed, why, or how severely. A hundred commits like that and the history is technically complete but practically opaque: you can see that things happened, not what kind of things.

Compare that to a history where fixes are consistently tagged — a conventional-commits `fix:` prefix, a linked issue number, a brief note on severity or root cause — and suddenly the same git log becomes something you can query. "Show me every fix commit in this file over the last year" becomes a one-line command instead of a manual read-through of vague messages trying to guess which ones were actually bug fixes.

## It's not really about the format

The specific convention matters less than the fact that there is one, followed consistently. Conventional commits, issue-linked messages, a team-specific tag scheme — any of them work, because what they're actually doing is turning an unstructured stream of text into structured, filterable metadata. A team with no convention at all doesn't lack information; the information is still technically in the diffs. What's missing is the index. Without it, every question about the history requires reading the history, which nobody has time to do, so the questions just don't get asked.

## What sloppy history costs you beyond the obvious

The direct cost — harder to search, harder to onboard new engineers into "why does this code look like this" — is the one people usually mention. The less obvious cost is that a noisy history degrades every downstream thing built on top of it: automated risk signals, changelogs, release notes, even a new engineer's mental model of which parts of the system are stable versus fragile. All of those either rely on the commit history directly or are shaped by people who consulted it. Noise at the source propagates.

## The low-effort fix

You don't need a company-wide RFC to start. Pick a minimal convention — even just "fix commits start with `fix:` and reference an issue if one exists" — and hold to it for fixes specifically, since that's the category of commit with the most downstream value when it's identifiable. It costs a few extra seconds per commit. It costs nothing retroactively — old history doesn't need to be rewritten, it's just noisier than new history will be. The value compounds the same way any structured data does: it's not useful on day one, it's useful eighteen months from now when someone's trying to figure out why a file keeps breaking and the answer is sitting right there in a query that would've been impossible without the convention.
