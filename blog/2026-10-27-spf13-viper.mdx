### `find` — viper.go

<FunctionCard fn='find' file='viper.go' risk='16.88' band='critical' cc='92' nd='3' fo='28' touches='0' />

<MetricBar label='Cyclomatic Complexity' value='92' threshold='10' max='100' />

I would start with `find`. A cyclomatic complexity of 92 means 92 independent execution paths, each one a potential bug surface and a required test case, and a fan-out of 28 means it is coupled to 28 distinct callees. It hasn't been changed in 134 days and had 0 touches in the last year, so this is structural debt with a large blast radius, not live churn.

From the source excerpt, `find` resolves a key through a layered precedence: aliases first, then explicit overrides set in code, then bound command-line flags, then environment variables, and so on. The flag step contains a long switch on the flag's value type, with cases for integers, booleans, and many slice and map types. Several of those slice cases repeat the same trim-the-brackets, parse-as-CSV, cast sequence, with only the final cast call differing. That repetition adds substantially to the 92 paths. The nesting depth is only 3, so the difficulty is breadth, not depth: a reader has to hold a long list of cases and early returns in their head.

The pattern tags agree: god function, long function, exit-heavy, and neighbor risk. God-function is a coupling signal, since changes here can ripple into the many functions it calls. Exit-heavy means a test has to cover each of the many return points. Neighbor-risk suggests that edits here may need coordinated changes elsewhere.

My recommendation is to split the lookup by source. Extract one function per precedence layer (override, flag, environment, config file, key/value store, default) and let `find` become a short ordered chain of them. Then move the flag-type switch into a table or a dedicated converter, which collapses the repeated slice cases. Before touching anything, write characterization tests that pin the current precedence order, since that ordering is the behavior users depend on.

**`writeConfig`, `unmarshalReader`, and `searchMap` — viper.go**

These three share a profile: moderate cyclomatic complexity, shallow nesting, an exit-heavy pattern, and no recent activity. I group them because the risk story is the same, and none is as extreme as `find`.

<FunctionCard fn='writeConfig' file='viper.go' risk='12.69' band='critical' cc='17' nd='1' fo='11' touches='0' />

`writeConfig` has a cyclomatic complexity of 17, a nesting depth of 1, and a fan-out of 11, and it hasn't been changed in 397 days. From the excerpt, it derives a config type from the file extension or a stored default, validates it against the supported extensions, opens the file with flags that depend on a force option, marshals the settings, and syncs. In Go, much of that complexity is explicit error-return branching, and each early return is a separate path to test. The sequence also touches the filesystem, so tests need a filesystem abstraction to cover the failure branches. My concrete step is to pull the config-type resolution and the open-flags decision into two small helpers, which would take the main function's path count down by a meaningful fraction and make the file-opening logic testable without I/O.

<FunctionCard fn='unmarshalReader' file='viper.go' risk='12.17' band='critical' cc='11' nd='1' fo='12' touches='0' />

`unmarshalReader` has a cyclomatic complexity of 11, a fan-out of 12, and 60 days since last change, making it the most recently changed of the top five. It reads input into a buffer, resolves the format, checks it against the supported list, looks up a decoder, decodes, and normalizes keys. Almost every step has its own error return, which is what the exit-heavy tag is picking up. The source has three TODO comments: one about removing the supported-extensions check once that list is deprecated, one about returning an unsupported-config error when the registry lacks a format, and one about deprecating that error type. That may point to a pending migration here, and if so I would fold the cleanup into that work: when the supported-extensions check goes away, the function loses a branch for free.

<FunctionCard fn='searchMap' file='viper.go' risk='12.07' band='critical' cc='12' nd='2' fo='3' touches='0' />

`searchMap` has a cyclomatic complexity of 12, a nesting depth of 2, and a fan-out of only 3, and it hasn't been changed in 397 days. It walks a nested map along a path, recursing through two map types and returning nil when it finds a value where a nested key was expected. The low fan-out means it is not tightly coupled, so this is the safest of the four to refactor. The fix is small: normalize the nested map type once at the top of each step so the type switch collapses, then add table-driven tests for the path-length, missing-key, and wrong-type cases. I rank it lower than the others because its complexity is moderate and its coupling is low.

### `getConfigManager` — remote/remote.go

<FunctionCard fn='getConfigManager' file='remote/remote.go' risk='11.61' band='critical' cc='26' nd='2' fo='16' touches='0' />

The odd one out is `getConfigManager` in `remote/remote.go`, with a cyclomatic complexity of 26, a nesting depth of 2, a fan-out of 16, and 397 days since last change. It lives in a different file, so the viper.go signals above do not apply. This file has 1 total commit, a bug-fix rate of 0%, and no reverts, so I read this one as maintainability debt, not as a function with a quality history.

From the excerpt, it builds a remote config manager for a given provider. It first branches on whether a secret keyring is configured, then in each branch runs a switch over provider names (etcd, etcd3, firestore, nats, with a default). That is two near-identical switch statements differing only in which constructor they call, and it explains most of the 26 paths and the 16 callees. I would replace them with a lookup table from provider name to constructor, with the keyring and non-keyring variants as two entries per provider. Adding a new provider then becomes a one-line change, not an edit to two switch statements.

**What the activity data says**

The top five are all dormant, so none of them is live churn. Their complexity is the issue, not recent change.

If I were prioritizing, I would sequence the work this way: characterization tests for `find` first, then the extraction of precedence layers, then the smaller viper.go functions as part of the same file-level cleanup, and `getConfigManager` as an independent, low-risk table refactor.
