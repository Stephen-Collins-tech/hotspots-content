### `getOwningResolver` — BindingGraphFactory.java

<FunctionCard fn='getOwningResolver' file='dagger-compiler/main/java/dagger/internal/codegen/binding/BindingGraphFactory.java' risk='18.02' band='debt' cc='18' nd='3' fo='22' touches='0' />

This is the CC outlier. At cyclomatic complexity 18 it has the most independent paths of anything on my list by a wide margin, and it calls 22 distinct functions. Nesting depth is only 3, so the difficulty is breadth of branching, not indentation. From the excerpt, the method decides which resolver in a component hierarchy owns a given contribution binding. It branches on production scope, then on reusable scope, then falls back to an explicit-binding search from child to parent, then to a scope-based search. Each branch has its own early return, which is why it carries the exit-heavy pattern: every exit path is a distinct test case.

The code already shows where to cut. A TODO in the method says to extract its pieces into separate methods, and a second TODO (referencing b/359893922) questions whether the child-to-parent iteration order is correct for misconfigured repeated modules. That second TODO matters for refactoring: changing traversal order is a behavioral change, so I would keep it out of an extract-method pass.

It has 0 touches in the last year and 134 days since last change, so this is structural debt, not live churn. The file-level history shows no bug-linked commits and no reverts across 2 total commits. I would split it into three methods, one per scope policy (production, reusable, explicit/scope fallback), each returning an Optional resolver, with the top-level method reduced to a sequence of attempts. The code is quiet now, so this is the time to do it, before the next feature work lands.

### `getValueExpression` — AnnotationExpression.java

<FunctionCard fn='getValueExpression' file='dagger-compiler/main/java/dagger/internal/codegen/binding/AnnotationExpression.java' risk='17.27' band='fire' cc='3' nd='11' fo='51' touches='1' />

This function sits in the 'fire' quadrant: it was touched once in the last year, 19 days ago. Its cyclomatic complexity is only 3 by the tool's count, but nesting depth is 11 and fan-out is 51. The excerpt shows a long chain of value-kind checks (array, enum, annotation, type, string, byte, char, double, float, long, short) that generate code expressions for annotation values, with a recursive call for arrays. Two TODOs point at workarounds: a KClass-to-Class swap tied to b/264464791, and a character-literal workaround tied to a JavaPoet issue.

The 51 callees are what worry me most. Every added value kind adds another distinct callee, and since each branch exits directly, a test per annotation value kind is the honest coverage target. The file shows 2 total commits and no bug-linked ones. I would replace the if-else chain with a small dispatch table keyed on value kind, and keep the two workaround branches isolated and labeled so they can be deleted when the upstream issues close.

### `getKindName` — XElements.java

<FunctionCard fn='getKindName' file='dagger-compiler/main/java/dagger/internal/codegen/xprocessing/XElements.java' risk='17.2' band='debt' cc='3' nd='8' fo='13' touches='0' />

This one maps an element to a kind string such as CLASS, INTERFACE, METHOD or FIELD. Nesting depth is 8 and cyclomatic complexity is 3. Taken together, the metrics and the excerpt suggest a lookup written as nested conditionals rather than a flat sequence of guards, with a fallback to the element's own kind name at the end. It has 0 touches in the last year and 134 days since last change, and the file has 6 total commits, with 2 distinct authors in the last 90 days.

This is low-urgency structural debt. Flattening the nesting with early returns would bring depth down to 2 or 3 with no behavior change, which makes it a good first-PR candidate. Both the exit-heavy and deeply-nested patterns apply, but the function is small enough that the fix is mechanical. A same-named function in XAnnotationValues.java has nesting depth 8 and sits in my context list, so I suspect a shared approach to kind-name lookup would help in both places.

### `build` — XTypeSpecs.java

<FunctionCard fn='build' file='dagger-compiler/main/java/dagger/internal/codegen/xprocessing/XTypeSpecs.java' risk='17.05' band='fire' cc='15' nd='2' fo='53' touches='2' />

If I had to pick one function for live regression risk, it is this one. It is a 'fire' function with 2 touches in the last year and 0 days since last change, meaning it changed on the day of the analysis. It has cyclomatic complexity 15, shallow nesting of 2, and fan-out of 53, and it carries the god-function, long-function and exit-heavy patterns together.

From the excerpt, it assembles a type specification: a switch on the kind (class, interface, annotation, object, anonymous class), then a long run of conditional steps for originating elements, modifiers, visibility, javadocs, superclass, superinterfaces, annotations, types, properties, functions, and a companion-object path for static members. Several TODOs say the Kotlin-side handling is not implemented yet, so I expect this method to keep growing as that support lands. An unsettled feature surface plus 53 callees is what makes it a churn risk.

The file has 4 total commits, with 2 distinct authors in the last 90 days, none of the commits bug-linked. I would extract the kind-specific builder creation into its own method, and group the modifier, member and companion-object steps into helpers. The switch alone is a natural first cut, and it would take cyclomatic complexity from 15 to under 10 in one change.
