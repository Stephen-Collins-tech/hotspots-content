Find the files in your repo with zero commits in the last year. Every codebase has a pile of them. The instinct is to read that list as reassuring — nothing's changed, nothing's broken it, it's stable. Sometimes that's exactly right. Sometimes it's the opposite of right, and the same word is doing two completely different jobs.

## Two ways to end up with zero commits

**The good kind of stable:** the problem the code solves is well understood, the interface is clean, the implementation was done carefully the first time, and there's simply nothing left to fix or extend. It hasn't changed because it doesn't need to. This is the outcome every engineer is aiming for, and when you achieve it, the reward is a file that quietly does its job forever without demanding anyone's attention.

**The bad kind of stable:** the code is fragile, under-tested, and the one or two people who understood it have moved on. Nobody's touched it in a year not because it's solid, but because touching it is a known risk nobody wants to own, and there's always a lower-risk way to accomplish the current task than opening that file. It hasn't changed because everyone's routing around it, not because it doesn't need work.

Both produce identical git history: zero commits over some window. Churn alone cannot tell them apart. That's the trap — the metric that looks like it's measuring stability is actually just measuring *absence of recent activity*, and absence of activity has at least two very different causes.

## What actually distinguishes them

You have to look past the recent silence to what came before it, and to the shape of the code itself:

- **What does the history before the silence look like?** A file with a clean, unremarkable commit history that simply tapered off is a different story from a file with a cluster of urgent, fix-flagged commits right before it went quiet — the second pattern looks a lot like a fire that got contained by avoidance rather than resolution.
- **How many people have ever understood it?** A file touched by many contributors over its life, each leaving it in reasonable shape, is more likely well-designed-stable. A file touched by one person who then left the team is more likely nobody's-touched-it-because-nobody-can stable.
- **What happens when someone finally has to change it?** This is the real tell, and it's retrospective — but if you have any recent example of someone touching a long-dormant file, look at how that went. A calm, uneventful change suggests the code was genuinely fine. A change that took far longer than expected, or that broke something unrelated, confirms the dormancy was avoidance, not health.
- **Is there a task actively being routed around it?** Sometimes this is visible in planning discussions or code comments — a TODO that's been there for two years, a workaround layered on top instead of a fix underneath. That's a stronger signal than the commit history alone will ever give you.

## Why this distinction matters practically

Treating both kinds of "stable" the same way produces two different failure modes. Leave the good kind alone — that's correct, it doesn't need attention. Leave the bad kind alone with the same confidence, and you're accumulating exactly the kind of risk that shows up as a surprise incident, because nothing in your normal process — no recent commits, no recent review comments, no obvious activity — was ever going to flag it. It sits quietly until someone has no choice but to touch it, at which point the avoidance debt comes due all at once.

The fix isn't to distrust every quiet file — most of them genuinely are fine, and re-litigating settled code for no reason is its own waste of effort. It's to stop treating "zero commits" as self-evidently good news and spend the extra few minutes checking which kind of quiet you're actually looking at before you decide it doesn't need a second look.
