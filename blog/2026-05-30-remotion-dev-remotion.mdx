### `get_frame` — `packages/compositor/rust/opened_stream.rs`

`get_frame` is the function that retrieves a decoded video frame from an open media stream inside remotion's Rust compositor. Based on its name and location in `opened_stream.rs`, it almost certainly handles the core read-decode-return loop: checking stream state, deciding which frame to seek to or decode next, and returning the result to the calling layer. With a cyclomatic complexity of 53, it contains at least 53 independent execution paths — each one a required test case and a surface for a conditional to drift out of sync with the others. A nesting depth of 7 means the deepest branches are seven control structures deep, well past the point where a reader can hold the full state space in their head. Fan-out of 20 makes this a structural centre of gravity: 20 distinct functions are called from here, so a change to the interface or semantics of any of them may require a coordinated edit inside `get_frame` as well.

The patterns paint a consistent picture: complex branching and deeply nested logic at CC 53 and ND 7, multiple early-return exits (exit-heavy), and a scope so broad it qualifies as a god function — long enough that line count alone would flag it. What makes this a live concern rather than accumulated debt is the activity signal: two commits in the last 30 days, with the most recent landing just one day ago. That is not a dormant function with theoretical blast-radius risk — it is a function being actively changed right now while carrying structural complexity that makes each edit harder to reason about. The file has a single author over the last 90 days, which concentrates both knowledge and risk. My recommendation here is to begin extracting the seek/decode decision logic and the error-path branches into smaller, named functions. Even splitting the happy path from the error-exit paths would reduce CC materially and make each remaining branch independently testable.

### `<anonymous>` — `packages/media-parser/src/emit-available-info.ts`

An anonymous function at the top level of `emit-available-info.ts` is the structural outlier in this entire dataset. Its cyclomatic complexity of 118 is more than double that of `get_frame`, placing it firmly in the extreme range. Based on the file name, this function is likely a dispatcher or callback that fires whenever new parsed media metadata becomes available — checking which fields have been populated and emitting or routing them accordingly. A design like that accumulates branches naturally: one conditional per supported metadata field or track type, compounding over time as the media-parser gains support for new container formats and codec properties.

With a fan-out of 26, it calls into 26 distinct functions, making it the broadest coupling point in the top hotspots. Six levels of nesting at ND 6, combined with CC 118 and 26 callees, means that reasoning about a single change requires mentally tracing through a large and branchy call graph simultaneously. Like `get_frame`, it received two commits in the last 30 days and was last modified one day ago — this is live development on a function that is already at the edge of comprehensibility. The file's external signals show no prior bug-linked commits or reverts, which means the complexity hasn't yet manifested as tracked defects — but that framing shifts quickly when a function this wide is being actively changed. I would prioritize introducing a discriminated-union type or a data-driven dispatch table to replace the conditional chain: that technique commonly reduces CC by an order of magnitude in functions that branch primarily on type or field presence, and it makes each emission path individually testable. Because the function is anonymous, naming it explicitly is the zero-cost first step — it makes stack traces legible and makes coverage reports meaningful.
