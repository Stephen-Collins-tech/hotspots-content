## Top 5 hotspots

### `get_daily_ohlcv` — binance_public_data.py

<FunctionCard fn='get_daily_ohlcv' file='freqtrade/exchange/binance_public_data.py' risk='16.03' band='critical' cc='19' nd='7' fo='19' touches='1' />

<MetricBar label='Cyclomatic Complexity' value='19' threshold='10' max='30' />
<MetricBar label='Max Nesting Depth' value='7' threshold='4' max='10' />
<MetricBar label='Fan-out' value='19' threshold='10' max='25' />

This async function fetches a single day of OHLCV candlestick data from Binance's public archive at `data.binance.vision`. The source excerpt makes its structure visible: an outer retry loop wraps an `aiohttp` session request, inside which the 200/404/other status branches diverge, and inside the 200 branch there is ZIP extraction, a CSV header-detection heuristic (reading the first byte to determine whether the file has a header row), timestamp normalization using a NumPy conditional, and DataFrame construction — all inside a `try/except` that itself manages retry state. That is a lot of distinct concerns layered inside one control-flow stack.

The nesting depth of 7 is the most telling number here. At that depth, a reader must hold seven levels of context simultaneously to reason about what any single line means. The cyclomatic complexity of 19 means there are 19 independent execution paths, each of which is a required test case if you want meaningful coverage. The fan-out of 19 in Python means this function is directly calling 19 distinct callees — and because Python resolves types at runtime, the actual coupling is likely broader than that count suggests.

The file carries 1 bug-linked commit against a total of 1 commit in the historical record, which means 100% of the file's tracked commit history is associated with a bug. That is a small sample, but it is directionally consistent with the structural signal.

The god-function pattern here is the core problem: HTTP retry logic, ZIP decompression, CSV parsing, header detection, and timestamp normalization have no business sharing a call stack. My recommendation is to extract the ZIP-to-DataFrame conversion into its own function — something like `_parse_binance_zip_response` — and separate the retry loop into a generic async retry wrapper. That decomposition alone would reduce the CC and ND substantially, and it would make the header-detection heuristic independently testable.

### `create_client` — ws_client.py

<FunctionCard fn='create_client' file='scripts/ws_client.py' risk='15.87' band='critical' cc='24' nd='6' fo='11' touches='1' />

<MetricBar label='Cyclomatic Complexity' value='24' threshold='10' max='30' />
<MetricBar label='Max Nesting Depth' value='6' threshold='4' max='10' />

This async function establishes and maintains a WebSocket connection to freqtrade's message API. The source excerpt shows a `while 1` outer loop for reconnection, nested inside which is a `websockets.connect` context manager, nested inside which is another `while 1` message-receive loop, nested inside which is an `asyncio.wait_for` with its own `try/except` for ping/pong logic, all surrounded by several distinct `except` clauses handling `socket.gaierror`, `ConnectionRefusedError`, `InvalidHandshake`, `ConnectionClosedError`, and `ConnectionClosedOK` separately.

The exit-heavy pattern is prominent here: multiple `break`, `continue`, and implicit loop exits are scattered across the exception handlers, making the control flow hard to trace without running the code. With a cyclomatic complexity of 24, there are 24 paths through this function. Testing even half of them requires carefully orchestrating mock WebSocket failures, ping timeouts, and clean disconnections in combination.

The historical signal is clean — no bug-linked commits, no reverts — but the structural signal is not. My recommendation is to extract the inner message-receive loop and its ping/pong fallback into a separate `_listen` coroutine. That would reduce the nesting depth from 6 to something closer to 3–4 for each piece, and it would make the reconnection logic independently readable from the message-handling logic.

### `load_leverage_tiers` — exchange.py

<FunctionCard fn='load_leverage_tiers' file='freqtrade/exchange/exchange.py' risk='15.39' band='critical' cc='26' nd='5' fo='17' touches='1' />

<MetricBar label='Cyclomatic Complexity' value='26' threshold='10' max='30' />
<MetricBar label='Fan-out' value='17' threshold='10' max='25' />

This method on the exchange class handles initialization of leverage tier data for futures trading. The source excerpt reveals a two-branch capability check — one path calls `get_leverage_tiers()` for exchanges that support bulk fetching, the other constructs a list of symbols, loads a disk cache, builds a list of coroutines for any symbols not already cached, batches them in chunks of 100, runs them through `asyncio.gather` via a loop lock, handles per-result exceptions, and then writes the updated cache back to disk. An inner async function `gather_results` is defined inline to bridge the sync/async boundary with `loop.run_until_complete`.

This is the most historically scrutinized function in the top five. The file has 15 bug-linked commits and a PR review comment density of 6.0 — the highest of any file in this analysis. Those are file-level signals, not proof that this specific function was the source, but given that `load_leverage_tiers` is the most structurally complex function in `exchange.py` with a cyclomatic complexity of 26 and fan-out of 17, it is a reasonable candidate to have attracted that review attention.

The exit-heavy pattern means there are multiple return points depending on which capability branch executes and whether coros are empty. My recommendation is to split this into at least two methods: one for the bulk-fetch path and one for the per-market fetch path, with cache management extracted into a third. That decomposition would drop the CC of each piece below 10 and make the cache-hit path testable without mocking async gather behavior.

### `_download_archive_ohlcv` — binance_public_data.py

<FunctionCard fn='_download_archive_ohlcv' file='freqtrade/exchange/binance_public_data.py' risk='15.28' band='critical' cc='23' nd='7' fo='13' touches='1' />

<MetricBar label='Cyclomatic Complexity' value='23' threshold='10' max='30' />
<MetricBar label='Max Nesting Depth' value='7' threshold='4' max='10' />

This is the orchestration layer above `get_daily_ohlcv`. It manages a date range, chunks dates into batches of up to 1,000, spawns one `asyncio` task per date, and then iterates over the tasks collecting results. The error handling is the complexity source: a `Http404` on day 1 triggers a different warning path than a `Http404` on a later day, with additional pair-specific guidance for `BTC/USDT:USDT`, `ETH/USDT:USDT`, and `BCH/USDT:USDT`. General exceptions cause an immediate return of whatever data has been collected so far, canceling remaining tasks via `cancel_and_await_tasks`.

The nesting depth of 7 matches `get_daily_ohlcv` exactly, which makes sense: `_download_archive_ohlcv` is essentially a parallel scheduler wrapped around the same kind of multi-level branching. The god-function pattern is visible in the fact that date-range chunking, task lifecycle management, 404 diagnostic messaging, and partial-result assembly all live in the same function body.

The leading underscore signals this is intended as a private function, but its structural profile says it has outgrown that framing. I would extract the per-task error handling — the `Http404` branch logic with its day-number and pair-specific cases — into a dedicated `_handle_ohlcv_download_error` function, then simplify the task iteration loop to a clean accumulate-or-stop pattern.

### `_download_archive_trades` — binance_public_data.py

<FunctionCard fn='_download_archive_trades' file='freqtrade/exchange/binance_public_data.py' risk='15.09' band='critical' cc='21' nd='7' fo='12' touches='1' />

<MetricBar label='Cyclomatic Complexity' value='21' threshold='10' max='30' />
<MetricBar label='Max Nesting Depth' value='7' threshold='4' max='10' />

This is the trade-data counterpart to `_download_archive_ohlcv`, and the structural resemblance is striking. The same chunked task pattern appears, but with a batch size of 30 instead of 1,000, and `get_daily_trades` in place of `get_daily_ohlcv`. The 404 error handling and pair-specific warning messages are nearly identical. The absence of the `else: dfs.append(None)` path (trades do not support gap-filling with `None` entries the way OHLCV does) is the main behavioral difference visible in the excerpt.

A cyclomatic complexity of 21 and nesting depth of 7 on a function that is structurally near-duplicate of `_download_archive_ohlcv` is a strong case for a shared abstraction. The duplicated 404 warning logic — including the identical pair-specific guidance for BTC, ETH, and BCH — is a maintenance liability: a wording change or a new pair needing the same advice requires editing two functions in sync.

My recommendation here is the most concrete of the five: extract a shared `_handle_archive_download_error` function that accepts the current-day index, the pair name, and the exception, and returns an instruction enum (stop, continue, log). Both `_download_archive_ohlcv` and `_download_archive_trades` can then call it, eliminating the duplication and cutting the CC of each by several points in one pass.

Three functions in the same file, all 'fire' quadrant, all last changed 14 days ago, all carrying nesting depths of 7 and cyclomatic complexities between 19 and 23 — that is a module that has grown organically to handle increasingly complex real-world edge cases (missing archive data, 404 gaps, partial downloads, per-pair quirks) without a corresponding investment in structural decomposition.
