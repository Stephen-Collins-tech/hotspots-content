The five highest-risk functions in square/picasso all live in one file, website/static/prettify.js, and that concentration is the story. The worst offender, `S`, has a cyclomatic complexity of 48, a fan-out of 29, and an activity-weighted risk score of 15.16, but it sits in the debt quadrant with 525 days since its last change, so my argument is structural blast radius, not live churn. Across the 16 functions analyzed, 4 are critical and all 4 are in this file, with the fifth-ranked function in the high band. The other 9 'ok' functions I did not rank are low-priority code.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `S` — prettify.js

<FunctionCard fn='S' file='website/static/prettify.js' risk='15.16' band='critical' cc='48' nd='3' fo='29' touches='0' />

I would start with `S` because it has the highest activity-weighted risk score in the repository (15.16), a cyclomatic complexity of 48, and a fan-out of 29. From the excerpt, it takes a list of regular expressions and combines them into a single alternation, rewriting character classes, back-references, and case-insensitivity handling along the way. That is a lot of regex-source manipulation packed into one function, with several nested helper functions inside it.

<MetricBar label='Cyclomatic Complexity' value='48' threshold='10' max='60' />

A cyclomatic complexity of 48 means 48 independent paths, each one a potential test case. The exit-heavy pattern flagged on this function adds to that: many return and throw points mean a test suite has to hit many distinct endings. Fan-out of 29 means it calls 29 distinct functions, so a change to any one of them can alter its behavior. It has gone 525 days without a change, and the file shows a single commit in its history with no bug-linked commits, reverts, or recent authors. That is a debt profile, not a defect signal. My recommendation: do not refactor this in place. If the file stays, pin it to a known upstream version and treat `S` as a black box with a regression test that feeds in a handful of regex lists and asserts on the combined output.

### `C` — prettify.js

<FunctionCard fn='C' file='website/static/prettify.js' risk='10.37' band='critical' cc='9' nd='5' fo='14' touches='0' />

`C` is a different kind of risk. Its cyclomatic complexity is only 9, but it has a nesting depth of 5 and a fan-out of 14, which is where its activity-weighted risk score of 10.37 comes from. Nesting of 4 or more makes code hard to reason about, and the deeply-nested pattern flag agrees. From the excerpt, it builds a lexer from two lists of pattern definitions and matches tokens against them inside loops within loops. It also calls `S` to compile the combined pattern, so its fan-out includes the heaviest function in the file.

The practical consequence is a coupling chain: a change in `S` can surface as a bug in `C`, and `C` is the function that actually does the tokenizing. I would flatten the nested loops with early `continue` statements or extract the inner token-classification step into its own function. That would cut depth without touching behavior, and it is the cheapest win among the five.

### `J` — prettify.js

<FunctionCard fn='J' file='website/static/prettify.js' risk='10.3' band='critical' cc='15' nd='3' fo='17' touches='0' />

`J` has an activity-weighted risk score of 10.3, a cyclomatic complexity of 15, a nesting depth of 3, and a fan-out of 17. From the excerpt, it walks DOM nodes and wraps code lines in list items to produce line numbers, with nested helper functions for splitting nodes. That is DOM mutation logic, which is easy to get subtly wrong because the order of insert, clone, and remove operations matters.

No pattern flags were raised for this function, so the risk here comes from the combination of moderate complexity and broad coupling rather than one standout problem. Fan-out of 17 is the number I would look at first: it means the function depends on many browser APIs and sibling helpers. If this code stays, a small browser-level test that renders a code block with line numbers enabled would give you a safety net before anyone edits it.

### `K` — prettify.js

<FunctionCard fn='K' file='website/static/prettify.js' risk='10.16' band='critical' cc='27' nd='4' fo='11' touches='0' />

`K` has a cyclomatic complexity of 27, a nesting depth of 4, a fan-out of 11, and an activity-weighted risk score of 10.16. It carries the complex-branching flag. From the excerpt, it appears to be the step that takes the lexer output and applies it to the page: it deduplicates and merges decoration ranges, then walks text nodes and wraps matched spans in elements, with a try/finally to restore display state and a catch that logs errors.

A cyclomatic complexity of 27 is in the range where I would want every branch covered before touching it, and nesting of 4 puts it at the edge of what I find readable. There is also a browser-specific branch for old versions of Internet Explorer, which is the kind of conditional that tends to outlive its usefulness. If anyone does need to edit this file, that legacy branch is the first thing I would check for removal, since it adds a path to test for an old browser.

**What the concentration tells me**

Five of five is not a coincidence of scoring. A minified bundle strips names and formatting but keeps the logic dense, so the metrics see exactly the structure a human reviewer would struggle with. The practical advice follows from that: the highest-leverage action in picasso's analysis is not refactoring any of these functions but deciding who owns this file. If it is a vendored copy of a third-party highlighter, replace it with a pinned dependency or the maintained upstream release and remove it from the analysis. If it is hand-maintained, it needs tests before anyone edits it.

On language framing: this repository is Kotlin, and none of these hotspots are Kotlin code. That means the coroutine and extension-function caveats that usually sharpen a Kotlin analysis do not apply here, and I would not read anything about the Android library's own code quality into this result. The snapshot says nothing about it beyond the fact that it did not produce a top-five function.
