## Large Repo Analysis

odoo is a large repository. To stay within memory constraints, this analysis used **hybrid touch mode**: structural complexity — CC, ND, FO — is measured precisely for every function. Git activity is tracked at the function level (via `git log -L`) only for files with 5 or more commits in the last 30 days; other files use a file-level approximation. Rankings therefore surface functions that are both structurally complex and in the most actively-changing parts of the codebase. Dormant code with high structural complexity will rank lower than it would under a full per-function analysis — to surface it, run `hotspots analyze . --per-function-touches` on a machine with sufficient memory.

### `parseDOMNode` — owl.js

<FunctionCard fn='parseDOMNode' file='addons/web/static/lib/owl/owl.js' risk='24.78' band='critical' cc='33' nd='8' fo='14' touches='1' />

`parseDOMNode` is the highest-risk function in the repository at an activity_risk of 24.78. From its name, location inside Owl's compiler, and the source excerpt, it is the core DOM-node parser in Odoo's in-house component framework — responsible for walking template nodes and handling every Owl directive: `t-ref`, `t-on-*`, `t-model`, namespace resolution, and `<pre>` tag context, among others.

The cyclomatic complexity of 33 reflects that branching directly: the excerpt shows attribute-by-attribute iteration with nested conditionals for `t-model` modifier combinations (`.trim`, `.lazy`, `.number`), radio vs. checkbox vs. select logic, and SVG namespace detection — each branch is a distinct execution path and a required test case. The max nesting depth of 8 means a reader must track eight levels of control flow simultaneously to reason about the deepest paths. A fan-out of 14 means the function calls 14 distinct collaborators — in a JavaScript duck-typed runtime, the real coupling may be broader than static analysis can surface.

The function is tagged as both a god function and a long function, which matches what the excerpt shows: attribute parsing, model binding logic, error throwing, and context mutation are all handled in a single body rather than delegated to specialized helpers. The exit-heavy pattern means there are multiple return paths scattered through that depth, each of which must be covered independently by tests.

The last change landed 2 days ago. Any engineer touching directive-handling logic right now is working inside all 33 execution paths at once.

**Recommendation:** Identify the `t-model` modifier resolution block — the excerpt shows it is the deepest and most branchy sub-section — and extract it into a dedicated `parseModelDirective(node, attr, value, tagName)` helper. That single extraction reduces the nesting depth of the parent function and isolates the checkbox/radio/select branching behind a testable boundary. Aim to bring cyclomatic complexity below 15 in the parent before the next directive feature lands.

### `parseComponent` — owl.js

<FunctionCard fn='parseComponent' file='addons/web/static/lib/owl/owl.js' risk='23.78' band='critical' cc='36' nd='6' fo='25' touches='1' />

`parseComponent` sits one rank below `parseDOMNode` with an activity_risk of 23.78, but its cyclomatic complexity is actually higher at 36 — the most complex of the two Owl parser functions. It handles component-node parsing: dynamic vs. static component detection, `t-props`, `t-slot-scope`, named slot extraction, and sub-component boundary detection during slot traversal.

The fan-out of 25 is what I find most notable here. In a JavaScript duck-typed context, 25 distinct callees means the function is orchestrating a broad surface of collaborators — DOM manipulation, AST construction, error reporting, and slot scope resolution — all within one body. The excerpt confirms this: the function clones nodes, queries for `[t-set-slot]` descendants, walks parent chains to detect sub-component boundaries, and dispatches to `parseNode` recursively. That recursive dispatch combined with a nesting depth of 6 creates paths that are difficult to trace without running the code.

Like `parseDOMNode`, this function carries all five Tier 1 patterns and was last touched 2 days ago. The `bug_fix_fraction` of 1.0 on the file means the single commit on record for this file was categorized as a bug fix — worth noting as historical context, though one data point is not a trend.

**Recommendation:** The named-slot extraction loop — which walks `[t-set-slot]` nodes, checks for sub-component containment, and builds slot ASTs — is a coherent sub-responsibility that could be extracted into a `extractNamedSlots(clone, ctx)` function. That reduces both the fan-out and the cyclomatic complexity of the parent, and it isolates the sub-component boundary-detection logic where it can be unit-tested independently.

### `apply_inheritance_specs` — template_inheritance.py

<FunctionCard fn='apply_inheritance_specs' file='odoo/tools/template_inheritance.py' risk='21.04' band='critical' cc='110' nd='10' fo='49' touches='1' />

<MetricBar label='Cyclomatic Complexity' value='110' threshold='30' max='120' />

This is the structural outlier of the five. A cyclomatic complexity of 110 means 110 independent execution paths through a single function — that is not a moderate branching problem, it is an extreme one. The max nesting depth of 10 and fan-out of 49 compound it: at depth 10, the human working-memory cost of understanding a single path is very high, and 49 callees in Python means runtime dispatch is hiding additional coupling.

From the name, path (`odoo/tools/template_inheritance.py`), and the source excerpt, `apply_inheritance_specs` is the engine that applies view inheritance to Odoo's XML architecture: it processes a queue of specification nodes, locates target nodes in the parent view, and applies positional operations — `replace`, `inside`, `before`, `after` — including deeply nested logic for `mode='outer'` replacement, `$0` placeholder substitution, `t-name` preservation, branding attributes, and comment handling. This is one of the most load-bearing functions in the entire Odoo view system; virtually every custom module that overrides a view runs through it.

The excerpt shows a `while len(specs)` loop that pops and re-extends the queue, with nested conditionals for each position mode and replace mode, and an inner `extract()` closure that also calls `locate_node`. That closure adds implicit control-flow depth that the nesting metric partially captures but does not fully reflect.

`apply_inheritance_specs` was last modified 2 days ago and touched once in the last 30 days. At CC 110, even a small logic change risks introducing a regression in one of the other 109 paths.

**Recommendation:** The `replace`/`mode='outer'` branch — including `$0` substitution, root-node handling, and `t-name` preservation — is a coherent, self-contained operation. Extracting it into a `_apply_replace_spec(source, node, spec, inherit_branding)` function would immediately reduce the cyclomatic complexity of the parent and make the replacement semantics independently testable. The `inside`, `before`, and `after` position cases are similarly extractable. A full decomposition of the positional dispatch would bring the parent function's complexity below 20.
