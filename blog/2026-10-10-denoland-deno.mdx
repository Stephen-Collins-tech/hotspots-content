I would treat this list as a refactoring queue to work through before the next development push, not as a list of things on fire.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `format_raw` — inspect.rs

<FunctionCard fn='format_raw' file='ext/web/console/inspect.rs' risk='20.16' band='debt' cc='115' nd='17' fo='60' touches='0' />

<MetricBar label='Nesting Depth' value='17' threshold='4' max='20' />

I would start with `format_raw`: it has the highest activity-weighted risk score in the repository at 20.16, a cyclomatic complexity of 115, and a nesting depth of 17. It has not been changed in 48 days and has 0 touches in the last year, so this is structural debt with a high blast radius when next touched. The file path suggests it renders values for console output, and the excerpt bears that out. It takes a V8 scope, intrinsics, a formatting context, a value, a recursion counter, and optional proxy details, then branches on constructor names, to-string tags, iterators, and proxies.

Two things stand out in the source excerpt. The function carries an explicit `#[allow(clippy::too_many_arguments)]` with a reason string, so the seven-parameter signature is a known compromise rather than an accident. And it works against V8 handles and scopes, where Rust's ownership and lifetime annotations (`'s`, `'i`) can hide complexity that a cyclomatic count alone understates. With a fan-out of 60, a change to any of the helpers it calls, such as `get_constructor_name` or `format_value`, can alter its behavior.

My recommendation: extract the type-specific branches (arrays, proxies, iterable objects) into separate functions that each take the shared formatting context. A 115-path function needs a test per path, and splitting by value kind lets each kind carry its own tests.

### `startJupyterKernel` — jupyter_kernel.js

<FunctionCard fn='startJupyterKernel' file='cli/js/jupyter_kernel.js' risk='19.82' band='debt' cc='50' nd='8' fo='59' touches='0' />

Next is `startJupyterKernel`, which scores 19.82 with a cyclomatic complexity of 50, nesting of 8, and fan-out of 59, unchanged for 48 days. The excerpt shows why the fan-out is so high. The function sets up four router sockets and a publish socket, generates a session ID, starts a heartbeat, and then defines nested helper functions (`publishStatus`, `publishIopub`, `iopubDrainer`, `kernelInfo`) inside its own body. It acts as a constructor, a protocol handler, and a message dispatcher in one closure.

The closure structure is the bigger problem, more than the raw complexity. State such as the execution count, the current parent header, and the shutdown flag is shared across all the inner functions, so any of them can alter what the others see. I would lift the inner functions into a small kernel class or module-level functions that take that state explicitly, then give each socket handler (shell, control, stdin) its own function. That cuts the nesting and makes each handler testable without standing up the whole kernel.

### `objectComparisonStart` — comparisons.ts

<FunctionCard fn='objectComparisonStart' file='ext/node/polyfills/internal/util/comparisons.ts' risk='19.77' band='debt' cc='91' nd='16' fo='38' touches='0' />

`objectComparisonStart` has a cyclomatic complexity of 91 and nesting of 16, second only to `format_raw` in nesting depth among my top five. It sits in the Node polyfill layer and, from the excerpt, compares two objects under strict, loose, and partial modes, then branches on arrays, dates, regular expressions, and typed array views. That is a deep-equality routine, and deep-equality routines tend to grow one type check at a time.

The exit-heavy pattern matters here because nearly every branch returns false early. Each early return is a separate test case, and the mode flag multiplies them. I would split it by value type, with one comparer each for arrays, dates, regular expressions, and buffer views, and keep the mode check at the top as a dispatch. Since this file mirrors Node's own assertion behavior, I would also confirm the existing tests cover each mode against each type before changing anything.

**`<anonymous>` — _win32.ts**

The fourth entry is an immediately invoked function wrapping the whole Windows path module, which is why the name is anonymous. It scores 19.48 with a cyclomatic complexity of 78, nesting of 8, and fan-out of 27, and it hasn't changed in 48 days. The excerpt shows the wrapper importing constants and helpers through `core.loadExtScript` and defining a reserved-names list (`CON`, `PRN`, `AUX`, `COM1` and so on) plus helpers like `isWindowsReservedName`.

Because the scored unit is the whole wrapper, the 78 paths are spread across everything inside it, including path normalization, joining, and resolving. The practical reading is that this is a module-level aggregate, not a single tangled function. I would check which inner functions actually carry the complexity, then split those out as named top-level functions inside the module. The next hotspot report would then point at a specific function instead of an anonymous wrapper.

### `inner_from_v8_exception` — error.rs

<FunctionCard fn='inner_from_v8_exception' file='libs/core/error.rs' risk='19.42' band='debt' cc='44' nd='8' fo='46' touches='0' />

Fifth is `inner_from_v8_exception` in `libs/core/error.rs`, scoring 19.42 with a cyclomatic complexity of 44, nesting of 8, and fan-out of 46, unchanged for 48 days. It converts a V8 exception into Deno's own error type, and the excerpt shows it handling a depth limit, a user-supplied format callback, `Error` instances, `cause` chains, and cycle detection through a set of already-seen objects. The comments in the source explain the cycle behavior in detail, which tells me the logic is deliberate and subtle: formatters depend on the repeated error appearing once more to label circular references.

That subtlety is why I would be careful here. The function recurses, clones the seen set per path, and reads properties like `stack` specifically to trigger `prepareStackTrace`, so ordering matters. This file also has the only mixed history in my top five, with a bug-fix rate of 50% across 2 total commits, a small sample but slightly more than the others. I would extract the cause-chain handling and the message-formatting step into separate functions, and add tests for the cycle and truncation paths before any other change.
