## Top hotspot analysis

### `processBlockElement` — html-to-docx.ts

<FunctionCard fn='processBlockElement' file='packages/docx/src/html-to-docx.ts' risk='16.83' band='critical' cc='31' nd='6' fo='7' touches='2' />

`processBlockElement` lives in the DOCX export package and, from its name and position, handles the translation of individual HTML block elements into their DOCX equivalents — headings, paragraphs, lists, tables, and so on. That kind of function almost inevitably accumulates branching as new HTML constructs are supported over time.

<MetricBar label='Cyclomatic Complexity' value='31' threshold='10' max='60' />
<MetricBar label='Max Nesting Depth' value='6' threshold='4' max='10' />

A cyclomatic complexity of 31 means there are at least 31 independent execution paths through this function — each one a required test case and a potential place where a new HTML element type could be mishandled. The nesting depth of 6 compounds that: reasoning about the outermost conditional requires holding the inner five levels in working memory simultaneously. In TypeScript specifically, type narrowing inside deeply nested branches can diverge silently from what the outer type signature implies, making the actual behavior harder to verify than the CC alone suggests.

The function was touched twice in the last 30 days and was last modified just four days ago. With no prior bug-linked commits on the file, the historical record is clean — but the combination of complexity, depth, and live change activity is precisely the profile where a well-intentioned change to handle one new element type silently breaks another.

The `complex_branching` and `deeply_nested` patterns are both flagged here, and it is the only function in the top hotspots to carry both. My recommendation is to extract element-type handlers into a dispatch map or a small set of single-responsibility functions — one per block category (heading, list, table, etc.). That restructuring would cut both CC and nesting depth by isolating each code path, and it makes the test surface explicit.

### `AgentChat` — $threadId.tsx

<FunctionCard fn='AgentChat' file='apps/web/src/routes/agent/$threadId.tsx' risk='14.95' band='critical' cc='15' nd='3' fo='57' touches='3' />

`AgentChat` is the React component backing the agent thread view. A cyclomatic complexity of 15 is moderate on its own, but the fan-out of 57 is what drives this into critical territory.

<MetricBar label='Fan-Out (distinct callees)' value='57' threshold='15' max='70' />

Fan-out of 57 means this component directly calls or references 57 distinct functions — hooks, utilities, API clients, UI primitives. That is an unusually broad coupling surface for a single component. A change to any one of those 57 callees can ripple back into `AgentChat` in ways that are difficult to anticipate without running the full integration path. The `god_function` pattern reflects exactly this: the component is likely orchestrating state management, API calls, streaming, and rendering in one place rather than delegating to purpose-built hooks or sub-components.

The file has 3 touches in the last 30 days, was last modified 9 days ago, and has one bug-linked commit in its history. The external PR review comment density of 14 is the highest in the top five — reviewers have already been spending significant effort on this file, which suggests the complexity is visible to the team and generating discussion.

The most direct reduction here is to extract data-fetching and state logic into custom hooks, leaving the component responsible only for rendering. Each extracted hook can be tested in isolation, and the fan-out of the component itself drops with each extraction.

<FunctionCard fn='ChipInput' file='apps/web/src/components/input/chip-input.tsx' risk='14.63' band='critical' cc='17' nd='3' fo='33' touches='2' />

`ChipInput` is a shared UI input component — the kind that handles keyboard events, selection state, validation, and rendering in one place. A cyclomatic complexity of 17 and a fan-out of 33 for what is nominally a leaf-level UI component is a signal that it has taken on responsibilities beyond rendering.

Because this sits in `apps/web/src/components/input/`, it is likely consumed broadly across the application. The `god_function` and `exit_heavy` patterns together suggest a function handling many distinct input scenarios — each with its own early return — rather than a clean compositional structure. In TypeScript, multiple conditional branches over union types or optional props tend to produce exactly this CC profile, and each branch needs its own test to verify correct behavior.

With 2 touches in the last 30 days and a single author in the last 90 days, there is a knowledge concentration risk here: the full logic of this component may exist primarily in one person's head. I would recommend splitting keyboard event handling, chip management logic, and rendering into separate concerns — either sub-components or extracted handler functions — before this component's usage spreads further.

### `parse` — reactive-resume-v4-json.tsx

<FunctionCard fn='parse' file='packages/import/src/reactive-resume-v4-json.tsx' risk='14.43' band='critical' cc='24' nd='3' fo='27' touches='4' />

`parse` in `packages/import/src/reactive-resume-v4-json.tsx` is responsible for deserializing the v4 JSON resume format. The version marker in the filename — `v4` — is worth flagging: this is explicitly a versioned parser, which implies v3 or earlier formats exist or did exist, and that the format is subject to evolution.

<MetricBar label='Cyclomatic Complexity' value='24' threshold='10' max='40' />

A CC of 24 in a parser is typical of field-by-field validation and normalization: each optional field, each supported variant, and each fallback adds a branch. The fan-out of 27 suggests it is calling into schema validators, transformers, and possibly other parsers. With 4 touches in the last 30 days — the most active function in the top five — and last modified 4 days ago, this is clearly in active development. One bug-linked commit appears in the file history.

The `exit_heavy` and `god_function` patterns indicate that error handling and field normalization are likely interleaved with the main parsing logic. I would extract each resume section (basics, work, education, custom sections) into its own typed parser function, using a result type or discriminated union to surface parse errors explicitly rather than via early returns. That reduces both the CC of `parse` itself and makes each section independently testable. Two authors have touched this file in the last 90 days, so the extracted functions would also reduce the coordination overhead between contributors.

<FunctionCard fn='ImportResumeDialog' file='apps/web/src/dialogs/resume/import.tsx' risk='13.86' band='critical' cc='10' nd='3' fo='32' touches='2' />

`ImportResumeDialog` is the UI dialog component that surfaces the import workflow to the user. Its cyclomatic complexity of 10 sits at the moderate threshold, but the fan-out of 32 is what earns it a critical band rating.

<MetricBar label='Fan-Out (distinct callees)' value='32' threshold='15' max='60' />

A dialog component calling 32 distinct functions is handling considerably more than presentation. It is likely managing file selection, format detection, parser invocation, error display, and state transitions — all of which connect directly to the `parse` function analyzed above. The `god_function` pattern confirms this: the dialog has become an orchestration layer rather than a thin UI wrapper.

With 2 touches in the last 30 days and a single author over the last 90 days, ownership is concentrated. The PR review comment density of 3 is modest but non-zero, indicating reviewers have flagged concerns. Given that `ImportResumeDialog` and `parse` are both actively changing and structurally connected, a change in either can affect the other. I would introduce an explicit state machine or reducer for the import flow steps — selecting, validating, parsing, confirming — and move each step's logic out of the component. That reduces fan-out and makes the import sequence testable without rendering the dialog.
