All five of the highest-risk functions in golang/go live in one file, src/cmd/compile/internal/ssagen/ssa.go: genssa, stmt, exprCheckPtr, call, and dottype1. Each is critical-band, active-tier code, touched 52 times in the last year and last changed 0 days ago, so this is live regression risk rather than a backlog item. The activity-weighted risk scores run from 3.67 to 3.77 across a repository of 49,774 functions, 5,705 of them critical. I would start with genssa, but anyone changing this file should treat the whole module as one review surface.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

The concentration is the finding. Five separate functions in one file share the same touch count (52 in the last year), the same recency (0 days since last change), and the same file-level history (55 total commits, 9 distinct authors in the last 90 days). The file itself is the unit of risk. A change to any one of these functions lands in a file where several other critical-band, high-coupling functions are changing at the same time.

These are file-level signals, so they apply equally to all five functions and prove nothing about any single one.

### `genssa` — ssa.go

<FunctionCard fn='genssa' file='src/cmd/compile/internal/ssagen/ssa.go' risk='3.77' band='critical' cc='215' nd='6' fo='99' touches='52' />

I would start with `genssa` because it has the highest activity-weighted risk score in the repository (3.77), a cyclomatic complexity of 215, nesting depth of 6, and fan-out of 99, and it was changed today. From the excerpt, it takes the SSA function and drives code emission: it sets up liveness computation, argument-info emission, open-coded defer funcdata, per-block start tracking, debug/print bookkeeping, location-list setup, and architecture-specific alignment handling. That reads as a long setup sequence with many independent optional features gated by flags and architecture switches, all in one body.

<MetricBar label='Cyclomatic Complexity' value='215' threshold='10' max='300' />

A complexity of 215 means 215 independent paths, each a potential test case. The fan-out of 99 means it directly calls 99 distinct functions, so a change to any of the liveness, debug-info, or architecture helpers it calls can surface here. The depth of 6 is above the level where I start asking for extraction. My recommendation: pull the setup phases that run before the block loop (liveness and arg-info, open-defer funcdata, print/HTML bookkeeping, location-list cache setup, hot-alignment configuration) into named helpers that take and return the shared state. That is a mechanical extract-method step that should cut both complexity and nesting without altering emission order.

### `stmt` — ssa.go

<FunctionCard fn='stmt' file='src/cmd/compile/internal/ssagen/ssa.go' risk='3.73' band='critical' cc='253' nd='5' fo='89' touches='52' />

`stmt` has a cyclomatic complexity of 253, nesting depth of 5, and fan-out of 89, with an activity-weighted risk score of 3.73. The excerpt shows a large switch over the statement operation kind (blocks, calls, defer, go, type-assertion assignments, and more), preceded by an early dead-code exit. Complexity here is mostly breadth: one case per statement form. That is a common and defensible shape for a lowering pass, but it means every new statement form or special case lands in the same function.

Some cases carry their own embedded logic rather than delegating. The call case, for example, contains a nested check against a list of runtime function names (throw, gopanic, panicwrap, and several panic-length variants) to decide whether to end the block as an exit. The defer case branches on open-coded versus stack-allocated versus heap-allocated handling. My recommendation: move each non-trivial case body into its own method (the runtime-panic-call detection is an obvious first extraction, since it is a pure predicate over a function name and package). Leave the switch as a thin dispatcher.

### `exprCheckPtr` — ssa.go

<FunctionCard fn='exprCheckPtr' file='src/cmd/compile/internal/ssagen/ssa.go' risk='3.69' band='critical' cc='297' nd='4' fo='139' touches='52' />

`exprCheckPtr` has the highest cyclomatic complexity (297) and the highest fan-out (139) of the five, with an activity-weighted risk score of 3.69. Its nesting depth is a modest 4, which tells me the complexity is wide rather than deep: the excerpt shows a switch over expression operation kinds, including string/byte conversions, function values, names, nil, and literals with a nested switch on integer size. Each case builds SSA values through a long list of constructor calls.

<MetricBar label='Fan-out' value='139' threshold='15' max='150' />

A fan-out of 139 is the number I would worry about most in this file. It means this one function is directly coupled to 139 other functions, so a signature or behavior change in any of the SSA value constructors, constant helpers, or type utilities can require a change here. The checkPtrOK parameter in the signature suggests a pointer-checking mode threaded through the whole expression lowering, which adds a cross-cutting concern to every case. My recommendation: split by expression family (conversions, constants, names and addresses, and so on) into separate methods and keep the top-level function as a dispatcher. Constants alone, with their size-keyed switch, are a clean first extraction.

### `call` — ssa.go

<FunctionCard fn='call' file='src/cmd/compile/internal/ssagen/ssa.go' risk='3.68' band='critical' cc='105' nd='4' fo='56' touches='52' />

`call` has a cyclomatic complexity of 105, nesting depth of 4, and fan-out of 56, with an activity-weighted risk score of 3.68. From the excerpt it lowers a call expression and handles several call kinds (normal, tail, go, defer, defer-stack), static versus closure versus interface dispatch, ABI selection, and defer-extra arguments. The excerpt also shows a conditional keyed on a build experiment for register-based arguments, with an older code path still present and marked with a TODO for removal after the register ABI is working.

That experiment-gated branch is worth noting: it means two ABI-selection strategies coexist in one function, and every path through the rest of the function has to be correct under both. My recommendation: extract ABI selection (static callee resolution plus the experiment-gated logic) into its own helper that returns the callee symbol and ABI. That isolates the TODO-marked legacy branch so it can be deleted cleanly when its time comes, and it removes a layer of branching from the body that handles arguments and results.

### `dottype1` — ssa.go

<FunctionCard fn='dottype1' file='src/cmd/compile/internal/ssagen/ssa.go' risk='3.67' band='critical' cc='73' nd='4' fo='39' touches='52' />

`dottype1` is the smallest of the five, with a cyclomatic complexity of 73, nesting depth of 4, fan-out of 39, and an activity-weighted risk score of 3.67. By its name and excerpt, it lowers type assertions: the visible portion handles conversion to an empty interface (with a nil check on the itab, a shortcut for empty-to-empty with comma-ok, and a branch-and-merge shape for the other cases) and then falls into a separate path for conversion to a non-empty interface that needs a runtime call.

The excerpt has several early returns with named results, plus manual block construction (create blocks, add edges, start and end blocks, merge point). Hand-built control flow like that is easy to get subtly wrong and hard to test through its outputs alone, so I would want each of the empty-interface, non-empty-interface, and concrete-type branches covered by their own tests. My recommendation: split the function along those three destination kinds, since the top-level `if dst.IsInterface()` and `if dst.IsEmptyInterface()` checks already mark the seams.

## Where to start

I would begin with `genssa` and `exprCheckPtr`, because they pair the highest complexity and fan-out values with the same 52 touches and same-day changes. The extractions I described are mechanical, they do not change behavior if done carefully, and each one shrinks the surface a reviewer must hold in their head. Since all five functions share one file and one change history, I would also agree on review ownership for the whole file rather than function by function: with 9 distinct authors in the last 90 days, a shared checklist for edits to ssa.go would be cheap and directly aimed at the risk this data shows.

For context, the next-highest scores in the repository are quiet-tier. That is structural debt with a high blast radius when next touched, but it is not the live risk that ssa.go represents.
