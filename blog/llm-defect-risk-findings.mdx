I spent a few weeks running a controlled experiment: can a small language model, fine-tuned on a specific codebase's history, learn to rank code by defect risk better than a hand-tuned heuristic? The short answer is yes — but with important caveats about when it works and when it doesn't.

Here's what I found.

---

## The Setup

The goal: rank functions in a codebase by how likely they are to be involved in future bug fixes — useful for prioritizing code review and refactoring effort.

My baseline is a deterministic, activity-weighted risk score — it combines static complexity metrics (cyclomatic complexity, nesting depth, fan-out) with git activity signals like touch frequency and recency, using fixed weights. It's cheap, explainable, and reasonably effective. The question was: can a model do better?

I fine-tuned [Qwen2.5-Coder-7B](https://huggingface.co/Qwen/Qwen2.5-Coder-7B-Instruct) using LoRA on per-repo training data. The model receives a prompt describing a function — its file path, structural metrics, and source code — and outputs a 0–9 risk score. I trained per-repo (one adapter per codebase), evaluated on held-out functions, and measured Spearman ρ (rank correlation, −1 to +1) against a ground-truth label derived from the repo's own bug-fix history. Ground-truth labels mark a function as risky if it appears in commits whose messages indicate bug fixes (via keywords or linked issue references).

I tested on six open-source repos: Django, scikit-learn, Vue.js core, VS Code, the Go standard library, and Vercel's Next.js.

---

## The First Trap: Circularity

Early results looked great. A full-prompt fine-tuned adapter on Django achieved ρ=+0.74. Then I looked more carefully at the prompt.

The prompt included git activity fields — how many times the function had been touched, when it was last changed, how many authors had modified it. These fields are derived from the same history used to construct the ground-truth label. The model wasn't learning to read code — it was learning to relay git signals back as scores.

I confirmed this with an ablation: zero out all git fields in the prompt, and the adapter's performance dropped from ρ=+0.74 to ρ=-0.04. The signal was entirely circular.

The fix was to train and evaluate with all git-history fields zeroed. After ablation, a fresh adapter trained on code structure and source text only achieved ρ=+0.48 on Django — well above the baseline at ρ=+0.17. That result is defensible: the model learned something from code, not from history it had already seen in its label.

---

## The Baseline Gate

Before celebrating, I ran a simple sanity check: train gradient-boosted tabular models on the same train/holdout splits using only path tokens, activity features, or structural metrics. The results were humbling.

On VS Code, activity-only features achieved ρ=+0.88. On Django, path-only features reached ρ=+0.58. Any fine-tuned model needs to beat these cheap baselines to claim it's learning something the heuristics don't already know.

This changed how I interpreted results. The LLM needed to be compared against both the baseline *and* the tabular baselines, on the same splits.

---

## Cross-Repo Generalization: A Clear Failure

I tested whether the Django-trained adapter could score functions in other repos. It couldn't. On VS Code it achieved ρ=-0.007. On scikit-learn and Vue.js the results were similarly poor — collapsed to constant predictions or strongly negative ρ.

I then tried training on multiple repos simultaneously and evaluating on a held-out repo (leave-one-repo-out). That helped — going from ρ=-0.007 to ρ=+0.17 on VS Code — but still fell short of the baseline (+0.22). No configuration I tried produced a universal cross-repo model.

The adapter learns repo-specific priors from file and function names plus code patterns. Those priors don't transfer. If you want this to work on a new codebase, you need to fine-tune on that codebase.

---

## When Does Per-Repo Fine-Tuning Work?

Once I accepted the per-repo constraint, the next question was: does it work consistently across repos, or was Django just easy?

I trained separate adapters for each repo, then swept checkpoints to find each repo's peak performance. "FT" in the tables below refers to the fine-tuned adapter.

| Repo | Best FT ρ | Baseline ρ | Verdict |
|---|---:|---:|---|
| scikit-learn | **+0.603** | +0.180 | ✓ strong |
| django | **+0.494** | +0.165 | ✓ strong |
| vue.js core | **+0.369** | +0.233 | ✓ beats baseline |
| vs code | +0.183 | +0.186 | ✗ at baseline |
| golang | −0.142 | +0.114 | ✗ anti-predictive |
| next.js | +0.068 | +0.043 | ✗ negligible |

Four repos showed clear signal above the baseline. Two didn't just fail — they failed badly.

The VS Code result was puzzling initially. It's a 157K-commit repo where defect risk is dominated by *how much* a file changes, not *what* the code looks like. The activity baseline achieves ρ=+0.88 there, leaving almost nothing for a structural model to add. But Go (activity baseline ρ=+0.114) and Next.js (ρ=+0.043) had much lower activity baselines, so activity dominance isn't the full explanation.

My working hypothesis — not yet confirmed with measurements across all six repos — is that label density explains the divergence: how much non-trivial defect signal was actually available in the training data. Django, scikit-learn, and Vue.js appear to have well-structured bug-fix histories with clear signals; Go and Next.js had sparse coverage. When the training labels themselves don't carry much information, the model has nothing to learn from.

One other consistent observation: the signal emerged late in training, after the model had cycled through the data multiple times. Early checkpoints were often below the baseline; the peak arrived sharply then declined, consistent with overfitting.

---

## Does the Signal Survive Time?

The experiments above use all-time bug-fix labels — a function is labeled "risky" if it has ever been involved in a bug fix. That makes the task somewhat easy: the model is evaluated against the same historical record it was trained on, just on held-out functions.

A harder and more production-relevant question: does the signal hold when evaluated against *future* bug fixes — ones that hadn't happened yet when the model was trained?

I re-derived the bug-fix labels for scikit-learn and Vue.js using only post-2024 commits, then evaluated the original adapters against these temporal labels without retraining them.

| Repo | FT ρ (all-time labels) | FT ρ (post-2024 labels only) | Baseline ρ (temporal) |
|---|---:|---:|---:|
| scikit-learn | +0.603 | **+0.331** | +0.154 |
| vue.js core | +0.369 | **+0.259** | +0.143 |

The correlation dropped — substantially for scikit-learn, moderately for Vue.js. That was expected: predicting future bugs from current code structure is genuinely harder than correlating with historical ones. What matters is that both adapters still beat the baseline by a meaningful margin under temporal separation — +0.18 on scikit-learn (ρ=+0.331 vs +0.154) and +0.12 on Vue.js (ρ=+0.259 vs +0.143).

Django's adapter was trained against post-2024 labels from the outset — a methodological difference from the other repos — so its ρ=+0.494 is already a future-bug prediction rather than an all-time result.

The practical interpretation: these adapters, trained on one snapshot of a codebase's history, retain meaningful predictive power about which functions will be involved in future fixes. The signal is real, not just a reflection of past events.

---

## The Ensemble

The strongest result came from combining the LLM scores with activity features using rank-averaging. On Django and scikit-learn the ensemble outperformed both components. On Vue.js — where activity signal is exceptionally strong — it fell short of activity-only but still substantially beat the fine-tuned model alone:

| Repo | FT only | Activity only | Ensemble |
|---|---:|---:|---:|
| scikit-learn | +0.603 | +0.749 | **+0.828** |
| django | +0.494 | +0.586 | **+0.648** |
| vue.js core | +0.369 | +0.835 | **+0.771** |

The FT and activity signals are measuring different things. Activity captures "this file changes a lot" — a strong but blunt predictor. The LLM captures something about which specific functions look risky from their code and naming patterns, independent of how often they've been touched. Together they're better than either alone.

The blend weights were tuned on each repo's holdout and varied — we treat them as experiment-specific findings rather than fixed constants.

---

## What I Didn't Prove

A few things to be clear about:

**The LLM is not understanding code in any deep sense.** Ablation experiments on the Django adapter showed that file and function names carry most of the signal in a path-conditioned model: masking source text while keeping the path drops performance to ρ=+0.385 (a moderate loss), while masking the path while keeping source drops to ρ=+0.268 (a larger loss). However, this doesn't mean path is fundamental. When a new adapter is trained from scratch with paths replaced by a placeholder throughout, it recovers ρ=+0.489 — essentially the same performance as the original +0.494. The original adapter's path-dependence was a training artifact: it learned to rely on path because path was available during training. When forced to work without it from the start, the model found nearly equivalent signal in source structure and code metrics.

**The ground-truth label has limits.** The label is derived from git history — it measures past defect involvement, not intrinsic code quality. A function could be defect-prone because it's genuinely fragile, or because it implements a specification that kept changing. The model learns whatever the label captures.

**The sample is still small.** Six repos across two languages is not enough to draw strong conclusions about what determines whether per-repo fine-tuning will work. The label density hypothesis fits the data but has one complication: VS Code showed 50% label coverage after full enrichment, yet the adapter performed only at baseline (ρ=+0.183 vs +0.186). The discriminating signal appears to be the *average density* of defect signal, not just whether labels are present — a subtlety the six-repo sample alone is not large enough to fully resolve.

---

## Open Questions

Two questions remain open from this work:

1. **Path-masked cross-repo generalization** — the path-masked retraining result suggests a source-text-only adapter might generalize better across repos, since it learned signal without relying on repo-specific file names. This hasn't been tested on an out-of-distribution codebase.
2. **Label quality and coverage** — the post-2024 temporal results (scikit-learn ρ=+0.331, Vue.js ρ=+0.259) represent the realistic production estimate. But the ground-truth label is itself derived from git history, which varies in quality across repos. Repos with structured bug-tracking (linked commits, issue references) produce cleaner labels than repos that rely on keyword matching alone.

The clearest result here: fine-tuning a small model on a specific codebase's history produces a real, measurable signal that survives temporal separation — but it's a structural complement to activity-based features, not a replacement for them. The ensemble is the most defensible configuration, and the per-repo constraint is real: no configuration we tested produced a universal cross-repo model.

---

*All experiments were run on Apple Silicon (MLX, 4-bit quantization). Spearman ρ reported on stratified holdout splits. Training used LoRA rank 8 with all git-history fields ablated from prompts to prevent circularity.*
