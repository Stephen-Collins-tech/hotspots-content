`site/src/assets/stackblitz.js` holds 3 of the 5 highest-risk functions in twbs/bootstrap (`splitTopLevel`, `getDocsStyles`, `getExampleProject`), so I would treat it as one module that needs a review, not three separate cleanup tickets. All three are in the active tier, each was touched 7 times in the last year, and each was last changed 6 days ago, with activity-weighted risk scores of 2.25, 2.23 and 2.2. That makes this a module worth reviewing soon. The analysis covers 763 functions at commit 2871f2a, 23 of them critical, and every function in the snapshot is in the active tier.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `splitTopLevel` — stackblitz.js

<FunctionCard fn='splitTopLevel' file='site/src/assets/stackblitz.js' risk='2.25' band='critical' cc='17' nd='3' fo='4' touches='7' />

I would start with `splitTopLevel` because it has the highest activity-weighted risk score in the repo (2.25) and a cyclomatic complexity of 17, in a file touched 7 times in the last year and last changed 6 days ago. From the source excerpt, it is a hand-written scanner that splits a string on a separator while tracking quote state and parenthesis depth. It is a small character-level state machine with a switch over quote, parenthesis and separator cases, plus an escape check on the previous character.

<MetricBar label='Cyclomatic Complexity' value='17' threshold='10' max='60' />

Its fan-out is only 4, so the risk is not coupling. It is the number of paths, and every one is a test case: escaped quotes, unbalanced parentheses, a separator inside quotes, and an empty trailing segment. The two calls in `getDocsStyles` split CSS selector lists on commas and declaration blocks on semicolons, so a boundary bug here would silently drop or merge CSS rules in the playground output. The function is pure and self-contained, which makes it the cheapest hotspot in the file to cover with a table-driven unit test. I would write that test before anyone changes the function again, then consider extracting the quote and depth tracking into a small state object so the switch only decides what to do on a separator.

### `getDocsStyles` — stackblitz.js

<FunctionCard fn='getDocsStyles' file='site/src/assets/stackblitz.js' risk='2.23' band='critical' cc='13' nd='1' fo='30' touches='7' />

`getDocsStyles` has a fan-out of 30, which is the second highest of the group (`getExampleProject` is at 31), with a cyclomatic complexity of 13 and nesting of just 1. The nesting figure is low because the function is built from many small closures (a class collector, a custom color mode matcher, a selector filter, a recursive rule collector) defined inside it. That keeps the indentation flat but not the cognitive load: the outer function holds the classes set, the custom mode set and the sheet list, and every inner closure reads them.

<MetricBar label='Fan-out' value='30' threshold='15' max='40' />

From the excerpt, it filters the docs stylesheets down to the rules that apply to one example element, handles nested at-rule blocks such as media, supports and layer through recursion, and finally emits the custom properties those rules use. That is several responsibilities in one function body, and the recursive collector sits behind a try/catch in a flat map over every stylesheet. My recommendation is to lift `appliesToExample` and `collect` out to module level with their inputs passed explicitly. That makes the selector-matching logic testable without a DOM full of stylesheets, and it cuts the outer function's job down to assembling the output.

### `getExampleProject` — stackblitz.js

<FunctionCard fn='getExampleProject' file='site/src/assets/stackblitz.js' risk='2.2' band='critical' cc='12' nd='3' fo='31' touches='7' />

`getExampleProject` has the highest fan-out of the group at 31, with a cyclomatic complexity of 12 and nesting of 3. It is an async function that fetches an example page, parses it, strips docs-only elements, rewrites stylesheet and script references, collects imports, calls `getDocsStyles`, and returns the file map for the playground. It is a pipeline, and each step is a reason to change.

<MetricBar label='Fan-out' value='31' threshold='15' max='40' />

The three stackblitz.js functions are not independent. `getExampleProject` calls `getDocsStyles`, which calls `splitTopLevel`, so a change at the bottom of that chain can surface in the generated playground project at the top. Since all three were last changed 6 days ago and the file had 2 distinct authors in the last 90 days, I would review them as one unit. The concrete step I would take is to split `getExampleProject` into named phases (clean the document, collect assets, assemble the project files) so that each phase has a name, a return value and a test, and the top-level function reads as a list of three steps.

### `_handleBeforeInput` — otp-input.ts

<FunctionCard fn='_handleBeforeInput' file='js/src/otp-input.ts' risk='2.18' band='critical' cc='12' nd='3' fo='5' touches='4' />

`_handleBeforeInput` in `js/src/otp-input.ts` is the most recently changed function in the top five: it was last changed 2 days ago and touched 4 times in the last year. Its cyclomatic complexity is 12, nesting is 3, and fan-out is 5, so it is structurally moderate but sits in code that is moving now. From the excerpt, it handles two input types, typed single characters and backward or forward deletion. Each branch carries its own guard conditions: readonly checks, sanitization, caret and selection arithmetic, and an early return when a delete would fall outside the value.

The risk here is the density of caret-position edge cases in one handler. The deletion branch alone distinguishes a selected slot from a collapsed caret, then splits again on backward versus forward delete, then bounds-checks. I would extract the insert and delete branches into separate methods, for example an insert handler and a delete handler, so each can be tested with a plain value and selection range. The data shows no bug-linked commits and no bug fixes in this file's 4 commits, so this is about keeping a young component easy to change, not about a known fault.

### `_handleInputKeydown` — chips.ts

<FunctionCard fn='_handleInputKeydown' file='js/src/chips.ts' risk='2.1' band='critical' cc='16' nd='4' fo='3' touches='2' />

`_handleInputKeydown` in `js/src/chips.ts` has a cyclomatic complexity of 16 and a nesting depth of 4, the deepest in the top five, with a low fan-out of 3. It was last changed 6 days ago and touched twice in the last year, which makes it the least churned function in this list and the one with the lowest score of the five (2.1). From the excerpt, it is a keyboard switch over Enter, Backspace and Delete, ArrowLeft and Escape, where the Backspace and ArrowLeft cases each nest a guard on the input state inside a check that chips exist.

The ArrowLeft case alone has an empty-caret check, a chip-count check, and a shift-key branch inside it. Its sibling `_handleChipKeydown` appears to use a similar switch with delegated helper calls such as `_handleChipDelete` and `_navigateChip`, and that is the pattern I would copy here. Moving each key's logic into a named method would flatten the nesting to 2 and leave the switch as a dispatch table. With only 2 touches in the last year this is not urgent, but the component is new enough that the refactor is cheapest now.

**What the five have in common**

Three of the five sit in one docs-side asset file and two sit in new component code. The two groups carry different kinds of risk. In stackblitz.js the concern is coupling and chained calls: fan-out of 30 and 31 on two functions that depend on each other. In the TypeScript components it is branching density in event handlers. My priorities would be: add tests around `splitTopLevel` first because it is cheap and everything above it depends on it, then split `getExampleProject` into phases, then pull the nested closures out of `getDocsStyles`, then do the two handler extractions as part of normal feature work.
