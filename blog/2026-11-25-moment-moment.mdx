Four of the five top hotspots in moment/moment live in src/lib/locale/locales.js, so I would treat that file, not any single function in it, as the unit of review. All four are in the active tier, each with 4 touches in the last year and 0 days since last change, which makes this active code rather than a backlog item; the highest, defineLocale, carries an activity-weighted risk score of 2.26. The repository has 1,983 functions with 127 in the critical band, and the pattern that stands out is how many of the highest-scoring ones are locale-related.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `defineLocale` — locales.js

<FunctionCard fn='defineLocale' file='src/lib/locale/locales.js' risk='2.26' band='critical' cc='8' nd='6' fo='7' touches='4' />

I would start with `defineLocale` because it has the highest activity-weighted risk score in the repository (2.26), a nesting depth of 6, and it was changed 0 days ago. Its cyclomatic complexity of 8 is modest, so the risk here comes from depth, not from path count.

<MetricBar label='Nesting Depth' value='6' threshold='4' max='8' />

From the source excerpt, the function branches on whether the config is null, then on whether a locale with that name already exists, then on whether a parent locale is named, then on whether that parent is already loaded or must be loaded on demand. When the parent cannot be found, it queues the child in a family list and returns null. Once the new locale is built, it re-defines any queued children recursively and sets the global locale as a backwards-compatibility step. The comment in the code says the global locale must be set only after all child locales exist. That ordering constraint is the kind of thing a nested structure hides. The same function also emits a deprecation warning when an existing locale is overridden, so one function handles creation, override, deferred-parent resolution and test teardown (the delete branch).

The file-level history adds context. Four commits touched the file, and 75% of them are tagged as bug fixes, with no revert and no commit directly linked to a tracked bug. Two distinct authors touched it in the last 90 days. That bug-fix rate does not show this function is defective, but a small file history that skews toward fixes is a reason to review it with more care.

My recommendation: flatten the nesting with guard clauses and extract the parent-resolution logic into its own function. The branch that finds the parent configuration (existing locale, loaded parent, or deferred parent) is a natural unit with a single output, either a parent config or a signal to defer. Pulling it out should take the nesting depth from 6 to around 3 without changing behavior.

### `loadLocale` — locales.js

<FunctionCard fn='loadLocale' file='src/lib/locale/locales.js' risk='2.11' band='high' cc='12' nd='2' fo='5' touches='4' />

`loadLocale` has the highest cyclomatic complexity of the four locales.js functions at 12, with shallow nesting of 2 and a fan-out of 5. It resolves a locale by exact name, then by normalized name, then, in a Node-style module environment, by requiring a locale file from disk. The excerpt shows comments about guarding against names like `__proto__` and `constructor` by using an own-property check, and about caching a null result so failed lookups do not repeat an expensive require call.

The function also mixes three concerns: cache lookup, name validation, and filesystem loading with global-locale save and restore around the require.

My recommendation: separate the cache lookup from the Node-specific load path. A small function that only answers 'is this name already registered' and another that only attempts the file load would let each be tested without stubbing module state.

### `chooseLocale` — locales.js

<FunctionCard fn='chooseLocale' file='src/lib/locale/locales.js' risk='2.11' band='high' cc='8' nd='3' fo='8' touches='4' />

`chooseLocale` has the highest fan-out of the group at 8, alongside a cyclomatic complexity of 8 and nesting depth of 3. It walks a list of candidate locale names, splits each into subtags, tries progressively shorter prefixes through `loadLocale`, and compares against the next candidate to decide whether to break early. If nothing matches, it returns the global locale.

The risk I see is the coupling. This function calls `loadLocale`, which itself calls `getSetGlobalLocale`, which can call `defineLocale`. So a change to any of those can alter what `chooseLocale` returns, and the dependency is not obvious from the signature. JavaScript's dynamic dispatch and shared module state make static fan-out undercount this kind of coupling, so I would treat the reported 8 as a floor.

My recommendation: write characterization tests around the prefix-fallback and next-candidate comparison logic before touching anything else in this file. That inner loop is where the subtle behavior lives.

### `updateLocale` — locales.js

<FunctionCard fn='updateLocale' file='src/lib/locale/locales.js' risk='2.08' band='high' cc='11' nd='4' fo='4' touches='4' />

`updateLocale` has a cyclomatic complexity of 11, nesting depth of 4 and fan-out of 4. From the excerpt, it has three distinct modes in one body: update a child locale in place, merge a new config onto a parent and register the result, or, when the config is null, undo a previous update. Each mode mutates the shared locales registry and may reset the global locale.

The null-config branch is described in a comment as useful for tests. That means the function carries a branch that the comment ties to test use.

My recommendation: split `updateLocale` into an update path and a revert path. The two share almost no logic once the config check is made, and separating them removes one top-level decision and several nested conditions.

## Where to start

I would start with locales.js as a whole. Four functions in one file, all touched 4 times in the last year and all changed on the day of the snapshot, means the file is under steady change. Begin with `defineLocale`, because its nesting depth of 6 is the clearest structural problem and `chooseLocale`, `loadLocale` and `updateLocale` all call into related locale-loading code. Then add tests around `chooseLocale` and `loadLocale` before any further changes, and split `updateLocale` into update and revert paths. The fifth entry, `processRelativeTime$1` in min/moment-with-locales.js, is a bundled copy (see the note below), so I would leave the Slovenian relative-time functions for later: the complexity is high but it is rule-driven, fan-out is 0, and the source copies have gone 77 days without a change.
