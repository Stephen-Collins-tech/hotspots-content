804 of dgraph's 4,429 functions sit in the 'fire' quadrant, meaning they are structurally complex and were touched recently, and 1,054 are in the critical band. The top three are all in that group: `rewriteObject` in graphql/resolve/mutation_rewriter.go (an activity-weighted risk score of 20.19, CC 133), `encode` in query/outputnode_graphql.go (20.13, CC 124), and `parseFunction` in dql/parser.go (18.8, CC 182) each had 3 touches in the last year and were last changed 70 days ago. If you are shipping changes to GraphQL mutations, GraphQL response encoding, or DQL function parsing this week, a small edit in any of these has the widest surface area for regression. I would start with `rewriteObject`.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

## Large Repo Analysis

dgraph is a large repository. To stay within memory constraints, this analysis used **hybrid touch mode**: structural complexity — CC, ND, FO — is measured precisely for every function. Git activity is tracked at the function level (via `git log -L`) only for files with 5 or more commits in the touch window (365 days by default); other files use a file-level approximation. Rankings therefore surface functions that are both structurally complex and in the most actively-changing parts of the codebase. Dormant code with high structural complexity will rank lower than it would under a full per-function analysis — to surface it, run `hotspots analyze . --per-function-touches` on a machine with sufficient memory.

### `rewriteObject` — mutation_rewriter.go

<FunctionCard fn='rewriteObject' file='graphql/resolve/mutation_rewriter.go' risk='20.19' band='fire' cc='133' nd='8' fo='56' touches='3' />

I would start here. `rewriteObject` has the highest activity-weighted risk score in the repo (20.19) and sits in the 'fire' quadrant: 3 touches in the last year, last changed 70 days ago. It turns a GraphQL mutation input object into the fragments that become Dgraph mutations. From the excerpt, one body handles ID-referenced nodes, nodes keyed by external ID fields, top-level versus nested objects, and error concealment when an ID already exists.

<MetricBar label='Cyclomatic Complexity' value='133' threshold='10' max='182' />

CC 133 means 133 independent paths, each a potential test case. A nesting depth of 8 is the level I treat as a strong refactoring signal, and a fan-out of 56 means it couples to a large number of other functions. The signature alone takes nine parameters, a hint that state is being threaded through rather than owned by a smaller unit. The file has a bug-fix rate of 33% across 3 commits, with no bug-linked commits, no reverts, and 1 distinct author in the last 90 days. That sample is small, so I read it as a light nudge toward closer review, not a defect claim.

Recommendation: split along the cases the function's own comment lists. Pull the ID-reference branch and the external-ID branch into separate functions that return the same result tuple, and leave `rewriteObject` as the dispatcher. The branches that return early with errors make the natural first cut, since each already has a clear contract.

### `encode` — outputnode_graphql.go

<FunctionCard fn='encode' file='query/outputnode_graphql.go' risk='20.13' band='fire' cc='124' nd='9' fo='52' touches='3' />

`encode` is a method on the GraphQL encoder in the query output path, and it serializes DQL results into GraphQL response JSON. The excerpt shows a scalar branch (value extraction, geo handling, scalar coercion checks) followed by an object branch that deals with custom-field nodes, type names, and opening braces. Its activity-weighted risk score of 20.13 trails `rewriteObject` by just 0.06, and its nesting is the deepest of the five at ND 9.

CC 124 paired with ND 9 is the combination that worries me. Deep nesting makes it hard to keep the output buffer's state in your head, and this function writes to a shared buffer and appends to an error list as it goes. Many exit paths return false to tell the caller how to write null, so each exit means something different to the caller and each needs its own test. The file shows a bug-fix rate of 0% across 3 commits, no reverts, and 1 distinct author in the last 90 days, so the history gives no extra cause for alarm. This is maintainability and regression-surface risk, not a defect signal.

Recommendation: separate the scalar path from the object path into two functions. The scalar half already reads as a self-contained unit with its own early returns, so extracting it is low risk and would cut the nesting depth of what remains.

### `parseFunction` — parser.go

<FunctionCard fn='parseFunction' file='dql/parser.go' risk='18.8' band='fire' cc='182' nd='7' fo='28' touches='3' />

At CC 182, `parseFunction` is the most complex function in this set, and it lives in the DQL parser. The excerpt shows a token loop with an inner token loop, a switch over token types, recursion for nested functions, and a second level of switches on special function names like value and len. It is a hand-written parser handling function-argument grammar in one place.

<MetricBar label='Cyclomatic Complexity' value='182' threshold='10' max='182' />

Grammar is inherently branchy, so parsers tend to post high branch counts, and I weigh the CC figure with that in mind. Even so, 182 paths plus several boolean state flags (expecting an argument, having seen a function argument, expecting a language tag, being after a dollar sign) means valid and invalid token sequences are encoded in flag combinations. The file has a bug-fix rate of 33% across 3 commits, with no reverts and 1 distinct author in the last 90 days. I would expect edits to the parser as a whole to collide.

Recommendation: extract per-argument-type handlers (attribute, value variable, len, literal) so the main loop only routes tokens. Table-driven tests that feed each function name valid and invalid argument sequences would pin behavior before the split.

### `handleValuePostings` — task.go

<FunctionCard fn='handleValuePostings' file='worker/task.go' risk='18.54' band='debt' cc='70' nd='6' fo='59' touches='0' />

This one is 'debt', not 'fire'. It hasn't changed in 218 days, has 0 touches in the last year, and is the only function in the top set flagged as stale and complex. That makes it a high blast radius item for whoever touches it next, not a live-churn item. It is a method on the query state in the worker package and handles value-posting retrieval for several function types, including a vector similarity branch that builds a search cache, picks an index, and applies optional search parameters.

Its fan-out of 59 is the highest in the set, with CC 70 and ND 6 stacked on top. The file shows a bug-fix rate of 60% across 5 commits, with no bug-linked commits, no reverts, and 2 distinct authors in the last 90 days. With only 5 commits that percentage is 3 commits, so I would not overread it, but it is the highest ratio of the five and it sits on a file that has been quiet for over seven months. That pairing is why I would refactor it deliberately rather than wait for a feature to force the change.

Recommendation: the vector similarity branch is already a self-contained block that returns early. Move it into its own method first. That strips out a large share of the fan-out and nesting without touching the remaining value-posting logic.

### `dgraphDirectivePredicateValidation` — rules.go

<FunctionCard fn='dgraphDirectivePredicateValidation' file='graphql/schema/rules.go' risk='18.38' band='debt' cc='55' nd='7' fo='22' touches='2' />

This function validates the @dgraph directive across a GraphQL schema, checking for conflicts between predicate types, ID versus non-ID fields, secret fields, and interface implementations. The data labels it 'debt', with 2 touches in the last year and 70 days since last change, so I frame it as structural debt with a high blast radius when next edited rather than as live churn.

The excerpt shows many closures (error builders and checkers) defined inside the function body before any work begins. That inflates length and complexity without adding real branching depth at the top level, and cleaning it up is fairly mechanical. CC 55 and fan-out of 22 are the lowest in the set. The file has a bug-fix rate of 0% across 2 commits, no reverts, and 1 distinct author in the last 90 days, which points toward maintainability debt rather than a quality concern.

Recommendation: promote the error-builder closures to package-level functions and the checker closures to a small validator struct that holds the predicate map. That should shrink the main function to setup plus a loop and make each check testable on its own.
