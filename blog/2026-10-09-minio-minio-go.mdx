If you are shipping code against this repository this week, the top of the list matters most: GetObject in api-get-object.go has an activity-weighted risk score of 17.63, with CC 27, nesting depth 7 and fan-out 25, and it was last changed 29 days ago. I would start there, then move to newRequest and executeMethod in api.go, which together form the path every client call passes through.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `GetObject` — api-get-object.go

<FunctionCard fn='GetObject' file='api-get-object.go' risk='17.63' band='fire' cc='27' nd='7' fo='25' touches='1' />

I would start with `GetObject` because it pairs the deepest nesting in the top five (ND 7) with an active change history: 1 touch in the last year and 29 days since last change. From the excerpt, the function validates bucket and object names, branches into an RDMA path when a buffer is supplied, and then starts a goroutine that serves read requests over a request channel and a response channel. That goroutine nests branches on first-request, read-versus-read-at, and offset handling, which accounts for the depth.

<MetricBar label='Nesting Depth' value='7' threshold='4' max='10' />

Here the Go-specific caveat matters. The structural numbers miss goroutine lifecycle, channel handoff, and the deferred cleanup of the HTTP reader and cancel function, and those interactions are where I would expect review to be hardest. File-level history shows a bug-fix rate of 75% across 8 commits, 3 distinct authors in the last 90 days, and no reverts or bug-linked commits recorded. That bug-fix rate is a small-sample ratio, not proof of a defect, but it moves this function up my review order. My recommendation: extract the goroutine body into a named type with methods for the first-request and subsequent-request paths, so the channel protocol can be tested without the HTTP layer.

### `testListObjectsChecksums` — functional_tests.go

<FunctionCard fn='testListObjectsChecksums' file='functional_tests.go' risk='17.35' band='fire' cc='56' nd='4' fo='32' touches='2' />

This is a functional test rather than library code, but it is changing right now: 2 touches in the last year and a last change 0 days ago. CC 56 with fan-out 32 matches what the excerpt shows: setup, a loop over roughly ten checksum algorithms, per-algorithm skip conditions, single-part and multipart uploads, and repeated log-and-return error handling. The file shows a bug-fix rate of about 29% across 17 commits and 4 distinct authors in the last 90 days.

A complex test carries a different risk than complex production code: it is hard to trust when it fails and easy to break when a new algorithm arrives. I would convert the algorithm loop into table-driven subtests with a shared helper for upload-and-expect, so each checksum type fails independently and the branch count drops sharply.

### `executeMethod` — api.go

<FunctionCard fn='executeMethod' file='api.go' risk='17.12' band='debt' cc='62' nd='5' fo='29' touches='0' />

`executeMethod` is the one debt-quadrant entry in my top five. It has not changed in 251 days and has no touches in the last year, so I would not call it live churn. Its danger is blast radius the next time someone edits it: CC 62, nesting depth 5, fan-out 29. From the excerpt it handles offline detection, retryability based on whether the body is seekable, trailer and checksum wrapping, and a retry loop with several distinct error-handling branches (request construction errors, transport errors, status handling).

It also carries the stale-and-complex pattern, the combination I would flag for refactoring before the next development push, because whoever edits it next will have little recent context. File-level signals show 15 commits, a bug-fix rate of about 33%, 4 distinct authors in the last 90 days, and no reverts. I would separate the retry policy (when to retry, how to rewind the body) from the response classification, so each half gets focused tests.

### `newRequest` — api.go

<FunctionCard fn='newRequest' file='api.go' risk='16.88' band='fire' cc='109' nd='4' fo='46' touches='0' />

<MetricBar label='Cyclomatic Complexity' value='109' threshold='30' max='120' />

`newRequest` has the highest cyclomatic complexity in my top five at 109, and the highest fan-out at 46. It sits in the fire quadrant, last changed 30 days ago, so I treat it as live even though it shows 0 touches in the last year. The excerpt explains the numbers: location lookup, virtual-host-style detection, S3 Express handling, credential retrieval with a de-duplication group, and a long block of comments on context detachment and panic propagation. That commentary suggests the concurrency semantics here are subtle.

Nesting is moderate at 4, so the problem is breadth rather than depth: many sequential decisions in one wide function. It shares file-level history with `executeMethod` (15 commits, bug-fix rate about 33%, 4 distinct authors in the last 90 days). I would extract credential resolution into its own function with a narrow signature, since the comments already describe a self-contained contract. Signing, header assembly, and URL construction can follow as separate steps.

### `getSSOCredentials` — pkg/credentials/file_aws_credentials.go

<FunctionCard fn='getSSOCredentials' file='pkg/credentials/file_aws_credentials.go' risk='16.5' band='fire' cc='55' nd='4' fo='37' touches='0' />

This function parses AWS profile and sso-session config, derives a cache filename from a SHA1 of the session name or start URL, reads and validates a cached token, and then prepares to call the SSO portal. CC 55 and fan-out 37 come mostly from error-return branches: the excerpt shows many distinct failure messages for missing account IDs, mismatched regions, missing home directories, and unreadable or expired tokens. That is the exit_heavy pattern, and each exit is a test case.

It was last changed 30 days ago, with 5 commits in the file's history, a bug-fix rate of 20%, and a single author in the last 90 days. That last number is the one I would act on: one person holds the context for a credentials path. I would split config resolution (profile versus sso-session precedence) from token loading, so the precedence rules can be tested with plain ini fixtures and no filesystem.
