I would start with `InstallLatest` in packer/plugin-getter/plugins.go. It hasn't been changed in 442 days, and it has a cyclomatic complexity of 95, a nesting depth of 7 and a fan-out of 56. That is a maintenance concern rather than an emergency: nobody is touching it now, but whoever has to modify plugin installation next will inherit all of that complexity at once. Across hashicorp/packer's 1,330 analyzed functions, 212 are in the critical band and 517 sit in the debt quadrant, so dormant complexity, not active churn, is the dominant risk here.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

They change because they are generated, not because anyone is working on hard logic. The real exposure is the 517 debt-quadrant functions, and all five of my top hotspots come from that group. All five share the same three antipatterns: exit-heavy, god function and long function. Each one orchestrates a lot, returns from many places, and cannot be covered by a handful of tests. I am not saying any of them is broken. File-level history is quiet, with no bug-linked commits or reverts in any of the five files. These are maintainability problems, and the cost lands on whoever touches them next.

### `InstallLatest` — plugins.go

<FunctionCard fn='InstallLatest' file='packer/plugin-getter/plugins.go' risk='19.3' band='critical' cc='95' nd='7' fo='56' touches='0' />

<MetricBar label='Cyclomatic Complexity' value='95' threshold='10' max='100' />

This is the plugin installer's main entry point for resolving and fetching the newest version that satisfies a requirement. From the code I can see that it loops over getters, fetches and parses a release list, filters releases against version constraints, sorts them highest first, then loops again over candidate versions to fetch checksums and install. That is several distinct jobs in one function, and the nesting depth of 7 follows from loops sitting inside loops sitting inside error checks.

Go's explicit error handling dominates the branching. Several branches build up a multi-error value, log at trace level, and then either continue to the next getter or return. A fan-out of 56 means the function is coupled to a very wide surface, so a change to checksumming or download behavior can surface here unexpectedly. A comment in the source already marks the inner version loop with a TODO to split it into its own install-version function. The function hasn't been changed in 442 days and has a single recent author, so institutional knowledge of the details may be thin.

I recommend acting on that TODO. Extract the per-version install loop first, then separate release discovery (get, parse, filter, sort) from installation. Two or three functions with a complexity under 30 each would be far easier to test with a fake getter.

### `RunContext` — build.go

<FunctionCard fn='RunContext' file='command/build.go' risk='17.76' band='critical' cc='71' nd='5' fo='60' touches='0' />

This is the body of the `packer build` command, and it reads like a long setup pipeline: load config, detect and initialize plugins, set up the HCP registry, populate a version, fetch builds, inject enforced provisioners, then run the builds. Each stage has its own early return on a non-zero status, which is where much of the exit-heavy pattern comes from. Its fan-out of 60 is the highest in my top five, so it touches more distinct collaborators than any other function here.

It hasn't been changed in 179 days, and the file shows no author activity in the last 90 days. Only `wrappedMain` (132 days) has changed more recently among my top five, and neither has been touched in the last year. The HCP registry and enforced-provisioner steps look like later additions to an older flow, and that kind of accretion is how a command handler ends up with a complexity of 71.

I would extract each pipeline stage into a named step that returns a status or diagnostics, so RunContext becomes a readable sequence. The HCP registry setup and enforcement block is the cleanest first cut: it is self-contained and already has its own error translation.

### `Run` — build.go

<FunctionCard fn='Run' file='packer/build.go' risk='16.84' band='critical' cc='74' nd='5' fo='20' touches='0' />

This is the core build's execution method. It copies hooks, wraps provisioners (with a debug variant when debugging is on), registers provision and cleanup hooks, then runs the builder and the post-processing that follows. It hasn't been changed in 530 days and is flagged stale-complex, so I would treat it as high blast radius when next touched. A cyclomatic complexity of 74 on a fan-out of only 20 tells me the difficulty here is branching rather than coupling.

The function opens with a panic if prepare was not called first, an ordering contract enforced at runtime. With this many paths, the interaction between debug mode, cleanup provisioners and post-processors is where I would want tests before changing anything. Because Go returns errors explicitly, each of those paths probably carries its own exit.

I recommend extracting hook assembly into its own function first. Building the hook map is mostly independent of running the builder, and moving it out would remove a large share of the branches without changing behavior.

### `wrappedMain` — main.go

<FunctionCard fn='wrappedMain' file='main.go' risk='15.53' band='critical' cc='34' nd='4' fo='31' touches='0' />

This is the process entry point behind the panic wrapper. It sets thread counts, configures log filtering, loads the global config, starts the checkpoint reporter in a goroutine, prepares the cache directory, and picks between machine-readable and normal UI. The source carries a long warning comment about how output written here interacts with the wrapper, and the author explicitly advises avoiding output changes in this function. I read that as a sign the function is fragile for reasons the metrics cannot fully capture.

The go statement launching the checkpoint run is the kind of goroutine interaction that structural metrics do not measure, so the real risk may be higher than a cyclomatic complexity of 34 suggests. It is the only function in my top five whose file has a non-zero bug-fix rate (17%, with 6 commits total), though with no bug-linked commits or reverts I would read that as mild context, not evidence of defects. It hasn't been changed in 132 days.

I would move configuration loading, cache setup and UI selection into separate setup helpers that return errors, keeping the output-stream workarounds in one place. That would make the delicate stderr and stdout handling easier to find and review.

### `Provision` — provisioner.go

<FunctionCard fn='Provision' file='provisioner/shell/provisioner.go' risk='15.51' band='critical' cc='54' nd='3' fo='36' touches='0' />

This is the shell provisioner's execution method. From the code I can see that it handles inline commands by writing a temporary script, optionally writes and uploads an environment-variable file with retries, and then runs the resulting scripts. Nearly every step has its own wrapped error return, which accounts for the exit-heavy pattern. The nesting depth of 3 is modest, so the complexity of 54 comes from many sequential decisions rather than deep structure.

It hasn't been changed in 530 days and is flagged stale-complex. Shell provisioning is one of the most commonly used provisioners, so I would expect a change here to reach many users' builds. The upside is that sequential, low-nesting complexity is the easiest kind to break apart safely.

I would extract the three obvious phases into functions: inline script preparation, environment-variable file preparation and upload, and script execution. Each can be tested without the others.

The common thread across these five is size and orchestration, not churn. Splitting each into named stages is the lowest-risk way to reduce the cost of the next change.
