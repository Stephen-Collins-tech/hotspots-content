### `generate_chat_prompt` — modules/chat.py

<FunctionCard fn='generate_chat_prompt' file='modules/chat.py' risk='21.05' band='fire' cc='152' nd='7' fo='55' touches='3' />

This is the top hotspot in the repo, and the numbers explain why. Cyclomatic complexity of 152 means 152 independent paths through a function that assembles the chat prompt — handling instruct vs. chat mode, system messages, tool responses, GPT-OSS-style channel tags, and history reconstruction, all in one body. The excerpt shows nested template rendering (`instruct_renderer`, `chat_renderer`), a loop over reversed history with per-entry tool-message branching, and a special case for `<|channel|>analysis<|message|>` tokens layered inside that loop — that's where the max nesting depth of 7 comes from. Fan-out of 55 means this function reaches into 55 other functions, so any behavioral change here has a wide blast radius across templating, tool parsing, and history management. With 3 touches in the last 30 days and 0 days since the last change, this is being actively worked on right now, not sitting dormant. My concrete recommendation: extract the tool-message-insertion block and the GPT-OSS channel-tag handling into their own named functions before the next feature lands on top of this — both are self-contained enough to pull out without touching the rendering setup at the top.

### `completions_common` — modules/api/completions.py

<FunctionCard fn='completions_common' file='modules/api/completions.py' risk='19.39' band='fire' cc='147' nd='7' fo='33' touches='1' />

Second-highest risk in the repo, and it shares the same nesting depth (7) as `generate_chat_prompt`. The excerpt shows it handling both legacy and current completion formats, converting `messages`-style multimodal input into a flat prompt string, validating `max_tokens` with four separate branches, then iterating per-prompt with token-list vs. string-list handling inside a `for idx, prompt in enumerate(...)` loop — each of those branches is a distinct path a test has to cover. One touch in the last 30 days and 23 days since last changed puts this a step behind `generate_chat_prompt` in immediacy, but it's still classified `fire`, meaning it's active enough to warrant the same attention. Given fan-out of 33, I'd isolate the messages-to-prompt conversion (the block extracting text from multimodal content items) into its own helper — it's already doing a distinct job and doesn't need to live inside the request-handling body.

### `generate_chat_reply_wrapper` — modules/chat.py

<FunctionCard fn='generate_chat_reply_wrapper' file='modules/chat.py' risk='18.95' band='fire' cc='131' nd='5' fo='63' touches='5' />

This one has the highest touch count of the top five — 5 commits in 30 days — and the highest fan-out at 63, meaning it coordinates the broadest set of collaborators of anything in this list. The docstring in the excerpt explains the intent directly: it wraps generation in a loop that detects tool calls, executes them, and regenerates until the model stops, consolidating tool output into a single chat bubble via `metadata['assistant_N']['tool_sequence']`. The code backs that up — conditional MCP server loading, tool executor merging with a name-conflict check, and a `while True:` loop tracking `_tool_turn` state across iterations. Cyclomatic complexity of 131 across that control flow, combined with 5 touches this month, makes this the function most likely to pick up a subtle regression from parallel edits. I'd move the MCP tool-loading and conflict-resolution block (the `for td in mcp_defs` loop) out into its own function — it's already logically separable from the outer regeneration loop.

### `chat_completions_common` — modules/api/completions.py

<FunctionCard fn='chat_completions_common' file='modules/api/completions.py' risk='17.90' band='fire' cc='146' nd='5' fo='38' touches='1' />

The second `completions.py` entry in the top five, and structurally close to its sibling `completions_common` — 146 cyclomatic complexity against 147, same file. The excerpt shows a long sequence of upfront validation checks (unsupported `functions`/`function_call` params, missing `messages`, per-message role and content-type validation for multimodal content), followed by template and character-loading logic pulled from several fallback sources (`instruction_template_str`, `chat_template_file`, `shared.settings`). That's a lot of early-return validation stacked in front of the actual generation setup — consistent with the `exit_heavy` tag it shares with three other functions in this list. With two `fire`-quadrant functions in the same file, `modules/api/completions.py` itself is worth treating as a unit for review, not just these two functions in isolation. A first step: extract the message-validation block (the loop checking `role`, `content`, and multimodal item structure) into a `validate_messages()` helper — it has no dependency on the generation-parameter logic that follows it.

### `_get_next_logits` — modules/logits.py

<FunctionCard fn='_get_next_logits' file='modules/logits.py' risk='17.55' band='fire' cc='48' nd='5' fo='26' touches='1' />

This one is a different shape than the other four — cyclomatic complexity of 48 is high but a third of `generate_chat_prompt`'s, and it reads as two largely separate code paths bolted together: a llama.cpp branch that escapes control characters and formats log-probability output, and an "all other model types" branch that handles ExLlamaV3 and standard HF models with device placement and top-k softmax scoring. The branch split itself explains most of the nesting depth of 5. Fan-out of 26 across two model backends is a real coupling signal in a dynamically typed codebase — `shared.model.__class__.__name__` checks stand in for a proper interface, so adding a third backend means another `if` branch here rather than a clean dispatch. One touch in the last 30 days keeps this in `fire` rather than `debt`, so I'd treat this as a good candidate for splitting into `_get_next_logits_llama_cpp` and `_get_next_logits_hf` before a third backend gets added to the same function body.

Worth noting for context: `do_train` in modules/training.py (activity risk 17.0, cyclomatic complexity 130, fan-out 89) and `generate_reply_HF` in modules/text_generation.py (activity risk 16.08, cyclomatic complexity 72) sit just outside the top five, both in the `debt` quadrant with 0 touches in 30 days. They're not being edited right now, but `do_train`'s fan-out of 89 is the highest in the entire dataset — when training code is next touched, expect a wide-reaching change. `get_single_file` in download-model.py carries a `stale_complex` tag with 189 days since last change, the most dormant complex function I found — high blast radius whenever someone next needs to modify model download logic.
