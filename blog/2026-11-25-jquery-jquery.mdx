## The manipulation.js cluster

Three hotspots share test/unit/manipulation.js: a very wide test body, and two helper functions that look like they belong to the same async-callback verification harness. Each of the three has 3 touches in the last year, a bug-fix rate of 0%, no reverts, no bug-linked commits and a single author in the last 90 days. So this is a maintainability and review-cost story, not a defect-history story. The concentration matters because anyone editing script-execution tests in this file touches code with three separate hotspot entries.

### `testAppend` — manipulation.js

I would start with `testAppend` because it has the highest activity-weighted risk score in the repo (1.58), a fan-out of 38, and it was changed on the day of analysis. Its cyclomatic complexity of 10 and nesting depth of 2 are modest, so the risk here is breadth, not branching. The excerpt shows a single function that sets an expected assertion count of 82, delegates to a helper for objects, then walks through a long sequence of independent scenarios: checked radio buttons in several attribute spellings, an iframe document, fieldset and legend, a map and area, select options and optgroups, and a loop over table-related element names.

That is a lot of unrelated behavior behind one test name. A failure message points at one of 82 assertions rather than at a scenario, and any change to shared setup affects all of them at once. My recommendation is to split it by element family (form controls, iframe, map, select, table) into separate tests that share a small fixture helper. That would cut the fan-out per function substantially and make a failing assertion identify its scenario directly. The assertion count would need to be redistributed across the new tests.

### `verify` — manipulation.js

<FunctionCard fn='verify' file='test/unit/manipulation.js' risk='1.56' band='high' cc='6' nd='3' fo='3' touches='3' />

`verify` has an activity-weighted risk score of 1.56, a cyclomatic complexity of 6, nesting depth of 3 and a fan-out of 3. It is small by the numbers, and it scores high mainly because it sits in a file that is changing right now. From the excerpt, it is a closure that checks whether four callback counters (outer external, inner external, outer inline, inner inline) have reached an expected count, returns early if they have not, and otherwise asserts and calls the done callback. A comment in the code notes that checking for zero calls cannot know when to run, so it waits until a timeout forces the check.

The subtle part is that it is invoked both from each callback and from a timer, with a flag distinguishing the two. That is hidden coupling of the kind JavaScript makes easy: the function's correctness depends on call order across four global callbacks. I would add a comment-level contract describing the three states (not ready, forced, already verified), and consider replacing the interval-based approach with a promise that resolves when all counts are met. It is low-effort to fix, and the nesting depth of 3 is the first thing I would flatten with early returns.

### `setup` — manipulation.js

<FunctionCard fn='setup' file='test/unit/manipulation.js' risk='1.55' band='high' cc='3' nd='3' fo='7' touches='3' />

`setup` has an activity-weighted risk score of 1.55, a cyclomatic complexity of 3, nesting depth of 3 and a fan-out of 7. The excerpt shows it encloses `verify` and four window-level callback assignments, registering each as a global so the harness can clean them up. That nesting depth comes from defining functions inside functions, which is why its risk is higher than its cyclomatic complexity of 3 suggests.

The same applies here as with `verify`: `setup` and `verify` score almost identically (1.55 and 1.56) because they are really one unit, and reviewing one without the other would miss the shared state (`calls`, `verified`, `timeoutId`). My recommendation is to lift `verify` and the four callbacks out into a small factory that returns the callbacks and a verify handle. That removes a nesting level, makes the shared state explicit, and lets the helper be reused by the other script-type tests that follow it in the file.

## The ajax.js pair

The remaining two hotspots are in test/unit/ajax.js. Each has 7 touches in the last year and the same clean external signals: 0 bug-linked commits, 0 reverts and a single author in the last 90 days.

### `pass` — ajax.js

<FunctionCard fn='pass' file='test/unit/ajax.js' risk='1.53' band='moderate' cc='2' nd='1' fo='4' touches='7' />

`pass` is in the moderate band with an activity-weighted risk score of 1.53, a cyclomatic complexity of 2, nesting depth of 1 and a fan-out of 4. It is a tiny callback in a timeout-related ajax test: it counts error callbacks and calls done on the second one. The score is driven by its 7 touches in the last year, not by structure. I would not refactor it. I would watch it, since a counter-based completion check like this is easy to break if the number of expected callbacks changes.

### `countComplete` — ajax.js

<FunctionCard fn='countComplete' file='test/unit/ajax.js' risk='1.49' band='low' cc='2' nd='1' fo='1' touches='7' />

`countComplete` sits in the low band with an activity-weighted risk score of 1.49, a cyclomatic complexity of 2, nesting depth of 1 and a fan-out of 1. It decrements a counter and calls done at zero. The enclosing test is the interesting part: the excerpt shows many nested ajax calls with different ways of binding status-code handlers, including late binding after a 100 ms timer. The helper itself needs no work. If the surrounding test grows, I would split the status-code binding variants into separate tests so the counter does not have to track so many completions.

## Where to start

I would start with `testAppend`: its fan-out of 38 and 82 assertions make it the most expensive to review and the hardest to diagnose when it fails, and it was changed on the day of analysis. Then I would treat `setup` and `verify` as a pair and extract the callback-counting harness in one change. The ajax.js entries need no action beyond awareness. None of the five has any recorded history of bug fixes, reverts or bug-linked commits in the signals, so this is about keeping the test suite cheap to change, not about known defects.
