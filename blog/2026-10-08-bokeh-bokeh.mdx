### `run_tests` — devtools.ts

<FunctionCard fn='run_tests' file='bokehjs/test/devtools/devtools.ts' risk='20.24' band='fire' cc='59' nd='7' fo='60' touches='2' />

I would start with `run_tests`. It has the highest activity-weighted risk score in the repo's top five (20.24), a CC of 59, and was last changed 4 days ago, with 2 touches in the last year. The fan-out of 60 stands out: the function calls 60 distinct functions, so it is coupled to a very large part of the test harness.

<MetricBar label='Cyclomatic Complexity' value='59' threshold='10' max='70' />

From the excerpt, the function does several unrelated jobs in one body. It clears stale report files under a baselines directory, defines browser initialization and a retry-based browser recovery routine as inner closures, collects tests from the page, optionally randomizes them with a seed, and validates test descriptions, all inside a nested try structure that reaches a depth of 7. The exit-heavy pattern shows up as `throw` paths and an early `fail` helper that throws an `Exit` with a code. Each is a separate outcome a test of the runner would need to cover.

The file has only 3 commits in total and a single author in the last 90 days, so ownership is narrow. That cuts both ways: coordinating a refactor is easy, but a function this central gets little review spread. I would extract along the seams the code already draws, pulling the report cleanup, the browser recovery loop, and test discovery and validation into named functions with their own tests. That alone would take a large share of the branches and most of the nesting out of the main body.

By its name and the excerpt, it compares Python-side and BokehJS-side default values for models. A run of special cases (graph renderers, date tickers, a dev-mode font substitution) appears as sequential `continue` branches. The function then defines helpers inside the loop and recurses into itself for nested objects and arrays, and that combination drives the depth. I would hoist `is_object`, `is_vector`, and `compare_recursively` out of the loop body into module-level functions and turn the special cases into a small table of skip rules. The file has 2 commits and one author, so a refactor here would be low-friction.

### `render_entries` — hover_tool.tsx

<FunctionCard fn='render_entries' file='bokehjs/src/lib/models/tools/inspectors/hover_tool.tsx' risk='18.75' band='debt' cc='32' nd='8' fo='35' touches='0' />

Also debt, also unchanged for 68 days with 0 touches in the last year. It has a CC of 32, nesting of 8, and fan-out of 35, and it lives in the hover tool, which is user-facing interaction code.

The excerpt shows the shape. After looking up the selection and converting screen coordinates to data coordinates, the function branches on the glyph's type, handling patch views, area views, and line and step views as separate arms. Inside the line arm it switches on a line policy (interpolate, previous, next, nearest, none). Each new glyph type or hit-test policy adds a branch to this one function. I would split it by glyph family, with one function per arm returning its collected tooltip data, and give the line-policy switch its own function. A fan-out of 35 also suggests the glyph-type imports and helpers are a coupling surface worth checking whenever someone adds a glyph.

### `_decode` — deserializer.ts

<FunctionCard fn='_decode' file='bokehjs/src/lib/core/serialization/deserializer.ts' risk='18.62' band='fire' cc='46' nd='10' fo='5' touches='1' />

This is my second live-risk function: an activity-weighted risk score of 18.62, 1 touch in the last year, and a last change 4 days ago. Its profile differs from `run_tests`. Fan-out is only 5, so it is not coupled widely, but a CC of 46 and a nesting depth of 10 make it dense.

The excerpt reads as a decoder for the serialized wire format: a chain of tests on reference, value, field, expression, and type markers, followed by a large switch over type names (ref, symbol, number, array, set, map, bytes, slice, date, value, field, expr, typed array, ndarray, object). The `value`, `field`, and `expr` arms repeat the same optional transform-and-units spread, which adds duplication to an already branchy function. A `_decoders` lookup is consulted before the switch, so the dispatch is partly table-driven and partly hand-written.

Because this is serialization, I read a CC of 46 as a test-coverage burden: every branch is a message shape that needs a round-trip case. I would finish what the registry started. Move the remaining switch arms into that decoder table so `_decode` becomes a small dispatcher, and extract the shared transform-and-units handling into one helper. The Python counterpart, `_decode` in `src/bokeh/core/serialization.py`, is in my context list and was also changed 4 days ago, so I would review the two as a pair.

### `__trigger` — ui_events.ts

<FunctionCard fn='__trigger' file='bokehjs/src/lib/core/ui_events.ts' risk='18.62' band='debt' cc='69' nd='7' fo='25' touches='0' />

`__trigger` has the highest CC of the five, at 69, and has gone 68 days without a change, with 0 touches in the last year. It is the clearest case of structural debt with high blast radius: it handles input events for the plot, and the file has a single commit in its history.

<MetricBar label='Cyclomatic Complexity' value='69' threshold='30' max='80' />

The excerpt shows a repeated pattern. For pan, then pinch, then rotate, the function branches on the event type, finds the first view that supports the gesture, remembers it as the current view, and routes later events to that view, calling `preventDefault` and returning along the way. The same start, continue, end structure appears once per gesture, which is why the CC climbs so high. That repetition is a gift for refactoring: a single gesture-dispatch helper parameterized by gesture kind would replace the copies, and each future gesture (the excerpt is cut off, so I can't see the rest) would stop adding a new branch here. Because it is unchanged, I would do this before the next gesture or input-handling change rather than during it.
