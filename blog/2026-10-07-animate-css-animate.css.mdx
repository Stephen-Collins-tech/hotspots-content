### `compileAnimationlist` — compileAnimationList.js

This function sits in the debt quadrant. It hasn't been changed in 1,135 days and has zero touches in the last year, so I would not describe it as actively changing. Its risk comes almost entirely from coupling, not from branching.

The numbers are lopsided. Cyclomatic complexity is 3 and nesting depth is 1, both low. Fan-out is 17, and that is where the score comes from.

<MetricBar label='Fan-out' value='17' threshold='10' max='20' />

The source excerpt shows what the function does. It reads the animate.css source file from disk, uses two regular expressions to pull out group headings and animation class names, builds a map of group to item list, then renders that map to HTML strings through template literals for list items and sections. All of it lives in one function body, with the item template, the section template, and the compile step defined as inner closures.

The fan-out figure reflects how many distinct calls are packed into that body: path joining, synchronous file reads, regex matching, string replacement, array iteration, key enumeration, and string joining. None of these is exotic, but they all sit in one place, and several depend on each other's output format.

Here is where I think the real blast radius sits. The parsing logic relies on the formatting of comments inside the main stylesheet. The regular expressions match slash-delimited lines, and the code treats a failed item match as a signal that the line is a group heading. That is an implicit contract with the stylesheet's comment layout. If the source file's comment style changes, this function is the most likely place for it to break, and the failure could be silent: a mis-grouped or missing animation in the generated docs page rather than a thrown error. I am inferring that from the excerpt, not from a test run, so treat it as a review prompt.

The file-level history is quiet. The file has one commit in total, no bug-linked commits, a bug-fix rate of 0%, no reverts, zero distinct authors in the last 90 days, and zero pull-request review comment density. Nothing in that history suggests defects. I read this as maintainability debt, not a quality problem: the function has simply not been changed.

My recommendation is to split it along the seams already visible in the code. Extract the parsing step (file read plus regex matching into a group map) into one function, and move the item and section templates out of the closure into module-level functions. That separates the file-format dependency from the HTML rendering, lets each piece be tested with a small string fixture instead of the real stylesheet, and brings fan-out in the main function well below its current 17. Do this before the next docs change, not during it.
