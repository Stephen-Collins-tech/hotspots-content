The riskiest function in kafka-go, `readFromVersion1` in protocol/record_v1.go, hasn't been changed in 1,519 days, and that is the argument for it: it has an activity-weighted risk score of 15.49. In the 1,112 functions I analyzed, 115 are critical and 295 are in the debt quadrant, and all five of my top picks are dormant, complex decoding or fetch code with CC between 25 and 41. I treat this as a scheduling concern rather than an emergency: it will cost whoever has to add or fix a record-format behavior next, and I would schedule the refactoring before that work starts.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

One caution before the details: Go's explicit error handling inflates cyclomatic complexity in decoders, because every read has its own error branch. Some of the CC below is that tax rather than genuine logic branching. It still counts as test surface, but it changes what refactoring looks like. Much of the win here is mechanical.

### `readFromVersion1` — record_v1.go

<FunctionCard fn='readFromVersion1' file='protocol/record_v1.go' risk='15.49' band='debt' cc='25' nd='5' fo='19' touches='0' />

I would start with `readFromVersion1`. It has the highest activity-weighted risk score in the repository, 15.49, and it has not been changed in 1,519 days. It decodes the version 1 message-set format, and from the excerpt I can see it handles three situations in one body: an uncompressed single message, a compressed wrapper whose inner messages must be decoded in a loop, and relative-to-absolute offset correction for the inner messages. CC is 25, nesting depth is 5, and fan-out is 19.

The nesting depth is the notable number. At 5, it is the only function in my top five tagged deeply-nested. The compressed branch sits inside an else, inside a nil check, and then contains a decode loop with its own error handling and cleanup. I can also see several deferred closes and an explicit cleanup loop over partially read records on the error path, so resource handling is spread across multiple paths. The file-level history is thin, with one commit and no bug-linked commits or reverts, so I would frame this as maintainability debt, not as a function with a defect record.

My recommendation: extract the compressed-wrapper path into its own function that returns a record reader. Pull the relative-offset adjustment into a small helper. That removes at least two nesting levels, and the offset math becomes independently testable without constructing a compressed stream.

### `readFromVersion2` — record_v2.go

<FunctionCard fn='readFromVersion2' file='protocol/record_v2.go' risk='14.84' band='debt' cc='36' nd='3' fo='32' touches='0' />

<MetricBar label='Fan-out' value='32' threshold='15' max='40' />

`readFromVersion2` has CC 36, nesting depth of only 3, and a fan-out of 32, the highest in my top five. It has not been changed in 1,519 days. It reads the version 2 batch header field by field, resolves the compression codec, reads the batch into a page buffer, verifies the CRC, and then decodes records using lazy allocators that the source comments explain in detail.

The shape differs from its version 1 sibling. This is a long linear sequence rather than a nested one, so the problem is breadth rather than depth. With a fan-out of 32, a change to header layout, checksum handling or allocation strategy lands in the same function. Its early exits include a codec error, a read error and a checksum mismatch, which I count as a test burden: each needs a crafted input to reach.

My recommendation: split it along the phases the code already shows. Parse the batch header into a struct, then decompress and verify the CRC in a second function, then decode records in a third. The linear structure makes this a low-risk extraction, and the header-parsing step in particular could be tested with byte fixtures alone. As with the other functions in this group, the file shows one commit and no bug or revert signals.

### `Fetch` — fetch.go

<FunctionCard fn='Fetch' file='fetch.go' risk='14.49' band='debt' cc='27' nd='4' fo='13' touches='0' />

`Fetch` is the public client entry point for fetching records, and it is the function in this group where blast radius matters most. It has CC 27, nesting depth 4, fan-out 13, and has not been changed in 1,519 days. From the excerpt it resolves symbolic offsets such as first and last offset by issuing a separate list-offsets request, builds the fetch request, round-trips it, and then validates the response shape before building the result.

The file has a bug-fix rate of 50% across 2 commits. That is one commit out of two, too small a sample to say much, and it does not prove the current function is defective. I mention it because a complex public API entry point with any fix history in its file deserves a little more review priority than a purely internal decoder. Nearly every failure path wraps its error with the same function-name prefix, so the many exits are repetitive rather than varied.

My recommendation: extract the offset-resolution block into a helper that takes the topic, partition and symbolic offset and returns a concrete offset. That removes the nested loop-and-switch from the main flow, and it is the most testable seam in the function. The response-validation checks for missing topic or partition could move into a second small helper.

### `readChunk` — xerial.go

<FunctionCard fn='readChunk' file='compress/snappy/xerial.go' risk='14.44' band='debt' cc='41' nd='4' fo='14' touches='0' />

<MetricBar label='Cyclomatic Complexity' value='41' threshold='10' max='60' />

`readChunk` has the highest CC in the set at 41, with nesting depth 4 and fan-out 14, and it has not been changed in 1,483 days. It is the chunk reader for xerial-framed snappy streams. The excerpt shows two distinct input paths: a framed path that reads a four-byte length and then a frame of that size, and an unframed path that grows an input buffer until EOF. After that comes a decode step with a branch that writes directly into the caller's buffer when it fits and otherwise goes through an intermediate output buffer.

That is at least three separate responsibilities in one body: input acquisition for two formats, then decode-and-buffer management. Its file shows a 50% bug-fix rate over 2 commits, the same small-sample caveat as `Fetch`. Buffer growth, short reads and EOF handling are classic places for subtle edge cases, and at CC 41 each branch needs its own test input.

My recommendation: split it into a framed-input reader, an unframed-input reader, and a decode step. The two input paths already differ in structure, so the split follows existing seams. I would write tests for the unframed growth loop and the direct-versus-intermediate decode choice before touching anything else.

### `readMessageV2` — message_reader.go

<FunctionCard fn='readMessageV2' file='message_reader.go' risk='14.32' band='debt' cc='35' nd='3' fo='18' touches='0' />

`readMessageV2` is the least dormant of the five at 1,161 days since last change, and its file has the deepest history, with 6 commits and a bug-fix rate of 33%. That is two of six commits, with no reverts. CC is 35, nesting depth is 3 and fan-out is 18. It reads a single version 2 record: on the first record of a batch it checks for compression and pushes a decompressed reader onto a stack, then it reads the length, attributes, timestamp delta, offset delta, key, value and headers.

The function uses named return values and bare returns for most of its roughly two dozen error exits, which I find makes the exit paths harder to audit than explicit returns would. The source also carries a comment marking the batch-length arithmetic as a magic number that needs documenting. That is an honest in-code admission of the kind of knowledge that gets lost, and with 1,161 days of dormancy it is the thing I would fix first. The compression setup block is also a separate concern from reading one record, and it runs only once per batch.

My recommendation: move the first-record compression handling into its own method, and replace the magic number with a named constant describing the fixed header size it represents. Then the per-record reading is a flat sequence of reads that is much easier to check against the wire format.

**What the group has in common**

Three of these five are the version 1 and version 2 record decoders and the snappy framing reader, and all three do the same job: turning bytes into records under several formats and compression modes. The branching comes from format variation and error handling, and the fix is the same each time: separate parsing the layout from handling compression from building the result.

**Where I would put effort**

None of these functions is under active change, so the case for refactoring is about cost deferred rather than risk right now. The practical trigger is simple: the moment someone plans work on record formats, compression or the fetch path, these five should be refactored first, with characterization tests written before any structural change.
