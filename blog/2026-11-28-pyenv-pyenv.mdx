The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. ### `main` — add_pypy.py

<FunctionCard fn='main' file='plugins/python-build/scripts/add_pypy.py' risk='2.11' band='critical' cc='8' nd='6' fo='12' touches='2' />

I would start with `main` in add_pypy.py because it is the highest-ranked function in the analysis and it is in code that changed today. It has cyclomatic complexity of 8, nesting depth of 6 and fan-out of 12, and its activity-weighted risk score of 2.11 puts it in the critical band.

The complexity count is moderate. The nesting is what stands out. From the source excerpt, the function fetches a checksums page, loops over the checksum blocks, filters out excluded releases, loops again over a binary and a source target, checks whether each output file already exists, formats a script template, and then branches between writing the file and printing it for a dry run. Six levels of nesting means a reader has to hold the page-scraping loop, the exclusion check, the per-target loop, the existence check and the write-or-print branch in their head at once. Fan-out of 12 adds broad coupling to the HTML session, path handling, the two parsing helpers and file I/O.

The file-level history adds some supporting context. It has 2 commits in total, a bug-fix rate of 50%, no bug-linked commits, no reverts, 2 distinct authors in the last 90 days and a review-comment density of 2. With only 2 commits, a 50% bug-fix rate means one commit, so I would not read much into it. I would read it as a file that is still settling, not as evidence that `main` is defective.

My recommendation is extract-method. Pull the per-release body into a function that takes a checksum block and returns the list of files to write, and pull the write-or-dry-run branch into its own small function. That should take nesting depth from 6 to roughly 3 and leave `main` as a loop over releases.

<FunctionCard fn='parse_pypy_ver' file='plugins/python-build/scripts/add_pypy.py' risk='1.86' band='moderate' cc='2' nd='1' fo='4' touches='2' />

The two parsers in add_pypy.py share a file and a score, so I am grouping them. Both have an activity-weighted risk score of 1.86 and both are in the moderate band. Their cyclomatic complexity is 2 and 3, nesting depth is 1, and fan-out is 4 and 5. Structurally they are small. They rank in the top five because they sit in a file that was changed today, not because they are hard to read. In a moderate band they bear watching, not a refactoring priority.

From the source excerpt, `parse_pypy_ver` uses a regular expression to pull the Python and PyPy version strings out of a checksum block, and returns an empty string when it does not find exactly one distinct match. That return value is an inconsistency worth a look. The signature declares a pair of strings, but the failure path returns a single empty string, so a caller that unpacks the result will fail in a way the type hint does not predict. I am inferring that from the excerpt, not from runtime behavior, but it is cheap to verify.

`parse_checksums_ext` builds a mapping of platform names to checksums by running one regular expression per platform, then returns a dictionary keyed by names that the script template consumes. The excerpt shows it indexing the first match for each platform directly, with no visible guard for a platform that has no match. If upstream ever drops or renames a platform in the checksum page, I would expect that to surface as an index error, not a readable message. A guarded lookup that names the missing platform would be an easy improvement.

The file-level history is the same as for `main`: 2 commits, a 50% bug-fix rate, no reverts, 2 distinct authors in the last 90 days. These are maintainability concerns in small functions, and the fix is small too. A few unit tests with sample checksum text would pin down both parsers.

### `list_versions` — add_rustpython.py

<FunctionCard fn='list_versions' file='plugins/python-build/scripts/add_rustpython.py' risk='1.9' band='high' cc='6' nd='3' fo='12' touches='1' />

`list_versions` has an activity-weighted risk score of 1.9 and is in the high band, with cyclomatic complexity of 6, nesting depth of 3 and fan-out of 12. It was last changed 1 day ago and has 1 touch in the last year.

From the excerpt, it pages through a tags endpoint, filters tag names to a three-part numeric version pattern, compares each against a minimum version, collects name and commit SHA pairs, follows the next-page link, and finally sorts the result. That is several responsibilities in one function: HTTP pagination, tag filtering and version ordering. The version-tuple conversion appears in both the filter and the sort, which is a small duplication I would pull into a helper.

Fan-out of 12 is the same as `main` in add_pypy.py, and the nesting depth of 3 is more manageable. The history here is thin: the file has 1 commit, no bug-fix signal, no reverts, 1 author in the last 90 days and no review comments. Nothing in the history raises concern. I would classify this as maintainability debt in a young file, and I would act on it while the file is small.

My recommendation is to split pagination from filtering. A generator that yields raw tags page by page, plus a separate function that filters and sorts, would make each piece testable without mocking the whole session.

### `parse_checksums_ext` — add_pypy.py

<FunctionCard fn='parse_checksums_ext' file='plugins/python-build/scripts/add_pypy.py' risk='1.86' band='moderate' cc='3' nd='1' fo='5' touches='2' />

This `main` has an activity-weighted risk score of 1.86, in the high band, with cyclomatic complexity of 7, nesting depth of 2 and fan-out of 9. It was last changed 1 day ago, with 1 touch in the last year.

The excerpt shows an orchestration function: it builds an HTTP session, optionally attaches an authorization header from an environment variable, iterates the versions from `list_versions`, skips any whose output file already exists, formats a script template, and either prints it for a dry run or writes it. It returns 0 if anything was added and 1 otherwise. That last detail is worth knowing: an exit code of 1 for no new versions is a design choice that a calling workflow has to interpret correctly, and I would want it documented where the workflow consumes it.

Compared with the PyPy `main`, this one is flatter. Nesting depth of 2 against 6 is the clearest difference, and it shows that the same job can be written with much less indentation. That makes the RustPython script a useful template for flattening the PyPy one.

The file history matches `list_versions`: 1 commit, no bug-fix signal, 1 author in the last 90 days. I would put this at low urgency. The practical step is to move the write-or-print branch into a small helper, which would also remove the duplication with the PyPy script.

## Where to start

I would start with `main` in add_pypy.py. It has the highest risk score, the deepest nesting in the set at 6, and it shares a file with two other top-five functions that were also changed today. A refactor there can be reviewed alongside the two parsers in one pass.

Second, I would add tests for `parse_pypy_ver` and `parse_checksums_ext` using real sample checksum text, including a case where a platform is missing. Third, I would look at whether the two scripts should share a helper for the write-or-dry-run branch, since the logic appears in both.

None of this says the scripts are broken. The risk scores say these are the places where complexity and recent change overlap, and that is where a review is most likely to pay off.
