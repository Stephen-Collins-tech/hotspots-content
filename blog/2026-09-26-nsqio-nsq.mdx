Across 575 analyzed functions in nsqio/nsq, 91 land in the fire quadrant - complex and actively changing right now - against 175 sitting as untouched structural debt. The top function, `subWorker` in the channel benchmark tool, carries an activity-weighted risk score of 16.13 with 43 branching paths and a fan-out of 23, and it shows 1 touch in the last 30 days and was last changed 22 days ago. That's the pattern across all five functions in my top list: none are stale, all were last changed 22 days ago, and each combines high branching or fan-out with the kind of exit-heavy, long-function shape that makes a small edit easy to get wrong. I'd start review here, not in the 175-function debt backlog, because these are the functions where the next commit is most likely to land.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `subWorker` — bench/bench_channels/bench_channels.go

<FunctionCard fn='subWorker' file='bench/bench_channels/bench_channels.go' risk='16.13' band='critical' cc='43' nd='4' fo='23' touches='1' />

This is a benchmark harness worker that opens a raw TCP connection, does the NSQ v2 handshake (magic bytes, IDENTIFY, SUBSCRIBE, READY), then loops reading and unpacking framed responses. The excerpt shows a long chain of `if err != nil { panic(err.Error()) }` guards after nearly every network write - that's the exit-heavy pattern showing up literally nine-plus times in one function, each one a distinct path a test would need to cover. With cyclomatic complexity at 43 and nesting depth of 4, and a fan-out of 23 distinct calls (mostly into the `nsq` protocol package), this is also a god function: it owns connection setup, protocol framing, flow control (the `rdy` counter), and response dispatch all in one body. The historical signals here are quiet - zero bug-linked commits and zero reverts against two total commits, with 1 touch in the last 30 days and a last change 22 days ago - so I'd frame this as maintainability debt inside an active file rather than a defect risk. My recommendation: extract the handshake sequence (dial, magic bytes, IDENTIFY, SUBSCRIBE) into its own helper and pull the response-dispatch loop into a second function; that alone would cut the branching in half without touching behavior.

### `main` — apps/nsq_to_http/nsq_to_http.go

<FunctionCard fn='main' file='apps/nsq_to_http/nsq_to_http.go' risk='15.68' band='critical' cc='64' nd='3' fo='21' touches='1' />

This is the entry point for the `nsq_to_http` bridge binary, and at cyclomatic complexity 64 it's the single most branch-heavy function in my top five - every flag validation (`--topic`, `--channel`, `--content-type`, `--get`/`--post` mutual exclusivity, `--sample` range checking) is its own conditional path, each ending in a `log.Fatal` call. That's the exit-heavy and long-function patterns compounding: nesting only reaches depth 3, so this isn't deeply nested logic, it's simply a flat wall of sequential validation checks, each one independently branchable and independently testable if pulled out. Fan-out of 21 means it's wiring together the publisher selection, HTTP client construction, and mode selection (`round-robin` vs `hostpool`/`epsilon-greedy`) inline. Five total commits with no bug-linked history and 1 touch in the last 30 days suggests this hasn't caused problems yet, but a function this size in `main` means every new CLI flag added in the future adds directly to that 64. I'd extract a `validateFlags(cfg) error` function to isolate the fatal-exit chain from the wiring logic - that's the highest-leverage single change here.

### `subWorker` — bench/bench_reader/bench_reader.go

<FunctionCard fn='subWorker' file='bench/bench_reader/bench_reader.go' risk='15.38' band='critical' cc='39' nd='3' fo='29' touches='1' />

A sibling to the channels benchmark worker above, this one drives the reader-side benchmark: same handshake pattern, but with a fan-out of 29 - the highest in my top five - because it also spins up a closing goroutine (`go func() { time.Sleep(td); conn.Close() }()`) alongside the response-read loop. That goroutine plus the main read loop reading from the same connection is a concurrency detail structural metrics can't fully capture: the loop explicitly checks `errors.Is(err, net.ErrClosed)` to distinguish a deliberate timeout-close from a real error, which is the kind of channel/goroutine interaction worth testing directly rather than inferring from complexity alone. Historical signals show a bug-fix rate of 20% across five commits - not alarming, but worth noting since this file has seen at least one commit tagged as a fix. Given the concurrency angle, I'd prioritize a focused test around the close-during-read race before doing any structural extraction here.

### `doMPUB` — nsqd/http.go

<FunctionCard fn='doMPUB' file='nsqd/http.go' risk='15.23' band='critical' cc='33' nd='4' fo='14' touches='1' />

This one sits in the actual daemon, not a benchmark tool, which raises the stakes. `doMPUB` handles the multi-publish HTTP endpoint - parsing either binary-framed or newline-delimited message batches from a request body, with explicit size-limit checks (`MaxBodySize`, `MaxMsgSize`) at multiple points and a `for !exit` loop reading one block at a time. The complex-branching pattern is visible directly in the excerpt: binary versus text mode is a fork near the top, and inside the text-mode branch there's a further set of conditionals handling EOF-as-exit, zero-length message discarding, and per-message size enforcement - that's how cyclomatic complexity 33 and nesting depth 4 accumulate in a single function serving live traffic. Twelve total commits show a bug-fix rate of about 16.7%, which is real historical signal that this endpoint has needed correction before, though it doesn't confirm the current code is defective. Given it's the request path for bulk message ingestion, I'd decompose the binary-mode and text-mode parsing into two named functions (`readBinaryBatch`, `readTextBatch`) so each can be tested against its size-limit edge cases independently.

### `New` — nsqd/nsqd.go

<FunctionCard fn='New' file='nsqd/nsqd.go' risk='14.98' band='critical' cc='56' nd='2' fo='29' touches='1' />

This is the daemon constructor - it builds the `NSQD` struct, locks the data path, validates a long list of option constraints (deflate level range, node ID range, TLS policy consistency, auth method, latency percentile bounds), and stands up the TCP listener. Cyclomatic complexity of 56 is the second-highest in my top five, but nesting only reaches depth 2 - this is a flat sequence of independent validation branches rather than nested logic, which is a more tractable shape to refactor than deep nesting would be. Fan-out of 29 reflects everything it wires together: TLS config builders, the lock-directory helper, the cluster-info client, HTTP client construction. Twenty-six total commits with one recorded revert and a bug-fix rate of 11.5% is the strongest historical signal in my top five - worth noting even though it doesn't prove today's version has a defect. Given this is the single entry point for daemon startup, I'd pull the option-validation block into a standalone `validateOptions(opts) error` function; it would drop the branching in `New` itself substantially while keeping validation independently testable.
