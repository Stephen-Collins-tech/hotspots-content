### `handleKeyDown` — tree.component.ts

<FunctionCard fn='handleKeyDown' file='src/components/tree/tree.component.ts' risk='1.45' band='critical' cc='28' nd='9' fo='8' touches='2' />

This is where I would start. It handles keyboard navigation for the tree, and the excerpt shows a long if/else-if chain keyed on the pressed key (arrows, Home, End, Enter, Space), with additional conditions layered on top for left-to-right versus right-to-left direction, disabled items, leaf nodes, lazy loading, and expanded state. Its activity-weighted risk score is 1.45, with cyclomatic complexity 28, nesting depth 9, and fan-out 8. A nesting depth of 9 is well past the point where I can hold the control flow in my head, and it is the deepest in my top five by a wide margin.

<MetricBar label='Nesting Depth' value='9' threshold='4' max='12' />

It was touched twice in the last year and hasn't been changed in 83 days, so it is structural debt rather than live churn. The file-level history is also quiet: no bug-linked commits, no reverts, and a single commit recorded in the enrichment data. I read that as maintainability debt, not a defect signal. The risk is forward-looking. Directional logic that branches on writing direction multiplies the test cases, and any new key binding (type-ahead, for example) has to be threaded through a function that already has 28 paths.

My recommendation: split the function by key family. Extract vertical movement, horizontal expand/collapse (with the left-to-right and right-to-left mapping resolved once up front into 'expand key' and 'collapse key'), and selection into separate small methods, and let 'handleKeyDown' only dispatch. The inline helpers for focusing and toggling are already the right shape for being promoted to private methods.

### `handleKeyDown` — tab-group.component.ts

<FunctionCard fn='handleKeyDown' file='src/components/tab-group/tab-group.component.ts' risk='1.37' band='critical' cc='22' nd='6' fo='5' touches='2' />

The tab group's handler has an activity-weighted risk score of 1.37, complexity 22, nesting depth 6, and fan-out 5. From the excerpt, it first confirms the event belongs to this tab group, handles activation keys, then computes the next tab for navigation keys. The next-tab computation branches on placement (top, bottom, start, end), writing direction, and the key, with two near-duplicate conditions for backward and forward movement that each re-derive the current index.

It has the same history as the tree handler: touched twice in the last year, 83 days since last change, no bug-linked commits or reverts, one commit in the enrichment data. Because the structure is the same, I treat the two as a pair. The duplicated placement-and-direction logic is the obvious first extraction: a single helper that answers 'which key means backward for this placement and direction' would remove one branch family and make both directions symmetric. After that, the tail of the function (focusing the tab, updating tab indexes, scrolling into view) can become its own method.

### `handleKeyDown` — docs/assets/scripts/search.js

Extracting an 'updateSelection(nextEl)' function would cut fan-out and give the selection logic a single place to be tested. It has been quiet for 83 days with two touches in the last year.

### `reposition` — popup.component.ts

<FunctionCard fn='reposition' file='src/components/popup/popup.component.ts' risk='1.31' band='critical' cc='28' nd='4' fo='12' touches='2' />

'reposition' in the popup component has complexity 28, nesting depth 4, and fan-out 12, with an activity-weighted risk score of 1.31. The excerpt shows it assembling an ordered list of floating-positioning middleware (offset, size sync, flip, shift, auto-size), each gated by a configuration property, with cleanup of style properties in the else branches. The code's own comment notes that middleware order matters, which is exactly the kind of implicit constraint that makes a 28-path function risky to edit. It is also quiet: 83 days since its last change, two touches in the last year.

Nesting is moderate here, so the high complexity comes from many sequential optional steps rather than deep conditionals. That is a more forgiving shape for refactoring: each step can become a small builder function that returns either a middleware entry or nothing, and 'reposition' becomes an ordered composition of them. Order stays visible in one place, and each option's behavior (including its cleanup branch) can be tested alone. Popup is a foundation that other floating components likely build on, so I would add characterization tests around the current output before touching it.

## Where to start

I would start with the tree 'handleKeyDown': it has the deepest nesting I found (9) and shares the highest complexity (28) with 'reposition'. Then the tab-group handler, because the same direction-and-placement logic is duplicated inside it and a shared helper pays off immediately. 'reposition' is third, and the search handler last, since it lives in the docs. None of these has a history of bug-linked commits or reverts in the data, so I am framing this as scheduled refactoring before the next feature lands, not incident response. One more note from the context data: 'getFormattedValue' in the color picker is also critical (complexity 19, 83 days quiet), so the dormant critical set is wider than these five.
