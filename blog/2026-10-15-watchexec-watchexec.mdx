### `ensure_guard` — recursor.rs

<FunctionCard fn='ensure_guard' file='crates/lib/src/sources/fs/recursor.rs' risk='16.54' band='debt' cc='51' nd='5' fo='20' touches='0' />

I would start with `ensure_guard` because it combines a cyclomatic complexity of 51 with a nesting depth of 5 and a fan-out of 20, and it hasn't been changed in 46 days. From the code excerpt, it walks the ancestor directories of a watch root in two different ways, depending on whether symlinks are followed, classifies each path, and then decides whether an existing guard is still valid, has been replaced, or must be detached. Several error exits push scan errors and queue a retry.

<MetricBar label='Cyclomatic Complexity' value='51' threshold='10' max='60' />

That is a lot of distinct decisions in one function: the two ancestor-walking branches, the identity comparison, the tombstone check, and the detach-and-retry paths. Each early return is a separate path that needs its own test. The file-level history is thin: 6 total commits, a bug-fix rate of 100%, no bug-linked commits and no reverts, with 2 distinct authors in the last 90 days. A 100% rate over 6 commits is a small sample, and I would not read it as proof of defects. It does mean most of the file's recorded history is fix work, which raises my priority for review.

My recommendation: extract the two ancestor-discovery loops (symlink-following and non-following) into separate helper functions that return the found guard candidate, and pull the 'same guard, already attached' fast path into its own predicate. That would leave `ensure_guard` as a short sequence of discover, compare, and reattach steps.

### `throttle_collect` — worker.rs

<FunctionCard fn='throttle_collect' file='crates/lib/src/action/worker.rs' risk='15.21' band='debt' cc='26' nd='6' fo='11' touches='0' />

`throttle_collect` nests deepest of my five, at 6 levels, with a cyclomatic complexity of 26 and 38 days since its last change. From the excerpt, it loops while collecting events inside a throttle window, handling a closed channel, a timeout, a priority bypass for urgent events, filter errors, filter rejections, and the throttle-window reset. Each of those is a separate continue-or-return decision inside a loop that itself sits inside an async match.

The file-level signals are mixed. Only 2 total commits are on record, which makes the 100% bug-fix rate nearly meaningless as a statistic. The more notable number is the review-comment density of 15.0, the highest in my set, which suggests this file drew substantial discussion in review. I would treat that as a reason for a careful read, not as evidence of defects.

The nesting is the first thing to fix. Pulling the 'decide whether this event passes the filter and priority checks' block into a helper that returns an enum (accept, skip, urgent) would flatten the deepest part of the loop and let the throttle logic be read on its own.

### `pause_watch_loop` — task.rs

<FunctionCard fn='pause_watch_loop' file='crates/supervisor/src/job/task.rs' risk='14.95' band='fire' cc='28' nd='4' fo='6' touches='3' />

This is the one function in my top five that is both complex and changing. It was touched 3 times in the last year, most recently 3 days ago, and its activity-weighted risk score of 14.95 reflects that: a cyclomatic complexity of 28 and a nesting depth of 4 in a function that is live, not dormant. The file-level history shows 13 total commits and a bug-fix rate of about 38%, with no reverts and 2 distinct authors in the last 90 days.

The doc comment in the excerpt says the function runs a polling loop on a background thread, using `waitid` with stop and continue flags and deliberately never consuming exit events, so that tokio's reaping still sees them. That is a delicate contract. The loop peeks at a status, then consumes it with a second call, and every error arm returns. The exit-heavy pattern is real: each return is a path that needs a test. Process-state code like this is also hard to exercise deterministically, so I would weight the testing gap more heavily than the raw complexity number suggests.

I would extract the 'consume the event and forward it over the channel' inner match into its own function. That removes a nesting level and gives the peek-then-consume protocol a name, which makes the invariant about exit events easier to protect during the next change. It is worth doing soon, since the file was last changed 3 days ago and this area is in active development.

### `step_root` — recursor.rs

<FunctionCard fn='step_root' file='crates/lib/src/sources/fs/recursor.rs' risk='14.91' band='debt' cc='50' nd='3' fo='20' touches='0' />

`step_root` shares a file with `ensure_guard` and its numbers are close: a cyclomatic complexity of 50, a fan-out of 20, 46 days since last change, and the same file-level history. Its nesting depth of 3 is lower, so the problem here is breadth rather than depth. From the excerpt, it first branches on whether the recursor is in a managed mode, then on whether symlinks are followed, then classifies the explicit root and matches on several entry states, each with its own retry-or-remove handling.

Both functions live in the same file and operate on the same retry and removed-prefix state, so a change to one is likely to need a matching change in the other. That is my inference from the shared state, not something the data proves. I would split `step_root` along its natural seam: the unmanaged path (the early block ending in a return) is a self-contained flow that can become its own method, and the root-classification match can become a function returning identity, scan flag, and retain-guard flag.

### `worker` — fs.rs

<FunctionCard fn='worker' file='crates/lib/src/sources/fs.rs' risk='14.50' band='debt' cc='32' nd='4' fo='23' touches='0' />

`worker` has the highest fan-out of my five at 23, with a cyclomatic complexity of 32, and it hasn't been changed in 47 days. It is the entry point for the filesystem event worker. From the excerpt, it sets up channels, applies configuration changes, and then runs a long loop polling control messages, ordinary events, and readiness state. That is the god-function pattern: a function that coordinates many collaborators and so has a broad blast radius when changed.

It has the busiest file history of my five: 14 total commits, a bug-fix rate of 50%, no bug-linked commits and no reverts, and 3 distinct authors in the last 90 days. That spread of ownership is worth noting, since several people are reading a function this central. With a fan-out of 23, a change in almost any of the worker's collaborators could surface here.

I would extract each arm of the main loop (config refresh, readiness fencing, control-message handling, ordinary-event handling) into methods on the worker state, so the loop body reads as a short list of steps. That reduces both the cyclomatic complexity and the number of things a reader has to track at once.

**What I would do first**

The recursor file is the clear priority: `ensure_guard` and `step_root` both sit in `recursor.rs`, and together they form a block of debt-quadrant code with a shared history of 6 commits. I would fix them before the next feature push touches that file, while no one is mid-change. `pause_watch_loop` is a different case: it is live, so I would refactor it alongside the work already happening in `task.rs` rather than as a separate cleanup.
