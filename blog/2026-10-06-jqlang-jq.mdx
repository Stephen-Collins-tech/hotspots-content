It is a refactoring candidate rather than an emergency, because nobody is editing it right now, but whoever touches it next inherits a very large blast radius. ### `main` — main.c

<FunctionCard fn='main' file='src/main.c' risk='20.2' band='debt' cc='113' nd='38' fo='74' touches='0' />

<MetricBar label='Max Nesting Depth' value='38' threshold='4' max='40' />

I would start with `main` because it combines the highest cyclomatic complexity in the top five (113, against 112 for `jq_next`) with a nesting depth of 38, far beyond the point where I consider a function a strong refactoring candidate. It hasn't been changed in 91 days and has zero touches in the last year, so this is structural debt rather than active churn. From the source excerpt, it does the whole job of a command-line program in one body: locale and platform setup guarded by preprocessor blocks (OpenBSD pledge, Windows console mode), initializing the jq state, and then a long loop over `argv` that decides whether each argument is an option, the program text, a file, or a string or JSON positional argument. A fan-out of 74 means it directly calls 74 distinct functions, so a change to option handling can ripple into input setup, output formatting, and exit-code logic.

The file-level history adds some weight. The file has 2 bug-linked commits out of 4 total (a bug-fix rate of 50%) and no reverts, and pull request review comment density is high at 26.0. That is a small sample, so I read it as a hint that changes here attract scrutiny, not proof of defects. There are 0 distinct authors in the last 90 days, which fits the dormancy. The patterns flagged are god function, long function, deeply nested, complex branching, and exit heavy. The exit-heavy flag matters in a function with `goto out` style cleanup, because every exit path is a separate test case for resource release. My recommendation: extract the argument-parsing loop into its own function that fills an options struct, and move the platform-specific setup into a small init routine. That alone should cut both nesting and complexity by more than half and makes option parsing testable without launching the whole program.

### `f_format` — builtin.c

<FunctionCard fn='f_format' file='src/builtin.c' risk='19.41' band='debt' cc='61' nd='12' fo='26' touches='0' />

I would look at `f_format` second, with a cyclomatic complexity of 61, nesting depth of 12, and fan-out of 26. It last changed 210 days ago and has zero touches in the last year. The excerpt shows it implementing jq's `@format` strings as one long if/else chain on the format name: json, text, csv, tsv, html, uri, and more below the excerpt. The CSV/TSV branch has its own switch over value kinds, and the URI branch builds an escaped byte buffer by hand. Every format is a separate branch with its own memory-release obligations, which is why the function carries the exit-heavy and stale-complex flags alongside god function.

The historical signals are more notable than for `main`. The file has 4 bug-linked commits out of 18 total, a bug-fix rate of 50%, and no reverts, with 3 distinct authors in the last 90 days. That is a busier file than `main`'s, which tells me other code in builtin.c is still changing even though this function is quiet. Those counts don't show the function is defective, but a function with 61 execution paths in a file with that history deserves a careful review before the next format is added. The obvious refactor is a dispatch table: one small function per format, selected by name, so adding or fixing a format touches one handler and not a 61-path body.

### `jq_next` — execute.c

<FunctionCard fn='jq_next' file='src/execute.c' risk='18.48' band='fire' cc='112' nd='5' fo='56' touches='2' />

`jq_next` is the only fire-quadrant function in my top five, and the one I would watch most closely. It has a cyclomatic complexity of 112, fan-out of 56, an activity-weighted risk score of 18.48, 2 touches in the last year, and was last changed 12 days ago. That makes it both structurally complex and recently changed, the combination that produces regressions. Its nesting depth is only 5, a different shape from `main`: the complexity here comes from breadth, not depth. The excerpt shows the core of the bytecode interpreter, a loop that fetches an opcode, optionally prints debug traces, remaps the opcode when backtracking, and then enters a large switch with cases like ERRORK and LOADK, each manipulating the value stack and frame state.

A switch-based interpreter loop naturally has a high path count, and I would not call that a defect in itself. The history is what concerns me. The file has 2 bug-linked commits out of 6 total, a bug-fix rate of 83%, with no reverts and 1 distinct author in the last 90 days. A rate that high on a small number of commits is a signal to review carefully, not a verdict. In C, where stack manipulation and reference counting are manual, each added opcode path is also a leak or double-free opportunity that cyclomatic complexity does not fully capture. I would not try to break up the dispatch loop itself. Instead I would pull the debug-trace block out into its own helper, which removes a chunk of branching with no behavior change, and make sure every opcode case has a test that exercises both forward execution and the backtracking variant.

### `run_jq_tests` — jq_test.c

<FunctionCard fn='run_jq_tests' file='src/jq_test.c' risk='17.56' band='debt' cc='44' nd='6' fo='31' touches='0' />

`run_jq_tests` is the test runner, with a cyclomatic complexity of 44, nesting depth of 6, and fan-out of 31. It hasn't been changed in 330 days. I rank it below the production-path functions because a complicated test harness is a maintenance cost rather than a user-facing risk, but it matters more than most test code because the whole suite funnels through it. From the excerpt, it reads a test file line by line, handles skip and take counters, distinguishes tests that must fail from tests that must compile, compares expected error messages, and uses `goto fail` style jumps for cleanup. That is a parser, a state machine, and a reporter in one function.

The file history is the quietest of the five: 0 bug-linked commits out of 4, no reverts, and 0 distinct authors in the last 90 days. I would frame this as maintainability debt. The practical risk is that a bug in the runner could silently skip or mis-score tests, and with 44 paths it is hard to be confident about every combination of skip, take, and must-fail state. I would split the line-reading and directive parsing from the compile-and-compare step, so the expected-error-message logic can be tested by itself.

### `expand_call_arglist` — compile.c

<FunctionCard fn='expand_call_arglist' file='src/compile.c' risk='17.48' band='debt' cc='31' nd='7' fo='18' touches='0' />

`expand_call_arglist` has a cyclomatic complexity of 31, nesting depth of 7, and fan-out of 18, and it is the most dormant function in my list at 365 days since its last change. It lives in the compiler and walks instructions to resolve bindings: it rewrites references to `ENV` and named arguments into constants, emits 'is not defined' errors for unbound symbols, and expands closure argument lists. The excerpt shows a switch on the kind of function being called, with recursion into itself for C-function arguments and a comment marking a FIXME on an assertion. Those are the marks of code that was made to work and then left.

The file history shows 2 bug-linked commits out of 4 total, a bug-fix rate of 25%, no reverts, and 1 distinct author in the last 90 days. I read that as modest. I still include the function because of the combination of recursion, deep nesting, and error reporting mixed with rewriting: every one of the 31 paths is a case where the compiler could accept or reject a program. Since the compiler decides what every jq program means, a mistake here affects all users. I would split the binding-resolution step from the argument-expansion step, which separates error reporting from instruction rewriting, and add targeted tests for the undefined-symbol messages before touching anything else.

Across these five, the pattern flags god function, long function, and deeply nested appear again and again. Four of five sit in the debt quadrant, so the practical plan is to refactor them in a quiet period rather than waiting for a feature to force a change under pressure. The other fire-quadrant entries outside this top five have much lower complexity, so I would keep them on a watch list rather than a refactoring list.
