### `cmd_listings_fix` — analytics.py

<FunctionCard fn='cmd_listings_fix' file='list_updater/analytics.py' risk='19.38' band='critical' cc='152' nd='6' fo='41' touches='1' />

<MetricBar label='Cyclomatic Complexity' value='152' threshold='30' max='160' />
<MetricBar label='Fan-out' value='41' threshold='15' max='45' />

This is the highest-risk function in the repository, and the metrics make the case immediately: a cyclomatic complexity of 152 means 152 independent execution paths, each of which is a required test case and a potential bug surface. A CC of 30 warrants attention; 152 is in a different category entirely.

From the source excerpt, `cmd_listings_fix` is an interactive CLI command that loads listings from JSON, scans for issues, and then routes each issue through a large inline decision tree — handling empty titles, duplicate URLs, blocked companies, dry-run mode, auto-accept mode, and manual user prompting all within a single function body. The nesting depth of 6 reflects the layered conditionals: issue type → auto/manual mode → suggested-fix availability → user choice → dry-run guard. Each added dimension multiplies the path count rather than adding to it.

The fan-out of 41 is the most consequential structural risk here. In Python, duck typing means those 41 callees are resolved at runtime — the actual coupling surface is broader than a static count suggests. A behavioral change in any of those 41 called functions could silently alter this function's output without a type error to catch it first.

The god_function and exit_heavy patterns compound this: the function not only does too much, it exits at multiple points throughout its body, which makes it difficult to instrument, mock in tests, or reason about end-to-end.

My concrete recommendation: extract at minimum three separate handler functions — one per issue type (`_fix_empty_title`, `_fix_duplicate`, `_fix_blocked`) — and move the auto/dry-run branching into a shared resolution helper that each handler calls. That alone would cut the CC roughly in thirds and bring fan-out within a testable range. The `author_count_90d` signal shows a single author in the last 90 days, which means this refactoring can proceed without cross-team coordination, but it also means there is no redundant reviewer familiar with every branch.

### `_get_contribution_data` — commands.py

<FunctionCard fn='_get_contribution_data' file='list_updater/commands.py' risk='18.32' band='critical' cc='94' nd='5' fo='29' touches='1' />

<MetricBar label='Cyclomatic Complexity' value='94' threshold='30' max='100' />
<MetricBar label='Fan-out' value='29' threshold='15' max='35' />

`_get_contribution_data` parses a free-text GitHub issue body into a structured listing dictionary. The source excerpt shows it splits the body on newlines, strips headers, and then walks every line with a long chain of `elif` comparisons — one branch per field name it recognizes (URL, company name, title, location, terms, sponsorship, and more). Each branch calls helper functions like `_is_no_answer`, `_add_https_to_url`, and `_clean`, which accounts for much of the fan-out of 29.

A cyclomatic complexity of 94 for a parsing function is a strong signal that the field-recognition logic has grown organically rather than being structured. Each new issue field adds at least one branch, and the nesting depth of 5 reflects the layered guards: field present → not a no-answer → clean → transform → store. Because this is Python and the field-matching uses string containment checks rather than a dispatch table, adding a new field requires inserting another `elif` deep in an already-long chain — a pattern that tends to introduce subtle ordering bugs when two patterns overlap.

The deeply_nested and complex_branching flags are both present here. I would refactor toward a field-handler registry: a dictionary mapping header substrings to small parsing callables. That converts the linear `elif` chain into a data-driven lookup, reduces CC dramatically, and makes adding or removing fields a one-line change rather than a surgery on the main body.

The `_provided_fields` set — visible in `cmd_contribution_process`'s excerpt — means the parsing output carries its own metadata about which fields were populated, suggesting callers depend on this function's internals in ways that make its interface harder to change without downstream effects.

### `embed_table` — readme_generator.py

<FunctionCard fn='embed_table' file='list_updater/readme_generator.py' risk='17.33' band='critical' cc='67' nd='6' fo='18' touches='1' />

<MetricBar label='Cyclomatic Complexity' value='67' threshold='30' max='70' />

`embed_table` in `list_updater/readme_generator.py` takes a list of listings and writes a formatted Markdown table into a README file. From the excerpt, it handles three distinct modes — active-only, inactive-only, and default — and within each mode separately counts listings by category, constructs per-category anchor links, and assembles a browse-section summary. It then parses the existing README line by line to locate and replace both the browse section and the table section in place.

A cyclomatic complexity of 67 with a nesting depth of 6 for a README generator is high. The branching comes from the three-mode logic being inlined throughout: every category count, every link, and every section boundary check repeats the `inactive_only` / `off_season` / default conditional rather than branching once at the top. The god_function and long_function flags confirm the function is doing file I/O, data filtering, URL construction, and string assembly all in one body.

Fan-out of 18 means it reaches into listing filters (`filter_active`, `mark_stale_listings`, `ensure_categories`), category constants, and string formatting helpers. In Python, changes to any of those callees — particularly ones that alter what `filter_active` returns or how categories are keyed — will silently change what this function writes without a type error as a warning.

I would start by extracting the three modes into separate entry points that each call a shared `_build_table_content` helper, then separate the file-rewriting logic into its own function. That decomposition reduces the CC by eliminating the repeated mode conditionals and makes the file-mutation logic independently testable.

### `cmd_contribution_process` — commands.py

<FunctionCard fn='cmd_contribution_process' file='list_updater/commands.py' risk='16.53' band='critical' cc='35' nd='4' fo='25' touches='1' />

<MetricBar label='Fan-out' value='25' threshold='15' max='30' />

`cmd_contribution_process` is the top-level handler for approved GitHub contribution issues. The excerpt shows it reads a GitHub Actions event JSON file, inspects issue labels to determine whether the event is a new internship, an edit, or a bulk-mark-inactive action, delegates bulk events to a separate handler, calls `_get_contribution_data` to parse the issue body, and then updates `listings.json` accordingly.

At CC 35 this is the least complex of the five, but the god_function flag still applies: it coordinates file I/O, label parsing, URL sanitization (stripping UTM parameters inline), and commit message generation inside a single function. The fan-out of 25 reflects that coordination role — it touches data loading, UUID generation, timestamp creation, output setting, and the `_get_contribution_data` function analyzed above.

The exit_heavy pattern is prominent here. The excerpt shows multiple early `return` points gated on exception handling and label validation, with a `fail()` call before each one. That structure means the function's success path is threaded between several abort conditions, and a test suite has to exercise each abort branch independently to achieve meaningful coverage.

Because `cmd_contribution_process` calls `_get_contribution_data` directly and both live in `commands.py`, changes to the parsing function's output contract (the `_provided_fields` set, for instance) can break the contribution orchestration logic without crossing a module boundary. I would extract the label-routing logic into a dedicated function and move the listing-update logic into its own helper, reducing this function to a thin coordinator that becomes much easier to test with mocked collaborators.

### `cmd_listings_diff` — analytics.py

<FunctionCard fn='cmd_listings_diff' file='list_updater/analytics.py' risk='15.87' band='critical' cc='54' nd='3' fo='14' touches='1' />

<MetricBar label='Cyclomatic Complexity' value='54' threshold='30' max='60' />

`cmd_listings_diff` compares listings across time, supporting three distinct comparison modes: diff against a specific git commit hash, filter by a date string, and default to comparing against `HEAD~1`. The excerpt makes the structural problem visible immediately: all three modes are inline branches within one function body, each with its own subprocess calls, JSON parsing, exception handling, and output formatting.

A cyclomatic complexity of 54 for a diff command stems from those three comparison strategies each contributing their own branch trees, plus the per-listing field comparisons and output limiting logic. The nesting depth of 3 is the lowest of the top five, which is why this function lacks the deeply_nested flag — but a CC of 54 still represents 54 paths to test.

The exit_heavy and god_function patterns are both present. Each comparison mode exits early on subprocess failure or JSON parse error, and the function formats and prints output directly rather than returning data for callers to consume. That makes it difficult to reuse the diff logic in a non-CLI context (a GitHub Actions step that needs a structured diff result, for example).

Fan-out of 14 is the lowest in the top five, and with no external_signals showing historical defects, this function reads more as accumulated scope than chronic instability. My recommendation is to extract each comparison strategy into its own function (`_diff_from_commit`, `_diff_since_date`, `_diff_from_head`) and separate the output formatting from the data assembly. That brings the main dispatcher down to a CC well under 10 and makes each strategy independently testable without subprocess mocking contaminating the others.
