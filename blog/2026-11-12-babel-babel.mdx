Four of the five top hotspots in babel/babel live in one file: packages/babel-parser/src/plugins/typescript/index.ts. That is a module-level finding, not a single-function one. `parseSubscript`, `parseStatementContent`, `tsParseMaybeAssign` and `tsParseNonArrayType` each have 40 touches in the last year and were changed 0 days ago, so this is actively changing code rather than a dormant backlog item. The fifth entry, `parseExprAtom` in packages/babel-parser/src/parser/expression.ts, leads the ranking with an activity-weighted risk score of 3.28, a cyclomatic complexity of 85 and 43 touches in the last year. The repository has 16,026 functions, 459 of them in the critical band, and I would start with the parser files because they are both the most complex and the most active.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `parseExprAtom` — expression.ts

<FunctionCard fn='parseExprAtom' file='packages/babel-parser/src/parser/expression.ts' risk='3.28' band='critical' cc='85' nd='6' fo='2' touches='43' />

<MetricBar label='Cyclomatic Complexity' value='85' threshold='10' max='100' />

This is the top-ranked function, with an activity-weighted risk score of 3.28, and it has the highest cyclomatic complexity in the list at 85. The excerpt shows a large switch over the current token type. Each case handles a different kind of expression atom: super, import, this, do-expressions, regex literals, numeric, bigint and string literals, null and boolean literals, parenthesized expressions, and array and object literals. Nesting goes to 6, which is mostly the import case branching on a following dot or parenthesis and then on an option flag.

The fan-out of 2 is low, and it looks that way because most cases are one-line delegations to dedicated parse methods. That is a good sign structurally. The complexity here comes from the number of branches in one dispatcher, not from deep coupling. It has 43 touches in the last year and a bug-fix rate of 42%, with no bug-linked commits or reverts recorded. Two distinct authors touched it in the last 90 days. Two caveats apply. The bug-fix rate is a file-level signal and does not prove this function is defective. And the flagged nesting comes from the multi-step import case, not from the flat part of the switch.

My recommendation is to pull the cases that do more than delegate into their own methods, starting with the import branch, which is the nesting-6 path. Leave the one-line delegating cases in the switch, since they are cheap to read. That would cut the nesting depth without changing the dispatch structure.

### `parseSubscript` — typescript/index.ts

<FunctionCard fn='parseSubscript' file='packages/babel-parser/src/plugins/typescript/index.ts' risk='3.22' band='critical' cc='31' nd='4' fo='4' touches='40' />

This is the first of four hotspots in the TypeScript plugin file. It has an activity-weighted risk score of 3.22, a cyclomatic complexity of 31, nesting of 4 and fan-out of 4, with 40 touches in the last year. From the excerpt, it handles non-null assertions (the postfix `!`), optional calls with type arguments, and type arguments on calls and tagged templates. It also contains a speculative parse attempt: a local closure tries to interpret `<` as the start of type arguments and backs out if that fails.

The speculative-parse structure is where I would be careful. When a parse attempt can fail and be rolled back, the number of states the function can end in grows faster than the cyclomatic complexity number suggests, and type narrowing across the closure boundary is easy to get subtly wrong. The file-level signals are worth noting: a bug-fix rate of 45% across 40 commits, no reverts, 3 distinct authors in the last 90 days, and a review-comment density of 5.0, which is ten times the 0.5 on `parseExprAtom`. Together, that suggests this file draws more review discussion than the core parser file. It does not show a defect.

I would extract the speculative attempt into a named method that returns either a result or a failure, so the control flow of the outer function reads as a short sequence of cases.

### `parseStatementContent` — typescript/index.ts

<FunctionCard fn='parseStatementContent' file='packages/babel-parser/src/plugins/typescript/index.ts' risk='3.19' band='critical' cc='33' nd='5' fo='0' touches='40' />

The activity-weighted risk score is 3.19, with a cyclomatic complexity of 33, nesting of 5 and 40 touches in the last year. The excerpt is a switch on token type that intercepts TypeScript-only statements before falling back to the base parser: const enums, abstract and declare declarations, enums, global and module declarations, and interfaces. The nesting-5 path is the combined abstract/declare case, which checks lookahead, then branches on which keyword was seen, then branches on whether the declaration parsed.

The fan-out of 0 is a measurement artifact worth noting. This function clearly calls other methods, so the zero most likely reflects how calls on `this` are counted, and I would not read it as low coupling. The structure is a classic candidate for a table of handlers keyed by token type, where each handler decides whether it claims the statement or returns nothing. That would flatten the nesting and make each TypeScript statement form testable on its own.

### `tsParseMaybeAssign` — typescript/index.ts

<FunctionCard fn='tsParseMaybeAssign' file='packages/babel-parser/src/plugins/typescript/index.ts' risk='3.18' band='critical' cc='35' nd='3' fo='4' touches='40' />

This one has an activity-weighted risk score of 3.18, a cyclomatic complexity of 35, only 3 levels of nesting and fan-out of 4. The excerpt explains why it needs care. It tries to parse JSX first when the JSX plugin is on, clones parser state, and falls back to parsing as a generic arrow function, with a comment noting that type assertions are not valid syntax when JSX is enabled. It also manipulates the tokenizer context stack when the JSX attempt fails.

Two things make this riskier than a complexity of 35 implies. It clones and restores parser state, so a missed restore on one path would leak state into the next parse. And it layers a JSX attempt, then an arrow-function attempt, then a type-parameter attempt, so behavior depends on the order of the fallbacks. I would treat the JSX attempt and the generic-arrow attempt as two extracted methods with an explicit contract about which parser state each one leaves behind. Whoever reviews a change here should check the state cleanup on every early return.

### `tsParseNonArrayType` — typescript/index.ts

<FunctionCard fn='tsParseNonArrayType' file='packages/babel-parser/src/plugins/typescript/index.ts' risk='3.17' band='critical' cc='42' nd='3' fo='2' touches='40' />

The activity-weighted risk score is 3.17, with a cyclomatic complexity of 42, nesting of 3 and fan-out of 2. This is the flattest of the five: a large switch over the current token, with each case delegating to a type-parsing method for literal types, `this` types, `typeof` queries, import types, mapped types versus type literals, tuples, parenthesized types and template literal types. The default branch contains a nested ternary that picks between void, null and keyword types.

This is mostly breadth, not depth. A complexity of 42 here largely reflects how many type forms TypeScript has, which is a property of the language and not of how this function is written. I would leave the main dispatch alone and extract two pieces: the negative-number literal case under the plus/minus token, and the default branch's keyword-type resolution. Those are the only parts doing real work beyond delegation, and the nested ternary is the easiest line in the function to misread.

## Where to start

I would start with the TypeScript plugin file as a unit, not with individual functions. Four hotspots there share the same 40 touches, the same 3 authors in the last 90 days, and the same file-level signals, which suggests they may change together. A refactor that handles them one at a time will keep colliding with itself. Within that file, I would order the work like this:

1. `tsParseMaybeAssign` first, because its state cloning and layered fallbacks are where a missed cleanup would be hardest to spot in review.
2. `parseSubscript` second, extracting the speculative type-argument attempt.
3. `parseStatementContent` third, moving toward handler-per-statement-form.
4. `tsParseNonArrayType` last, since its complexity is mostly breadth and the dispatch itself is fine.

Separately, `parseExprAtom` deserves a look because it has the highest complexity and the most touches of the five, at 85 and 43. The change I would make is narrow: extract the import branch and leave the flat delegating cases alone.

For context, the quiet tier shows the other kind of risk. The identifier helpers in identifier-browser.ts sit at 134 days since last change with one touch each, so they are lower priority than the active parser code.
