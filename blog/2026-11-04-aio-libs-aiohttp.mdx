I found 76 critical-band functions among the 1,226 I analyzed in aiohttp, the async HTTP client/server framework, and all five of the top hotspots are in the active tier, meaning they are both structurally complex and in code that is changing now. `_request` in aiohttp/client.py leads with an activity-weighted risk score of 2.78, a cyclomatic complexity of 96 and a fan-out of 67, and it was last changed 8 days ago after 10 touches in the last year. Two WebSocket reader functions were changed 2 days ago, so anyone shipping client, WebSocket or request-parsing changes this week is touching live regression risk rather than a backlog item.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

Most of the repository is not a problem. Of the 1,226 functions, 700 sit in the low band and 887 are in the active tier. What stands out is where the critical band meets recent change. The five functions below are all critical and all active, and they cluster in four places: the client request path, the WebSocket frame reader, server-side request body parsing, and TLS connection setup.

I want to be clear about what this ranking does and does not say. High activity-weighted risk means a function is hard to reason about and sits in code that is being modified. It is not a claim that the code is defective, and only one of these five files shows any bug-fix history in the data I have. It is a claim about where a mistake would be easiest to make and hardest to catch.

### `_request` — client.py

<FunctionCard fn='_request' file='aiohttp/client.py' risk='2.78' band='active' cc='96' nd='6' fo='67' touches='10' />

I would start with `_request` because it has the highest activity-weighted risk score in the repo (2.78) and it was changed 8 days ago, after 10 touches in the last year. This is the core of the client session: it takes roughly thirty keyword parameters covering SSL, proxies, timeouts, redirects, compression, header and field size limits, middlewares and an upload tracker. The excerpt shows it validating the session state, normalizing the method, checking the SSL argument type, rejecting simultaneous data and json arguments, and then setting up redirect history and tracing state inside a try block built to guarantee that tracing and upload tracking settle.

<MetricBar label='Cyclomatic Complexity' value='96' threshold='10' max='100' />

A cyclomatic complexity of 96 means about 96 independent paths, each of which is a test case you need and a place a regression can hide. A fan-out of 67 means it calls 67 distinct functions, and in Python, where those calls resolve at runtime, the real coupling is probably wider than that number suggests. The file-level history is quiet: no bug-linked commits, no reverts, and a bug-fix rate of 0% across 4 commits, with 2 distinct authors in the last 90 days. That makes this maintainability debt under active modification, not a known trouble spot.

My recommendation is to extract the pre-flight validation (session closed check, SSL type check, data/json exclusivity) and the payload construction into helpers, so the redirect loop and tracing lifecycle can be read and tested on their own. The comments in the excerpt show the settlement guarantees for the upload tracker and traces are deliberately subtle; those invariants are exactly what extraction should make more visible, not less.

**`_feed_data` and `_handle_frame` — _websocket/reader_py.py**

<FunctionCard fn='_feed_data' file='aiohttp/_websocket/reader_py.py' risk='2.71' band='active' cc='54' nd='5' fo='12' touches='9' />

These two share a file, a change history and a role, so I will treat them together. Both were changed 2 days ago, both have 9 touches in the last year, and the file has 3 distinct authors in the last 90 days. Together they make up the pure-Python WebSocket read path: `_feed_data` parses raw bytes into frames, and `_handle_frame` interprets each frame.

The `_feed_data` excerpt shows a loop over a state machine that reads header bytes, extracts the fin, reserved-bit and opcode fields by bit shifting, and then raises protocol errors for non-zero reserved bits, unknown opcodes, fragmented control frames and oversized control payloads. It also has a backpressure check against a queue size limit that stalls the reader. With a cyclomatic complexity of 54 and nesting depth of 5, validation, buffering, flow control and framing all live in one function, which is where I would expect ordering mistakes to creep in.

`_handle_frame` has a cyclomatic complexity of 29 and a fan-out of 16. The excerpt shows it validating continuation frames, accumulating partial payloads, decompressing deflate-compressed messages with a size limit, and raising different close codes for each failure. The type annotations carry a note that a Cython declaration file uses C int, which suggests this file has a compiled counterpart that must stay in step with the Python version. That is an inference from the annotations, but if it holds, every change here has a second place to be verified.

Neither function shows bug-linked commits or reverts at the file level, and the bug-fix rate is 0% across 5 commits. The risk is that the file is changing at a steady pace while both functions carry a lot of protocol logic. I would pull the header validation out of `_feed_data` into a function that takes the parsed fields and returns or raises, and split `_handle_frame` into message assembly, decompression and control-frame handling. The RFC-driven checks are easy to table-test once they are isolated.

### `post` — web_request.py

<FunctionCard fn='post' file='aiohttp/web_request.py' risk='2.64' band='active' cc='30' nd='7' fo='31' touches='8' />

`post` has the deepest nesting among the five: a nesting depth of 7, with a cyclomatic complexity of 30 and a fan-out of 31. It was last changed 8 days ago after 8 touches in the last year. It is the only file in this group with any bug-fix signal, at a bug-fix rate of 25% across 4 commits, along with 4 distinct authors in the last 90 days, the widest ownership spread of the five. One bug-fix commit in four is a small sample and I would not read much into it, but it does mean this file deserves a bit more review attention than a quiet one with the same complexity.

The excerpt shows it parsing form bodies, with a multipart branch that loops over fields, enforces total size and field count limits, streams file uploads into a spooled temporary file, and switches to executor-based writes once the file rolls to disk. The size checks appear at several levels, once per field and again mid-read per chunk, and the close-and-raise cleanup path is duplicated depending on whether the file has rolled over. That duplication, at depth 7, is where I would look first.

My recommendation is to extract the file-upload branch into its own coroutine that owns the spooled file, its rollover state and its cleanup, so the limits are checked in one place and the temporary file is closed in one place. The outer function would then handle the content-type dispatch and field accumulation, which should bring nesting down by several levels.

### `_start_tls_connection` — connector.py

<FunctionCard fn='_start_tls_connection' file='aiohttp/connector.py' risk='2.59' band='active' cc='20' nd='6' fo='17' touches='7' />

`_start_tls_connection` has the lowest cyclomatic complexity of the five at 20, but a nesting depth of 6 and a fan-out of 17 put it in the critical band. It was changed 8 days ago after 7 touches in the last year, and the file has 2 commits in the history I have, with no bug-linked commits or reverts. The excerpt shows a TLS upgrade of an existing transport, used for connections through an HTTPS proxy. It has two near-identical `start_tls` calls differing only in whether a shutdown timeout is passed, transport cleanup in a bare exception handler, fingerprint verification, and a long chain of exception translations for certificate, SSL, OS and type errors.

The nesting comes mostly from try blocks inside try blocks inside a timeout context, which is the shape resource-cleanup code usually takes. The repeated `start_tls` call is the easiest win: build the keyword arguments once and conditionally add the shutdown timeout. Moving fingerprint checking and the error translation into helpers would flatten the structure without changing behavior.

**What I would do this week**

All five are in the active tier, so the review priority is clear: anything touching `_request`, the two WebSocket reader functions, `post` or `_start_tls_connection` deserves a second reviewer and a targeted test pass. Further down the list there are critical-band functions that are quiet, and I would treat those as structural debt to schedule rather than rush.
