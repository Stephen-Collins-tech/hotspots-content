The riskiest function in linkerd/linkerd2 is `AuthorizationsForResource` in `pkg/k8s/policy.go`: cyclomatic complexity 59, nesting depth 7, fan-out 28, and it hasn't been changed in 65 days. That makes this a time-bomb rather than an emergency, and the next developer to open it inherits all of that complexity cold. Across 3,619 functions, 418 are critical and 1,078 sit in the debt quadrant, while zero are in the fire quadrant, so my argument here is about structural debt with high blast radius when next touched, not live churn.

### `AuthorizationsForResource` — policy.go

<FunctionCard fn='AuthorizationsForResource' file='pkg/k8s/policy.go' risk='17.22' band='debt' cc='59' nd='7' fo='28' touches='0' />

I would start with `AuthorizationsForResource` because it combines the deepest nesting in the list (7) with cyclomatic complexity of 59 and fan-out of 28, and it hasn't been changed in 65 days. Its activity-weighted risk score is 17.22. From the excerpt, it resolves pods for a resource, then walks ServerAuthorization resources, then walks AuthorizationPolicy resources, matching each against the pods via Server lookups. Two distinct authorization models share one function body, with a per-namespace server cache and a lookup path through label selectors layered on top.

The error handling is what I would flag first. Several failure branches print to standard error and continue, while two others print and call `os.Exit(1)` from inside what is otherwise a library function returning an error. A function that can terminate the process is hard to test and surprising to any caller. The log-and-continue branches also mean partial results come back silently when a lookup fails.

My recommendation: split it into one function that collects ServerAuthorization matches and one that collects AuthorizationPolicy matches, each returning an error to the caller. Move the `os.Exit` calls out to the CLI layer. That alone should cut nesting depth substantially and make each half testable with a fake client.

### `TapByResource` — grpc_server.go

<FunctionCard fn='TapByResource' file='viz/tap/api/grpc_server.go' risk='17.08' band='debt' cc='53' nd='5' fo='36' touches='0' />

`TapByResource` in `viz/tap/api/grpc_server.go` has cyclomatic complexity of 53, nesting depth of 5, and fan-out of 36, with an activity-weighted risk score of 17.08 and no change in 65 days. It is a gRPC streaming handler. The excerpt shows a run of up-front request validations that each return an invalid-argument status, then object lookup, then pod classification into tap-enabled, tap-disabled, and tap-not-enabled groups, then a multi-line error message built when no pods qualify, then rate division across pods and match construction. The excerpt cuts off before the streaming logic, and since this is a streaming handler in Go, goroutine and channel interactions probably fill the remainder. Structural metrics cannot see those, so the real risk may be higher than the numbers suggest.

The exit-heavy pattern matters here: every early return is a path that needs a test. The validation block and the no-pods error-message builder are the easiest seams. I would extract request validation into its own function and the diagnostic message builder into another, which would remove a large share of the branches without touching the streaming core.

### `GetPodsFor` — controller/k8s/api.go

<FunctionCard fn='GetPodsFor' file='controller/k8s/api.go' risk='16.2' band='debt' cc='58' nd='4' fo='28' touches='0' />

The second `GetPodsFor` lives in `controller/k8s/api.go` as a method on `API`, with cyclomatic complexity 58, nesting depth 4, fan-out 28, an activity-weighted risk score of 16.2, and 65 days since last change. It does the same conceptual job as the one in `pkg/k8s/api.go`, but takes a typed Kubernetes object and uses informer listers instead of a clientset. The excerpt shows a type switch over namespaces, cron jobs, daemon sets, deployments, replica sets, jobs, replication controllers, services, and stateful sets, with the same owner-reference recursion pattern.

I would treat the pair as one finding. Two parallel implementations of pod resolution, with combined cyclomatic complexity of 58, mean a behavior change in one has to be weighed against the other. From the data alone I cannot say whether they have drifted apart, but the duplication is the risk. My first step would be a side-by-side test that feeds both the same resource tree and compares the pods returned, before any refactoring begins.

### `getEndpointByHostname` — workload_watcher.go

<FunctionCard fn='getEndpointByHostname' file='controller/api/destination/watcher/workload_watcher.go' risk='16.35' band='debt' cc='30' nd='6' fo='15' touches='0' />

`getEndpointByHostname` is the smallest of the five by cyclomatic complexity (30) but has nesting depth of 6 and an activity-weighted risk score of 16.35, with 65 days since last change. It finds a pod for a given hostname and service, with one path through EndpointSlices and a parallel path through legacy Endpoints. Both paths follow the same shape: loop, loop, match hostname, check the target reference is a pod, look up the pod. That duplication is the clearest refactoring opportunity in the whole set.

One detail from the excerpt deserves a test: when a hostname matches but the target reference is missing or not a pod, the function returns nil with no error, whereas a miss returns a not-found status. Callers have to handle a nil pod and a not-found error differently. The function also sits in the destination watcher, so I would expect it to be on a path that matters for service discovery.

My recommendation: extract a function that takes a target reference and resolves it to a pod, and call it from both loops. Then flatten each loop with early continues. That should bring nesting depth from 6 down to around 3.

### What I would do with this list

All five functions share one profile: high complexity, many early exits, and a long stretch of dormancy. The pattern counts reinforce it, with 5 complex-branching, 4 god-function, 4 long-function, 4 exit-heavy, and 3 deeply-nested flags across the top five. The cheapest wins are the two `GetPodsFor` implementations and `getEndpointByHostname`, where the repeated structure makes extract-method mechanical. `AuthorizationsForResource` has the `os.Exit` problem, which I would fix first for testability regardless of the rest.
