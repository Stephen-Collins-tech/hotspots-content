### `ChatInput` — ChatInput.tsx

`ChatInput` is the main React component handling all user input in the chat interface. The source excerpt shows exactly why the metrics are this extreme: the component accepts roughly 25 props covering session identity, chat state, token counts, cost accumulation, recipe data, working directory, queued messages, animation flags, and more. On top of that prop surface, it manages at least 10 distinct pieces of local and ref state — including a message queue with its own pause/resume lifecycle, in-flight message tracking via both a `useRef` and a `useState` mirror, and derived loading state that feeds back into ref guards.

A cyclomatic complexity of 137 means 137 independent execution paths through this component. Manual test coverage at that scale isn't realistic; the practical consequence is that any change to branching logic — say, adjusting how `queueProcessingBlocked` interacts with `pauseQueueOnStop` — can open a path that was never exercised. The fan-out of 160 distinct callees compounds this: a change here can ripple into 160 other functions or components, an extraordinarily broad blast radius for a UI component.

The nesting depth of 5, combined with complex-branching and exit-heavy patterns, means control flow inside callbacks like `setSendNowInFlightMessage` and `clearPendingSendAfterStop` must be traced through multiple layers of conditional state before the outcome is clear.

**Recommendation:** The most tractable first step is extracting the message queue — the `queuedMessages` state, `queuePausedRef`, `sendAfterStopMessageIdRef`, and associated callbacks — into a dedicated custom hook (e.g. `useChatQueue`). That alone should reduce both the prop surface and the internal cyclomatic complexity by roughly a third, and it creates a unit-testable boundary for queue pause/resume logic that currently has no isolation.
