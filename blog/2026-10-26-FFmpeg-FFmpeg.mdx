All five of the highest-risk functions I found in FFmpeg/FFmpeg sit in the 'fire' quadrant: structurally extreme and changed 1 day ago, which makes them live regression risks rather than backlog items. `ff_h264_decode_mb_cabac` in `libavcodec/h264_cabac.c` leads with an activity-weighted risk score of 21.17 (CC 137, ND 10, FO 61 for the CABAC decoder; the FLV packet reader is a separate function with CC 194, ND 9, FO 42). The CAVLC decoder, the MOV muxer's packet writer, an MPEG encoder thread, and the FLV packet reader trail it closely. The codebase holds 31,404 functions, 7,234 of them in the critical band and 13,758 in the 'fire' quadrant, so these five are a small slice of a broadly active, broadly complex tree. I would start with the two H.264 macroblock decoders: they pair the deepest nesting with a mirrored structure, so a fix in one often implies a review of the other.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

## Large Repo Analysis

FFmpeg is a large repository. To stay within memory constraints, this analysis used **hybrid touch mode**: structural complexity — CC, ND, FO — is measured precisely for every function. Git activity is tracked at the function level (via `git log -L`) only for files with 10 or more commits in the touch window (365 days by default); other files use a file-level approximation. Rankings therefore surface functions that are both structurally complex and in the most actively-changing parts of the codebase. Dormant code with high structural complexity will rank lower than it would under a full per-function analysis — to surface it, run `hotspots analyze . --per-function-touches` on a machine with sufficient memory.

### `ff_h264_decode_mb_cabac` — h264_cabac.c

<FunctionCard fn='ff_h264_decode_mb_cabac' file='libavcodec/h264_cabac.c' risk='21.17' band='fire' cc='137' nd='10' fo='61' touches='1' />

This is the CABAC-entropy-coded macroblock decoder for H.264. From the excerpt I can see it handles skip-flag decoding and MBAFF field handling, then branches on slice type (B, P, or I) to decode the macroblock type through a chain of context-adaptive bit reads. A `goto decode_intra_mb` jumps from the B-slice path into the shared intra path, which is one reason the control flow resists linear reading.

The numbers tell the story. CC 137 means 137 independent paths, each a potential test case. FO 61 means it calls 61 distinct functions, so a change here can ripple into many collaborators. ND 10 is well past the point where I treat nesting as a strong refactoring signal. The exit-heavy pattern adds a coverage burden: the early `return 0` for skipped macroblocks is one of several exits that each need a test.

My recommendation: extract the per-slice-type macroblock-type decoding (the B-slice ladder in particular) into its own function that returns the type and partition count, then replace the intra `goto` with an explicit call. An entropy decoder is performance-sensitive, so I would benchmark the split before merging; inlining decisions on a codec hot path are invisible to these metrics.

### `ff_h264_decode_mb_cavlc` — h264_cavlc.c

<FunctionCard fn='ff_h264_decode_mb_cavlc' file='libavcodec/h264_cavlc.c' risk='21.07' band='fire' cc='123' nd='11' fo='54' touches='1' />

The CAVLC counterpart mirrors the same skeleton: skip handling (here a skip-run counter read with a Golomb code), the MBAFF field flag, then slice-type branches that look up macroblock type info and a shared `decode_intra_mb` label reached by `goto`. At ND 11 it has the deepest nesting of the H.264 pair, with CC 123 and FO 54.

Because the two decoders share structure, I would treat them as a pair. A bug fix or behavior change to the skip logic or MBAFF handling in one is a prompt to inspect the other, and both changed on the same day. The excerpt also shows several early error exits (invalid skip run, oversized macroblock type). That is where exit-heavy risk becomes concrete: each is a path that needs a malformed-input test.

My recommendation: extract the skip-run handling and the macroblock-type resolution into helpers, then align their signatures with the CABAC versions so both decoders can share the shape of the dispatch even though the bitstream reads differ. Flattening the slice-type ladder should make cutting ND from 11 to under 5 a realistic first target.

### `ff_mov_write_packet` — movenc.c

<FunctionCard fn='ff_mov_write_packet' file='libavformat/movenc.c' risk='20.93' band='fire' cc='160' nd='14' fo='46' touches='1' />

This is the packet-writing entry point of the MOV/MP4 muxer. The excerpt shows it selecting a track, validating the packet, and checking for unsupported pts/dts pairs. It then branches on fragmentation flags, codec IDs (AMR-NB, ADPCM variants), and sample-size logic to compute samples per chunk. At ND 14 it has the highest nesting in this analysis, and CC 160 is the second highest.

ND 14 is the figure I would put in front of a team lead. At that depth, a reviewer must hold many enclosing conditions in mind to know which state a given line runs under. Per-codec special cases (AMR packet counting, ADPCM frame sizes) sit beside container-level concerns (fragment buffers, interleaving) in one function. That is a classic god-function shape, and FO 46 reflects the breadth.

My recommendation: separate the container-level buffering decision (which `pb` to write to) from the per-codec sample counting, and extract the sample-count computation into a function keyed on codec. The fragment-interleave block is another clean extraction candidate. This function sits on the muxing hot path for a very common output format, so I would add or confirm tests for each codec branch before restructuring.

### `encode_thread` — mpegvideo_enc.c

<FunctionCard fn='encode_thread' file='libavcodec/mpegvideo_enc.c' risk='20.88' band='fire' cc='146' nd='9' fo='43' touches='1' />

This is the per-thread macroblock encoding loop for the MPEG-family encoder. The excerpt shows setup of bit buffers and put-bit contexts, codec-specific initialization (AMV, MPEG-4 partitioned frames), and nested loops over macroblock rows and columns, with SpeedHQ-specific row ordering handled inline. It also returns an error when the encoded frame is too large.

One function owns initialization, iteration, and per-macroblock encoding for many codecs at once, which fits CC 146 and ND 9. With codec-specific branches embedded in a shared loop, a change aimed at one codec has to be reasoned about against all the others.

My recommendation: pull the one-time setup (the bit-buffer initialization and last-DC reset) into an init helper, and extract the per-row logic, including the SpeedHQ ordering, so the main loop reads as 'for each row, for each macroblock'. That alone should cut nesting by a couple of levels without touching the encoding math.

### `flv_read_packet` — flvdec.c

<FunctionCard fn='flv_read_packet' file='libavformat/flvdec.c' risk='20.86' band='fire' cc='194' nd='9' fo='42' touches='1' />

The FLV demuxer's packet reader has the highest cyclomatic complexity in the set at CC 194, approaching the 'extreme' range. The excerpt shows a `retry` label, tag-header parsing, index validation, and branches on tag type (audio shown) that handle enhanced-FLV extensions: mod-ex data, multitrack packets, and codec ID signalling. Several `goto leave` jumps funnel error paths to shared cleanup.

The enhanced-FLV handling is the part I would flag. Multitrack and extended-header support reads like newer protocol surface layered onto an older tag-parsing core, with both in the same function. That layering is a common way for complexity to accumulate, though I am inferring it from the code shape, not from commit history, which I do not have here.

My recommendation: split by tag type, with separate functions for audio, video, and script/data tags, and move the enhanced-header parsing into its own helper that returns the parsed packet type and track information. At CC 194, even a three-way split by tag type would bring each piece into a range a reviewer can reason about.
