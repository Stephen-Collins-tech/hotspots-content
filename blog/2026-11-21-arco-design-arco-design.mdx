Three of the five top hotspots in arco-design live in one file, components/DatePicker/picker-range.tsx, and the other two are disabled-date helpers in components/DatePicker/util.ts, so the whole DatePicker range-selection module needs attention rather than any single function. The top function, `Picker`, has an activity-weighted risk score of 2.34 and a cyclomatic complexity of 170, and it was last changed 0 days before this snapshot. That makes it complex code that is changing right now, worth prioritizing over a backlog item. I analyzed arco-design at commit 84504be: 2,193 functions, 148 of them critical. I would start with the range picker because it is where the critical band and the active tier overlap most heavily.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `Picker` — picker-range.tsx

<FunctionCard fn='Picker' file='components/DatePicker/picker-range.tsx' risk='2.34' band='active' cc='170' nd='4' fo='109' touches='3' />

`Picker` is the range picker component itself. From the excerpt, it reads props from the config context, merges them with defaults, destructures roughly forty options (shortcuts, time handling, timezone, disabled-date and disabled-time callbacks, custom trigger element, panel rendering, and more), sets up refs and an imperative handle, and then goes on to compute formats. The excerpt cuts off at that point, so the rest of the function is not visible to me, but the metrics say it keeps going.

<MetricBar label='Cyclomatic Complexity' value='170' threshold='30' max='180' />

A cyclomatic complexity of 170 means 170 independent paths through a single function, and each is a potential test case. The nesting depth of 4 is modest, which tells me the complexity is wide rather than deep: many sequential branches and options rather than a tangle of nested conditionals. A fan-out of 109 means it calls 109 distinct functions, so a change to any of those helpers is something `Picker` is exposed to.

<MetricBar label='Fan-out' value='109' threshold='15' max='120' />

The file has 3 touches in the last year, a bug-fix rate of 67% over its 3 commits, one distinct author in the last 90 days, and no bug-linked commits or reverts. Those history numbers are thin, and I would not call this function defective on them. What I would say is that a single-author, single-function component of this size has no second pair of eyes built into its structure.

My recommendation: since the excerpt already shows the inner handlers (`onSelectPanel`, `onSelectValueShow`, `switchFocusedInput`, `getShowDatesFromFocused`) defined as closures inside this component, start by extracting the state and handler logic into custom hooks, for example one for panel/selection state and one for focus management, leaving `Picker` as mostly composition and rendering. Even moving the handlers out would cut both the path count and the fan-out substantially.

### `onSelectPanel` — picker-range.tsx

<FunctionCard fn='onSelectPanel' file='components/DatePicker/picker-range.tsx' risk='1.99' band='active' cc='24' nd='4' fo='10' touches='3' />

`onSelectPanel` handles a date being clicked in the panel. The excerpt shows it computing an out-of-range flag, building a new value array (reset or copy of the current panel value), picking a focused input index (with a nested ternary for the custom trigger element case), optionally attaching time values, sorting the result, and then branching on whether to reset the range, switch focus, or confirm the value. It also mutates a ref (`firstRange.current`) inside some of those branches.

With a cyclomatic complexity of 24 and nesting depth of 4, it is far smaller than `Picker`, but the branch conditions interact: reset mode, selected length, half-available state, custom trigger, time picker presence, and out-of-range state all feed into whether the value is confirmed or focus moves. That combination, plus the ref mutation, is what I would worry about, because the correct behavior depends on state combinations that are easy to miss in tests.

My recommendation: write a table-driven test that enumerates those state combinations (reset on/off, 0/1/2 selected values, show-time on/off, custom trigger on/off) and records the expected confirm and focus outcome for each. Once that exists, split the function into a 'compute new value' step and a 'decide what happens next' step, with the second returning a small action description instead of calling setters directly.

### `getShowDatesFromFocused` — picker-range.tsx

<FunctionCard fn='getShowDatesFromFocused' file='components/DatePicker/picker-range.tsx' risk='1.94' band='active' cc='14' nd='2' fo='4' touches='3' />

This function decides which pair of dates the two side-by-side panels should display given the current value and which input is focused. The excerpt shows it handling arrays shorter than two, arrays of exactly two, and a nested fallback to the other index when the focused one is empty, with a 'prev' versus 'next' direction passed to a page-dates helper.

The cyclomatic complexity is 14 with shallow nesting of 2 and a fan-out of 4, so this is the easiest of the three picker-range.tsx functions to fix. The cost is in the conditionals that choose direction: the expression that combines the 'prev' flag with whether the other index has a value is hard to verify by reading. The function also falls through to returning nothing when the input is not an array, which is a path callers have to handle.

My recommendation: pull the direction decision into a small named function with its own tests, and make the not-an-array case an explicit return rather than an implicit one. That alone should bring the complexity under 10.

**`isDisabledDate` and `getDisabledFromRange` — util.ts**

<FunctionCard fn='isDisabledDate' file='components/DatePicker/util.ts' risk='2.05' band='active' cc='17' nd='3' fo='8' touches='2' />

<FunctionCard fn='getDisabledFromRange' file='components/DatePicker/util.ts' risk='1.99' band='active' cc='12' nd='3' fo='3' touches='2' />

These two belong together. `getDisabledFromRange` is an inner helper defined inside `isDisabledDate`, which is why it appears as a separate row with its own metrics. Together they answer 'is this cell disabled?' for each picker mode. For date and week modes it calls the user's disabled-date callback directly. For month, quarter, and year it loops through every date or month in the period and reports the cell as disabled only if every sub-unit is disabled. The helper contains a switch on the sub-mode inside a while loop, and the month and year cases call `isDisabledDate` again, so the function is recursive.

`isDisabledDate` has a cyclomatic complexity of 17 and a nesting depth of 3. The helper adds another 12 on its own, and because it lives inside the outer function, its paths count toward the outer function too. A recursive loop-and-switch structure is where off-by-one and boundary errors tend to hide: a month's last day, quarter boundaries (the excerpt computes the start month with integer division by 3), and year mode scanning months 0 to 11. I am inferring risk from structure here, not pointing at a known fault.

Both functions have 2 touches in the last year and a bug-fix rate of 100% across 2 commits, with no bug-linked commits, reverts, or review comments recorded. That is a two-commit sample, so I would not read much into the percentage. It does mean both commits were tagged as fixes, which is at least consistent with this being a corner-case-prone area.

My recommendation: lift `getDisabledFromRange` out to a module-level function that takes the date and callback as parameters, so it can be tested on its own. Then replace the month and year loops with a single helper that enumerates sub-units for a given mode, which removes the inner switch and the recursion. Test with a callback that disables exactly one day, first and last days of month, and leap-year February.

## Where to start

I would start with `onSelectPanel`, not `Picker`. `Picker` has the biggest numbers, but it is also the biggest job, and the handlers inside it are the natural seams for breaking it up. Extracting and testing `onSelectPanel` and `getShowDatesFromFocused` first gives me tests and named units to lean on when I tackle the component itself. In parallel, I would pull `getDisabledFromRange` out of `isDisabledDate`, since it is a small, self-contained change in a file that is also being modified now.

The quiet critical functions are the second priority. They have not changed in 308 days, so they carry structural debt, but they are not where the live regression risk is today.
