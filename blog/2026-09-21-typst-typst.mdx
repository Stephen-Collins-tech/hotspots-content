Typst is a markup-based typesetting system written in Rust, and this analysis covers 6,190 functions, 220 of which land in the critical band. The top-ranked function, `collect` in `crates/typst-layout/src/inline/collect.rs`, carries an activity-weighted risk score of 18.75 but sits in the debt quadrant — zero touches in the last 30 days and 67 days since its last change. That's the core of the story here: the riskiest code in this repo isn't mid-refactor, it's been quietly accumulating branches and nesting while nobody's looking, so whoever touches it next inherits all of that complexity at once.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `collect` — crates/typst-layout/src/inline/collect.rs

&lt;FunctionCard fn='collect' file='crates/typst-layout/src/inline/collect.rs' risk='18.75' band='critical' cc='21' nd='9' fo='16' touches='0' /&gt;

This function builds the text and segment structure that inline layout works from — collecting styled children, handling directional embedding, smart quotes, spacing, and line breaks into one flattened representation. A nesting depth of 9 is a strong refactoring signal on its own, and the source confirms why: a long if-else-if chain branches on element type (space, text, horizontal spacing, line break, smart quote), each branch doing its own nested logic for styles and directionality. With a fan-out of 16, this function is also a hub — it calls into many collaborators, so any signature or behavioral change here has a wide blast radius across inline layout. It hasn't been touched in 67 days and shows no history of bug-linked commits or reverts on the file, so I'd frame this as maintainability debt rather than an active fire: nobody is fighting this code right now, which makes it a good, low-pressure candidate to extract the per-element-type branches into separate handler functions before the next feature forces someone to add a tenth level of nesting.

### `named_items` — crates/typst-ide/src/matchers.rs

&lt;FunctionCard fn='named_items' file='crates/typst-ide/src/matchers.rs' risk='17.95' band='critical' cc='52' nd='7' fo='14' touches='0' /&gt;

This one walks the syntax tree upward from a cursor position to find named bindings and imports for IDE features like autocomplete and go-to-definition. A cyclomatic complexity of 52 is severe, and the source shows why: nested loops over ancestors and siblings, pattern matches on let-bindings versus module imports, and further matches on wildcard versus named versus bare imports, each with its own early return via the callback-based `recv` closure. That's the 'exit_heavy' pattern in practice — many `return Some(res)` points scattered through nested match arms, which makes exhaustive test coverage expensive. It's had zero touches in the last 30 days and hasn't changed in 42 days, with only two total commits and two distinct authors on the file historically, so there's no evidence of recurring defects — this reads as one person's original design that hasn't needed revisiting, not a known trouble spot. Given the entangled control flow, I'd split the let-binding branch and the import-resolution branch into two dedicated functions; the import logic alone (wildcard vs. named vs. bare) looks big enough to justify its own name.

### `visit_styled` — crates/typst-realize/src/lib.rs

&lt;FunctionCard fn='visit_styled' file='crates/typst-realize/src/lib.rs' risk='17.76' band='critical' cc='34' nd='7' fo='13' touches='1' /&gt;

This is the one function in the top five that's actually live right now. It handles styled elements during content realization — applying document, page, and format-level set rules and validating where they're allowed (bailing with an error if a document set rule shows up inside a container, for instance). At cyclomatic complexity 34 and nesting depth 7, it's already dense, and it's been touched once in the last 30 days, with its most recent change 17 days ago. A third of the file's recorded commits are bug fixes, and three distinct authors have touched it in the last 90 days — that combination of shared ownership, a recent history of fixes, and an activity-weighted risk score of 17.76 is what puts this in the fire quadrant rather than debt: it's both hard to reason about and being actively edited. This is the one I'd review before the next merge lands, not queue for later — specifically the branches handling document versus bundle versus container targets, since the bail conditions there are exactly the kind of logic that's easy to get subtly wrong under time pressure.

### `resolve_realized` — crates/typst-library/src/math/ir/resolve.rs

&lt;FunctionCard fn='resolve_realized' file='crates/typst-library/src/math/ir/resolve.rs' risk='17.32' band='critical' cc='39' nd='36' fo='4' touches='0' /&gt;

This function dispatches a realized math element to its type-specific resolver — symbols, fractions, accents, matrices, underbraces, and roughly two dozen more element kinds, each in its own `else if` arm. The cyclomatic complexity of 39 tracks with that — one branch per element type — but the nesting depth of 36 is the real outlier in this entire dataset, an order of magnitude beyond anything else in the top hotspots. In Rust, that depth combined with generic type-packing (`to_packed::<T>()`) on each branch means the borrow checker is threading a lot of lifetime reasoning through a single long function, which likely explains why fan-out is only 4 despite the size — this is a wide dispatch table, not a function calling many collaborators. It hasn't moved in 67 days and carries no bug-linked history, so this reads as intentional structure (a match-like dispatch over element kinds) rather than accidental sprawl. Still, that nesting number alone justifies converting this into a proper `match` on an element-kind enum or a lookup table of resolver functions, both of which would flatten the structure without changing behavior.

### `write` — tests/src/report/mod.rs

&lt;FunctionCard fn='write' file='tests/src/report/mod.rs' risk='16.94' band='critical' cc='13' nd='3' fo='17' touches='0' /&gt;

This is test-harness code, not product logic — it generates an HTML test report and figures out which historical outputs are missing by walking git blame across hash-reference files. Complexity and nesting here are modest (13 and 3), but fan-out of 17 is the highest in the top five, and the source confirms it: writing files, sorting, filtering, iterating over blame lines, and building an index map all in one function marked with both 'god_function' and 'hub_function' patterns. That breadth of direct calls is what drives the risk score up despite low branching — it's coupled to a lot of moving parts (filesystem, git, report generation) in one place. It hasn't been touched in 67 days and only has one commit and one author on record, so this is low-pressure debt: I'd extract the git-blame-scanning loop and the missing-output detection into separate helper functions, both because it would make the harness easier to test in isolation and because test infrastructure this coupled tends to get avoided rather than fixed when it eventually breaks.

Worth noting in the context data: `jump_from_click_in_frame` in `crates/typst-ide/src/jump.rs` sits at a similar profile to today's top five — complexity 46, zero recent touches, 67 days dormant — but didn't make the top five cut. If IDE responsiveness or accuracy becomes a focus, that function and `named_items` sit in the same file family of debt and are worth reviewing together. On the other side, `progress_tree_start` and `build_group_tag` in the PDF tagging code, along with `new_impl` in the CLI compile path and `footnote` in flow composition, are all fire-quadrant functions with real edits in the last 6 to 17 days — a cluster of active work in PDF tag-tree construction that's worth keeping an eye on given their complexity scores (58, 38, 29, and 27 respectively).
