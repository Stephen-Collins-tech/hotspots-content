The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

## Large Repo Analysis

kafka is a large repository. To stay within memory constraints, this analysis used **hybrid touch mode**: structural complexity — CC, ND, FO — is measured precisely for every function. Git activity is tracked at the function level (via `git log -L`) only for files with 5 or more commits in the touch window (365 days by default); other files use a file-level approximation. Rankings therefore surface functions that are both structurally complex and in the most actively-changing parts of the codebase. Dormant code with high structural complexity will rank lower than it would under a full per-function analysis — to surface it, run `hotspots analyze . --per-function-touches` on a machine with sufficient memory.

First, what this ranking does not show. None of these five functions is structurally tangled in the usual sense: cyclomatic complexity runs from 1 to 7 and nesting depth never exceeds 3. Fan-out is what lifts them. Test methods that build a whole coordinator context, replay records and assert on many collaborators pile up calls to dozens or hundreds of distinct functions. The god-function and long-function flags on most of the highlighted functions fit that picture.

The historical signals for the file are quiet. It has 5 total commits, no bug-linked commits, no reverts, a bug-fix rate of 0% and no review-comment density. Four distinct authors have touched it in the last 90 days. I read that as a maintainability problem in an active file, not a defect problem. These are file-level signals and do not describe any single function.

All five functions show 1 touch in the last year and 16 days since last change, which is why they all land in the fire quadrant with nearly identical scores. The ranking among them is close to a tie, and the score differences are small enough that I would treat the five as a single review unit.

**generatePendingAssignmentCases — GroupMetadataManagerTest.java**

This is the top-ranked function, with an activity-weighted risk score of 168.9. Its cyclomatic complexity is 1 and its nesting depth is 0, yet it calls 57 distinct functions. The excerpt shows why: it returns a stream of lambdas, each mocking a share group, stubbing a handful of methods, optionally replaying partition metadata records into the manager and committing, then returning a case object with verification callbacks. In effect it is a long list of near-identical case builders written inline in one method. The pattern flags include exit-heavy, which I read here as many separate lambda return points; each is its own case and has to stay consistent with the others.

I would extract each case into a named private factory method, or a small table of case definitions, so that a sixth or seventh scenario does not make this method longer. The repeated mock setup for the group id and empty flag could move into one helper.

### `verifyClassicGroupJoinResponses` — GroupMetadataManagerTest.java

<FunctionCard fn='verifyClassicGroupJoinResponses' file='group-coordinator/src/test/java/org/apache/kafka/coordinator/group/GroupMetadataManagerTest.java' risk='168.09' band='fire' cc='5' nd='3' fo='12' touches='1' />

This is the only one of the five without a pattern flag, and its fan-out of 12 makes it the least coupled. It loops over join results, fails if any future is incomplete, counts successes, asserts the expected error code on failures and collects member ids. The loop, the try block and the success-or-failure branch inside it account for its cyclomatic complexity of 5 and nesting depth of 3. Because it is shared verification logic, a change to it affects every test that calls it.

I would leave its size alone and look at one thing: the catch block that converts any exception into a test failure with a message. That is a small readability issue, not a refactoring priority. Since it is a helper, I would confirm that its callers all want the same behavior on an incomplete future before touching it.

### `testLastStaticConsumerProtocolMemberReplacedByClassicProtocolMember` — GroupMetadataManagerTest.java

<MetricBar label='Fan-out' value='186' threshold='15' max='200' />

A fan-out of 186 is the highest in the top five and the clearest example of the god-function and long-function flags. The excerpt shows a parameterized test that builds topic ids, serializes a classic-protocol subscription, constructs two consumer group members through long builder chains, builds a metadata image and then configures a test context with a migration policy and assignor. All of that is setup before a single assertion, so the scenario under test is buried beneath construction code.

I would extract the member-building and subscription-serialization steps into named helpers, such as one that builds a stable member with a given instance id and assignment. That keeps the scenario, a static member replaced by a classic one, readable at the top level, and the same helpers can serve neighboring tests that build similar members.

### `testClassicMemberJoinToConsumerGroupWithDisabledMigrationPolicy` — GroupMetadataManagerTest.java

<FunctionCard fn='testClassicMemberJoinToConsumerGroupWithDisabledMigrationPolicy' file='group-coordinator/src/test/java/org/apache/kafka/coordinator/group/GroupMetadataManagerTest.java' risk='167.39' band='fire' cc='7' nd='1' fo='50' touches='1' />

This one has the highest cyclomatic complexity in the set at 7, and it comes from the static-versus-dynamic parameter: the test branches on that boolean to set instance ids, add a second member and run a third assertion block. Three scenarios (new member joins, existing member rejoins, classic member tries to replace a consumer static member) share one method, each asserting the same error message. Fan-out is 50, and it carries a god-function flag.

If one of the three assertions starts failing, the test report points at the whole method rather than a named scenario. I would split it into three tests that share a group-building helper, keeping the boolean parameter only on the ones that need it. That should cut the cyclomatic complexity to roughly half.

### `testRebalanceCompletesBeforeMemberJoins` — GroupMetadataManagerTest.java

<FunctionCard fn='testRebalanceCompletesBeforeMemberJoins' file='group-coordinator/src/test/java/org/apache/kafka/coordinator/group/GroupMetadataManagerTest.java' risk='166.91' band='fire' cc='4' nd='1' fo='100' touches='1' />

This one reads as a timeline: create a group with a static leader, join and sync, add a second dynamic member, advance a simulated clock in steps while sending heartbeats, then complete the join phase and sync again. Fan-out is 100, and it carries both god-function and long-function flags. A small heartbeat loop and little else gives it a cyclomatic complexity of 4, so the difficulty is length and sequencing, not branching.

Clock advances and state assertions interleave, which makes a failure mid-timeline hard to localize. I would extract the first half, building a stable one-member group, into a shared fixture method and keep only the rebalance steps in the test body. The short comments already marking each phase would map cleanly to extracted method names.

**Neighboring functions**

The context-only list shows the same shape continuing: three more test methods (fan-out 100, 128 and 68) all carry activity-weighted risk scores of 166.17 and a cyclomatic complexity of 2. That is why I would treat this as a file-level cleanup: fixing five methods leaves the same construction pattern in many more.

If I were setting a plan, I would start with a shared builder for consumer group members and a shared helper for classic group setup. Those two extractions would shorten most of the methods above in one pass, and they are the changes the next person adding a coordinator test is most likely to reuse.
