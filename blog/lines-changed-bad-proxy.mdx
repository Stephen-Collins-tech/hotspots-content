Open any PR queue and the sorting is implicit: big diffs get flagged for careful review, small diffs get rubber-stamped. It's not written down as a policy anywhere — it's just what "this looks like a big change" does to a reviewer's attention, and it happens automatically. The trouble is that diff size measures *effort*, and effort and *risk* are not the same axis, even though we routinely treat them as if they were.

## Two changes, opposite risk profiles

A five-line change to a file that's been patched forty times in the last year, in a function with tangled ownership and a history of fixes triggering new fixes — that's a small diff sitting on top of a deeply unstable foundation. The change itself might be perfectly correct. What it's landing on isn't.

A two-hundred-line change to a stable utility file — new functionality, cleanly added, in a module nobody's had to touch defensively in years — is a large diff on top of solid ground. It takes longer to review line by line. It is not, by that fact alone, more dangerous.

If your review process allocates attention by diff size, you're spending your scarcest resource — careful human attention — in inverse proportion to where it's actually needed.

## Why size became the default proxy in the first place

It's not a bad proxy because reviewers are lazy or careless — it's a bad proxy because it's the only signal available *at a glance*, in the PR list, before anyone's opened a single file. Diff size is free. Risk is not free to compute; it requires knowing something about the file's history that isn't visible in the diff itself: how often it's broken before, how many people understand it, how tangled its dependencies are.

Diff size is a decent proxy for *review effort* — a two-hundred-line change genuinely does take longer to read carefully than a five-line one. It is a poor proxy for the thing effort is supposed to be protecting against, which is *shipping something that breaks in production*. Those two things correlate loosely enough, and diverge often enough, that treating them as interchangeable produces predictable blind spots: small, dangerous changes wave through on the strength of looking small.

## What actually correlates with risk

Not diff size — the *history of the file being touched*. A file with a long tail of past fixes, contested ownership, or heavy coupling to other parts of the system carries risk that has nothing to do with how many lines the current change happens to be. A five-line change in that context deserves the scrutiny a two-hundred-line change usually gets by default; a two-hundred-line addition to a quiet, well-owned utility often doesn't need it.

## The practical shift

You don't need to abandon diff size as a review-effort signal — it's genuinely useful for that. The fix is to stop letting it stand in for risk when they diverge. Before triaging a PR by size alone, ask one extra question: what's the history of the files this diff touches? A small diff against a file with a rough history is worth the same care as a large one. A large diff against quiet, stable code often isn't. The argument isn't that size measures nothing — it's that it measures effort, and effort and risk are different things, and conflating them is exactly how small, dangerous changes get through.
