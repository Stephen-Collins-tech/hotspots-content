### `parseInsert` — MySqlStatementParser.java

I would start with `parseInsert` because it has the highest activity-weighted risk score in the repo at 2.39, and it is active: 5 touches in the last year and 0 days since last change. It parses MySQL INSERT statements. From the excerpt, the opening section is a loop that checks for modifier keywords such as LOW_PRIORITY, DELAYED, HIGH_PRIORITY, IGNORE and ROLLBACK_ON_FAIL, followed by a sequence of independent optional-clause checks for hints, INTO, OVERWRITE, TABLE, line comments and FULLTEXT before it reads the table name. Every one of those is a separate branch, which is how the function reaches a cyclomatic complexity of 44 and a nesting depth of 7.

<MetricBar label='Fan-out' value='101' threshold='15' max='250' />

The fan-out of 101 is the number I would pay attention to. A change to any token-handling helper or AST setter could ripple into this function. A concrete first step: extract the modifier loop into something like `parseInsertModifiers` and the INTO/OVERWRITE/TABLE preamble into its own method. That removes the deepest nesting and gives each piece its own focused test cases. A nesting depth of 7 is already past the point where I consider it a strong refactoring signal.

### `parseStatementListDialect` — MySqlStatementParser.java

<FunctionCard fn='parseStatementListDialect' file='core/src/main/java/com/alibaba/druid/sql/dialect/mysql/parser/MySqlStatementParser.java' risk='2.33' band='critical' cc='112' nd='5' fo='170' touches='5' />

`parseStatementListDialect` has an activity-weighted risk score of 2.33, a cyclomatic complexity of 112 and a fan-out of 170. The excerpt shows it behaving as a statement dispatcher: a long run of checks for PREPARE, DEALLOCATE, LOAD, REPLACE, START, SHOW, CLEAR and DISABLED, each delegating to a dedicated parse method and returning true. Some branches, like the CLEAR DDL CACHE path, carry inline parsing logic that includes a loop over job ids and its own error handling, so the dispatcher is also doing parsing work.

<MetricBar label='Cyclomatic Complexity' value='112' threshold='30' max='250' />

My recommendation is to separate dispatch from parsing. Move the inline branches, starting with the CLEAR DDL handling, into their own methods so the top-level function becomes a flat sequence of keyword checks. A table or map from leading keyword to handler would shrink the path count further, though that is a larger change and I would do the extract-method pass first. Because the function returns a boolean to signal whether it handled the statement, every branch is also a return path that needs a test.

### `parseCreateDatabase` — MySqlStatementParser.java

<FunctionCard fn='parseCreateDatabase' file='core/src/main/java/com/alibaba/druid/sql/dialect/mysql/parser/MySqlStatementParser.java' risk='2.3' band='critical' cc='42' nd='5' fo='63' touches='5' />

`parseCreateDatabase` has an activity-weighted risk score of 2.3, a cyclomatic complexity of 42, a nesting depth of 5 and a fan-out of 63. The excerpt shows two separate blocks that inspect hint comments by splitting the text on whitespace and matching words: one looks for a trailing IF NOT EXISTS, the other walks the words looking for CHARACTER SET and COLLATE. Then a later loop handles the same options again as ordinary tokens (CHARACTER, CHARSET and so on).

That duplication is the most useful finding here. The same logical options, character set and collation, are recognized through at least two different mechanisms: version-comment hints and regular tokens. That is a reasonable thing to support, since MySQL dumps use versioned comments, but it means a fix to how character set is parsed has to be applied in more than one place. I would extract the hint-comment parsing into a helper that returns the options it found, and keep the token-based loop as the single place that applies them to the statement. That removes the deepest nesting and the repeated word-matching logic.

Because this is an override, its effective coupling extends into the base class and any other dialect that overrides the same hook, which static fan-out does not capture. Much of this element-list parsing looks similar to what a CREATE TABLE parser would need, so I would check whether it can share an element-parsing helper with the table path instead of maintaining a parallel copy. ## Where to start

I would treat `MySqlStatementParser.java` as one refactoring project with an order of attack. First, `parseShow` and `parseStatementListDialect`, because their cyclomatic complexity of 250 and 112 make them the largest test-coverage gaps and the most likely places for a new branch to cause a surprise. Second, `parseInsert`, because it has the highest activity-weighted risk score and the deepest nesting. Third, `parseCreateDatabase` and `parseCreateMaterializedViewRest`, where the wins are removing duplicated hint handling and sharing element parsing.

The five functions above are both complex and changing today, which is why I would start with them.
