### `credentialedProxyHandler` — credentialed.js

<FunctionCard fn='credentialedProxyHandler' file='src/utils/proxy/handlers/credentialed.js' risk='19.75' band='critical' cc='53' nd='26' fo='19' touches='2' />

From the name and path, this function handles outbound proxy requests to services that require authentication credentials. The source excerpt confirms that: it resolves a widget configuration, constructs request headers, and then dispatches authentication based on the specific service type — Bearer tokens, basic auth, proprietary API key headers, and so on for well over a dozen distinct service types.

The cyclomatic complexity of 53 means there are 53 independent execution paths through this function. Each is a potential bug surface and, formally, a required test case. The nesting depth of 26 is the most striking single number in this analysis — control structures are stacked 26 levels deep in places, which means a reader must hold an extraordinary amount of context to reason about any one branch. The fan-out of 19 means the function directly calls 19 distinct functions, so any signature change in a dependency has a plausible path back here.

Looking at the excerpt directly: the authentication dispatch is a long if/else-if chain covering `stocks`, `coinmarketcap`, `gotify`, `checkmk`, a grouped Bearer-token list of 17 services, `truenas`, `ntfy`, `proxmox`, `proxmoxbackupserver`, `autobrr`/`jellystat`/`pulse`, `tubearchivist`, and more. Each branch injects different header values. That structure is the source of the CC 53 — every new integration adds at least one branch. The file-level signals show a `bug_fix_fraction` of 0.5 across 2 total commits, and a `pr_review_comment_density` of 0.71, which is relatively high given the commit count. That review pressure is consistent with a function where reviewers are manually checking each new service branch.

The function was touched twice in the last 30 days and last changed 12 days ago. With integrations actively being added, the branch list will grow, and CC will climb further without intervention.

**Recommendation:** Extract the per-service header injection into a lookup table or a map of service-type to header-builder function. That collapses the if/else-if chain to a single dispatch, drops CC by roughly 30 points, and makes each service's credential logic independently testable. A new integration then adds a single entry to the map rather than a new branch inside an already-complex function.

### `omadaProxyHandler` — proxy.js

<FunctionCard fn='omadaProxyHandler' file='src/widgets/omada/proxy.js' risk='19.46' band='critical' cc='59' nd='8' fo='18' touches='1' />

This is the dedicated proxy handler for the Omada network controller widget. The source excerpt shows it doing something architecturally heavier than most widget proxies: it first queries the controller's info endpoint to determine which major version of the Omada API is running (3, 4, 5, or 6), selects the correct login URL via a switch statement, manages a session cache, and then retries on authentication failure — all before making the actual data request.

At CC 59 this is the most cyclomatically complex function in the top five. The version-branching logic alone (four major versions, each with distinct URL patterns and potentially distinct API shapes) accounts for a significant portion of that. A nesting depth of 8 is high but not extreme given the retry loop wrapping the session management; the real risk is the breadth of decision points. Fan-out of 18 means it is pulling from HTTP proxy utilities, session cache, login helpers, and the base widget config resolution.

The file-level `bug_fix_fraction` is 1.0 — the single commit recorded against this file was a bug fix. That is a weak signal given a total commit count of 1, but it is worth noting that the one time someone touched this file, it was to fix something. The function was last changed 22 days ago with 1 touch in the last 30 days.

**Recommendation:** Split version-specific behavior into separate strategy objects or functions keyed by `controllerVersionMajor`. The version detection and URL selection logic can become a pure `getLoginConfig(version, url, cId)` function that returns a configuration object. That removes the switch and the version-conditional blocks from the main handler, dropping CC substantially and making each version's behavior testable in isolation.

### `QuickLaunch` — quicklaunch.jsx

<FunctionCard fn='QuickLaunch' file='src/components/quicklaunch.jsx' risk='18.23' band='critical' cc='38' nd='6' fo='59' touches='1' />

This is a React component function — the entire QuickLaunch UI feature lives here. The excerpt shows it doing: settings resolution from context, search provider selection across multiple fallback paths (explicit config, widget config, localStorage), URL detection logic, keyboard navigation state, and search suggestion management. That is a large amount of product behavior concentrated in a single component function.

The fan-out of 59 is the standout metric. This component directly calls 59 distinct functions, which in a React context means it is importing and invoking hooks, utility functions, SWR fetchers, translation helpers, context accessors, and DOM APIs all in one place. In JavaScript, dynamic property access and the callback-heavy nature of React hooks mean the actual coupling is likely broader than even that count suggests — event handlers closed over state variables create implicit dependencies that fan-out metrics cannot fully capture.

The `bug_linked_commit_count` is 1.0 and `bug_fix_fraction` is 1.0 — the single recorded commit against this file was both linked to a bug and a bug fix. That is consistent with the kind of subtle interaction bugs that arise from a component managing too many concerns: a change to search provider resolution can silently affect keyboard navigation state, or vice versa.

The CC of 38 comes from the branching inside provider selection (custom provider, named provider, search widget provider, array provider, localStorage fallback), URL detection in `handleSearchChange`, and keyboard event dispatch in `handleSearchKeyDown`. With nesting depth of 6, individual branches are readable, but the sheer count of paths makes full test coverage expensive.

**Recommendation:** Extract search provider resolution into a `useSearchProvider(settings, searchWidget)` custom hook. That alone removes 8–10 cyclomatic complexity points from the component body and isolates the most-branched logic into a unit-testable function. The URL detection in `handleSearchChange` is another good extract-method candidate — it has a clear input/output contract and no dependency on component state beyond `setUrl` and `setSearchString`.

### `handler` — proxy.js (services)

<FunctionCard fn='handler' file='src/pages/api/services/proxy.js' risk='17.28' band='critical' cc='35' nd='6' fo='18' touches='1' />

This is the Next.js API route handler that sits at the top of the service proxy dispatch chain. From the excerpt, it resolves the requested service widget, maps the widget type to an internal type where needed (e.g. `calendar` → `ical`), looks up the widget's proxy handler, and then — when the widget has an endpoint mapping — validates request method, resolves URL segments, filters query parameters, and injects extra headers before forwarding to the appropriate sub-handler.

The CC of 35 is driven by the endpoint mapping resolution block: there are validation branches for method mismatches, missing endpoints, invalid URL segments (path traversal checks), optional versus required query parameters, and header injection. Each of those is a necessary security or correctness check, which makes this harder to simplify than a function that is complex due to business logic branching. The nesting depth of 6 and fan-out of 18 are consistent with a function that is genuinely a coordination hub.

The `bug_fix_fraction` of 1.0 on a single commit mirrors the pattern seen in the Omada handler — the one recorded change was a fix. The `handler` name is generic; the god-function pattern here is structural rather than nominal.

**Recommendation:** Extract the endpoint mapping resolution block — everything from `if (widget?.mappings)` through header injection — into a separate `resolveEndpoint(req, widget)` function that returns a normalized request descriptor or an error response. That reduces the top-level handler to a dispatch function with a clear responsibility boundary, drops its CC to roughly 10–12, and makes the segment validation and parameter filtering logic independently testable.

### `handler` — [...service].js (Docker status)

<FunctionCard fn='handler' file='src/pages/api/docker/status/[...service].js' risk='16.54' band='critical' cc='20' nd='6' fo='23' touches='1' />

This Next.js API route handler resolves Docker container and Swarm service status. The excerpt shows three distinct operational modes: direct container lookup by name, Swarm replicated-service status with replica count comparison, and Swarm global-service status with local container affinity preference. Each mode has its own error handling and response shape.

At CC 20, this is the least cyclomatically complex of the five, but the fan-out of 23 is the highest among the proxy-layer handlers (excluding QuickLaunch). It calls into the Dockerode client, a `getDockerArguments` utility, container inspection, task listing, and service inspection — each with its own async error surface. The nesting depth of 6 is consistent with the conditional structure visible in the excerpt: the Swarm branch contains nested checks for replicated versus global mode, which in turn contain the replica count comparisons.

The `bug_fix_fraction` of 1.0 on a single commit again signals that when this file was touched in the last 30 days, it was to fix something. The Docker Swarm path is the most structurally complex branch — the global-service logic with local container affinity requires correlating two separate API responses (task list and container list), which is where the nesting accumulates.

**Recommendation:** Extract the Swarm status resolution into a `getSwarmStatus(docker, containerName, containers)` function. The replicated versus global branching is a natural seam — these are meaningfully different operational concepts that happen to share setup code. Separating them removes the deepest nesting from the main handler and makes each Swarm mode's status logic testable without a full HTTP request context.
