Five of the functions I would review first in webpack are both structurally critical and in code that is changing right now: all five are in the active tier, and all five were modified today or the day before. The top three each carry an activity-weighted risk score of 4.0, led by `createNodePrinter` in `lib/javascript/syntax-printer.js` with a cyclomatic complexity of 6,504, nesting depth 14 and fan-out of 1,607, touched 291 times in the last year. That makes it a strong candidate for early review. This analysis covers 25,530 functions in webpack, a JavaScript module bundler, of which 1,956 land in the critical band, and anyone shipping changes to the printer or CSS parser this week is working in exactly this code.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `_composeBlockBody` — syntax-parser.js

<FunctionCard fn='_composeBlockBody' file='lib/css/syntax-parser.js' risk='4.0' band='active' cc='202' nd='8' fo='106' touches='88' />

`_composeBlockBody` in `lib/css/syntax-parser.js` has a cyclomatic complexity of 202, nesting depth 8 and fan-out of 106, with 88 touches in the last year and a change today. Based on the excerpt, it reassembles a CSS block from its split declarations and child rules in source order, then applies minification transforms: merging longhand properties into shorthands, finding dead writes of the same property, handling keyframe rules and legacy box layouts, and computing where child rules sit relative to declarations.

The file's bug-fix rate is 53%, the highest in this analysis, with 5 distinct authors in the last 90 days. Zero bug-linked commits and zero reverts are recorded, and review comment density is 0. I read the high bug-fix rate as a reason to prioritize review, not as evidence about this function specifically. A function that does ordering, dead-write detection and merge planning in one body is working against the cascade rules its own comments call out ('reordering would change the cascade'), so I would review changes here carefully.

The code already shows the decomposition points. Merging into items, detecting dead writes, collecting the property tables, and computing child rules before each declaration are separate phases with separate local state. I would extract each phase into a named function that returns its result (the merges map, the dead-writes set, the rules-before array), leaving `_composeBlockBody` as an orchestrator that sequences them.

### `collectDroppable` — syntax-printer.js

<FunctionCard fn='collectDroppable' file='lib/javascript/syntax-printer.js' risk='4.0' band='active' cc='219' nd='14' fo='88' touches='291' />

`collectDroppable` is an inner function of the same printer, and it shares the file-level history: 291 touches in the last year, modified today. On its own it has a cyclomatic complexity of 219, nesting depth 14 and fan-out of 88. From the excerpt, it walks syntax nodes and branches on node type: expression statements, for statements, switch cases, and further cases past the excerpt. It decides which statements and declarators can be dropped from output, tracking dead code after an always-exiting statement in a switch case.

The nesting of 14 is what stands out to me. It comes from a single function handling many node types in sequence, each with its own conditions and loops. That shape is a natural fit for a dispatch table keyed on node type, with one small handler per case (`collectFromExpressionStatement`, `collectFromSwitchCase`, and so on). Each handler would then be unit-testable with a minimal syntax tree. I would do the switch-case handler first, since its loop with the exited flag and lexical-declaration checks is the densest part of the excerpt.

### `createNodePrinter` — syntax-printer.js

<FunctionCard fn='createNodePrinter' file='lib/javascript/syntax-printer.js' risk='4.0' band='active' cc='6504' nd='14' fo='1607' touches='291' />

<MetricBar label='Cyclomatic Complexity' value='6504' threshold='30' max='6504' />

I would start with `createNodePrinter` because a cyclomatic complexity of 6504,504 is not a number I can reason about as a single unit, and it was modified today. The excerpt shows what is happening: it is a factory that takes a modules argument, destructures the parser, side-effects and data modules, then builds lookup tables (child fields per node type, node types that print bare, node types that may be parenthesized) and, from the metrics, evidently defines a very large number of inner printing functions as closures. With a fan-out of 1607,607, the function touches an enormous surface, and the closure-based structure means many inner functions share state that static analysis cannot easily separate.

The file has been touched 291 times in the last year, with 4 distinct authors in the last 90 days. Its bug-fix rate is 32%, and historical signals show zero bug-linked commits and zero reverts. The pull request review comment density is 13.8, the highest in this set, which suggests this file draws more review discussion than the others. None of these signals says the function is defective. They say a lot of people are reviewing a lot of change in a function no reviewer can hold in their head.

My recommendation: split the factory along its natural seams. The setup tables (the Uint8Array lookups and child-field construction) can move to module-level constants computed once, and the printing logic can be grouped into separate factories per node family (statements, expressions, patterns, modules) that receive a shared context object. Even a first cut that removes the table construction from the factory body will make later diffs easier to review.

### `_initializeEvaluating` — JavascriptParser.js

<FunctionCard fn='_initializeEvaluating' file='lib/javascript/JavascriptParser.js' risk='3.97' band='active' cc='69' nd='20' fo='99' touches='93' />

<MetricBar label='Max Nesting Depth' value='20' threshold='8' max='20' />

`_initializeEvaluating` has the deepest nesting in the set at 20, against a cyclomatic complexity of only 69. That ratio tells me the problem is shape, not path count. The excerpt shows why: the method registers many evaluate hooks for expression types such as Literal and NewExpression, each tapped with an inline callback, and the callbacks contain their own switches and conditionals. From the excerpt, the nesting appears to accumulate from callback inside tap inside method.

It has 93 touches in the last year and was last changed 1 day ago. The bug-fix rate is 25%, with 4 distinct authors in the last 90 days, no bug-linked commits and no reverts. In a hook-based architecture, fan-out of 99 undercounts coupling, because behavior also depends on which plugins tap the same hooks.

This is the cheapest fix of the five. Moving each inline callback to a named method (`_evaluateLiteral`, `_evaluateNewExpression`, and so on) and leaving `_initializeEvaluating` as a flat list of registrations would take nesting from 20 to roughly 3 or 4 without changing behavior, and would give each evaluator its own stack frame name in traces.

### `_mergeBoxLonghands` — syntax-parser.js

<FunctionCard fn='_mergeBoxLonghands' file='lib/css/syntax-parser.js' risk='3.95' band='active' cc='72' nd='7' fo='46' touches='88' />

`_mergeBoxLonghands` is the helper `_composeBlockBody` relies on for shorthand merging, with a cyclomatic complexity of 72, nesting depth 7 and fan-out of 46. It shares the file's 88 touches, 53% bug-fix rate and change-today status. From the excerpt, it iterates candidate shorthand table entries, checks that all longhands are present and not repeated, guards on whether newer shorthands like `inset` and the place shorthands are allowed, tracks claimed declarations so two shorthands do not overlap, and refuses to merge when a child rule or an order-sensitive property sits between slots.

That is a chain of guard conditions, each protecting against a specific CSS corner case. The `continue` statements inside the loop make it a good fit for extraction into a predicate such as `canMergeEntry(...)` that returns a boolean, leaving the loop body to build the merge. That shrinks both cyclomatic complexity and the test surface per function: each guard becomes a case in a small table-driven test.

## Where to start

I would split my review time like this. First, `_initializeEvaluating`: the refactor is mechanical, the payoff is a drop in nesting from 20, and it is the lowest-risk change of the five. Second, `_composeBlockBody` and `_mergeBoxLonghands` together, since they share a file, a 53% bug-fix rate and the same CSS ordering semantics. Third, `collectDroppable`, extracted handler by handler. `createNodePrinter` last, but with a plan: pull the static tables out now so that later splits have a smaller starting point. Because all five are changing as I write this, any extraction should land behind the existing test suite in small pull requests, not as one large rewrite.
