## Top Hotspot Analysis

### `main` — `modules/vector-sets/examples/cli-tool/cli.py`

<FunctionCard fn='main' file='modules/vector-sets/examples/cli-tool/cli.py' risk='15.12' band='critical' cc='35' nd='4' fo='18' touches='0' />

This is the highest-ranked function in the repo, and the argument for prioritizing it is entirely structural — it hasn't been touched in 51 days and sits in the debt quadrant. A `main` function in a CLI tool tends to be the top-level orchestrator: argument parsing, dispatch, error handling, and exit logic all pulled into one place. The metrics confirm that shape. A cyclomatic complexity of 35 means there are 35 independent execution paths to reason about; the exit-heavy pattern flag tells me many of those paths terminate with their own exit or error condition, each of which requires its own test case to cover reliably. Fan-out of 18 means the function calls 18 distinct other functions — changes here can ripple into a wide surface area.

The god-function pattern flag is the part I'd stress most to a reviewer. A CLI `main` that orchestrates 18 callees across 35 branches is doing far too many jobs. It's a structural time-bomb: the next developer who adds a new subcommand or flag will have to navigate all of that branching just to find the right insertion point, and a misstep anywhere in those 35 paths produces an exit that may be hard to trace back to the source.

The external signals show only one commit ever touched this file, and 100% of that commit history is tagged as a bug fix. That's too thin a history to draw conclusions from — the file is very new — but it does mean there's no established pattern of incremental improvement here.

**Recommendation:** Decompose `main` using the extract-method pattern. Argument parsing, subcommand dispatch, and each major operation branch should each become their own function. The goal is to bring cyclomatic complexity below 10 for the orchestrating `main` and push branch logic into named, testable units.

### `test_recall_with_filter` — `modules/vector-sets/tests/filter_int.py`

<FunctionCard fn='test_recall_with_filter' file='modules/vector-sets/tests/filter_int.py' risk='14.68' band='critical' cc='52' nd='6' fo='23' touches='0' />

<MetricBar label='Cyclomatic Complexity' value='52' threshold='10' max='60' />

A cyclomatic complexity of 52 in a test function is one of those numbers that gives me pause. Test functions are supposed to be the readable ground truth for a system's behavior — when a test itself has 52 independent execution paths and nesting six levels deep, the test has become as hard to reason about as the production code it's meant to validate. This function hasn't been modified in 51 days and sits in the debt quadrant.

Fan-out of 23 is the highest in the top five, which tells me `test_recall_with_filter` is calling into a very broad surface of the vector-sets filtering system. That's not unusual for an integration-style recall test — you'd expect it to exercise filter construction, execution, and result validation across many cases — but the combination of nesting depth 6, CC 52, and the deeply-nested pattern flag means those cases are stacked inside each other rather than being expressed as independent test cases or parameterized runs.

The deeply-nested pattern is the structural signal I'd act on first. Nesting depth 6 means there are at least six levels of conditional or loop structure to track simultaneously. In a test context, that usually means a single monolithic function is covering what should be dozens of discrete scenarios, each with its own setup and assertion.

**Recommendation:** Flatten `test_recall_with_filter` into parameterized test cases or a test table. Each distinct filter configuration and expected recall threshold should be its own row, not a nested branch. This alone would collapse both the nesting depth and cyclomatic complexity dramatically.

### `process_file` — `utils/req-res-log-validator.py`

<FunctionCard fn='process_file' file='utils/req-res-log-validator.py' risk='14.25' band='critical' cc='25' nd='4' fo='11' touches='0' />

From the name and path, `process_file` is the core processing loop of a request/response log validator — the function that reads a log entry, applies validation rules, and decides whether it passes or fails. It hasn't been touched in 51 days and sits in the debt quadrant. A cyclomatic complexity of 25 with the complex-branching and exit-heavy pattern flags is characteristic of log-processing code where each line format, protocol variant, or error condition gets its own branch, and many of those branches end in an early return or explicit exit.

Fan-out of 11 with 25 branches means the function is both doing a lot of conditional work internally and delegating broadly to other functions. That combination — high internal branching plus broad external coupling — makes it expensive to change safely: you need to understand the internal branch logic to know which callee you're affecting, and you need to understand the callees to know what the branch is actually doing.

With 25 execution paths and exit-heavy control flow, I'd estimate this function requires a significant number of test cases to achieve meaningful coverage. The single-author, single-commit history means none of that coverage has been externally reviewed.

**Recommendation:** Map the 25 branches explicitly — even a comment block listing each case helps — then extract each validation rule into its own named function. The exit-heavy pattern suggests some branches exist only for early termination on invalid input; those can often be pulled into a guard-clause layer before the main processing logic begins.

### `matches_filter` — `modules/vector-sets/tests/filter_int.py`

<FunctionCard fn='matches_filter' file='modules/vector-sets/tests/filter_int.py' risk='13.55' band='critical' cc='32' nd='3' fo='8' touches='0' />

This function sits in the same file as `test_recall_with_filter` and, based on its name, appears to be the predicate that determines whether a given item satisfies a filter expression — likely the core logic that the recall test exercises. It hasn't been modified in 51 days and sits in the debt quadrant.

A cyclomatic complexity of 32 with the exit-heavy pattern flag is a meaningful combination for a filter-matching function. Filter predicates typically branch over operator types, value types, and logical combinators (AND, OR, NOT), and each combination is an independent path. At CC 32, there are 32 such paths — each one is both a potential bug surface and a test case that needs to exist for the function to be verifiably correct.

The nesting depth of 3 is relatively contained compared to `test_recall_with_filter`, which suggests the branching is wide rather than deep — many sibling cases rather than stacked conditionals. That's actually easier to decompose. Fan-out of 8 is moderate; this function isn't a hub, but it does call into enough supporting logic that its behavior depends on multiple moving parts.

**Recommendation:** Apply decompose-conditional refactoring. Each major branch in the filter-matching logic — operator dispatch, type coercion, edge cases — should become a named helper. This reduces the per-function cyclomatic complexity to something closer to 5–8 per handler, makes each case independently testable, and gives the exit paths clear names that document why the function terminates early.

### `test` — `modules/vector-sets/tests/deletion.py`

<FunctionCard fn='test' file='modules/vector-sets/tests/deletion.py' risk='13.34' band='critical' cc='43' nd='3' fo='21' touches='0' />

<MetricBar label='Fan-Out' value='21' threshold='10' max='25' />

A function named `test` in a deletion test file is almost certainly the top-level test driver for the vector-set deletion behavior: inserting elements, deleting them under various conditions, and asserting on the resulting state. It hasn't been touched in 51 days and sits in the debt quadrant. The cyclomatic complexity of 43 combined with a fan-out of 21 makes it the broadest-coupling function in the top five — it reaches into 21 distinct callees while managing 43 execution paths internally.

The god-function and long-function pattern flags together describe a test that has grown to cover far too many scenarios in a single body. Fan-out of 21 in a test function means it's exercising a very wide surface of the deletion subsystem — potentially covering partial deletions, full deletions, deletions under memory pressure, deletions of non-existent keys, and more — all inside one function that has to be read top to bottom to understand any individual scenario.

The structural debt here is that the next developer who needs to add a new deletion edge case, or who debugs a failure in this test, has to parse 43 branches and 21 callees to find where to look. That's an expensive context-load even when nothing is going wrong.

**Recommendation:** Split `test` into individually named test functions, one per deletion scenario or scenario group. Each should have its own setup, action, and assertion, with no shared branching between scenarios. Fan-out will naturally distribute across those smaller functions, and cyclomatic complexity per test should drop below 10.
