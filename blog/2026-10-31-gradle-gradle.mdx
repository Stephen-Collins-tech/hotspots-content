The leader, `printStatement`, has an activity-weighted risk score of 531.65 and sits in the 'fire' quadrant: it is both structurally non-trivial and was changed 11 days ago, which makes it worth reviewing soon. Across the 52,175 functions I analyzed at commit 252861a, 838 are critical, and the 4,371 in the 'fire' quadrant show how much of the codebase is moving at once. I would start with this file before touching anything else in build-init.

## Large Repo Analysis

gradle is a large repository. To stay within memory constraints, this analysis used **hybrid touch mode**: structural complexity — CC, ND, FO — is measured precisely for every function. Git activity is tracked at the function level (via `git log -L`) only for files with 5 or more commits in the touch window (365 days by default); other files use a file-level approximation. Rankings therefore surface functions that are both structurally complex and in the most actively-changing parts of the codebase. Dormant code with high structural complexity will rank lower than it would under a full per-function analysis — to surface it, run `hotspots analyze . --per-function-touches` on a machine with sufficient memory.

### `printStatement` — BuildScriptBuilder.java

<FunctionCard fn='printStatement' file='platforms/software/build-init/src/main/java/org/gradle/buildinit/plugins/internal/BuildScriptBuilder.java' risk='531.65' band='fire' cc='9' nd='3' fo='7' touches='1' />

I would start with `printStatement` because it has the highest activity-weighted risk score in the repository (531.65) and the highest complexity of the five: cyclomatic complexity 9, nesting depth 3, fan-out 7. From the excerpt, it is the pretty-printer's core routine: it skips empty statements, decides whether a separator line is needed, handles three comment modes (on, off, and external) through a switch, delegates to the statement to write its own code, and then updates separator state. That is a lot of mutable printer state (first-statement-of-block, separator-needed, end-of-line comment, comment count) being updated across several branches in one method. The ordering of those updates matters, and a reader has to hold all of it in their head to change any one branch safely. My recommendation: extract the comment-mode switch into its own method, and extract the separator decision into a small helper that returns a boolean, so the method body reads as three steps instead of one block. Before doing that, I would confirm there are tests that cover each comment mode combined with group and block statements.

### `expressionValue` — BuildScriptBuilder.java

<FunctionCard fn='expressionValue' file='platforms/software/build-init/src/main/java/org/gradle/buildinit/plugins/internal/BuildScriptBuilder.java' risk='530.28' band='fire' cc='7' nd='1' fo='2' touches='1' />

`expressionValue` has an activity-weighted risk score of 530.28 with cyclomatic complexity 7, nesting depth 1, and fan-out 2. It is flagged exit-heavy, and the excerpt shows why: a flat chain of type checks that each return a different value wrapper (string, literal, map, enum) and finish with an exception for anything unrecognized. The nesting is shallow, so this is easy to read. The cost is on the testing side: each exit is a separate case, and the final throw is a path that only a deliberately unsupported input will reach. I would not restructure this one. I would make sure there is one test per branch, including the failure case, because adding a new supported value type means adding another exit to a function that is already at seven paths.

### `printFileHeader` — BuildScriptBuilder.java

<FunctionCard fn='printFileHeader' file='platforms/software/build-init/src/main/java/org/gradle/buildinit/plugins/internal/BuildScriptBuilder.java' risk='528.92' band='fire' cc='5' nd='3' fo='8' touches='1' />

`printFileHeader` scores 528.92 with cyclomatic complexity 5, nesting depth 3, and fan-out 8. It writes the generated-file banner only when comments are enabled, then loops over header lines with a branch for blank lines. The fan-out of 8 is mostly repeated calls to the same line-printing helper, so the coupling is narrower than the number suggests. It is the same printer class as `printStatement`, and both mutate the same separator and first-statement flags. That shared state is the real risk: a change to how one method resets those flags can change the output of the other. I would add a golden-output test that prints a header followed by statements and compares the full text, since that is where an interaction would show up.

### `getLiteral` — BuildScriptBuilder.java

<FunctionCard fn='getLiteral' file='platforms/software/build-init/src/main/java/org/gradle/buildinit/plugins/internal/BuildScriptBuilder.java' risk='528.65' band='fire' cc='4' nd='2' fo='1' touches='1' />

`getLiteral` has an activity-weighted risk score of 528.65 with cyclomatic complexity 4, nesting depth 2, and fan-out 1. In the excerpt it builds a Kotlin-DSL container-creation string, branching on whether a variable name and an element type are present. Four combinations produce four slightly different strings, written out as separate concatenations. This is the lowest-risk function of the five structurally; it ranks here because it was changed recently. The practical hazard is duplication: the same creation expression is spelled out four times, so a change to the output format has to be made in four places. I would collapse the four returns into a small composition of an optional declaration prefix and an optional type argument. That reduces the paths and removes the duplicated string assembly.

### `makeDepSpec` — BuildScriptBuilder.java

<FunctionCard fn='makeDepSpec' file='platforms/software/build-init/src/main/java/org/gradle/buildinit/plugins/internal/BuildScriptBuilder.java' risk='527.85' band='fire' cc='4' nd='2' fo='8' touches='1' />

`makeDepSpec` scores 527.85 with cyclomatic complexity 4, nesting depth 2, and fan-out 8. It loops over dependencies and, for each one, branches on whether a version exists and a version catalog is in use: one path registers the library with the catalog and emits a catalog reference, the other emits the plain notation. A sibling method in the same file repeats the same catalog-or-notation branch with a different spec type. I would pull that decision into one shared helper that returns the notation and a flag, so the two methods stop carrying the same conditional. The fan-out is the more interesting number here, since version-catalog registration reaches through the script builder and its generation context. A change to catalog behavior would have to be checked in both methods today.
