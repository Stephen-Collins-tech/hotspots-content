The riskiest function I found in kubernetes-sigs/kustomize, `ParseQuantity`, hasn't been changed in 1,356 days. That makes it structural debt with a high blast radius for whoever touches it next, not an emergency. All five top-ranked functions sit in the debt quadrant, out of 2,226 functions analyzed, 367 of them in the critical band. I would treat this list as a refactoring backlog ordered by how painful the next change will be.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `ParseQuantity` — quantity.go

<FunctionCard fn='ParseQuantity' file='cmd/config/internal/commands/internal/k8sgen/pkg/api/resource/quantity.go' risk='17.03' band='debt' cc='57' nd='5' fo='30' touches='0' />

I would start with `ParseQuantity`: it has the highest activity-weighted risk score in the repository at 17.03, a cyclomatic complexity of 57, and 1,356 days since last change with zero touches in the last year. The path (`k8sgen/pkg/api/resource`) suggests code generated or copied from the Kubernetes resource-quantity package, so before deciding how much to refactor locally, I would confirm whether it is meant to track upstream.

<MetricBar label='Cyclomatic Complexity' value='57' threshold='10' max='60' />

The source excerpt shows the function validating input, handling a zero shortcut, parsing the string into components, then branching on format (decimal exponent, decimal SI, binary SI). Nested conditions choose between a fast integer path and a slower arbitrary-precision decimal path. Fan-out of 30 means heavy coupling to helpers, and the nesting depth of 5 sits inside the format switch. The file has only 1 commit in its history and no bug-fix, revert or review-comment signals, so I would frame this as maintainability debt, not a defect hotspot. My recommendation: if this copy is meant to stay close to upstream, pin and document that. If not, extract the fast-path integer parsing and the decimal fallback into separate functions so each can be tested against its own table of inputs.

### `actualMain` — main.go

<FunctionCard fn='actualMain' file='cmd/gorepomod/main.go' risk='15.99' band='debt' cc='48' nd='4' fo='30' touches='0' />

`actualMain` in the `gorepomod` tool has a cyclomatic complexity of 48, a fan-out of 30, and hasn't been changed in 1,005 days. The excerpt shows a command dispatcher: it parses arguments, loads a repo manager, resolves two modules, then switches on the command. The pin case alone contains nested fallback logic that repeats the same pin-with-local-version recovery in several places, and that repetition drives much of the complexity and nesting.

The file has 2 total commits and no quality-related signals. I would make each command a small handler function and share one helper for the 'fall back to the local version and pin' sequence. That shrinks the dispatcher to a table of cases and removes the duplicated error-wrapping branches.

### `setAssociativeSequenceElements` — associative_sequence.go

<FunctionCard fn='setAssociativeSequenceElements' file='kyaml/yaml/walk/associative_sequence.go' risk='15.91' band='debt' cc='36' nd='5' fo='17' touches='0' />

This function lives in the YAML walker that merges lists keyed by one or more fields (the source comment uses `containerPort` and `protocol` as the example). It has a cyclomatic complexity of 36, nesting depth of 5, fan-out of 17, and 1,356 days since last change. That is the same unchanged window as `ParseQuantity`, so both appear to date from the same period of the repository's history.

The excerpt shows a loop over key-value sets, a nested walk, a loop over keys with delete-or-set-field branches, an early-continue flag, and end-of-function handling that depends on a merge-direction option. Every step has its own error return, which accounts for the exit count. List-merge semantics matter to users here, so a change without characterization tests is risky. I would write tests that pin current merge behavior for single-key and multi-key lists, then extract the per-element handling into its own function.

### `appendReplaceOrMerge` — reswrangler.go

<FunctionCard fn='appendReplaceOrMerge' file='api/resmap/reswrangler.go' risk='15.10' band='debt' cc='31' nd='4' fo='16' touches='0' />

`appendReplaceOrMerge` is the one function in this top five with the shortest time since last change at 43 days, though it has zero touches by the last-year commit-count window. Its file shows 6 total commits with a bug-fix rate of 67% and 2 distinct authors in the last 90 days. That is historical context, not proof that this function is defective, but combined with the more recent change it is the one I would review first, even though it does not have the biggest score.

The excerpt shows a switch on the number of matching resources (none, one, many), with nested switches on the resource's behavior (create, merge, replace) and special-case handling for Secret `stringData` normalization. I would split the zero-match, one-match and multiple-match cases into three functions and move the Secret normalization behind a named helper, so each behavior combination has a direct test.

### `applyReplacement` — replacement.go

<FunctionCard fn='applyReplacement' file='api/filters/replacement/replacement.go' risk='14.89' band='debt' cc='25' nd='5' fo='9' touches='0' />

`applyReplacement` has a cyclomatic complexity of 25, nesting depth of 5, and 431 days since last change. Its file has 9 commits with a bug-fix rate of 11%, low enough that I read it as ordinary history rather than a warning sign. The excerpt shows three nested loops (selectors, candidate nodes, resource IDs) with early continues for label, annotation and reject filtering before the value is copied to the target.

Nesting is the main cost here, not the fan-out of 9. I would extract the 'does this node match this selector' check into a single predicate function, which would flatten two levels and leave the loop body as a filter followed by a copy.

**What I would do with this list**

I would not schedule all five. `appendReplaceOrMerge` gets a review first because it has the shortest time since last change (43 days) and a notable bug-fix history on its file. After that, `ParseQuantity` and `setAssociativeSequenceElements` deserve characterization tests before anyone edits them, since both have gone 1,356 days unchanged and will be unfamiliar to whoever opens them next.
