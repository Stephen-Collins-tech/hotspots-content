### `main` — resource_tracker.py

<FunctionCard fn='main' file='joblib/externals/loky/backend/resource_tracker.py' risk='17.31' band='debt' cc='62' nd='8' fo='22' touches='0' />

This is the entrypoint of loky's resource tracker process. From the excerpt, it sets up logging, ignores SIGINT and SIGTERM, closes stdin and stdout, then reads a stream of messages and branches on commands such as REGISTER, UNREGISTER, PROBE and MAYBE_UNLINK. The comments mark the loky-specific changes layered on top: Windows support, reference counting and extra logging. Each of those adds another branch inside the same loop.

The numbers are the largest in the table: 62 independent paths, nesting eight levels deep, and 22 distinct functions called. Nesting at 8 is the strongest refactoring signal on my own threshold list. It has zero touches in the last year, and its last change was 31 days ago. The file has 6 commits in its history, a bug-fix rate of 0%, no reverts, and one author in the last 90 days. I read that as maintainability debt, not a defect signal. The risk is that the next person to add a command or platform branch has to hold the whole message loop, the signal setup and the reference-count bookkeeping in their head at once.

<MetricBar label='Cyclomatic Complexity' value='62' threshold='10' max='70' />

My recommendation: extract a dispatch step per command (register, unregister, probe, maybe-unlink) so each handler can be tested with a fake cache. Pull the process setup (signals, closing standard streams, Windows handle conversion) into its own function. That would take the loop body from eight levels of nesting to roughly three.

### `_process_worker` — process_executor.py

<FunctionCard fn='_process_worker' file='joblib/externals/loky/process_executor.py' risk='16.8' band='fire' cc='48' nd='4' fo='24' touches='1' />

Here the risk is live. `_process_worker` evaluates calls from a queue inside a separate worker process and puts results on a result queue. It has an activity-weighted risk score of 16.8, a cyclomatic complexity of 48, a fan-out of 24, and it was changed 1 day ago. The excerpt shows it handling the initializer failing, the queue timing out, a sentinel shutdown signal, locks around worker exit, and nested-parallelism depth. Those are separate concerns sharing one loop, and the exit-heavy pattern means many return and exit paths that each need a test.

The file has 5 commits in its history with a bug-fix rate of 20%, no reverts, and 2 distinct authors in the last 90 days. That is a small history, so I would not lean on the bug-fix rate, but it does mean the file is not purely dormant. A fan-out of 24 in a function that runs at a process boundary means many separate dependencies to keep in mind when changing it.

My recommendation: separate the 'fetch next item' step (get, timeout, sentinel, exception) from the 'execute and report' step, and give the shutdown handshake its own function. The fetch step has the most branches and is the easiest to cover with focused tests.

### `get_oldest_pypy_package_version` — continuous_integration/versions.py

<FunctionCard fn='get_oldest_pypy_package_version' file='continuous_integration/versions.py' risk='15.43' band='fire' cc='28' nd='4' fo='14' touches='1' />

This one is CI tooling, not library code, so the blast radius is the build matrix rather than users. It downloads a package's release list from PyPI, filters versions by upload date and required Python version, then runs a binary search that calls out to look up supported Python versions. It has a cyclomatic complexity of 28, a fan-out of 14, one touch in the last year, and was last changed 7 days ago. The file has a single commit in its history, so there is nothing more to draw on.

My recommendation: split the version-filtering loop from the binary search, so the filter can be tested against a canned PyPI JSON payload. I would put the network calls behind a parameter so tests never leave the machine.

### `filter_args` — joblib/func_inspect.py

<FunctionCard fn='filter_args' file='joblib/func_inspect.py' risk='14.92' band='debt' cc='49' nd='3' fo='21' touches='0' />

This is the first top function in joblib's own public-facing code. `filter_args` takes a callable, a list of argument names to ignore, and the call's positional and keyword arguments, and returns the filtered set. The excerpt shows it handling methods, plain functions, partial-style objects it cannot inspect, positional-or-keyword parameters, keyword-only parameters, varargs and varkw, and errors for arguments given twice. The ND of 3 is modest; the problem is the 49 paths and many exits.

It hasn't been changed in 109 days and has zero touches in the last year. The file has 6 commits with a bug-fix rate of 50%, no reverts, and one author in the last 90 days. Half of a six-commit history being bug fixes is a small sample, but it is the highest rate among my top five, and the signal I would weight most for review order. The blast radius is high when this is next touched: anything built on joblib's argument handling inherits a change here.

My recommendation: split signature parsing (collecting names, defaults, varargs) from argument binding (matching positional and keyword values and raising on duplicates). The parsing half is a pure function of the callable and is easy to test exhaustively.

### `dump` — joblib/numpy_pickle.py

<FunctionCard fn='dump' file='joblib/numpy_pickle.py' risk='14.47' band='debt' cc='39' nd='3' fo='18' touches='0' />

`dump` is one of joblib's most visible entry points: it persists an arbitrary Python object to a file, with optional compression. The excerpt shows a long block that normalizes the `compress` argument, which can be a bool, an integer, a string, or a 2-tuple, then validates the method and level, with a check for lz4 not being installed. That normalization is where most of the 39 paths come from, with the actual writing coming after.

It hasn't been changed in 78 days, with zero touches in the last year. The file has 12 commits in its history, a bug-fix rate of about 42%, no reverts, and 2 distinct authors in the last 90 days. As a public API function, it is the one where a signature or behavior change reaches every caller.

My recommendation is the cleanest refactor in this set: extract the compression-argument handling into a function that returns a validated method-and-level pair. It is a pure function, trivially testable with a table of inputs, and it would remove a large share of the branches from `dump` without touching the write path.
