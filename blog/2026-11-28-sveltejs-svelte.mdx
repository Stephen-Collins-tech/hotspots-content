I would start with `batch.js` rather than any single function in it: three of the top five hotspots in sveltejs/svelte (`flush_queued_effects`, `mark`, and `activate`) live in packages/svelte/src/internal/client/reactivity/batch.js, each with an activity-weighted risk score between 3.32 and 3.52 and 90 touches in the last year. All of them were changed today, which makes this a review-now item and not a backlog item. The other two, `get` and `is_dirty`, are in runtime.js, so the entire top five is the client reactivity engine, out of 6,211 functions analyzed and 245 in the critical band.

### `flush_queued_effects` — batch.js

<FunctionCard fn='flush_queued_effects' file='packages/svelte/src/internal/client/reactivity/batch.js' risk='3.52' band='active' cc='30' nd='7' fo='9' touches='90' />

I would start with `flush_queued_effects` because it has the highest activity-weighted risk score in the repo (3.52), a cyclomatic complexity of 30, and a nesting depth of 7, in a file touched 90 times in the last year.

<MetricBar label='Max Nesting Depth' value='7' threshold='4' max='10' />

From the excerpt, the function walks a queue of effects, skips destroyed, inert, skipped, or deferred ones, runs the dirty ones, and then handles a second pass over 'eager block effects' that includes an ancestor-before-descendant ordering step and a try/finally that restores saved module-level state. The nesting depth of 7 comes from that second pass: a loop inside a loop inside a try inside a conditional inside the outer loop. The function also reads and writes several module-level variables (the eager block set, the eager block writes map, the teardown context), which fan-out of 9 undercounts as coupling because those are shared state and not calls.

My recommendation: extract the eager-block pass into its own function with an explicit parameters-in, state-restored-out contract. The ancestor ordering loop can come out separately as a small helper that takes an effect and a set and returns an ordered list. That would take the nesting depth from 7 to roughly 4 without changing behavior, and it makes the save-and-restore of module state something a test can assert directly.

### `mark` — batch.js

<FunctionCard fn='mark' file='packages/svelte/src/internal/client/reactivity/batch.js' risk='3.4' band='active' cc='19' nd='5' fo='7' touches='90' />

`mark` has an activity-weighted risk score of 3.4 with a cyclomatic complexity of 19. It propagates a status to the reactions of a signal and recurses into itself for derived reactions. The excerpt shows a runes-versus-legacy check, a cycle guard that activates a seen set once a dependency counter crosses 100,000, and three distinct branches (eager effects, deriveds, plain effects) with different scheduling rules.

The recursion plus the lazily activated seen set is the part I would be cautious about. The guard only exists on a high-count path, so most tests will never exercise it, and the comment in the code ties it to a specific issue with a very large graph. A branch that only fires at scale is exactly the kind a coverage report can hide.

My recommendation: split the per-reaction body into three named handlers, one per branch, so `mark` becomes a loop that dispatches. Then add a test that forces the seen-set path with a small threshold injected for the test.

### `get` — runtime.js

<FunctionCard fn='get' file='packages/svelte/src/internal/client/runtime.js' risk='3.38' band='active' cc='64' nd='6' fo='22' touches='39' />

`get` is the outlier in this list: the lowest-touch function of the five at 39 touches in the last year, but with by far the largest structure. Its cyclomatic complexity of 64 is more than double `flush_queued_effects`, and its fan-out of 22 is well past the level I treat as a strong coupling signal.

<MetricBar label='Cyclomatic Complexity' value='64' threshold='30' max='80' />

This reads as the central signal-read path. The excerpt shows it registering dependencies on the active reaction, handling late reads after an await, and then a large block gated on a development flag covering reactivity-loss warnings and tracing. Dependency tracking and development diagnostics share one function body, and that is where most of the 64 paths come from.

My recommendation: the development-only block is the cleanest first cut. Move it into a separate function called behind the same flag, which should remove a large share of the paths from the hot read path and leave the production logic readable on its own. After that, the dependency registration branches (in-update versus late read) are the next natural split. Because `get` is called from everywhere, I would do this in small steps with the existing suite as the safety net.

### `activate` — batch.js

<FunctionCard fn='activate' file='packages/svelte/src/internal/client/reactivity/batch.js' risk='3.32' band='active' cc='15' nd='4' fo='4' touches='90' />

`activate` is the smallest of the three batch.js entries (cyclomatic complexity 15, nesting 4, fan-out 4) but shares the same 90-touch history. It sets the current batch and view, resets state in several early-return cases, and then builds a values map that overrides values from other batches, folding earlier intersecting batches into this one. The comments describe this as 'time travelling' between batches.

The metrics make this look manageable. The risk is conceptual: the function encodes rules about which batches fold into which, and those rules interact with `mark` and `flush_queued_effects` through shared module state. I would treat it as part of the same review as the other two and not in isolation.

My recommendation: pull the loop over other batches into a named function that returns the folded list and the value overrides, so the early-return cases and the batch-merging logic stop sharing one body.

### `is_dirty` — runtime.js

<FunctionCard fn='is_dirty' file='packages/svelte/src/internal/client/runtime.js' risk='3.28' band='active' cc='18' nd='6' fo='6' touches='39' />

`is_dirty` has a cyclomatic complexity of 18 and a nesting depth of 6, and I would read the nesting as the main concern. It decides whether a reaction needs to rerun, with separate paths for assigned deriveds, dirty flags, and a dependency walk that either compares versions or consults a batch-aware check. Inside the dependency walk there is a memoization branch that only activates after a counter exceeds 100,000, the same scale-triggered pattern as in `mark`.

The duplicated threshold idea across `mark` and `is_dirty` is worth noting. Both guard against the same class of large-graph blowup in different files, and the `is_dirty` comment explicitly references `Batch#mark`. Those two safeguards are coupled by intent, so a change to one probably needs a look at the other.

My recommendation: extract the non-batch dependency walk, including the memo handling, into its own function. That isolates the scale-triggered path and cuts the nesting depth by two levels.

## Where to start

I would review batch.js as one unit, starting with `flush_queued_effects`, then `mark`, then `activate`, because they share module state and a single file history of 90 commits. In parallel, I would peel the development-only diagnostics out of `get` in runtime.js, since that gives the largest single reduction in paths (cyclomatic complexity 64) for the least behavioral risk.

For framing, a few critical-band functions outside the top five are quiet: they were touched once in the last year and have been unchanged for months, so they are quiet debt, not a live risk.
