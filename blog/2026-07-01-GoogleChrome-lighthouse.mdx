Every function in this table carries the same three-pattern signature — `complex_branching`, `deeply_nested`, `exit_heavy` — and all five sit under `test/fixtures/` paths: a legacy-JavaScript detection sample and two bundled third-party scripts (a Mixpanel tracker and a course-hero web app) checked in to validate lighthouse's polyfill-detection and source-map remapping logic. That's not a lighthouse code-health finding — the ignore-paths config for this run was supposed to exclude test fixtures and vendored bundles from analysis, and it didn't get applied, so fixture code got scored and ranked right alongside lighthouse's own audit and gathering logic. I'm publishing the numbers as produced rather than re-running with a manual filter, but treat this post as a heads-up about a pipeline gap rather than a finding about lighthouse itself; the ignore-paths fix belongs in the crawler config, not in this repo.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

## Large Repo Analysis

lighthouse is a large repository. To stay within memory constraints, this analysis used **hybrid touch mode**: structural complexity — CC, ND, FO — is measured precisely for every function. Git activity is tracked at the function level (via `git log -L`) only for files with 5 or more commits in the last 30 days; other files use a file-level approximation. Rankings therefore surface functions that are both structurally complex and in the most actively-changing parts of the codebase. Dormant code with high structural complexity will rank lower than it would under a full per-function analysis — to surface it, run `hotspots analyze . --per-function-touches` on a machine with sufficient memory.

### `parseURL` — cli/test/fixtures/legacy-javascript.js

CC 216 is not a typo — it's roughly six times the median CC across this table (38) and more than double the next-highest score. Under hybrid-touch mode, that raw complexity got amplified by real commit activity in `legacy-javascript.js`, which is what pushed the risk score to 20.1 despite an unremarkable nesting depth of 8. The catch is provenance: this function sits inside a fixture built to feed lighthouse's legacy-JavaScript audit test cases, so the complexity was very likely inherited from whatever library the sample was pulled from, not authored inside this project. **Recommendation:** don't spend refactoring effort on it — the actual fix is upstream, in the crawler's ignore-paths config, which should have excluded `cli/test/fixtures/` from this run in the first place.

### `MixpanelEventTracking` — core/test/fixtures/source-maps/coursehero-bundle-2.js

MixpanelEventTracking and the next function in this table, `get_page_type`, both post a nesting depth of 60 — by far the deepest in this sample, where every other top-five function sits in single digits. That matches `deeply_nested`, one of the three patterns shared across the whole table, but a depth of 60 isn't typical hand-written control flow; it's the signature of a bundler or minifier collapsing many small scopes into one wrapped module. That lines up with the file: `coursehero-bundle-2.js` is a vendored analytics bundle captured to test lighthouse's source-map remapping.

**Recommendation:** treat the ND figure as a bundling artifact rather than a refactoring target — flattening it wouldn't touch any behavior lighthouse itself owns. If the fixture ever needs updating, pull a fresh bundle from the vendor rather than hand-editing the existing one.

### `get_page_type` — core/test/fixtures/source-maps/coursehero-bundle-2.js

`get_page_type` shares its file's ND 60 depth but carries more branching of its own — CC 85 against a fan-out of just 3, meaning almost all of its complexity is self-contained conditional logic rather than delegated calls. Same caveat as its neighbor: this is bundled fixture content, not code lighthouse actively maintains, so I'd rank it below anything found in `core/audits` or `core/gather` regardless of what this table says.

### `AskQuestionController` — core/test/fixtures/source-maps/coursehero-bundle-1.js

AskQuestionController calls into 62 distinct functions — the highest fan-out in this sample by a wide margin, and unusual paired with a comparatively modest CC of 20. That combination, low branching with huge fan-out, is the fingerprint of a coordinating layer that mostly delegates rather than computes, closer to `middle_man` than to the branching-heavy pattern the rest of this table shows. **Recommendation:** in maintained source I'd check whether all 62 callees are load-bearing or whether some are copy-pasted dispatch entries; here, since it's vendored bundle content shared with `_matches` below, the only real action is confirming the fixture hasn't drifted from its upstream source.

### `_matches` — core/test/fixtures/source-maps/coursehero-bundle-1.js

`_matches` closes out the table with the most balanced profile of the five — CC 38, ND 9, FO 9 — and the lowest risk score. Same file, same fixture provenance as `AskQuestionController`: a reasonable one to leave alone.

## Key Takeaways

- All five of lighthouse's top hotspots are vendored test fixtures (`legacy-javascript.js`, `coursehero-bundle-1.js`, `coursehero-bundle-2.js`) that should have been excluded by this run's ignore-paths config — the fix belongs in the crawler, not in lighthouse's source.
- `parseURL`'s CC 216 is the standout number in this table, but it's inherited complexity from vendored code — not worth refactoring time regardless of when the ignore-paths gap gets fixed.
- `AskQuestionController`'s fan-out of 62 is worth a five-minute look regardless of provenance, mainly to confirm the bundle hasn't drifted from its upstream source.
