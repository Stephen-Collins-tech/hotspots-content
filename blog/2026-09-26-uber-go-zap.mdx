### `convertAttrToField` — exp/zapslog/handler.go

<FunctionCard fn='convertAttrToField' file='exp/zapslog/handler.go' risk='13.65' band='critical' cc='26' nd='2' fo='25' touches='0' />

This function converts a `slog.Attr` into zap's internal `Field` type — the bridge between Go's standard-library structured logging and zap's own field system. The source shows a large switch over `attr.Value.Kind()` with nine cases (bool, duration, float64, int64, string, time, uint64, group, and a recursive log-valuer branch), each one calling directly into a distinct zap constructor function. That's exactly why fan-out sits at 25: every case is a one-line delegation to a different `zap.X()` helper, so the function is a thin dispatcher, but a wide one. Nesting is only 2, so this isn't a deeply tangled conditional — it's breadth, not depth, that drives the complexity score of 26. It hasn't been changed in 954 days, and the file's history shows a bug-fix rate of 25% across 8 total commits, with 2 distinct authors in the last 90 days — mild historical churn, not a red flag, but enough to say this file has needed correction before. Because this is the adapter surface between two logging APIs, I'd add table-driven tests enumerating every `slog.Kind` before anyone extends it to support new attribute kinds, since a missed case here fails silently into the `default` branch rather than erroring loudly.

### `check` — logger.go

<FunctionCard fn='check' file='logger.go' risk='13.39' band='critical' cc='31' nd='2' fo='19' touches='0' />

This is the internal gatekeeper every logging call passes through before a message is written — it decides whether the level is enabled, builds the checked entry, wires up panic/fatal/dpanic terminal behavior, and conditionally captures caller and stack trace information. The source confirms this: it's doing level-gating, a three-way switch on `PanicLevel` / `FatalLevel` / `DPanicLevel`, then two more early-return checks (`willWrite`, `addCaller`/`addStack`) before touching the stack-capture path at all. That's a lot of responsibility for one function, which is exactly what the god-function and long-function tags are flagging, and cyclomatic complexity of 31 is the highest raw branch count in this list after `AddTo`. Fan-out of 19 means it calls into stack capture, core checking, terminal-hook overrides, and error output — a change to any of those dependencies could ripple back here. It hasn't been touched in 839 days and currently shows 0 distinct authors in the last 90 days, so nobody is holding active context on it, and the file's bug-fix rate sits at 33% across 6 commits with a review comment density of 13.0 on past reviews — a signal that when people have touched this function, reviewers had a lot to say. Given that every `Info`, `Fatal`, and `Check` call routes through here, I'd treat this as the single highest blast-radius candidate in the whole repo if it needs to change for a new log level or exit behavior.

### `AddTo` — zapcore/field.go

<FunctionCard fn='AddTo' file='zapcore/field.go' risk='11.56' band='critical' cc='65' nd='2' fo='42' touches='0' />

This is the largest single branch structure in the dataset: cyclomatic complexity of 65 driven by a switch statement covering roughly 30 field types (array, object, binary, bool, complex64/128, duration, every integer width, string, time, uint variants, reflected, namespace, stringer, error, skip). Fan-out of 42 confirms it — nearly every case calls a distinct `enc.AddX()` method on the `ObjectEncoder` interface. Nesting stays shallow at 2, so again this is a breadth problem, not a depth problem: one enormous dispatch table rather than nested conditionals. It's been untouched for 1124 days, tied with `getBenchmarkRow` for the longest dormancy in this set, with just 3 total commits on file and 1 author in the last 90 days. The god-function and stale-complex tags both apply for the same reason: this function is the encoding contract every zap field type must satisfy, so any new field type added to the `Field` struct requires a corresponding case here, and missing one fails silently to the `panic` in the default branch. If a new field type is ever added, I'd extract the encoder dispatch into a lookup table keyed by field type rather than extending the switch further, since 65 branches is already well past the point where a linear scan through cases is maintainable.

### `getBenchmarkRow` — internal/readme/readme.go

<FunctionCard fn='getBenchmarkRow' file='internal/readme/readme.go' risk='11.46' band='critical' cc='17' nd='1' fo='10' touches='0' />

This one is different in character from the others — it's tooling, not runtime logging code. Based on the path and the source, it parses `go test -bench` output lines to build a markdown benchmark table for the README, extracting duration, allocated bytes, and allocation count via string splitting and `strconv` parsing. Cyclomatic complexity of 17 is driven almost entirely by four sequential error checks (`findUniqueSubstring`, duration parse, two `strconv.Atoi` calls), each with its own early return — that's the exit-heavy pattern showing up as a straightforward chain of 'parse or bail' steps rather than nested logic (nesting depth is just 1). It hasn't changed in 1124 days, matching `AddTo` for the oldest dormancy in this set, with only 2 total commits and a bug-fix rate of 0% — there's no historical defect signal here at all. Because this feeds documentation generation rather than production logging paths, I'd deprioritize it relative to the other four, but if it's ever touched again, collapsing the four parse-or-return blocks into a small helper that returns `(value, error)` pairs would cut the branch count roughly in half.

### `EncodeEntry` — zapcore/json_encoder.go

<FunctionCard fn='EncodeEntry' file='zapcore/json_encoder.go' risk='10.86' band='critical' cc='33' nd='3' fo='21' touches='0' />

This is the function that turns a log entry and its fields into a JSON line — the hot path for every JSON-formatted log statement zap emits. The source shows five conditional blocks, each guarding one output field (level, time, logger name, caller, message), and each with its own 'did the user-supplied encoder actually write anything, or do we need a string fallback' check. That doubled-conditional pattern per field is what pushes nesting to 3, the deepest of the five hotspots here, and cyclomatic complexity to 33. Fan-out of 21 spans the various `Encode*` and `Add*` calls plus namespace closing and buffer management. It's been dormant for 1077 days, and the file carries one bug-linked commit in its history — worth noting as context, not as proof of a current defect, especially since the bug-fix rate for this file is 0% overall (3 total commits, 0 authors in the last 90 days). Given this is the primary JSON serialization path, I'd extract each 'encode field or fall back to string' block into a single small helper function — that pattern repeats four times in the source and is the most mechanical extract-method opportunity in this entire list.

Worth noting for contrast: the fire-quadrant functions in this repo — `encodeError`, `Handle` in the same `zapslog` package, and `Build` in `config.go` — are actively changing right now and carry live regression risk, each touched once in the last 30 days, with `Build` changed as recently as today (0 days since last change). None of them cracked the Top 5 because their complexity is lower (cyclomatic complexity 10, 14, and 11 respectively), but they're the functions I'd watch for near-term regressions, not the ones I'd schedule a refactor sprint around.
