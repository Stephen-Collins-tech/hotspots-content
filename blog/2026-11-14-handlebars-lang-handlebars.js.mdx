One file, lib/handlebars/compiler/javascript-compiler.js, holds three of the top five hotspots in handlebars.js, and all three were last changed 0 days ago, so this is a module under live edit, not a single function to tidy. The other two are in lib/handlebars/runtime.js: `template`, which has the highest activity-weighted risk score at 2.21 with a cyclomatic complexity of 25 and fan-out of 27, and the `invokePartialWrapper` closure it contains. Across the 210 functions I analyzed, 8 are critical and 75 sit in the active tier. I would start with `template`, because it is complex, heavily coupled, and changing now, and I would put test coverage around the compiler file's `strictLookup`, because it sits on a cross-file contract with `template`.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `template` — runtime.js

<FunctionCard fn='template' file='lib/handlebars/runtime.js' risk='2.21' band='critical' cc='25' nd='4' fo='27' touches='6' />

`template` is the runtime entry point that takes a precompiled template spec and an environment and builds the callable template. From the excerpt, it validates its inputs, checks the compiler revision, defines the partial-invocation wrapper, and builds a container object of lookup helpers (strict lookups, property lookups with prototype access control, depth lookups). Those are several distinct responsibilities inside one function body.

<MetricBar label='Fan-out' value='27' threshold='15' max='30' />

A fan-out of 27 means it directly calls 27 distinct functions, so a change here can ripple in many directions, and the excerpt's comment about letting external users override env.VM references as pseudo-supported APIs tells me some of that coupling is deliberate and public. In a prototype-based JavaScript codebase, dynamic property access like that can hide dependencies a static fan-out count misses, so I would treat 27 as a floor. A cyclomatic complexity of 25 puts it well above the moderate range of about 10, with a nesting depth of 4.

The file-level history adds context without proving anything about this function: 8 bug-linked commits against 6 total commits, a bug-fix rate of 50%, no reverts, and a review-comment density of about 3.1 per commit. It has 6 touches in the last year and was last changed 10 days ago. With a critical band and active tier, this is a live regression risk. My recommendation: pull the container construction out into a separate factory function so `template` is left with validation and wiring, and pin the container's lookup behavior with tests first.

### `invokePartialWrapper` — runtime.js

<FunctionCard fn='invokePartialWrapper' file='lib/handlebars/runtime.js' risk='1.98' band='critical' cc='9' nd='4' fo='5' touches='6' />

This is the nested function inside `template` that resolves a partial, invokes it, and falls back to compiling it on the fly when the invocation returns nothing and a compile function is available. It then applies indentation line by line and throws if the partial cannot be compiled in runtime-only mode. A cyclomatic complexity of 9 is moderate, but a nesting depth of 4 comes from the indent loop sitting inside two conditionals, and it has 5 distinct callees.

It shares its file's history with `template`: 6 touches in the last year, last changed 10 days ago, a bug-fix rate of 50%. It is also in the critical band and the active tier, so the same live regression risk applies. Because it is a closure inside `template`, it is hard to test in isolation, which is the main practical problem. I would extract the indentation step into a small named helper and hoist the wrapper out of `template` so it can be exercised directly. That alone would remove one nesting level and make the partial fallback path testable.

**`strictLookup`, `<anonymous>`, and `JavaScriptCompiler` — javascript-compiler.js**

<FunctionCard fn='strictLookup' file='lib/handlebars/compiler/javascript-compiler.js' risk='2.19' band='high' cc='5' nd='1' fo='5' touches='7' />

The three compiler entries need to be read together, because they share one file and one history: 7 touches in the last year, 0 days since last change, 14 bug-linked commits across 7 total commits, a bug-fix rate of about 29%, no reverts, and a review-comment density of 5.5, the highest in this set. Their activity-weighted scores of 2.19, 1.92, and 1.92 are driven by that file-level activity, not by structural complexity.

`strictLookup` is the clear outlier on structure. With a cyclomatic complexity of 5, a nesting depth of 1, and fan-out of 5, it is a small function, and I would not call it complex. It generates the code for strict-mode property lookups: it walks path parts, then emits a call to either container.strictLookup or container.strict depending on whether compat mode has already consumed the path via a depthed lookup. The comment in the excerpt about that compat-mode case is the part I would pay attention to, because the generated string has to match what `template` in runtime.js builds into its container. That cross-file contract is where a change here can break something there, and it is the reason this small function ranks second overall. It is a function where a small, recent edit needs a test pinning the emitted output for both branches.

The other two entries are low-band and I would not refactor them for complexity. `JavaScriptCompiler` has a cyclomatic complexity of 9, a nesting depth of 4, and no fan-out, and the excerpt shows it as the empty constructor whose prototype is then populated with methods like `nameLookup`, `appendToBuffer`, `compile`, and the helper-setup functions. The `<anonymous>` entry has the same metrics, and its excerpt shows the prototype's `setupHelper`, `setupParams`, and `setupHelperArgs` methods being attributed to it. They rank at 1.92 only because they inherit the file's churn. In the active tier with a low band, they bear watching rather than refactoring. I read these as a measurement artifact of prototype-assigned methods and do not draw conclusions from their individual scores. The useful signal is that the file as a whole was last changed 0 days ago, with 7 touches in the last year.

For the module, I would add snapshot-style tests of generated source for strict, compat, and depthed lookups before the next edit lands, since generated-code output is the contract here.

## Where to start

I would start with `template` in runtime.js, because it combines a critical band, a fan-out of 27, a cyclomatic complexity of 25, and a change 10 days ago. Next I would take `invokePartialWrapper`, since extracting it from `template` is the cheapest way to reduce both functions' risk. For javascript-compiler.js, I would not refactor anything for complexity; I would add tests around `strictLookup`'s two emitted forms and review how its output couples to the runtime container. Outside this set, I would leave the quiet-tier code alone for now.
