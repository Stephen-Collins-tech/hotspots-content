### `ParseParamComment` — operation.go

<FunctionCard fn='ParseParamComment' file='operation.go' risk='18.55' band='debt' cc='81' nd='7' fo='23' touches='0' />

I would start with `ParseParamComment`. It has the deepest nesting in my top five (7 levels), a cyclomatic complexity of 81 and a fan-out of 23, and it hasn't been changed in 195 days, with 0 touches in the last year. It parses the param annotation line. From the excerpt, it matches a regular expression, classifies the type as object, array or primitive, resolves enum schemas, and then branches by parameter location (path, header, query, formData, and others), with a further loop over struct properties in the object case. That is at least four separate responsibilities in one function.

<MetricBar label='Cyclomatic Complexity' value='81' threshold='10' max='172' />

The file's history adds some weight. operation.go shows a bug-fix rate of about 35% across 17 commits, with no bug-linked commits and no reverts recorded, and a single distinct author in the last 90 days. None of that is evidence of defects in this function. But the PR review comment density of 6.4 is the highest among my top five, which suggests this code draws more discussion than its neighbors. A single recent author also means the working knowledge of this file may sit in one head.

My recommendation is extract-method along the seams already visible in the code. Pull type detection (array, primitive, object) into one helper, enum resolution into a second, and the per-location validation switch into a third. The object-case property loop, with its query and formData extension-name lookups, is the deepest nest, so I would lift it out first.

### `ParseAPIMultiSearchDir` — parser.go

<FunctionCard fn='ParseAPIMultiSearchDir' file='parser.go' risk='17.8' band='fire' cc='54' nd='5' fo='22' touches='1' />

This is the only function in my top five that is changing right now: 0 days since last change and 1 touch in the last year. A cyclomatic complexity of 54, nesting of 5 and fan-out of 22 make it the live regression risk on the list. From the excerpt, it handles the main API file path, then branches between Go package loading, per-directory scanning, and two dependency-resolution strategies (a package-listing route and a dependency-tree route), with an early error return at almost every step.

parser.go carries a bug-fix rate of about 47% across 30 commits, including 3 bug-linked commits, and 2 distinct authors in the last 90 days. Those are file-level numbers and don't prove this function is defective. Still, a complex function with bug-linked file history, edited today, deserves review before the next merge. Every early return is a path that needs a test, and the dependency branches multiply the cases.

I would split the two dependency strategies into separate methods and leave the top-level function only choosing between them. That alone removes the deepest nesting and lets each strategy be tested with its own fixtures.

### `parseGeneralAPIInfo` — parser.go

<FunctionCard fn='parseGeneralAPIInfo' file='parser.go' risk='17.06' band='debt' cc='102' nd='5' fo='24' touches='0' />

A cyclomatic complexity of 102 and a fan-out of 24 put this in the extreme range, for a function untouched in 285 days. From the excerpt, it loops over comment lines and runs a large switch on the annotation attribute (version, title, host, basepath, accept, produce, schemes, tag fields and more), with markdown-loading and error paths inside several cases. A switch like this is complex mostly by enumeration, but any one case can pull in state from the others through the shared previous-attribute and current-tag variables.

It shares parser.go's file-level history with the previous function: a bug-fix rate of about 47% across 30 commits and 3 bug-linked commits. That raises review priority for the next change, though it says nothing about today's behavior. Because the function is dormant, the blast radius is what worries me: the next person to add an annotation will edit a 102-path function that has been stable for 285 days.

I would convert the switch into a table of handlers keyed by attribute, so each annotation gets its own small function and its own test. The tag-related cases, which depend on the shared current-tag state, are the first group I would extract.

### `EvaluateBinary` — const.go

<FunctionCard fn='EvaluateBinary' file='const.go' risk='16.91' band='debt' cc='172' nd='5' fo='22' touches='0' />

The cyclomatic complexity of 172 is the highest in this analysis, and the function hasn't been changed in 285 days. The excerpt shows why: shift operations are handled with nested type switches over ten integer types for both left and right shifts, followed by a reflection-based path for the remaining operators. Much of that complexity is repetition rather than tangled logic, which makes it more tractable than the number suggests.

<MetricBar label='Cyclomatic Complexity' value='172' threshold='30' max='172' />

The file history is quiet: 4 commits in total, a bug-fix rate of 25%, no bug-linked commits, no reverts and no recent authors. I would frame this as maintainability debt, not an active risk. The danger is that a function this size is nearly impossible to cover exhaustively by hand, so any future edit is hard to verify.

The practical fix is a reflection-driven helper that normalizes both operands once, then applies the operator. Go generics, or a small table keyed by operator, would also collapse the repeated integer cases. Before touching it, I would add a table-driven test over operator and type pairs.

### `evaluateConstValue` — package.go

<FunctionCard fn='evaluateConstValue' file='package.go' risk='15.81' band='debt' cc='57' nd='4' fo='18' touches='0' />

This function walks Go AST expression nodes (identifiers, selectors, literals, unary and binary expressions, parentheses, calls) to compute constant values. It calls `EvaluateBinary` for the binary case, so the two functions form a dependency chain: a change to one can alter results through the other. It has a cyclomatic complexity of 57, nesting of 4 and fan-out of 18, and it hasn't been changed in 285 days.

The excerpt includes a `panic(err)` in the integer-literal branch, reached when neither signed nor unsigned parsing succeeds. In a tool that processes arbitrary user source, I would flag that for review, since a panic there ends the whole run instead of returning an error. That observation comes from the excerpt alone; I haven't checked how callers guard against it.

File history is thin: 5 commits, a bug-fix rate of 40%, no bug-linked commits and no recent authors. I would split the function by AST node type, giving each case a small evaluator, and change the panic into an error return with a test for the malformed-literal case.
