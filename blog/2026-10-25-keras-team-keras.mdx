### `print_summary` — summary_utils.py

<FunctionCard fn='print_summary' file='keras/src/utils/summary_utils.py' risk='18.25' band='fire' cc='42' nd='6' fo='39' touches='1' />

This is the function behind model summaries, and it takes seven parameters covering line length, column positions, a custom print function, nested-model expansion, trainable display and a layer range. The excerpt shows it first classifying the model as Sequential, subclassed or Functional. For Functional models it then walks the graph nodes by depth and runs a nested loop to look for shared layers, which decides whether the model counts as 'sequential-like'. That classification logic, plus the layout and printing work that follows, accounts for much of its CC of 42 and its nesting depth of 6.

The file has only 3 commits in its history, one of them tagged as a bug fix (a bug-fix rate of 33%), with no bug-linked commits, no reverts and 3 distinct authors in the last 90 days. That is thin history, so I read this mainly as maintainability risk, not as a record of defects. With 39 callees, it is also a coupling point. Python resolves those calls at runtime, so the real dependency surface is likely wider than the number suggests.

My recommendation: pull the model-topology detection (the Sequential, subclassed and Functional branching plus the shared-layer search) into its own helper that returns the layer list and the sequential-like flag. That alone would remove the deepest nesting and make the classification testable without rendering a table.

### `export_onnx` — onnx.py

<FunctionCard fn='export_onnx' file='keras/src/export/onnx.py' risk='17.13' band='fire' cc='35' nd='5' fo='36' touches='1' />

`export_onnx` writes a model out as an ONNX artifact. The excerpt shows a long docstring with caveats per backend (TensorFlow, JAX and Torch), a dtype-policy requirement, and special handling for recurrent models under Torch. It also resolves an input signature and must distinguish single-input from multi-input layouts before generating input names. A CC of 35 and a fan-out of 36 fit a function that accommodates several backends and signature shapes in one body.

The file-level history is a single commit, tagged as a bug fix (a bug-fix rate of 100%), with one author in the last 90 days and no reverts. One commit is too little to draw conclusions from, but a lone author on a function this branchy means few people have recently held its full logic in their heads.

My recommendation: split the function by phase. Input-signature resolution and naming become one unit, per-backend conversion another, and the final write a third. The backend-specific branches are the natural seams.

### `MobileNetV3` — mobilenet_v3.py

<FunctionCard fn='MobileNetV3' file='keras/src/applications/mobilenet_v3.py' risk='16.85' band='fire' cc='49' nd='4' fo='38' touches='1' />

This has the highest cyclomatic complexity of the five, at 49, yet its nesting depth of 4 is the lowest. That combination points to a wide function rather than a deep one. The excerpt opens with a long run of argument validation: weights must be 'imagenet', None or an existing file path; 'imagenet' with the top layer requires exactly 1,000 classes; and when both an input shape and an input tensor are supplied, their dimensions must agree under channels-first or channels-last layouts. Each check adds branches and error exits before any model building starts.

The file has one commit in its history, tagged as a bug fix (100%), with a single author in the last 90 days. As with the others, I would not infer defects from that.

My recommendation is the most mechanical of the five. Move the argument validation into a dedicated function that raises the same errors, and let the model-building body start from validated inputs. That should take a large share of the 49 paths out of the main function and give the checks their own unit tests. The shape-versus-tensor reconciliation likely recurs in sibling application models, so a shared helper may pay off beyond this file.

### `rnn` — torch/rnn.py

<FunctionCard fn='rnn' file='keras/src/backend/torch/rnn.py' risk='16.63' band='fire' cc='39' nd='4' fo='43' touches='1' />

`rnn` has the highest fan-out in the set, at 43 distinct callees. It is the Torch backend's generic recurrence driver, taking a step function, inputs, initial states, and flags for backward processing, masking, unrolling, time-major layout and output handling. The excerpt shows nested helpers defined inside it, for swapping batch and time axes, expanding masks and splitting inputs per time step, plus an unrolled path that raises an error when the number of time steps is not fixed. Parameters like `go_backwards`, `unroll`, `mask` and `time_major` multiply the combinations the function must handle, which is consistent with a CC of 39.

The file history is one commit, tagged as a bug fix (100%), with one author in the last 90 days.

My recommendation: lift the inner helpers to module level so they can be tested directly, and separate the unrolled path from the looped path. At the very least, the mask handling should be testable without running a full recurrence.

### `call` — compile_utils.py

<FunctionCard fn='call' file='keras/src/trainers/compile_utils.py' risk='16.58' band='fire' cc='31' nd='5' fo='23' touches='1' />

This `call` method computes the loss from true and predicted values, with an optional sample weight. The excerpt shows a fast path for non-nested single-output cases and a fallback for nested structures. In the fallback, a chain of nested try/except blocks tries progressively looser ways to reconcile the structure of the targets with the predictions: wrapping a single target, reordering a dict by output names, repacking containers of different types, and handling losses defined only over part of the outputs. That reconciliation ladder is where the nesting depth of 5 comes from.

Its file history is one commit, tagged as a bug fix (100%), with one author in the last 90 days. Of the five, it has the lowest fan-out (23) and the lowest complexity (31), but the nested try/except fallbacks are the hardest part of the set to reason about, because each rung depends on the previous rung having failed.

My recommendation: extract the structure-reconciliation ladder into a function that takes the targets and predictions and returns repacked targets. Each rung then becomes a named, individually tested case instead of a handler inside another handler.

**What the group has in common**

All five are exit-heavy, so each needs a test for every return and raise path, not only the happy path. All five are long, which makes extract-method the common first move. None shows a revert or a bug-linked commit in the file-level data, so I am framing this as structural risk during active change, not as evidence of defects.
