It is in the active tier with an activity-weighted risk score of 1.99, was changed 4 days ago, and sits in the critical band, so it is structural complexity in code that is changing now rather than a backlog item. I looked at 12,079 functions across the repository, 41 of them critical, and I would start with `createFromParts` because it is the only top-five function where the structure itself, not the volume of setup code, drives the score.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `createFromParts` — DefaultLocaleExtension.java

<FunctionCard fn='createFromParts' file='junit-jupiter-api/src/main/java/org/junit/jupiter/api/util/DefaultLocaleExtension.java' risk='1.99' band='critical' cc='7' nd='3' fo='10' touches='2' />

I would start with `createFromParts` because it has a cyclomatic complexity of 7, a nesting depth of 3, and a fan-out of 10, and it was touched twice in the last year, most recently 4 days ago. Reading the excerpt, it takes a `DefaultLocale` annotation and validates which combination of language, country, and variant was supplied. It first rejects configurations that mix a locale provider with explicit parts, then walks an if/else-if chain that accepts language plus country plus variant, language plus country, or language alone, and throws a configuration exception for anything else.

<MetricBar label='Cyclomatic Complexity' value='7' threshold='10' max='20' />

That is a modest complexity in absolute terms, below the usual threshold of 10, and I want to be clear about that. What puts it at the top is the combination of seven paths, several compound boolean conditions (`!language.isEmpty() && !country.isEmpty() && !variant.isEmpty()` and its siblings), and recent activity. Compound conditions like these are where gaps in combination coverage tend to hide: for example, the third branch's `variant.isEmpty()` condition is an easy line to misread. The file shows no historical defect signal: no bug-linked commits, a bug-fix rate of 0%, no reverts, 2 total commits, and 2 distinct authors in the last 90 days. So I read this as maintainability debt in code that is in motion, and the live regression risk comes from the next edit rather than from any track record of problems.

My recommendation is concrete. Confirm there is a test for every one of the seven paths, including the invalid combinations (country without language, variant without country). Then consider replacing the chain with a small decision on which parts are present, so the valid combinations are listed once and everything else falls into a single error path. Because the same file also validates provider-based configuration in `getFromProvider`, a shared validation helper would keep the two error-message styles consistent.
