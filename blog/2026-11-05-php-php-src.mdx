Across php-src's 19,997 analyzed functions, 3,766 land in the critical band and every function is in the active tier, so the useful question is which ones are most exposed to change right now. The top five are the answer: zend_compile_args_ex, zend_ast_evaluate_inner, zend_jit, zend_jit_trace, and zend_jit_trace_build_tssa all have an activity-weighted risk score between 3.14 and 3.17, and each shows 0 days since last change, so this is live regression risk, not backlog. I would start with the two JIT trace functions in ext/opcache/jit/zend_jit_trace.c, because zend_jit_trace combines cyclomatic complexity of 1208 with nesting depth 14 and 205 distinct callees, and it is being edited today.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `zend_compile_args_ex` — zend_compile.c

<FunctionCard fn='zend_compile_args_ex' file='Zend/zend_compile.c' risk='3.17' band='critical' cc='67' nd='8' fo='29' touches='10' />

`zend_compile_args_ex` has the highest activity-weighted risk score of the five at 3.17, despite having the lowest cyclomatic complexity (67) and fan-out (29). It was touched 10 times in the last year and changed today, so its position at the top comes from activity as much as structure. Nesting depth 8 is a strong refactoring signal on its own.

The excerpt shows a loop over call arguments that tracks several overlapping flags: whether argument unpacking is used, whether named arguments are used, whether any arguments may be undefined, and whether extra named arguments may land in a variadic. It also takes a partial-application flag and a variadic-placeholder pointer, which suggests the function is absorbing newer language features, and several compile-error paths enforce rules such as no unpacking after named arguments. A function that combines a flag-tracking loop, several feature interactions, and a TODO comment about tracking out-of-order arguments is a place where each new language feature adds another flag and another branch.

The file shows 3 bug-linked commits out of 4 total commits in the history I have, a bug-fix rate of 25%, no reverts, 4 distinct authors in the last 90 days, and a review-comment density of 2.5. Four total commits is a small sample, so I would treat the signals as a prompt to look closer rather than a finding.

My recommendation: separate the per-argument classification (unpack, named, positional) from the code that emits opcodes, and bundle the four tracking flags into a small state struct passed between the pieces. That makes the interaction rules testable on their own and keeps the next argument-handling feature from deepening the nesting.

**What I would do this week**

The two functions in zend_jit_trace.c share a file, a change cadence, and a defect history, so one reviewer should own both. Start by writing characterization tests around whatever outputs these functions produce today, then extract along the seams the code already documents: the numbered phases in `zend_jit_trace_build_tssa`, the block loop in `zend_jit`, and the case bodies in `zend_ast_evaluate_inner`.

### `zend_ast_evaluate_inner` — zend_ast.c

<FunctionCard fn='zend_ast_evaluate_inner' file='Zend/zend_ast.c' risk='3.16' band='critical' cc='149' nd='7' fo='96' touches='10' />

`zend_ast_evaluate_inner` has a cyclomatic complexity of 149, nesting depth 7, and 96 distinct callees, touched 10 times in the last year and changed today. The excerpt shows a large switch over AST node kinds, with cases for binary operations, comparisons, unary operations, constants, class names, and more. Each case repeats a similar pattern: evaluate children, bail out on failure while cleaning up already-evaluated operands, then compute the result.

That structure is more forgiving than the JIT functions, because a switch with per-case handling is easier to read than deeply interleaved logic. Its nesting depth of 7 is moderate by comparison. But the repeated evaluate-then-clean-up pattern spread across many cases is where a missed operand destructor would hide, and in C that means a leaked reference rather than a compile error.

The file history is the quietest of the five: no reverts, a bug-fix rate of 33.33% across 15 total commits, and 6 distinct authors in the last 90 days. I would frame this one mainly as maintainability debt rather than a defect risk. My recommendation: move each non-trivial case body into its own static helper so the switch becomes a dispatch table of one-line calls, and consolidate the repeated two-operand evaluate-and-clean-up sequence into one shared helper.

### `zend_jit` — zend_jit.c

I read the review-comment density as a sign this file draws discussion, though that is context rather than evidence of a defect.

My recommendation: pull the per-block body out of the reverse-post-order loop into its own function, and give the receive-entry handling a named helper. That alone removes a chunk of the nesting.

The excerpt shows a function that declares a very large set of locals up front (operand info for op1, op2 and results, several address variables, frame and stack pointers, and a pile of boolean state flags such as the delayed-fetch-this and avoid-refcounting flags). It then wraps its body in a try block and drives SSA construction, trace naming, and register allocation. That shape, one function holding the whole trace-to-machine-code pipeline plus per-opcode state, fits a function that grew by accretion. It has been touched 7 times in the last year and was changed today.

The file's history gives me supporting context: 4 bug-linked commits out of 8 total commits, with a bug-fix rate of 25%, no reverts, and 5 distinct authors in the last 90 days. That does not prove this function is defective, since the signals are file-level. It does mean a file with this much structural weight and some defect history deserves stronger review priority than complexity alone would give it.

My recommendation: extract the per-opcode handling into helpers grouped by opcode family, and move the long local-variable set into a context struct so each helper takes only the state it needs. Do it in small, behavior-preserving steps, since a function with 1208 paths needs a regression net before anyone restructures it.
