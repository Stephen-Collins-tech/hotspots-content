### `php_openssl_sockop_set_option` — xp_ssl.c

<FunctionCard fn='php_openssl_sockop_set_option' file='ext/openssl/xp_ssl.c' risk='3.73' band='critical' cc='69' nd='8' fo='36' touches='53' />

This is the stream-option handler for SSL sockets. From the excerpt, it dispatches on an option code through a large switch and, in the metadata branch, assembles a report of the negotiated protocol version, cipher details, session reuse, early-data status and ALPN protocol. Much of that is wrapped in preprocessor guards for TLS 1.3, 1.2, 1.1, ALPN and SSLv3, which means the number of compiled shapes of this function depends on build configuration. Cyclomatic complexity does not capture that, so the real surface is larger than 69.

<MetricBar label='Cyclomatic Complexity' value='69' threshold='10' max='160' />

It was touched 53 times in the last year and changed on the day I analyzed it. The file's historical signals show a bug-fix rate of 30.12% across 83 commits, with no reverts and 9 distinct authors in the last 90 days. It does not prove this function is defective, but it is context for review priority. I would start by splitting each option case into its own static helper, beginning with the metadata case, so the preprocessor guards live in a small function rather than inside a switch with nesting depth 8.

### `zend_compile_args_ex` — Zend/zend_compile.c

<FunctionCard fn='zend_compile_args_ex' file='Zend/zend_compile.c' risk='3.73' band='critical' cc='67' nd='8' fo='29' touches='84' />

This function compiles the argument list of a call. The excerpt shows a loop over arguments that branches on argument unpacking, named arguments, partial application and variadic placeholders, tracking several boolean flags as it goes (uses_named_args, may_have_undef, may_have_extra_named_args). The flags interact: a named argument after an unpack is a compile error, but an unpack after a named argument is a different one, and a named argument against a known function target takes a different path than one against an unknown target.

I would start here because it combines CC 67, nesting depth 8 and fan-out 29 with 84 touches in the last year. The file has 108 total commits, a bug-fix rate of 24.07%, one revert and 18 distinct authors in the last 90 days. Eighteen people editing the same file in a quarter, in a function whose correctness depends on flag interactions, is the pattern where two reasonable changes collide. My recommendation is to extract the unpack case and the named-argument case into separate helpers that take and return an explicit state struct, so the flag combinations become visible in one place.

### `zend_try_compile_special_func_ex` — Zend/zend_compile.c

<FunctionCard fn='zend_try_compile_special_func_ex' file='Zend/zend_compile.c' risk='3.68' band='critical' cc='36' nd='32' fo='25' touches='84' />

This one is an outlier, and the numbers need care. Its nesting depth is 32, the highest in the list by a wide margin, while its cyclomatic complexity of 36 is the lowest of the five. The excerpt explains the gap: it is one long else-if chain comparing the lowercased function name against literals such as strlen, is_null, intval, in_array, array_map and sprintf, and delegating to a dedicated compile helper for each. The chain is structurally flat; every branch does the same thing.

So I would not read nesting depth 32 as 'hard to follow'. I would read it as 'every new compile-time optimization adds another branch here', which fits 84 touches in the last year. The practical risk is merge conflicts and ordering mistakes in a growing chain, not tangled logic. Replacing the chain with a lookup table keyed by interned function name, mapping to a handler, would drop the nesting to 1 and make additions a one-line change. Because this shares a file with `zend_compile_args_ex`, it carries the same file-level history: 108 commits, a 24.07% bug-fix rate and one revert.

### `zend_jit_fetch_dimension_address_inner` — ext/opcache/jit/zend_jit_ir.c

<FunctionCard fn='zend_jit_fetch_dimension_address_inner' file='ext/opcache/jit/zend_jit_ir.c' risk='3.68' band='critical' cc='151' nd='8' fo='59' touches='64' />

This is the extreme case: cyclomatic complexity of 151 is well past the 100+ line I treat as extreme, and fan-out of 59 is the highest in the data. The signature alone takes 17 parameters, including several output arrays and exit addresses. From the excerpt, it generates JIT code for array dimension fetches, branching on the possible types of the index (long, string and others), whether the array is packed, whether the key is a constant, and the access mode (read versus write). Every one of those type and mode combinations is a path that needs a test.

<MetricBar label='Cyclomatic Complexity' value='151' threshold='30' max='160' />

It was touched 64 times in the last year and changed on analysis day. The file has 154 commits, a 24.03% bug-fix rate, no reverts and 16 distinct authors in the last 90 days. I would start by splitting along the index type: one helper for the integer-key path and one for the string-key path, each taking the shared state through a context struct rather than a 17-argument signature. The parameter list is the first thing I would attack, because it is what makes any extraction awkward today.

### `zend_jit_switch` — ext/opcache/jit/zend_jit_ir.c

<FunctionCard fn='zend_jit_switch' file='ext/opcache/jit/zend_jit_ir.c' risk='3.67' band='critical' cc='93' nd='10' fo='55' touches='64' />

This function emits JIT code for the switch-style opcodes. The excerpt handles SWITCH_LONG, SWITCH_STRING and MATCH, with a constant-operand branch that resolves the target at compile time and a non-constant branch that generates a runtime jump. It also changes behavior depending on whether it is compiling a trace or a function. Nesting depth 10 is the deepest true nesting in the list (the compile function above is deeper only because of its else-if chain), and its CC of 93 with fan-out 55 sits below the other JIT function in the same file, which has CC 151.

It shares a file with `zend_jit_fetch_dimension_address_inner`, so the history is the same: 154 commits, a 24.03% bug-fix rate, no reverts and 16 distinct authors in the last 90 days. Two functions of this size in one file, both changing, means a reviewer needs to hold a lot of context for a small diff. I would separate the constant-operand path from the runtime path first, since that split is already visible in the structure and would remove one level of nesting.

**Quiet structural debt for contrast**

The context list is useful as a contrast. The next group of critical functions is all in the bundled GD library under `ext/gd/libgd/`. Their activity-weighted risk scores sit between 1.75 and 1.81, roughly half of the top five, because each was touched 8 times in the last year and last changed 111 days ago. That is structural debt with a high blast radius when next touched, not live churn. If you are not working in image decoding, I would leave them alone; if you are, plan refactoring before the next feature push.

## Where to start

If I had one review slot this week, I would spend it on `zend_compile_args_ex`: it has the most distinct authors, a recorded revert in its file, and a flag-interaction structure that extraction can make explicit. If I had a second, it would go to `zend_jit_fetch_dimension_address_inner`, where the 17-parameter signature is the concrete first target. For `zend_try_compile_special_func_ex`, the fix is mechanical and low-risk, so it is a good candidate for a contained cleanup that also reduces merge friction in `Zend/zend_compile.c`.
