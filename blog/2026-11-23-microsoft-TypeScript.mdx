### `getPropertyTypeForIndexType` — checker.go

<FunctionCard fn='getPropertyTypeForIndexType' file='tsc/internal/checker/checker.go' risk='3.86' band='critical' cc='154' nd='7' fo='65' touches='293' />

This function resolves the type you get when you index into an object type, whether through an element access expression or an indexed access type node. From the excerpt I can see it branching on access flags (contextual, deprecated reporting, writing, cache symbol, missing-element handling), on whether the access node is an element access expression, a private identifier or an indexed access type node, and on tuple-specific handling with negative indices and out-of-range elements. Each of those is a separate concern, and they are interleaved in one function body.

<MetricBar label='Cyclomatic Complexity' value='154' threshold='10' max='230' />

A cyclomatic complexity of 154 means 154 independent paths, each a potential test case. Nesting depth of 7 puts it past the point where I would expect a reader to hold the control flow in their head, and a fan-out of 65 means it reaches into 65 distinct functions, so a change to any of them can alter this one's behavior. The error branches are also worth noting: the excerpt shows several distinct diagnostics reported inline (read-only assignment, negative tuple index, missing tuple element), each with its own return value, and each of those exits is another path to cover.

My recommendation is to extract the property-found branch (deprecation suggestion, reference marking, read-only check, flow-type computation) and the tuple-index branch into their own functions. Both are already visually separated by the `if hasPropName` structure, so the seams exist. That alone would pull the top-level function down substantially without changing behavior.

### `resolveExternalModule` — checker.go

<FunctionCard fn='resolveExternalModule' file='tsc/internal/checker/checker.go' risk='3.86' band='critical' cc='222' nd='7' fo='91' touches='293' />

This is the structurally largest function in my top five: a cyclomatic complexity of 222 and a fan-out of 91. It resolves a module reference to a symbol. The excerpt shows it first flagging imports of type declaration files from the @types namespace, then checking for ambient modules, then working out a context specifier through a long chain of fallbacks (string literals, module declarations, import type nodes, require calls, import calls, import declarations, export declarations, import-equals declarations), then deriving a resolution mode from that specifier, and then looking up the resolved module and reporting diagnostics.

<MetricBar label='Fan-out' value='91' threshold='15' max='100' />

The context-specifier ladder is the clearest extraction candidate: it takes a location node and returns a specifier node, with no need to know anything about what happens next. Pulling it into something like a dedicated lookup function isolates one large block of branching behind a narrow interface. The diagnostic-reporting tail of the function is the second candidate. A fan-out of 91 means the function is coupled to a very large surface, and splitting by phase (find specifier, derive mode, resolve, report) would let each piece carry a far smaller set of dependencies.

This one also has the highest cyclomatic complexity in the repository's top five, so if I could only refactor one function this quarter, I would pick it, not because it scores highest on risk (it ties with the first) but because the extraction path is the most obvious.

### `checkVariableLikeDeclaration` — checker.go

<FunctionCard fn='checkVariableLikeDeclaration' file='tsc/internal/checker/checker.go' risk='3.82' band='critical' cc='107' nd='6' fo='77' touches='293' />

This function validates variable-like declarations: variables, parameters, and binding elements. The excerpt shows it handling decorators, computed property names, private identifiers in destructuring, renamed binding elements in function types, rest bindings that need emit helpers, binding patterns, and parameter initializers without a function body. That is a wide set of declaration kinds funneled through a single entry point.

A cyclomatic complexity of 107 with a fan-out of 77 is a pairing I would treat with care. The shallow-looking early returns (missing name, ambient or type node, parameter initializer in a bodiless function) each cut the function short, so the number of exit paths is high, and every one of them needs its own test. The binding-element branch is a self-contained block that starts with `if ast.IsBindingElement(node)` and handles property name validation, rest helpers, and accessibility checks on the parent type. Moving that into a dedicated binding-element check would give the main function a clearer shape and make the binding logic testable alone.

### `removeSubtypes` — checker.go

<FunctionCard fn='removeSubtypes' file='tsc/internal/checker/checker.go' risk='3.8' band='critical' cc='49' nd='7' fo='24' touches='293' />

This is the smallest of the five by fan-out and close to the smallest by cyclomatic complexity, which makes it the most approachable. It reduces a list of types by removing those that are subtypes of others. From the excerpt: a cache keyed on the type list, a pass that looks for empty object types, a loop that walks the list backward, a special case for type parameters constrained to a union, a key-property optimization for discriminated unions, and a check that bails out with a 'too complex to represent' error after an estimated number of subtype checks.

The nesting depth of 7 comes from a loop inside a conditional inside a loop, with further conditions on the inner comparison. Of the five, this is where nesting is the main driver, not branching. The practical fix is to extract the inner per-source comparison (the key-property check, the empty-object skip, and the related-and-derived check) into a helper that answers a single question: is this source made redundant by this target. That flattens the nesting and gives the complexity-limit logic a clearer place to live.

### `getInferredTypeParameterConstraint` — checker.go

<FunctionCard fn='getInferredTypeParameterConstraint' file='tsc/internal/checker/checker.go' risk='3.78' band='critical' cc='44' nd='8' fo='37' touches='293' />

This function computes a constraint for a type parameter introduced by an infer declaration, drawing on the position of that declaration. The excerpt shows a switch over the parent node's shape: a type reference (constraint taken from the corresponding type parameter), a rest parameter or rest type (an array of unknown), a template literal span (string), a mapped type parameter, and a conditional type with a mapped check type. Several of those cases are long compound boolean conditions.

It has the deepest nesting in the top five at 8, and my guidance puts 8 and above in strong-refactoring territory. The type-reference case is the deepest, with a nested sequence of checks on type parameters, an index lookup, a declared constraint, a deferred mapper, and an instantiation. Extracting that case into its own function, named for what it does (constraint from the enclosing type reference), would take the nesting down immediately, and the mapped-type-in-conditional case is a second candidate. The cyclomatic complexity of 44 is the lowest of the five, so after those two extractions the function would be in reasonable shape.

## Where to start

I would take these in order of payoff per hour of work. `getInferredTypeParameterConstraint` and `removeSubtypes` have the lowest cyclomatic complexity and clear extraction seams, so they are the fastest wins and a good way to establish a pattern for the rest. `resolveExternalModule` is the largest single improvement available, and its context-specifier ladder is a near-mechanical extraction. `getPropertyTypeForIndexType` and `checkVariableLikeDeclaration` need more care because their branches are interleaved with early returns and diagnostics, so I would add characterization tests around the exit paths before splitting them.

One caution on scope. These five share a file, a risk profile, and 23 recent authors, so refactoring them concurrently invites merge conflicts in a file that changes constantly. I would sequence the work as small, separate changes, one function at a time, and keep each behavior-preserving. None of this says the checker is poorly written. It says the code that is hardest to hold in your head is also the code that gets changed most, and that is where small structural improvements pay back fastest.
