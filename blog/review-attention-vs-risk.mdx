Try this before reading the rest of this post: pull your team's last 90 days of PR review comments, and separately pull your last 90 days of hotfix or incident-linked commits. Now look at which files show up on both lists. In most codebases I've looked at closely, the overlap is surprisingly small — the files getting the most careful review attention and the files actually generating production fixes are, for large stretches, different files.

That's not because reviewers are bad at their jobs. It's because review attention and defect risk are driven by different things, and nothing in a normal workflow forces them into alignment.

## What drives review attention

Review attention clusters around what's *visible*: the PR open right now, the diff that's large, the feature that's new, the code that's recently changed. All of that is reasonable to attend to — new code genuinely needs scrutiny, and a big diff genuinely needs more of it than a small one. But "recently changed and currently visible" is a description of *where activity is happening right now*, not a description of *where risk actually concentrates*.

## What drives defect risk

Defect risk clusters around a different profile: code that's old enough to have accumulated edge cases, dense enough that changes have unintended side effects, and has a track record of needing repeated fixes rather than one clean one. Crucially, none of that requires the file to be part of anyone's current PR. A file can sit untouched for months, generate no review conversation at all, and still be the most dangerous thing in the codebase — because risk, unlike review attention, doesn't decay just because nobody's looking at it.

## Why the mismatch persists

There's no natural feedback loop that corrects this. A file that's risky but stable doesn't generate PRs, so it doesn't generate review comments, so nobody's attention is drawn to it — until it breaks, at which point it generates an incident instead of a review comment, and the cycle resets without ever routing proactive attention where it was needed. Review processes are built to respond to change, not to risk. Most of the time those two things happen to coincide closely enough that nobody notices the gap. When they diverge, the gap is exactly where things break without warning.

## Closing the gap without more process

The fix isn't more review — it's *redirecting* some of the review capacity you already have. A useful practice: alongside "these files changed in this PR," periodically ask "which files have generated the most fixes over the last quarter, independent of anything currently in flight." That second list rarely overlaps cleanly with what's showing up in review right now, and that's exactly the point — it surfaces the code that's been quietly accumulating risk while getting zero scrutiny, because nothing about it looked urgent in the moment.

Run the overlap exercise from the top of this post occasionally. If the two lists mostly match, your review attention is already well-calibrated. If they don't, you've just found where to look next — not because anyone did anything wrong, but because nothing in a normal workflow was ever going to point there on its own.
