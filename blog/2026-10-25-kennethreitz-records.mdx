### `__getitem__` — records.py

<FunctionCard fn='__getitem__' file='records.py' risk='8.98' band='high' cc='5' nd='2' fo='9' touches='0' />

I would start with `__getitem__` because it has the highest activity-weighted risk score in the repository at 8.98, and it hasn't been changed in 681 days. The excerpt shows it handling both integer lookup and string-key lookup on a row, with a branch that unwraps a key view type for SQLAlchemy 2.x compatibility, then a duplicate-column check that raises distinct errors for ambiguous and missing fields. The metrics are modest on paper (CC 5, ND 2), but a fan-out of 9 stands out for a method this short, and in Python that count understates the coupling, since attribute and method calls on duck-typed objects are resolved at runtime.

The shape matters more than the CC. This is the lookup path behind attribute access and the `get` helper in the same class, as the excerpt shows, so its behavior with unusual key views is inherited by those callers. I recommend writing characterization tests for the four paths I can see (integer index, key found once, key found more than once, key missing) plus the key-view unwrapping branch, then extracting the key-normalization step into a small helper. That shrinks the method and gives the compatibility workaround one place to live.

### `cli` — records.py

<FunctionCard fn='cli' file='records.py' risk='8.54' band='high' cc='11' nd='3' fo='18' touches='0' />

`cli` is the structurally largest function in the set: CC 11, ND 3, and a fan-out of 18, the highest of the four. It is also the only function flagged with the god-function, long-function, and stale-complex patterns together, and it hasn't been changed in 681 days. The excerpt shows why. It builds a long usage string inline, parses arguments, validates the format, splits key=value parameters, opens the database connection, branches between file and query-string execution, and prints results, with several distinct exit codes along the way.

One function owns argument parsing, validation, database access, and output. A change to any of those concerns means reading the whole thing, and the multiple exit paths are a test-coverage burden. The long-function pattern points to extract-method, and I would do it in this order: move the usage text to a module-level constant, pull parameter parsing into its own function, then separate query resolution from output formatting. After that, each piece can be tested without spinning up a database. With 681 days of dormancy, whoever does this refactor will be working from the code and the test suite, not recent memory.

### `isexception` — records.py

<FunctionCard fn='isexception' file='records.py' risk='6.43' band='high' cc='4' nd='1' fo='3' touches='0' />

`isexception` is the outlier. At CC 4, ND 1, and fan-out 3, it is a small type-check helper, and the excerpt confirms it: an instance check followed by a class-and-subclass check. It lands in the high band because it is the most dormant function in the set at 3,366 days since last change, and because it shares the file-level history of records.py.

I would not refactor this function. The reasonable action is to confirm a test or two covers exception instances, exception classes, and non-exceptions, then leave it alone. I include it because it shows how much of the ranking in a small, stable repository comes from file-level context and dormancy, not from function-level difficulty.

### `__iter__` — records.py

<FunctionCard fn='__iter__' file='records.py' risk='6.38' band='high' cc='4' nd='3' fo='2' touches='0' />

`__iter__` on the row collection has CC 4, ND 3, and fan-out 2, and hasn't been changed in 3,292 days. The excerpt shows a generator that loops indefinitely, checks a cache of already-fetched rows, and otherwise pulls the next row from the underlying source, handling end-of-iteration explicitly so it doesn't bubble up out of the generator. The comment in the excerpt cites the Python rule about StopIteration inside generators, which suggests the explicit handling is intentional.

The risk is in the interaction, not the metrics. A nesting depth of 3 inside a generator, combined with state shared across `__next__`, `__getitem__`, and `__len__` on the same collection (all visible in the excerpt), means iteration order and caching behavior depend on several methods staying in agreement. Generators add control flow that the cyclomatic count doesn't capture. I would write a test that interleaves iteration, indexing, and length checks on a partially consumed collection, because iteration, indexing, and length all share the same cache and iterator state.

**What I would do first**

The four records.py functions share a file, a long dormancy, and a lazy-fetching design where the row class and the collection class lean on each other. I would take them in this order: tests around `__getitem__` and `__iter__` first, since they define how rows and collections behave, then the `cli` extraction, the only one with a clear structural payoff.
