Five functions in bun are structurally complex and sit in code that is changing right now: every one is in the critical band, in the active tier, and was last changed 0 to 2 days before this snapshot, so anyone shipping code this week is likely to land near them. My analysis at commit ca7729d covers 307,573 functions, 10,850 of them critical, and the top five cluster tightly at an activity-weighted risk score between 3.83 and 3.89 (`to_bytes` leads at 3.89). I would start with `to_bytes` in `src/standalone_graph/StandaloneModuleGraph.rs` because it combines a cyclomatic complexity of 66, nesting depth 8, and fan-out of 54 with 98 touches in the last year and a change today.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

## Codemod / Tooling Files in Results

`scripts/orderfile/app/tui.js` appeared in the context list with a critical band. The pattern across the top five is not one bad module. It is the places where bun does the most translation work between formats and protocols: module graphs into bytes, exceptions into terminal output, JS objects into HTTP/2 frames, TypeScript classes into lowered statements, and import specifiers into file paths. Those are naturally branchy, and they are also the places people keep editing.

### `to_bytes` — StandaloneModuleGraph.rs

<FunctionCard fn='to_bytes' file='src/standalone_graph/StandaloneModuleGraph.rs' risk='3.89' band='active' cc='66' nd='8' fo='54' touches='98' />

This is the highest-ranked function in the analysis, and it appears to serialize the standalone module graph (what `bun build --compile` embeds) into a byte buffer. From the excerpt, it takes nine parameters and makes a first pass over every output file to size a string builder, with a long if/else chain keyed on output kind: sourcemaps, several flavors of bytecode, module info, module-info string tables, a prelinked module graph, and ordinary modules. Each branch carries its own hand-written capacity arithmetic, including alignment padding and size_of-based record sizes. Nesting depth 8 and fan-out 54 on top of CC 66 mean a reviewer has to hold a lot of sizing rules in their head at once.

<MetricBar label='Nesting Depth' value='8' threshold='4' max='10' />

The file has 98 touches in the last year, 4 distinct authors in the last 90 days, a bug-fix rate of about 17%, and exactly one revert. One revert is a small signal, but it is the only revert among the five files, and it makes this the file I would review first. The capacity estimates read like invariants that must match what a later pass actually writes; if the sizing pass and the writing pass drift apart, the failure mode is a mis-sized buffer. I cannot see the second pass in the excerpt, so I will say only that the structure invites that risk.

My recommendation: extract the sizing arithmetic into a small function per output kind (for example, one that returns the capacity contribution for a bytecode file), so the first pass becomes a loop that dispatches on kind. That would cut both CC and nesting substantially and give each sizing rule its own unit test.

### `print_error_instance_body` — VirtualMachine.rs

<FunctionCard fn='print_error_instance_body' file='src/jsc/VirtualMachine.rs' risk='3.88' band='active' cc='80' nd='6' fo='47' touches='188' />

This function has the most history of the five: 188 touches in the last year and a change today. Its doc comment says it renders source-line previews, the name and message line, an owned-property dump, the stack trace, and the cause and AggregateError chain, in two modes (a live JS value or a pre-built exception). That is at least five distinct rendering jobs in one body, which is consistent with a cyclomatic complexity of 80.

<MetricBar label='Cyclomatic Complexity' value='80' threshold='30' max='100' />

The excerpt also shows scope-exit guards (a drop-based GitHub annotation printer and a deferred reset of the had-errors flag), a local macro that routes a runtime color flag into a compile-time formatting parameter, and a parameter list long enough to need a clippy allow for too many arguments. None of that is wrong, but it means control flow is spread across early returns, guards that fire on exit, and macro expansion. The history signals are modest: a bug-fix rate of about 20%, no reverts, and 4 distinct authors in the last 90 days.

My recommendation: split along the rendering jobs the doc comment already names. A function for source-line previews, one for the property dump, one for the stack trace, and one for the cause chain would each take a shared context struct instead of eight parameters. Since this is the most frequently edited function in the set, that split pays off sooner here than anywhere else.

### `request` — h2_frame_parser.rs

<FunctionCard fn='request' file='src/runtime/api/bun/h2_frame_parser.rs' risk='3.85' band='active' cc='149' nd='6' fo='58' touches='91' />

`request` has the highest cyclomatic complexity in the top five at 149, well past the extreme threshold of 100, along with the highest fan-out at 58. The excerpt shows it validating its JS arguments, allocating a stream ID and returning -1 when it exceeds the maximum, and then iterating the headers in two passes because pseudo-headers must go first. It handles both a flat raw-pairs array form and an object form, with header-name validation and error construction in each.

<MetricBar label='Cyclomatic Complexity' value='149' threshold='30' max='160' />

The two-form structure is where I would look. The raw-pairs branch and the object branch each repeat a two-pass loop with name validation, so likely a large share of the 149 paths are duplicated shape rather than distinct behavior. This file was changed 2 days ago, has 91 touches in the last year, 3 distinct authors in the last 90 days, a bug-fix rate of about 20%, and no reverts.

My recommendation: pull header-name validation and pseudo-header classification into helpers shared by both forms, and separate the argument-parsing phase from the frame-encoding phase. With HTTP/2 framing, every path is a protocol edge case that deserves its own test, and at CC 149 that is not currently practical.

### `lower_class` — p.rs

<FunctionCard fn='lower_class' file='src/js_parser/p.rs' risk='3.85' band='active' cc='45' nd='8' fo='30' touches='106' />

`lower_class` in the JS parser handles class lowering for both statement and expression forms, including the standard decorator path and the legacy TypeScript decorator path (the excerpt references a runtime helper for parameter decorators). Its complexity is the lowest of the five at CC 45 and fan-out 30, but nesting depth 8 ties `to_bytes` for second highest. In the excerpt the property loop nests through method checks, an optional value, a match on expression kind, constructor detection, and a per-argument decorator loop.

<MetricBar label='Nesting Depth' value='8' threshold='4' max='10' />

There is also a Rust-specific point worth flagging. The comments in the excerpt explain that arena-owned references are accessed through short-lived borrows so that `&mut self` helper calls never overlap an outstanding mutable borrow of the class. That discipline is the kind of ownership reasoning that cyclomatic complexity does not measure, so I would treat this function as somewhat riskier than its CC suggests. I saw no unsafe blocks in the excerpt, and I will not claim any beyond what is shown. It has 106 touches in the last year, a change today, 4 distinct authors in the last 90 days, a bug-fix rate of about 20%, and no reverts.

My recommendation: extract the per-property decorator collection (the inner argument-decorator loop) into its own method returning the parameter decorators. That removes two or three nesting levels in one move without touching the borrow structure.

### `load_node_modules` — resolver.rs

<FunctionCard fn='load_node_modules' file='src/resolver/resolver.rs' risk='3.83' band='active' cc='142' nd='9' fo='52' touches='87' />

This function has the deepest nesting in the set at 9, and the second-highest cyclomatic complexity at 142. From the name and excerpt it implements the node_modules lookup step of module resolution: tsconfig path overrides, base-URL lookups, finding the enclosing package.json, subpath imports starting with '#', and (by the parameter list) global cache handling. The code explicitly decrements a debug-log indent counter at every return point by hand, which is a pattern where adding one more early return can silently skip the cleanup.

<MetricBar label='Nesting Depth' value='9' threshold='4' max='10' />

The Rust angle matters here too. A comment in the signature explains that the directory-info parameter is a shared arena handle rather than a mutable reference because the body can re-enter the directory cache and reach the same slot, and a mutable parameter would be undefined behavior under Stacked Borrows. That is a deliberate aliasing constraint documented in the source, and it is a good reason to be careful with any restructuring that changes how that handle is passed. The file was changed 2 days ago, with 87 touches in the last year, 4 distinct authors in the last 90 days, a bug-fix rate of about 17%, and no reverts.

My recommendation: make the debug-indent cleanup a scope guard so the manual decrement at each return goes away, then split the function by resolution phase (tsconfig overrides, subpath imports, self-reference, package lookup). The guard is the cheap first step and removes a class of mistakes before any larger restructuring.

For contrast, the quiet tier shows what the same structural pattern looks like when nobody is editing it. Those critical-band functions were each touched once in the last year and have not changed in over a month. They are structural debt with a high blast radius when next touched, not the live risk the five above represent.

## Where to start

I would review in this order. First, `to_bytes`: it has the only revert among the five files, the deepest sizing logic, and a change today. Second, `print_error_instance_body`: 188 touches in the last year make it the most frequently edited function in the set, so splitting it pays off fastest. Third, `request` and `load_node_modules`: both are in the extreme CC range and both were changed 2 days ago, so a test-per-branch strategy is overdue there. `lower_class` is the cheapest win, a single extract-method for the decorator loop.

These scores say nothing against the maintainers. They say these are the functions where a small, careless edit is hardest to review and most likely to land this week.
