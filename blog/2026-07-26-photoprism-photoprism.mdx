## Top 5 hotspots

### `searchPhotos` — `internal/entity/search/photos.go`

<FunctionCard fn='searchPhotos' file='internal/entity/search/photos.go' risk='21.77' band='critical' cc='60' nd='11' fo='114' touches='3' />

<MetricBar label='Cyclomatic Complexity' value='60' threshold='10' max='100' />
<MetricBar label='Max Nesting Depth' value='11' threshold='4' max='12' />
<MetricBar label='Fan-out' value='114' threshold='20' max='120' />

This is the primary photo search function and, by the metrics, the highest-priority function in the entire repository. A cyclomatic complexity of 60 means 60 independent execution paths — each one a required test case and a potential site for a regression. The nesting depth of 11 means the deepest conditional logic sits eleven levels inside the function body, which makes it genuinely difficult to reason about what state is in scope at any given branch.

The source excerpt confirms what the metrics suggest: `searchPhotos` handles query string parsing, geographic proximity lookups (the "near" feature resolving S2 cell IDs from photo UIDs), dynamic SQL join assembly, album scope resolution including backward-compatibility aliasing, shared-album filter deserialization, and distance-range enforcement — all within a single function body. Each of those concerns branches independently, which is exactly how you accumulate a CC of 60.

The fan-out of 114 is the most operationally significant number here. A change to any one of those 114 callees — a helper that changes its return signature, a filter parser that starts rejecting previously accepted input — can silently alter search behavior. With 3 commits touching this function in the last 30 days and the most recent change landing right at the analyzed commit, this is not a theoretical risk.

One in three of the file's recent commits has been classified as a bug fix, which is worth noting. That does not prove the current code is defective, but it does suggest the search function has needed corrective attention recently.

**Recommendation:** Start decomposing by concern. The album-scope resolution block — which handles UID validation, cache lookup, filter deserialization, and the hidden-photo exclusion join — is a self-contained unit that could become a `resolveAlbumScope` helper returning a scoped query builder. Extracting that alone would reduce the branching depth materially without requiring a full rewrite. Each extracted helper is independently testable and reduces the number of paths through the remaining function body.

### `UserPhotosGeo` — `internal/entity/search/photos_geo.go`

`UserPhotosGeo` is the geographic variant of the same search pattern, scoped to map/geo results. Its CC of 48 and nesting depth of 11 are only marginally lower than `searchPhotos`, and the structural relationship between the two functions is visible directly in the source: the album-scope resolution block, the "near" proximity lookup, the S2 cell ID assignment, and the distance clamping logic appear in both. Half of the file's recent commits were classified as bug fixes — the highest bug-fix share of any file in the top 5. That history reinforces the case for prioritizing it.

The structural duplication between `UserPhotosGeo` and `searchPhotos` is itself a risk vector: a fix applied to the album scope logic in one function must be manually mirrored in the other, and the history suggests that has already been necessary.

**Recommendation:** The shared logic between `searchPhotos` and `UserPhotosGeo` — proximity resolution, S2 cell assignment, album scope resolution, distance clamping — should be extracted into shared helpers that both functions call. This eliminates the synchronization burden and reduces CC in both functions simultaneously. Given that both files are being touched right now, this refactoring has a lower coordination cost than it would if the functions were dormant.

### `UserMediaFile` — `internal/photoprism/index_mediafile.go`

<FunctionCard fn='UserMediaFile' file='internal/photoprism/index_mediafile.go' risk='20.64' band='critical' cc='97' nd='7' fo='214' touches='3' />

<MetricBar label='Cyclomatic Complexity' value='97' threshold='10' max='100' />
<MetricBar label='Fan-out' value='214' threshold='20' max='220' />

This function has the highest cyclomatic complexity of any function in the top 5 at 97 — nearly at the extreme threshold — and by far the largest fan-out at 214. It handles the full indexing pipeline for a single media file on behalf of a user: nil-guard checks, skip-file logic (by path, by file type for face-only runs), stat collection, hash computation with a per-hash distributed lock, existing-file lookup by both path and hash, and event publication, all before the excerpt even reaches the core indexing logic.

The Go-specific concern here is the `defer unlock()` pattern visible in the excerpt: a per-hash lock is acquired when a hash collision is possible, and released via defer. With a CC of 97, there are 97 paths through this function — and only some of them reach the lock acquisition point. Any path that panics or returns early before the defer fires correctly needs careful review. The source excerpt also shows a `recover()` is not present in this function (unlike `Start` in `vision.go`), so a panic here would propagate to the caller.

With 3 touches in 30 days, 2 distinct authors active in the last 90 days, and the most recent change landing right at the analyzed commit, `UserMediaFile` is under active collaborative development. That is the highest author count of any function in the top 5, which means two engineers are independently making changes to a 97-CC function with 214 callees. The blast radius of a merge conflict or a missed invariant here is large.

**Recommendation:** The skip-file decision logic (nil check, ignore-by-path, ignore-by-type) is a clean early-return cluster that could become a standalone `shouldSkipFile` predicate. The hash-lookup-and-lock block is another extractable unit. Given 2 active authors, establishing those boundaries now reduces the chance of concurrent edits creating subtly incompatible assumptions about function state.

### `Start` — `internal/workers/vision.go`

<FunctionCard fn='Start' file='internal/workers/vision.go' risk='19.58' band='critical' cc='18' nd='8' fo='61' touches='2' />

<MetricBar label='Max Nesting Depth' value='8' threshold='4' max='12' />

`Start` is the entry point for the vision worker, which orchestrates AI model runs (labels, NSFW classification, captions, face detection) across a filtered set of photos. Its CC of 18 is lower than the search functions, but the nesting depth of 8 and fan-out of 61 are significant — and the god-function pattern flag indicates it is doing far more than dispatching work.

The source excerpt shows the function doing model selection filtering, per-model boolean flag extraction, a search query to fetch candidate photos, a pagination loop, cancellation checking via mutex, and what appears to be face marker tracking (`updateFaces`) — all before the main processing body. The `recover()` at the top is a good defensive practice, but it also signals awareness that something inside this function can panic, which with a nesting depth of 8 and 61 callees is easy to believe.

In Go, worker functions like this one often involve goroutine lifecycle management. The mutex-based cancellation check (`mutex.VisionWorker.Canceled()`) inside the loop, combined with the `defer mutex.VisionWorker.Stop()` at the top, means the function is managing its own concurrency contract. With 2 commits in the last 30 days and the most recent landing right at the analyzed commit, any change to the model selection or loop logic risks disrupting that contract.

**Recommendation:** The model-flag extraction block (`updateLabels`, `updateNsfw`, `updateCaptions`, `detectFaces`) and the initial photo query setup are stateless setup steps that could be extracted into a `buildVisionRunConfig` helper. This would reduce the nesting depth in the main function and make the worker's concurrency contract easier to audit in isolation from the setup logic.

### `WebDAVAuth` — `internal/server/webdav_auth.go`

<FunctionCard fn='WebDAVAuth' file='internal/server/webdav_auth.go' risk='19.26' band='critical' cc='15' nd='8' fo='53' touches='1' />

<MetricBar label='Cyclomatic Complexity' value='15' threshold='10' max='20' />
<MetricBar label='Max Nesting Depth' value='8' threshold='4' max='12' />

`WebDAVAuth` is a Gin middleware handler that authenticates WebDAV requests. It has the lowest CC of the top 5 at 15, but a nesting depth of 8 in an authentication function is a meaningful concern: each additional nesting level is a branch in the access-control decision tree, and a missed branch or an incorrectly ordered check is a potential security-relevant defect.

The source excerpt shows the function nesting a `basicAuth` closure inside the outer handler, then layering header token checks, cache lookups, app-password detection (using `rnd.IsAppPassword`), session validation, username matching, rate-limit reservation, audit logging, and disabled-app-password checks — all within a single handler. The fan-out of 53 reflects that breadth: this function calls into header parsing, cache, session management, rate limiting, audit logging, and config — all to make a single access-control decision.

With 1 commit in the last 30 days landing right at the analyzed commit, this function is still being actively modified. Authentication middleware is exactly the kind of code where an exit-heavy, deeply-nested structure creates risk: the 15 execution paths through this function represent 15 distinct authentication outcomes, and each must be tested to confirm that no path inadvertently grants or denies access incorrectly.

**Recommendation:** Extract the token-based session resolution (`WebDAVAuthSession` + username match + rate-limit + audit log) into a named helper that returns a clear enum or typed result — authorized, denied, or fall-through-to-basic-auth. This flattens the nesting in the main handler and makes each authentication pathway independently testable. For authentication code specifically, testability at the individual path level is not optional.
