I scanned 2,113 functions in rayon-rs/rayon, and the top structural risk isn't a function under active churn — it's the opposite. `parse_tsp_data` in the demo crate's TSP parser carries a cyclomatic complexity of 38 and hasn't been changed in 1,279 days, putting it squarely in the structural-debt quadrant with an activity-weighted risk score of 14.11, the highest in the repository. All five of my top hotspots land in that same debt quadrant — meaning the risk here is accumulated complexity waiting for the next person who has to modify it, not code currently in flux. Out of 2,113 functions, only 10 land in the critical band, but the pattern across them is consistent enough to be worth a dedicated look.

The table below ranks functions by **activity-weighted risk** — a score that multiplies structural complexity by recent commit frequency. A function that is both hard to understand (high cyclomatic complexity) and actively changing is a higher priority than one that is complex but untouched. CC = cyclomatic complexity (independent execution paths); ND = max nesting depth; FO = fan-out (distinct callees).

### `parse_tsp_data` — rayon-demo/src/tsp/parser.rs

<FunctionCard fn='parse_tsp_data' file='rayon-demo/src/tsp/parser.rs' risk='14.11' band='critical' cc='38' nd='3' fo='12' touches='0' />

This is a hand-rolled parser for TSPLIB-format graph files, and the excerpt confirms it: a header-parsing loop with a match arm per field name ('NAME', 'COMMENT', 'TYPE', 'DIMENSION', 'EDGE_WEIGHT_TYPE'), each with its own inline error path, followed by coordinate parsing and a nested double loop over all node pairs. A cyclomatic complexity of 38 with a fan-out of 12 is a lot of surface area for one function — the exit-heavy pattern flags what I can see directly in the source: at least six separate early-return error paths, each one a distinct case a test suite would need to hit. It hasn't been changed in 1,279 days and has only 2 commits total in its history, with zero bug-linked commits and zero reverts on file. That's not a red flag for defects — it's a sign nobody has needed to touch it, which is exactly why it's risky: the next person who does will have to hold all 38 paths in their head at once with no recent context to lean on. My recommendation is to split the header-parsing loop out from the coordinate-matrix construction before adding any new TSPLIB field support — two functions of complexity ~15-20 each are far more tractable than one at 38.

### `par_mergesort` — src/slice/sort.rs

<FunctionCard fn='par_mergesort' file='src/slice/sort.rs' risk='11.46' band='critical' cc='17' nd='4' fo='9' touches='0' />

This is rayon's parallel merge sort entry point, and the source shows exactly why it scores where it does: an insertion-sort fast path for small slices, a sequential fallback under a chunk-length threshold, then a parallel chunked sort with manual pointer arithmetic wrapped in `unsafe` blocks to share a scratch buffer across threads via a `SendPtr` wrapper. That's cyclomatic complexity 17 and nesting depth 4 sitting on top of unsafe memory sharing — the kind of code where cyclomatic complexity alone understates the real cost of review, because verifying the unsafe pointer aliasing logic requires reasoning about ownership across parallel closures, not just counting branches. It hasn't changed in 381 days, and this is structural debt rather than a function anyone is actively working through right now. Given the unsafe blocks, I'd treat any future change to the chunking or buffer-reuse logic as requiring a second reviewer by default, not just a CI pass.

### `fold_with` — src/iter/par_bridge.rs

<FunctionCard fn='fold_with' file='src/iter/par_bridge.rs' risk='11.41' band='critical' cc='13' nd='4' fo='3' touches='0' />

This function bridges a sequential iterator into rayon's work-stealing model. The source makes the risk concrete: it checks a per-thread flag to guard against re-entrant recursion from work-stealing, then loops on a mutex-guarded iterator, with three distinct early returns depending on whether the lock succeeds, the iterator is exhausted, or another thread panicked. A cyclomatic complexity of 13 isn't extreme, but nesting depth 4 combined with mutex locking under concurrent access is the kind of code where a small change can introduce a subtle deadlock or a missed unlock path. It hasn't been touched in 1,279 days, and it sits in the debt quadrant, not the actively-changing one — this is dormant complexity, not live churn. I'd add an explicit comment at each of the three return points documenting why that path is safe under panics, so the next editor doesn't have to reconstruct the reasoning from scratch.

### `recurse` — src/slice/sort.rs

<FunctionCard fn='recurse' file='src/slice/sort.rs' risk='11.05' band='critical' cc='19' nd='3' fo='11' touches='0' />

This is the core recursive step of rayon's pattern-defeating quicksort, and it's dense: pivot selection, a heapsort fallback when the partition-imbalance limit hits zero, pattern-breaking on imbalanced partitions, an optional partial-insertion-sort short-circuit for likely-sorted input, and special-casing for predecessor-equal pivots before falling through to a general partition step. Cyclomatic complexity 19 with a fan-out of 11 is a wide fan-out for a single function — `heapsort`, `break_patterns`, `choose_pivot`, `partial_insertion_sort`, `partition_equal`, and `partition` are all called from inside this one control flow, meaning a change to any of their signatures ripples straight back here. It's gone 876 days without a change, on a file with 8 total commits, none bug-linked or reverted. Given how many sort-correctness invariants live in this one function, I'd want dedicated unit tests around the balanced/imbalanced branch transitions before touching the pivot logic — right now the safety net for a change here is the broader test suite, not anything scoped to this function.

### `sort_panic_safe` — tests/sort-panic-safe.rs

<FunctionCard fn='sort_panic_safe' file='tests/sort-panic-safe.rs' risk='10.95' band='critical' cc='10' nd='6' fo='9' touches='0' />

This is a stress test verifying that rayon's parallel sort behaves correctly under panics, and the nesting depth of 6 stands out immediately — the source shows four levels of nested loops (over length, modulus, and a boolean flag for pre-existing runs) wrapping a conditional swap-or-reverse block, then calling into both `par_sort_by` and `par_sort_unstable_by` via a test macro. A nesting depth of 6 on a test file is worth flagging on its own: deeply nested test setup is harder to debug when a specific parameter combination fails, since the failure is buried four loops deep. This file has a bug-fix rate of about 17%, the only non-zero defect signal across my top five, meaning it has previously seen at least one bug-fix commit — consistent with it being a panic-safety regression test in the first place. I'd flatten the nested loops using a single generated parameter matrix (a vector of tuples for length/modulus/has_runs) iterated once, which keeps the same coverage while cutting the nesting to 2.

Worth noting: none of the five functions above show any bug-linked commits, reverts, or hotfixes in their history. The risk they carry is entirely structural and dormant, not evidence of past defects. In the context data, several test helpers in `src/iter/test.rs` sit in the watch quadrant — low structural complexity, with 1 touch in the last 30 days and 0 days since last change — which is the healthy end of the spectrum and a useful contrast to the debt-heavy top five.
