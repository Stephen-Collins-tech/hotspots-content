### `visitMetric` — MQEVisitor.java

<FunctionCard fn='visitMetric' file='oap-server/server-query-plugin/query-graphql-plugin/src/main/java/org/apache/skywalking/oap/query/graphql/mqe/rt/MQEVisitor.java' risk='17.73' band='debt' cc='11' nd='9' fo='59' touches='0' />

I would start with `visitMetric` because it combines a nesting depth of 9 and a fan-out of 59 with 142 days of dormancy. That dormancy is the blast-radius argument: active development isn't exercising this function, so a regression introduced later will land on code nobody has recently re-read.

From the excerpt, it is a parse-tree visitor method that resolves a metric name, looks up its value column definition, and then branches on the data type: common values versus labeled values. Inside each branch it checks the parent context type (top-N, trend, baseline, or a plain query) and runs a different query path. The same parent-type dispatch is written out twice, once per data type, and that duplication drives most of the nesting. Early returns cover the unknown-metric and unsupported-combination cases, which fits the exit-heavy tag: each exit is a separate case to cover in tests.

The cyclomatic complexity of 11 is modest on its own. Depth and coupling make this function risky, not branch count. My recommendation: extract one method per parent-context type (top-N, trend, baseline) and have both data-type branches call into them. That would likely cut the nesting by half and remove the duplicated dispatch. The file's history is thin (two commits, with a bug-fix rate of 50% meaning one of them), so I read this as maintainability debt, not a defect signal.

### `searchTagValuesImpl` — ZipkinTraceQLApiHandler.java

<FunctionCard fn='searchTagValuesImpl' file='oap-server/server-query-plugin/traceql-plugin/src/main/java/org/apache/skywalking/oap/query/traceql/handler/ZipkinTraceQLApiHandler.java' risk='17.55' band='fire' cc='21' nd='6' fo='61' touches='1' />

This is the only fire-quadrant function in the top five, and the 'why now' case is simple: an activity-weighted risk score of 17.55, last changed 18 days ago, touched once in the last year, in a file where one author was active in the last 90 days. It is a live review target, not a backlog item.

The excerpt shows a tag-value lookup for a Tempo-compatible TraceQL endpoint backed by Zipkin. It parses a filter, takes a sampled-trace path for anything narrower than a service name, then falls through a long if/else-if chain on the tag name (service name, status, duration, kind, instance, span-prefixed tags, span name, remote service), returning either a result or a bad-request response in most branches. With a cyclomatic complexity of 21 and a fan-out of 61, every tag type adds another path and another dependency. The file also shows a pull-request review comment density of 7.0, which suggests the logic drew discussion, though I can't tell from the number alone what that discussion concluded.

I would replace the if/else-if chain with a small handler per tag category, selected by a lookup, so that adding a tag type means adding a handler rather than another branch. The sibling `searchTagValuesImpl` in `SkyWalkingTraceQLApiHandler.java` (also fire) has the same name and a similar shape, so I would refactor the two together.

### `generateClosureMethodChain` — MALClosureCodegen.java

<FunctionCard fn='generateClosureMethodChain' file='oap-server/analyzer/meter-analyzer/src/main/java/org/apache/skywalking/oap/meter/analyzer/v2/compiler/MALClosureCodegen.java' risk='17.32' band='debt' cc='22' nd='9' fo='75' touches='0' />

No other function in the top five matches this one for complexity and coupling combined: cyclomatic complexity of 22, nesting depth of 9 and fan-out of 75. It has not been changed in 59 days, and the file has six commits in its history, the most of any file in this set, with a bug-fix rate of 50%. That is still a small sample, but it gives this file slightly more historical context than its neighbors.

The path (`v2/compiler`) and the excerpt tell me this is a code generator for meter-analysis closures. It builds Java source text into a string builder from a chain of segments, with separate handling for static class references, empty chains, and a bean mode that rewrites field access into getter calls and array `.size()` into `.length`. An instanceof check handles each segment kind (method call, field access, index access), and the static-call and bean-mode branches repeat similar argument-rendering loops.

An instanceof ladder over segment types is a natural fit for a visitor or per-segment-type renderer. I would extract the argument-list rendering into a shared helper first, since it appears in at least two branches; that alone removes a nesting level. Code generators are also hard to verify by reading, so before any restructuring I would pin the current output with golden-output tests for each segment type.

### `prepareBatchInsert` — BanyanDBRecordDAO.java

<FunctionCard fn='prepareBatchInsert' file='oap-server/server-storage-plugin/storage-banyandb-plugin/src/main/java/org/apache/skywalking/oap/server/storage/plugin/banyandb/stream/BanyanDBRecordDAO.java' risk='16.62' band='debt' cc='10' nd='8' fo='42' touches='0' />

`prepareBatchInsert` has gone 115 days without a change, and it sits on the write path to a storage backend. That raises the stakes of the blast radius: a mistake here affects what gets persisted, not just what gets displayed.

The excerpt shows three responsibilities in one method: a self-healing schema lookup that retries once after repopulating local metadata, a trace-model branch with a further split between merge-table records and ordinary trace records, and a stream-model branch for everything else. Several paths throw an IOException when a model or record type doesn't match, which is the exit-heavy pattern showing up as error handling. In the merge-table branch, a loop over schema tags picks a value by comparing the tag name against three configured column names, and a caught exception there is logged rather than propagated. I would flag that for a reviewer to confirm it's intentional.

My recommendation is to split this into three methods: schema resolution, trace-write preparation (with merge-table as its own helper) and stream-write preparation. The cyclomatic complexity of 10 is not high, so the split targets depth (8) and fan-out (42), not branch count. The file has two commits in its history and no distinct authors in the last 90 days.

### `transform` — ColumnTypeEsMapping.java

<FunctionCard fn='transform' file='oap-server/server-storage-plugin/storage-elasticsearch-plugin/src/main/java/org/apache/skywalking/oap/server/storage/plugin/elasticsearch/base/ColumnTypeEsMapping.java' risk='16.56' band='debt' cc='10' nd='9' fo='17' touches='0' />

This is the mildest of the five, and I include it because the data and the code disagree about how scary it is. The score reads nesting depth 9, but the excerpt shows a flat if/else-if chain mapping Java types to Elasticsearch field types (integer, long, double, keyword, text, binary), plus one recursive call for list element types and a final exception for unsupported types. A chain like that is cheap to read; the depth figure likely reflects the length of the chain, not genuinely nested logic. It hasn't been changed in 142 days, has a single commit in the file's history, and its fan-out is 17, the lowest in the group.

I would not prioritize it ahead of the others. If someone does touch it, a type-to-mapping lookup table with explicit entries for the special cases (the 32,766-length text threshold, the list recursion) would make the rules easier to audit than a ten-way chain. The one thing worth a test is the ordering: in an if/else-if chain the first match wins, so reordering conditions can silently change a mapping.

**What I'd do with this list**

The two TraceQL `searchTagValuesImpl` implementations are fire-quadrant and were last touched 18 days ago, so they get reviewed first. Then `generateClosureMethodChain` and `visitMetric`, where coupling is highest and the next change will be harder than it needs to be. `prepareBatchInsert` follows because of its position on the storage write path. `transform` can wait.
