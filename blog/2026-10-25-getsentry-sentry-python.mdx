### `_wrap_huggingface_task` — huggingface_hub.py

<FunctionCard fn='_wrap_huggingface_task' file='sentry_sdk/integrations/huggingface_hub.py' risk='19.8' band='fire' cc='42' nd='8' fo='31' touches='2' />

This is the top-ranked function, and the one I would review first. It is a decorator factory that wraps Hugging Face client calls to produce spans. From the source excerpt, the inner wrapper packs a lot into one body: it resolves the integration, extracts a prompt from either keyword or positional arguments, chooses between a streaming-span path and a legacy span path, builds an attribute mapping, and then branches on whether data collection is enabled versus the legacy PII-based behavior.

<MetricBar label='Cyclomatic Complexity' value='42' threshold='10' max='60' />

A cyclomatic complexity of 42 means 42 independent paths, each a potential test case. A nesting depth of 8 is well past the point where I treat depth as a strong refactoring signal, and a fan-out of 31 means a change here touches a wide surface. The function is marked exit-heavy, long, and a god function, and the excerpt shows why: early returns for an uninstrumented client, an unrecognized call shape, and several configuration branches that appear to be duplicated between input handling and attribute setup.

It was touched twice in the last year and last changed 10 days ago, with 2 distinct authors in the last 90 days. File-level history shows 3 total commits, a bug-fix rate of 33%, and no reverts or bug-linked commits. With only 3 commits, that percentage is a single commit, so I would not read much into it. My recommendation: extract the prompt-resolution logic, the span-creation branch, and the data-collection gating into separate helpers. The legacy-versus-data-collection split is already commented in the code as temporary, which makes that branch a natural candidate for isolation now and deletion later.

### `_set_input_messages` — pydantic_ai/spans/ai_client.py

<FunctionCard fn='_set_input_messages' file='sentry_sdk/integrations/pydantic_ai/spans/ai_client.py' risk='16.73' band='debt' cc='46' nd='8' fo='21' touches='0' />

Debt, not fire. It hasn't changed in 43 days and has zero touches in the last year, so I frame it as structural debt with a high blast radius the next time someone edits it. Its cyclomatic complexity of 46 is the highest in my top five, with nesting depth 8 and fan-out 21.

From the excerpt, it converts a message history into a span attribute. It checks a series of optional part classes with isinstance to assign roles such as assistant, tool, or user, then handles tool calls and tool returns separately. The repeated 'is not None and isinstance' pattern suggests optional imports are guarded inline, which multiplies branches, and the streamed versus non-streamed span split is duplicated for system instructions. I would extract a role-classification helper and a per-part conversion function, then add a tiny setter wrapper so the streamed/non-streamed branch exists once. The file has 1 commit and no defect signals, so I read this as maintainability debt rather than a known problem area.

### `main` — populate_tox.py

<FunctionCard fn='main' file='scripts/populate_tox/populate_tox.py' risk='16.24' band='debt' cc='32' nd='5' fo='31' touches='0' />

This is a build-tooling script, not SDK runtime code, and that matters when prioritizing. It generates tox.ini from a template. The excerpt shows it running environment checks, fetching SDK metadata, creating and loading two cache files, parsing arguments, and then looping over integration groups. Cyclomatic complexity is 32, fan-out is 31, and it has not changed in 43 days.

The blast radius is CI configuration rather than customer-facing behavior. The sequence reads like several separate stages sharing one body, with module-level globals mutated along the way. I would split it into setup, cache-loading, and package-processing functions and replace the global state with an explicit context object. It is lower urgency than the runtime wrappers, but it will be unpleasant to modify when a new integration group needs special handling.

**`setup_once` and `sentry_app_handle` — aiohttp.py**

<FunctionCard fn='setup_once' file='sentry_sdk/integrations/aiohttp.py' risk='15.99' band='fire' cc='7' nd='6' fo='55' touches='2' />

<FunctionCard fn='sentry_app_handle' file='sentry_sdk/integrations/aiohttp.py' risk='15.93' band='fire' cc='26' nd='6' fo='34' touches='2' />

I'm grouping these because they share a file, a change history, and most likely overlapping logic. `sentry_app_handle` is the nested request handler defined inside `setup_once`, so the analysis counts it separately while the outer function carries its weight too. That explains the odd shape of `setup_once`: a cyclomatic complexity of only 7 against a fan-out of 55, the highest in my top five. The outer function has little branching of its own, but it contains a very large closure whose calls are counted toward it.

<MetricBar label='Fan-out (setup_once)' value='55' threshold='15' max='60' />

Both are fire. Each was touched twice in the last year and last changed 22 days ago, with 3 distinct authors in the last 90 days. File-level history shows 4 total commits, a bug-fix rate of 25%, and no reverts or bug-linked commits. Three authors in 90 days on one file is the widest ownership spread in this set.

From the excerpt, the handler creates an isolated scope, tracks the session, clears breadcrumbs, attaches an event processor, sets localhost and user-agent attributes, and then forks into a span-streaming path that builds header, URL, query-string, and client-address attributes. Because Python resolves types at runtime, a fan-out of 55 likely understates the implicit coupling. I would move the nested handler out of `setup_once` into a module-level function and extract request-attribute collection (headers, URL, client address) into its own helper. That alone would shrink the registration logic to a handful of lines and make the handler testable without running the integration setup.

The two debt functions can wait until someone has to open them, though I would schedule the extract-method pass before that change rather than during it.
